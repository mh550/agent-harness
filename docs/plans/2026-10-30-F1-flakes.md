## The method (every build feature, copied from `docs/plans/2026-10-29-R1-flakes.md`)

1. **Reproduce before any fix.** `KEEP=1 bash tests/run.sh --repeat 10 <file>`, run directly in the session (never
   through the suite command, whose timeout is the whole suite's), a budget of 30 minutes per file, stopping at the
   first red copy. Quote the red copy's `FAIL` line and what its kept `$T` shows (`run.log`, `harness-log.md`, the
   check's own files) in the row. A file green in 10 of 10 copies is recorded as `not reproduced (10/10 green)`.
2. **A test's clock assumption** is fixed with `wait_for` or a `stub_wait`/`stub_go` barrier (`tests/lib.sh`), never a
   longer sleep (`bash tests/lint-sleeps.sh` prints nothing).
3. **A real race in `lib/` or `bin/`** is fixed there, with a check of its own that is red first (a barrier-ordered stub
   run, or a hold knob like `HARNESS_COUNT_HOLD`), and a change to the driver's behaviour gets a decision file.
4. **No check is loosened.** An assertion stays as strong or gets stronger. This plan refuses any weakening: no raised
   bound, no dropped `&&` clause, no `||` fallback, no check removed or skipped, no `wait_for` limit that stands in for
   a race in the code under test. A renamed check is one removed and one added line in
   `tests/fixtures/check-names.txt`; a new check is one added line (`LC_ALL=C` sorted).
5. **After the fix**, `bash tests/run.sh --repeat 10 <file>` prints `10/10 green`; its result line goes in the
   before → after column and the entry's `verified_how`.

## The two timing checks (*default*)

**Default:** the bound stays at **1000 ms** but measures the status process's **CPU time** (user plus system), not
wall: each of the three calls runs under bash's `time` keyword with `TIMEFORMAT='%3U %3S'` (stderr captured,
`{ time J > /dev/null; } 2> "$T/cpu"` and the like), its two numbers summed and turned into milliseconds; the best of
three is kept and printed as `best of 3: <n> ms CPU` (the measure named), and `(( best < 1000 ))` stays. The 38-run
count (52) and the 41-line and `31 older runs:` assertions (53) are unchanged.

**Why.** The load curve shows the two checks red only at `some avg60` above 24 % (only at 8 jobs paired, 73.6 %;
`findings-and-research/2026-10-30-suite-load-curve.md` §1), and the walls above grow with load for the same work: wall
measures the box's queue, not the status command. CPU time is what the command costs, so a real slowdown (a quadratic
read of the runs, a node start per run) still turns the check red, and a busy box doesn't.

**Rejected:** a ratio against a one-run baseline (time one run, then require 38 runs under k× that). The baseline is
taken under the same load and noise, so the ratio is as noisy as the wall, and it no longer says "under 1 s", the
number the status UX promised (`docs/specs/2026-10-27-status-ux.md`).

## The `whole suite` rerun (`tests/run.sh`, F1-05)

**How it happens, as the code stands** (`tests/run.sh` lines 104–127). A file stopped at `TEST_FILE_TIMEOUT` (line 67,
`still running after TEST_FILE_TIMEOUT=$to; stopped`) or killed before its `.end` (line 106, `ended without its exit
status (killed?)`) goes into `broken` and is counted as one `FAIL`, but it never printed the names of its checks that
had not run yet. The conformance block (lines 115–124) then finds those names in `tests/fixtures/check-names.txt` and
not in the run, prints them under `missing (in the fixture, not run):`, fails the conformance check and sets
`outside=1`. Line 127 prints `HARNESS_FAILED=` only when `! outside`, so no such line follows, and `lib/check.sh`'s
rerun guard (line 131 reads the names; none → its "whole suite") runs the **whole suite** again instead of the stopped
file. Seen in both 8-job paired runs of the load curve (`lc-8-a.out` and `lc-8-b.out`: file 15 stopped at `:683`, 22
of its names `missing` at `:1339`, `FAIL conformance` at `:1362`, then `files that exited non-zero: …` and no
`HARNESS_FAILED=`), and as `flaky: whole suite` at `29-3:42` (a 2533 s session suite cost for S2-03).

**Default fix:** `missing` names count as outside **only when no file was stopped or killed in that run**; `new` and
`doubled` always count. With a stopped or killed file, the `missing` list is still printed, followed by one line saying
it is not counted while a file was stopped or killed, the conformance check passes or fails on `new` and `doubled`
alone, and `HARNESS_FAILED=` names the broken files (the stopped one among them), so check.sh reruns those files.
`lib/check.sh` is unchanged.

**The fixture for its checks (*default*):** a full run of a `TEST_CHECKS` directory that holds its own
`check-names.txt` checks conformance against that file (today conformance runs only for `tests/checks`, against
`tests/fixtures/check-names.txt`, which stays its fixture). No new environment variable; the usage header says it in
the `TEST_CHECKS` line. F1-05's two checks in `tests/checks/33-suite-runner.sh` build such a directory with one file
stopped at `TEST_FILE_TIMEOUT=2s`.

**What the default gives up.** In a run with a stopped file, a name that is missing for another reason (a check
deleted in some other file) is not counted, and check.sh's rerun of the named files is a subset run, without
conformance. It is caught by the next full run on a tree without a stopped file (the verify's fresh full run on the
merged tree has a new key). Accepted: a stopped file and a dropped check in one tree are both rare, and today's cost is
a whole-suite rerun (up to 25 minutes) every time a file is stopped.

**Rejected:** mapping names to files (the runner would need each file's own name list, a second fixture to keep in step
with the first, or parsing the check files); a second conformance pass after the rerun (the rerun is check.sh's, a
subset of named files, so the pass would need check.sh to merge two runs' names, and `lib/check.sh` would change for a
fault that lives in the runner).
