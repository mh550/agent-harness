## The three questions

- **Can any path start a real `claude` from the tests?** No. `tests/run.sh:11` exports
  `HARNESS_CLAUDE=$HERE/stub-claude.sh`, and nothing in the suite unsets it. `lib/desk.sh` resolves the binary in its
  own environment (`claude=$(command -v "${HARNESS_CLAUDE:-claude}")`) and puts that absolute path in the argv tmux
  runs, so the tmux server's PATH never picks it. The suite has a private server (`unset TMUX TMUX_PANE`,
  `TMUX_TMPDIR=$T/tmux`), and its EXIT trap kills it. Every caller (driver `--foreground`, the env list `bin/harness`
  passes into tmux, the debrief) inherits the suite's environment.
- **Can a desk failure change a run's end reason?** No. `desk()` (`lib/driver.sh:124`) drops the output, turns a
  non-zero exit into a note and returns 0. The driver has no `set -e`. `desk.sh` exits 0 through `plain()` on every
  failure after its argument checks, the lock timeout included. Each `desk()` call comes after a commit, and in
  `finish` it runs before the retro, whose revert would drop its note. Check: **a desk that cannot start never
  changes the run** (P3-04). After this review a wedged tmux can't hang the driver either (M6), and a refused merge
  doesn't block every `merge_milestones` pass on a desk (I2).
- **Does any prompt or log carry `NTFY_TOKEN`?** No. `render.mjs` fills only the `HARNESS_*` names the desk template
  uses, in one pass. The claude argv holds the name, the model and `--add-dir` only. `t()` and the pane's `env` both
  `-u NTFY_TOKEN`. The notes carry the URL and the why only, and `notify` logs the title only. Checks: **the desk
  notification** (no `tok-secret` in the prompt) and, new, **the desk's environment has no NTFY_TOKEN** (an exported
  token is absent from the pane's environment and from the tmux server's global one). Outside P3, and older: real
  `curl` carries `Authorization: Bearer …` in its argv, visible in `ps` while it runs (`lib/notify.sh:31`); `-H @-`
  would hide it. Left for a later milestone.
