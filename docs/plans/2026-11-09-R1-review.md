## Important

### I1. The `Memory-review: held` trailer can be forged, so a reused facts branch can merge an unreviewed commit under `auto`

- **Where:** `lib/record.sh:579` (the guard), `lib/record.sh:554` (the comment says "no session can push"),
  `lib/record.sh:436-443` (`memory_foreign`), `lib/record.sh:428-430` (`memory_tip` takes such a tip as `MEM_BASE`),
  and `decisions/2026-11-09-memory-reviewer` line 99 ("the trailer lives in a commit only the driver can push").
- **What's wrong:** the guard trusts any commit in `MEM_MAIN..fhead` whose message has a line `Memory-review: held`.
  But other sessions can push. Coding, verify, retro and resolve sessions run with no deny list (`grep -n S_DENY lib/*.sh`:
  only `driver.sh:281,309`). `CURATOR_DENY` is a prefix rule (`Bash(git push:*)`), so `git -C . push …` is not matched
  either; the curator's comment at `driver.sh:266-267` says as much ("memory_foreign stays the second layer for a push
  in another form"). That second layer, `memory_foreign`, checks only three things: the subject (`memory: <run>: <n>
  facts`), the paths (memory files only) and a single parent. The test suite itself forges the trailer:
  `tests/checks/memory-branch.sh:252` pushes a hand-made commit with `-m "Memory-review: held"`.
- **Failure scenario (`MEMORY_POLICY=auto`):**
  1. During segment 1 (or during that segment's reviewer, via `git -C . push`), a session pushes a commit to
     `harness-memory/<run>`. The commit has the driver's subject, edits only `CLAUDE.md` and carries the trailer.
  2. At finish, `memory_tip` sees the tip with no PR (`TIP_NOPR`) and `memory_foreign` passes it, so the tip becomes
     `MEM_BASE`.
  3. The reviewer reads only this segment's ops (`memreview.mjs input` builds its items from the dry `applied`). The
     forged commit's diff is never one of its items.
  4. This segment's held commit gets the trailer and `x` is empty, so `memory_merge` merges the forged lines into
     `main`.
  Before R1 the same push would also have merged (this part is pre-existing). But R1 adds this guard to close exactly
  that gap (invariant 3: "every operation in the commit held"), and the guard does not close it.
- **Suggested fix (smallest, fails closed):** under `auto`, merge only when this segment's driver pushed every commit
  in `MEM_MAIN..fhead`. Concretely, require `git rev-list MEM_MAIN..fhead` to equal `fhead` alone, with
  `fhead^ == MEM_BASE == MEM_MAIN`. A reused tip that `main` lacks is then left open with one note
  (`memory PR: harness-memory/<run> carries commits from an earlier segment; not merged …`). This drops the trailer
  entirely. It also drops the "continue after a held-but-refused merge" case, which only Michael's merge recovers.
  That costs little: the mn continue case already stays open. A heavier alternative is to put each earlier commit's
  diff into `memory-review-input.json` as an item (`carried/<sha12>`) so the reviewer reads it too.
- **Test:** in `tests/checks/memory-review.sh`, under `auto`, push `hand <run> "" "Memory-review: held"` (the
  memory-branch.sh helper) and then run that run with a fact the stub holds. The check: `gh.log` has no `pr merge` of
  its URL, and one note names the carried commit.
