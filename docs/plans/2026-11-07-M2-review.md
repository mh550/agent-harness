## The three hard questions

1. **Does the driver take the tier from the heading, never from the op's `tier`?** Yes.
   - `lib/curator.mjs` `apply` sets `tier = tierOf(given.section)` and builds the op as `{...given, tier}`. The op's own
     `tier` is only compared against that, to count `rederived`.
   - The gate, the tier-3, tier-2 and tier-1 branches, and `body` all use the derived tier.
   - `memory_pr` (`lib/record.sh`) only reads the lengths of the arrays.
   - One thing the claimed `tier` does: `validate` refuses the whole file when it is not 1, 2 or 3. That is a format
     rule, and it never moves an op from one tier to another.
2. **Can the curator's own process write a project file?** Not through the driver.
   - `restrict "$cstart" nothing curator` reverts every edit in the run's worktree before `apply` reads anything.
     `tests/checks/curator-run.sh` checks this.
   - `file` must be one of two names, so `../x` and absolute paths are refused.
   - `plain()` never reads or writes through a symlink.
   - `apply` writes only `join(<worktree>, f)`, in the detached `$SCRATCH/memory` worktree, at the base the driver
     chose (not `memory-base/`, which the session can see).
   - Nothing in M2 touches `$RWT` or the lane slots.
   - Gap: `restrict` covers only the session's own checkout. A push to `harness-memory/<run>` was out of its reach and
     could become a later segment's base (I1, fixed).
3. **Does `record_pr`'s `":!$RUN_DIR"` guard stay untripped?** Yes.
   - The curator's tree goes back to `cstart`.
   - What the driver writes on `harness/<run>` is all under `$REC`: `memory-ops.json`, `memory.md`, `metrics.jsonl`.
   - The tier-1 commit is made only in the detached scratch worktree and pushed as `HEAD:refs/heads/harness-memory/<run>`.
   - The proof is `memory PR: the run's record PR opens too`. That run's curator edits nothing, so the review also
     asked for the case with edits: `curator-run.sh`'s `cu` check now also asserts that the record PR opens (M5).
