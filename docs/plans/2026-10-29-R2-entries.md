Facts checked for this plan, so the builders needn't re-derive them:

- **The ingest appends before it says minimal.** `entries.mjs ingest` writes the minimal line into `entries.jsonl` and
  only then exits 3. A resume decided *after* that exit would leave a minimal line behind it. So the resume is decided
  **before** the ingest, by the same test the ingest makes (§The resume, *Where*).
- **`journal_` holds the record lock.** It runs as `record journal_ …` (`_record`: `flock 9` on `$STATE/record.lock`),
  and every lane's `note` takes that lock. A resume inside `journal_` could hold it for `ENTRY_RESUME_TIMEOUT` (10m)
  and stall the other lane's notes and the coordinator's merges. So the resume runs in `journal`, outside the lock.
- **A trimmed summary of 400 code points plus `…` is 401 and fails `validate`**, and `readEntries` drops every line
  that fails `validate` (`readEntries` in `lib/entries.mjs`), so it would vanish from `progress.md` and the pack.
  The cut is therefore `minimal()`'s: 399 code points then `…`, 400 in all (the header: 1999 + `…`, 2000).
- **The header cap's message today is `header: not a string of at most 2000 characters`**, the same for a number and
  for a long string, so "only the caps" can't be told from it. R2-02 gives a long string its own message, shaped as
  the summary's: `header: <n> characters (at most 2000)`.
- **Result `usage` is per run; `total_cost_usd` and `modelUsage` are cumulative** over every run of a session id.
  The fixtures (`tests/fixtures/claude-resume/`): `total_cost_usd` 0.0031115200000000004 (`first.jsonl`) →
  0.00552003 (`resumed.jsonl`) → 0.00580227 (`resumed-again-under-cap.jsonl`); `modelUsage` `inputTokens` 2 → 4 → 6,
  `cacheReadInputTokens` 11382 → 26503 → 52877. `metrics.mjs tokens()` reads `modelUsage` first, so the difference
  of two `tokens()` is the resume's own tokens: `resumed.jsonl` minus `first.jsonl` is exactly `resumed.jsonl`'s
  `usage` (2 in, 3 out, 15121 cache read, 11278 cache write), a cross-check for R2-03.
- **`unknown-id.out` is two lines of output plus a `(exit 1)` annotation line**: the stub prints lines 1 (to stderr) and
  2 (to stdout) and exits 1; it never prints line 3.
- **`summary.mjs` counts every metrics row with no run.log line as a session** (`for (const r of rows.filter((_, j) =>
  !used.has(j))) all.push(r)`; `sessions.total = all.length`), and `metrics.mjs summary` prints `rows.length sessions`.
  An `entry-resume` row must be left out of both counts and kept in the cost (§Metrics).
- **`session()` (`lib/record.sh`) moves an existing `entry.json` aside** before it runs (`entry-stale-<t>.json`). The
  resume must keep it: the invalid entry is what it fixes.
- **Stub paths that end with no entry and no refusal** (so today a minimal entry, and after R2-04 a resume): the two
  `PARKED:` paths (`STUB_PARK` and `STUB_INBOX_IN_COMMENT`, `ok 0.3 "Not done: needs two values only Michael can
  set…"`), `STUB_OOM` (exit 137, no result), and the `STUB_BAD_ENTRY` path. Refused ones (`usage-limit.jsonl` and its
  line 2 in `STUB_LIMIT_MIDWAY` / `STUB_PASS_THEN_LIMIT`, `STUB_NOWORK`'s $0) are `MET limit` and stay
  unresumed; `tests/checks/21-run-11-verify-refused.sh` and `22-run-12-session-claims.sh` check their `minimal ==
  "missing"` entries and must stay green unchanged (they are the "refused → no resume" evidence). Only
  `tests/checks/25-run-13b-bs-entry.sh` greps the note text `B: entry.json invalid (not JSON: …); recorded a minimal
  entry`.

## The entry check

**What.** `prompt_env` in `lib/prompt.sh` exports, beside `HARNESS_LINT`:

```bash
HARNESS_ENTRY_CHECK="node $HARNESS_HOME/lib/entries.mjs validate"
```

so `{{ENTRY_CHECK}}` renders in every template (`lib/render.mjs` fills `{{X}}` from `HARNESS_X`).

**The prompts.** The finish steps that write `entry.json` end with one sentence, worded the same in all three:

- `prompts/coding.md` §3 step 4 (after the example): "Then run `{{ENTRY_CHECK}} <run directory>/entry.json <feature
  id> coding` and fix every line it prints; it prints nothing when the entry is valid."
- `prompts/verify.md` step 4: the same with `<milestone> verify`.
- `prompts/initializer.md` (the `entry.json` bullet, beside the existing `{{LINT}}` sentence): the same with `init init`.

**The validator's exit.** `validate`'s CLI keeps its lines and gains one distinction the driver needs: exit 0 valid,
**2 when every error is a cap** (`summary: <n> characters (at most 400)`, `header: <n> characters (at most 2000)`),
1 otherwise (and `missing` for no file, exit 1, as today). One pure, exported `onlyCaps(errs)` in `lib/entries.mjs`
decides it, shared by the CLI and `journalEntry`. A session sees the cap line all the same and should fix it; exit 2
only tells the driver that the ingest will keep the entry.

## The trim

**Where.** `journalEntry` in `lib/entries.mjs`. Today: any error → `minimal` with `why = invalid: <first error>`.
New: when `onlyCaps(errs)` holds, the entry is parsed, `summary` cut to `SUMMARY_MAX` and/or `header` to `HEADER_MAX`
with the existing `cut`-style helper made to end at the cap (`[...s].slice(0, n - 1).join("") + "…"`, as `minimal()`
does), then normalized and stamped as a valid entry, no `minimal` field. It returns `{ entry, why: "", trimmed:
["summary 410", …] }`; any other error, alone or beside a cap, is minimal as today (`why` from the first error, which
for an entry with a bad outcome is `invalid: outcome: "maybe" is not passes · not yet · parked`, since `outcome` is
checked before `summary`).

**The ingest's output.** `ingest` prints `trimmed summary <n>` and/or `trimmed header <n>` (one line each, like
`filled <n>`) and exits 0.

**The note.** `journal_` in `lib/record.sh` reads those lines as it reads `filled` (and strips them from `$out`):

```
<who>: entry.json summary <n> characters; cut to 400 and kept
<who>: entry.json header <n> characters; cut to 2000 and kept
```

**Stub.** `STUB_LONG_SUMMARY=<id>`: that feature's first coding session's entry summary is 410 characters (`"<id>: "`
padded with `x`), its other fields as usual.

## The background-work rule

The finish sections of `prompts/coding.md` (§3), `prompts/verify.md` and `prompts/initializer.md` each gain one line:
"Never end your turn while a background task or subagent is still running: wait for it, or stop it and say so in your
entry." (The 10-26 retro: P1-03's session ended on a pending background review and wrote no entry.) A check greps
each file for `background`.

## The resume

**The function.** `entry_resume` in `lib/record.sh`: `entry_resume <kind> <id> <transcript> <model> <who>`, called
from `journal` (after the `case` that sets `outcome`, before the restoration loop for `entries.jsonl` /
`progress-archive.md`, so that loop also undoes a resume's edit to them, and before `record journal_`). It sets
`ENTRY_RESUMED=1` when it ran a resume, which `journal_` reads for its note, and resets it at its start.

This is the feature's "called from `journal_` after an ingest exit 3" moved one step earlier: the condition is the
same (the ingest *would* exit 3), checked before the ingest and outside the record lock (facts 1 and 2 above).

**When.** All of:

1. `kind` is `coding`, `verify` or `init` (never `retro`, a probe or a debrief).
2. `node "$HARNESS_HOME/lib/entries.mjs" validate "$RUN_DIR/entry.json" "$id" "$kind"` exits 1 (missing, not JSON,
   any error but the caps). Exit 0 or 2: no resume (2: the ingest trims). `$RUN_DIR` is the working tree's copy: the
   slot's in a lane, the record's for the initializer; `journal_` moves it to `$REC` afterwards as today. Its lines
   are kept for the prompt.
3. The session was not refused: `MET limit "$3" "$S_WALL" "$S_EXIT"` exits 1 (the same call `journal` makes for
   coding; for verify and init `entry_resume` makes it itself). `S_WALL`/`S_EXIT` are still the session's: nothing
   runs a session between `session` and `journal`.
4. The transcript has a session id: `MET session-id "$3"` prints it (R2-03). None → `note "<who>: no session id in
   its transcript; not resumed"` and no resume.

**The prompt.** `prompts/entry-resume.md`, first line `# Entry resume` (the stub keys on it), rendered by `prompt
entry-resume` into `$LS/prompt.md` (the session's own prompt is already beside its transcript). `prompt_render` gives
this template **no sections** (no policy, run block or rules: the resumed session has them in its context). Its text:

```
# Entry resume

Your session ended without a valid journal entry. {{ENTRY_ERRORS}}

Write `{{RUN_DIR}}/entry.json` and nothing else: no code, no commits, no other file. Then run
`{{ENTRY_CHECK}} {{RUN_DIR}}/entry.json {{FEATURE}} {{ENTRY_KIND}}` and fix every line it prints. Then end.

# This session

Feature: `{{FEATURE}}`
Kind: `{{ENTRY_KIND}}`
```

with `HARNESS_ENTRY_ERRORS` = "It is missing." or "The entry check printed:" and the validator's lines indented,
`HARNESS_FEATURE=<id>` (the milestone for a verify, `init` for the initializer), `HARNESS_ENTRY_KIND=<kind>`.

**The command.** `session()` is reused, not copied: it gains four optional overrides read from the caller's prefix
assignments, defaulting to today's values, so a plain session is unchanged:

| override | default | the resume's |
|---|---|---|
| `S_RESUME` | empty | the session id: adds `--resume <id>`, and skips the stale-`entry.json` move |
| `S_TURNS` | `$MAX_TURNS` | `$ENTRY_RESUME_TURNS` (8) |
| `S_TIMEOUT` | `$SESSION_TIMEOUT` | `$ENTRY_RESUME_TIMEOUT` (10m) |
| `S_BUDGET` | `$SESSION_BUDGET_USD` | the session's `total_cost_usd` + `$ENTRY_RESUME_BUDGET_USD` (1) |

```bash
S_RESUME=$sid S_TURNS=$ENTRY_RESUME_TURNS S_TIMEOUT=$ENTRY_RESUME_TIMEOUT S_BUDGET=$budget \
  session entry-resume "$4" "${3%.jsonl}.resume.jsonl" "$5"
```

which runs, in a new scope unit `s<n>` (`rec_count "$STATE/scope-seq" 1`, as every session; a lane's
`harness-<run>-<m>-s<n>`):

```
timeout -k 30s $ENTRY_RESUME_TIMEOUT $CLAUDE -p "<the rendered prompt>" --model <the session's model> \
  --permission-mode auto [--settings $WT/$AGENT_SETTINGS] --strict-mcp-config [--mcp-config $WT/.mcp.json] \
  --max-turns $ENTRY_RESUME_TURNS --max-budget-usd <budget> --output-format stream-json --verbose --resume <id>
```

The session's model, settings and MCP flags are the session's because `session()` builds them the same way from the
same `$WT`. `budget` = `MET cost "$3"` (a new `metrics.mjs cost <transcript>`: the max `total_cost_usd`, `outcome`'s
`cost`, 0 without a result) plus `ENTRY_RESUME_BUDGET_USD`, summed in node or awk (bash has no floats). The cap is set
on the cumulative figure because a resume's `total_cost_usd` is cumulative; a cap below the spend so far did not stop a
one-turn resume (`resumed-again-under-cap.jsonl`, `--max-budget-usd 0.003`), and whether the CLI checks it between
turns against the cumulative figure is unmeasured: the sum works either way. `session()`'s usage reads (`MET usage`
into `$USAGE`/`$USAGE5`) and its scope notes run for the resume too. The run.log line is `  entry-resume exit <n>`,
which `summary.mjs parseRunLog` doesn't match (only `init|coding|verify|retro`), so no session is counted. `$STATE/
sessions` (MAX_SESSIONS) is not bumped: only `lane.sh` and the driver bump it, before a session.

**The transcript.** `<nn>-<id>.resume.jsonl` beside the session's (`${3%.jsonl}.resume.jsonl`: `01-A.resume.jsonl`,
`00-init.resume.jsonl`, the verify's own name with `.resume`); its prompt `…resume.prompt.md` beside it.

**After it** (in this order, all in `entry_resume`):

1. `feature_list.json` and `INBOX.md` of `$RUN_DIR` are put back from copies taken before the resume (`cmp` → a note
   `<who>: the resume changed <file>; restored`): the driver reads the list's claim and the INBOX's questions after
   `journal`, and the resume may write `entry.json` only. (`entries.jsonl` and `progress-archive.md` are restored by
   `journal`'s existing loop, which runs after.)
2. Its uncommitted edits outside the run record are dropped without a commit: `git checkout -q -- . ':!.harness/runs'`
   and `git clean -fdq -- . ':!.harness/runs'`. The tree was clean before the resume (the WIP commit in `lane.sh`, the
   driver's `commit_all` and `restrict` for the initializer and verify), so only the resume's files go. This is what
   keeps `resumed.txt` (`STUB_RESUME_ENTRY=good-edits`) out of **every** commit: `restrict` alone commits a WIP first.
3. `restrict "$base" record entry-resume` (`base` = HEAD before the resume) reverts anything a resume **committed**
   outside the run record, as for a verify; in a lane, `sync_lane` when it printed anything.
4. The metrics row (§Metrics), under `record`.

Then `journal` goes on as today: `record journal_` runs the ingest again on whatever `entry.json` is now there.

**The notes.** `journal_`, when `ENTRY_RESUMED=1`:

- ingest exit 0 → `<who>: entry.json written on a resume`
- ingest exit 3 → `<who>: entry.json still <why> after one resume; recorded a minimal entry` (`<why>` as today:
  `missing` or `invalid (<first error>)`), in place of today's `<who>: entry.json <why>; recorded a minimal entry`.

Without a resume (refused, no id, retro) the old note stands, so checks 21 and 22 are unchanged. Check 25
(`STUB_BAD_ENTRY=B`, not refused) is now resumed; the stub's resume writes nothing unless `STUB_RESUME_ENTRY` says
so, so B's `{not json` stays and 25's grep becomes `B: entry.json still invalid (not JSON: .*) after one resume;
recorded a minimal entry$`. R2-04 runs the full suite once with the resume wired and fixes each red check at its
cause: a stub path a real session would end with an entry (the two `PARKED:` paths write one with `outcome:
"parked"`), or an expectation that the resume changes for real (25; a check that counts scope units, notes or metrics
rows), each named in the entry.

**Config.** `lib/config.sh` `harness_config` defaults, beside `SESSION_BUDGET_USD`:
`ENTRY_RESUME_TURNS=8 ENTRY_RESUME_TIMEOUT=10m ENTRY_RESUME_BUDGET_USD=1`.

## Metrics

**`metrics.mjs session-id <transcript>`** prints the `session_id` of the first `{"type":"system","subtype":"init"}`
event; exit 1 when there is none. **`metrics.mjs cost <transcript>`** prints `outcome(events(f)).cost`.

**The row.** A pure, exported `resumeRow(sessionEvs, resumeEvs, args)` in `lib/metrics.mjs`: `metricsRow(outcome(
resumeEvs), args)` with `kind: "entry-resume"`, `role` the session's kind, and `cost_usd`, `tokens_in`,
`cache_read`, `cache_write`, `tokens_out` each the resume's cumulative figure **minus** the session's (`outcome().cost`
and `tokens()`), when the resume's init `session_id` equals the session's; otherwise (an unknown id: the CLI's
`error_during_execution`, cost 0, no init line) the resume's own figures. `turns`, `api_s` and `wall_s` are the
resume's own (per run already). CLI: `metrics.mjs append-resume <session.jsonl> <resume.jsonl> <metrics.jsonl> <run>
<feature> <model> <role> [<wall_s> <exit> <mem_peak_mb> <lane>]`, called as `record MET append-resume "$3"
"${3%.jsonl}.resume.jsonl" "$REC/metrics.jsonl" "$RUN_ID" "$2" "$4" "$1" "$S_WALL" "$S_EXIT" "$S_PEAK" "${LANE:-}"`.

**Fixture figures**, cumulative `total_cost_usd` 0.0031 → 0.0055 → 0.0058 (R2-03's checks compute them with jq from the files, never as literals in the check):
`resumed.jsonl` − `first.jsonl` = 0.00552003 − 0.0031115200000000004 (≈ 0.0024085); `resumed-again-under-cap.jsonl`
− `resumed.jsonl` = 0.00580227 − 0.00552003 (≈ 0.00028224, positive). Both node and jq subtract IEEE doubles, so an
`==` on the two results holds.

**Readers.** `summary.mjs`: `entry-resume` rows are kept out of `all` (so out of `sessions.total`, `real`,
`environmental` and every per-feature session count) and their `cost_usd` added to `cost.total`. `metrics.mjs
summary`: the session counts filter them out, the cost keeps them. `status.mjs` (sums every row's cost: spend
includes the resume, as the spec asks) and `show.mjs` (lists rows) need no change; `eval.mjs` filters
`kind === "coding"` already.

## The stubs

New `tests/stub-claude.sh` behaviours, each documented in its header comment:

- **An init line per headless session.** Before the `case $first`, every headless session prints first
  `{"type":"system","subtype":"init","cwd":…,"session_id":"<uuid>",…}`: `first.jsonl`'s init line (line 3) with
  `cwd` and `session_id` replaced (`jq -c`), the id from `/proc/sys/kernel/random/uuid`. The refused paths print it
  too (the real CLI starts the session before the API refuses). The id is recorded as `$STUB_DIR/sessions/<id>`
  (empty), and `ok()` writes its result line into it, so a resume knows the session's cumulative figures.
- **`--resume <id>`.** The arg loop reads `--resume <id>`; the stub appends its argv (one line, `printf '%q '`) to
  `$STUB_DIR/resume.log`. An id with no `$STUB_DIR/sessions/<id>`: line 1 of
  `tests/fixtures/claude-resume/unknown-id.out` with the id substituted to stderr, line 2 (id substituted) to stdout,
  exit 1. A known id: `resumed.jsonl`'s lines with `session_id` (and `cwd`) replaced, and its `result` line's
  `total_cost_usd` = the stored result's + the fixture's increment (resumed − first), `modelUsage` = the stored one's
  plus `resumed.jsonl`'s `usage`, so the figures are cumulative as the CLI's are. The resume prompt's `# Entry resume`
  first line selects the branch; its `Feature:`/`Kind:` lines under `# This session` give the id and kind
  (`after_session`, as for coding).
- **`STUB_NO_ENTRY=<id>`**: that feature's first coding session writes no `entry.json` (in `entry()`, beside
  `STUB_BAD_ENTRY`).
- **`STUB_RESUME_ENTRY=good|bad|good-edits`**: a resumed session writes a valid entry for its feature and kind with
  one `dead_ends` item (`good`), or `{not json` (`bad`); `good-edits` writes the good entry and also `resumed.txt` in
  the worktree (uncommitted). Unset: it writes nothing.
- **`STUB_LONG_SUMMARY=<id>`** (R2-02, §The trim).

## Decision and docs (R2-05)

`journal/decisions/2026-10-29-entries-survive.md`: finding (the minimal entries of 10-26 and 10-28, P1-03's lost
50 minutes) · choice (the entry check, the trim, no background work, one resume before the ingest, outside the lock)
· rejected: dropping the 400 cap (progress.md is read on a phone; the cap is what keeps an entry a line), resuming
more than once (a session that can't write a JSON object in 8 turns won't in 16; the cost is unbounded), resuming a
refused session (the limit that refused it refuses the resume, and a refusal's attempt is given back anyway), writing
the entry from the transcript by code (the parts lost are the session's judgement: dead ends, discoveries,
questions; code can only rebuild what the minimal entry has). `docs/architecture.md` §4 (the trim, the resume, the
`entry-resume` row) and §5 (the entry check, no background work); `README.md`'s steering section (entries).

## Live steps

None: build-only, and every step runs against the stubs. The first real resume will be a real session's; its row is
`kind == "entry-resume"` in that run's `metrics.jsonl`, and `harness-log.md` says `entry.json written on a resume` or
`still … after one resume`.
