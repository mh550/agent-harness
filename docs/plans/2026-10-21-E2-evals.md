## 2. The task set (E2-02)

### 2.1 task.json

```json
{ "id": "ps-vc2-retry", "project": "portfolio_site", "repo": "~/projects/portfolio_site",
  "base": "<full sha>", "features": [ { "id": "VC2-01", "milestone": "VC2", "...": "verbatim" } ],
  "check_cmd": "optional: overrides the project's CHECK_CMD", "policy": "build-only",
  "model": "optional: WORKER_MODEL for the task", "spec": "optional: SPEC_FILES (paths in the repo at base)",
  "brief": "optional: the source run's brief text", "why": "category, source run, the base commit and why" }
```

- **Required**: `id` (`^[a-z0-9][a-z0-9-]*$`, equal to its directory name), `project` (the source's directory name,
  so the replay's run worktree and prompt name the same project), `repo` (a local path; `~` expands; a URL is
  allowed by the schema but no proposed task uses one: reading GitHub is a network call), `base` (a full 40-hex sha:
  the commit the source's first session of these features started from, i.e. the parent of that session's first
  commit; named in `why`), `features` (1–3 entries copied verbatim from the source `feature_list.json`; each with
  `id`, `milestone`, `description` and at least one step), `policy` (must be `build-only`), `why`.
- **Optional**: `check_cmd`, `model`, `spec`, `brief`. `spec`/`brief` exist because a new run needs one
  (`cmd_start`), and the source session saw them: the builder copies the source run's spec list and `brief.md`
  (as of `base`). With neither, the eval passes `--brief "Eval task <id>: build the features in feature_list.json."`.
- `after` stays verbatim. A dependency on a feature or milestone outside the task counts as met
  (`features.mjs deps`: `byId.get(id)?.passes ?? true`), which is right: it is in `base` already.

### 2.2 Validator

`validateTask(obj)` (pure, exported) returns a list of error strings, each naming the field
(`features: 1 to 3 entries`, `policy: must be build-only`, `base: a full commit sha`, `features[1].steps: at least
one`, `id: …`). No `features` → `features: required`. Unknown top-level keys are an error (typos in optional keys
would silently change a replay). `node lib/eval.mjs validate evals/tasks` exits 0 on the committed set.
The task text may not mention a live system, a secret or a `.env` value: E2-02 checks it by hand and with
`grep -ril 'live\|secret\|\.env' evals/tasks` (must be empty); the validator does not grep prose. That grep matches
substrings too ("deliver", "alive", "process.env") and covers the verbatim `features` and a copied `brief`: features
can't be reworded, so a task whose features or brief hit it is dropped (or its `brief` left out), and `why` is
written without those words.

### 2.3 Where the source records are (read-only)

| Project | Records | POLICY (`.harness/config.sh`) |
|---|---|---|
| dj-crate-streaming | `~/projects/dj-crate-streaming/.harness/runs/*` on disk (run `dj-2026-10-17`: 33 features, 14 passing, 14 features had two sessions) | **live-staged** |
| portfolio_site | `~/projects/portfolio_site/.harness/runs/*` on disk (5 runs; `portfolio_site-2026-10-20` VC2-01, VC2-06 and `…-vc4` VC5-01/03/04 passed on a second session; those runs' `after` lists name milestones (`VC1`), while `…-2026-10-21-v3` (P1-02 after P1-01, P1-03 after P1-02) and `v2-2026-10-18` (M1-02 after M1-01) name features) | build-only |
| pathways | only in git history: `.harness/runs` on its run branches | none set → build-only (the default) |
| hit_list | only in git history | build-only |

**Ground rule (stay out of other checkouts).** Never `git -C ~/projects/<p> …`, never check anything out there. For
history, E2-02 makes a read-only mirror in its scratch dir and reads that:
`git clone -q --mirror ~/projects/<p> $HARNESS_SCRATCH/src/<p>.git`, then
`git -C $HARNESS_SCRATCH/src/<p>.git log --all --format='%H %s' -- .harness/runs` and `git show <sha>:<path>`.
(`--mirror` copies `refs/heads/harness/*` and `refs/remotes/*`, so deleted-but-pushed run branches are there too.)
Files on disk are read with `cat`/`jq`. The same mirror confirms each task's `base` resolves
(`git -C … cat-file -e <base>^{commit}`); E2-02's progress entry lists that for every task.

**Policy rule.** Eval tasks always run build-only, whatever the source's POLICY (§3.3 forces it), and never need a
live system or a secret. A dj-crate-streaming feature qualifies only if its steps hold without the live system
(no deploy, no staging data, no credentials); its 14 two-session features look environmental (live steps that a
build-only session can't do) and are the first to rule out. Ties go to portfolio_site, pathways and hit_list.

### 2.4 Choosing 8–12 tasks

Three categories, at least two tasks each; README columns: `id | project | source run | category | why`.

- **first-time pass**: every feature passed in its first real session and held verify (keeps the easy ones easy);
- **retried or given up**: a feature with more than one real coding session (`metrics.jsonl`, `env` false), a red
  suite un-pass or a verify re-check failure in `harness-log.md`, or one given up (does a change fix the hard ones?);
- **depends on an earlier feature**: 2–3 features where a later one's `after` names an earlier one **in the same
  task** (does the handoff carry what's needed?). At least one task has that: an `after` entry that is a feature
  **id** of the task (not a milestone name), e.g. portfolio_site v3's P1-01 → P1-02.

**The source run's record stays in `base`.** A base on a source run branch carries `.harness/runs/<source run>/`
(its progress.md and a feature list with the same ids, as of that commit). It is kept: the source session saw it too,
so stripping it would change the replay; nothing in it is from after `base`. (D-H35.)

Prefer tasks whose suite runs in minutes (the check runs before every session) and spread them across projects.
`evals/sets/default.txt` lists every proposed task.

## 3. `harness eval run` (E2-03, E2-04)

### 3.1 Layout

```
${HARNESS_EVAL_TMP:-/tmp/harness-eval}/<stamp>/        (= $E; stamp = date +%Y%m%d-%H%M%S, mkdir fails → exit 1)
  harness/                       git worktree of <ref> (--detach), removed at exit by a trap, whatever happens
  config.sh                      HARNESS_CONFIG for the runs (§3.3); state/ wt/ scratch/ ledger/  (HARNESS_* roots)
  <task>[/r<N>]/origin.git       the local bare origin (main = base)
  <task>[/r<N>]/<project>        the clone (the run's PROJECT_DIR; its basename is the source project's name)
${HARNESS_EVAL_RESULTS:-$HARNESS_HOME/evals/results}/<stamp>-<short sha>-<label>/
  eval.json  eval.log  <task>[/r<N>]/{summary.json,metrics.jsonl,harness-log.md,feature_list.json,progress.md,
                                      commits.json,probe-prompt.md}
```

`HARNESS_HOME` is the **invoking** harness (Michael's checkout); only the driver comes from `<ref>`. `<short sha>` is
`$HARNESS_VERSION` after `harness_version "$E/harness"` (`lib/version.sh`: the last commit outside `ledger/`), so it
equals every task's `summary.json` `harness.version` even when the ref's tip is a ledger commit (live `main` often
is); for a tag or a branch commit it is `git rev-parse --short <ref>`, which is what E2-03's checks compare. `<label>` defaults to `adhoc` (`^[A-Za-z0-9._-]+$`).
`/r<N>` appears only with `--repeat N` > 1; a task dir with `summary.json` directly in it is one repeat (§4 reads
both). The clone sits one level below `<task>` so the project keeps its source name (summary.json's `project` is the
worktree's parent dir), which deviates from E2-03's `/tmp/harness-eval/<stamp>/<task>` by one path segment.
Tests set `HARNESS_EVAL_TMP=$T/evaltmp` and `HARNESS_EVAL_RESULTS=$T/results`: the suite never writes into the repo.

### 3.2 One task, step by step

1. **Harness** (once per eval): `git -C "$HARNESS_HOME" worktree add -q --detach "$E/harness" <ref>`; `trap` removes
   it (`git worktree remove --force`) on every exit. `eval.log` gets `harness <ref> (<sha>) in $E/harness`.
2. **Origin and clone** (fresh per task and repeat): `git init -q --bare -b main origin.git`;
   `git clone -q --no-checkout <repo> <project>` (reads `<repo>`, never writes it; a local clone copies all objects,
   so a base reachable only from the source's remote-tracking refs still resolves);
   `git -C <project> checkout -q -B main <base>`; `git remote remove origin` (drops every `origin/*` ref of the source);
   `git remote add origin <abs path>/origin.git`; `git push -q -u origin main`.
3. **Seed** the run (`run=eval-<task>[-r<N>]`, branch `harness/<run>`): `git checkout -q -b harness/<run>`; write
   `.harness/runs/<run>/feature_list.json` from `node lib/eval.mjs seed task.json <run>` (`{run, branch, features}`,
   every `passes: false`) and `progress.md` (`# Progress — eval task <task>` + one line); commit
   `EVAL: seed <task>`; `git push -q -u origin harness/<run>`; `git checkout -q main` (the branch must not be checked
   out in the clone: `cmd_start` adds the run's worktree on it). `cmd_start` then sees `origin/harness/<run>` and
   takes it (`worktree add -B harness/<run> origin/harness/<run>`), and the driver finds the list and **skips the
   initializer**.
4. **Run**: pre-write `$E/state/<project>/<run>/run.env` (§3.3), then, with the environment of §3.3:
   `"$E/harness/bin/harness" start "$E/<task>/<project>" "<run>" --foreground --no-supervisor (--spec … | --brief …)`.
   Its exit code is logged, never fatal: the next task goes on.
5. **Collect**: copy `summary.json metrics.jsonl harness-log.md feature_list.json progress.md` from
   `$E/wt/<project>/<run>/.harness/runs/<run>/` into the result dir; from E2-06, write `commits.json` (§5.1) and render
   `probe-prompt.md` (§5.2) while `$E/harness` and the clone still exist, so `probes` works from the results alone
   after `/tmp` is cleared. Append the task to `eval.json`.

### 3.3 Isolation: nothing real is touched or reached

Environment of the `start` call: `HARNESS_STATE=$E/state HARNESS_WORKTREES=$E/wt HARNESS_SCRATCH_ROOT=$E/scratch
HARNESS_LEDGER=$E/ledger HARNESS_CONFIG=$E/config.sh HARNESS_GH=${HARNESS_EVAL_GH:-false}
HARNESS_CURL=${HARNESS_EVAL_CURL:-false} HARNESS_NO_RUNNER=1 HARNESS_EVAL=1` (the suite sets `HARNESS_EVAL_GH` and
`HARNESS_EVAL_CURL` to the logging stubs, so `nothing reaches a remote` can fail: forcing `false` there would make
the logs unable to grow whatever the code did); `HARNESS_MERGE_ONLY`, `TMUX`, `TMUX_PANE` unset; `HARNESS_CLAUDE` and `HARNESS_LIMIT_SLEEP` pass
through (the tests' stub; `claude` for Michael). `HARNESS_EVAL=1` lets Michael's own `~/.claude` hooks skip eval
sessions if he wants (sessions load his user settings exactly as real runs do; the eval can't change that).

The safety lines go in **both** `$E/config.sh` (layer 2: Michael's `~/.config/harness/config.sh` is not read, so his
NTFY and models don't leak in and A/B runs share harness defaults) and the run's `run.env` (layer 4: beats a
project's `.harness/config.sh`, e.g. dj-crate-streaming's `POLICY=live-staged`):

```bash
POLICY=build-only MERGE_POLICY=off PR_POLICY=off RETRO=0 AUTO_CONTINUE=0 DESK=0 LEDGER_COMMIT=0
NTFY_URL='' NTFY_TOKEN='' NOTIFY_CMD='' DESK_URL='' DEBRIEF_PAGE_CMD='' LIVE_LOCK=$E/live.lock
# from the task, when set:  CHECK_CMD=<check_cmd>  WORKER_MODEL=<model>
```

Why each holds: origin is a local path, so `deploy_status` finds no GitHub slug (no `gh api`), `gh_url` is empty,
every push and tag lands in `origin.git`; `MERGE_POLICY=off` skips `merge_milestones` (verify still runs and tags,
locally); empty NTFY/NOTIFY makes `notify` a no-op, and `HARNESS_CURL=false`/`HARNESS_GH=false` turn any missed call
into a failed command instead of a request. Not reached: the real state root, `~/worktrees`, the project checkouts
(only cloned from), the harness's ledger. E2-08 greps `lib/eval.sh` for `gh `, `curl`, `NTFY`, `push` and accounts
for every hit.

```json
{ "stamp": "20261022-0130", "ref": "run/…/E2", "sha": "abc1234", "label": "baseline", "set": "default",
  "repeat": 1, "eval_dir": "/tmp/harness-eval/20261022-0130", "harness_dir": "…/harness",

               "clone": "…/t1/portfolio_site", "worktree": "…/wt/portfolio_site/eval-t1",

               "end_reason": "done" } ] }
```

Written after every task (so an interrupted eval still has a record). `budget.not_started` and `weekly` (the
refusal text, if the window stopped it midway) say why tasks were skipped.

### 3.5 Results stay out of git by default

Untracked files under `evals/results/` would make every later real run `+dirty` (`lib/version.sh` ignores only
`ledger/`). `.gitignore` gets `evals/results/*` and `!evals/results/.gitkeep`. Michael commits a result he wants to
keep with `git add -f` (D-H35 *default*, question in E2-03's progress entry).

### 3.6 Budget (E2-04)

`EVAL_BUDGET_USD=10` in `lib/config.sh`'s defaults. The eval reads its config with `harness_config` on an empty
directory (§3.7) (Michael's user config applies to the eval command itself: `WEEKLY_STOP_AT`, `EVAL_BUDGET_USD`); an
`EVAL_BUDGET_USD` in the environment wins (kept before `harness_config`, restored after), so NEXT.md can say
`EVAL_BUDGET_USD=80 harness eval run …`. Before each task (and repeat) it sums `node lib/eval.mjs spent <results>`;
at or over the cap it starts nothing more, prints and stores
`budget: $<spent> of $<cap>; <n> tasks not started` (n counts task × repeat units). A running task is never cut:
the overshoot is at most one task's spend (each session keeps `SESSION_BUDGET_USD`). The stub's coding session costs
$0.25 and its verify $0.10, so task t1 spends $0.35 ≥ $0.30 and t2 is not started.

### 3.7 The 7-day window (E2-04)

Before anything is created (no `$E`, no results dir): `weekly_over "${HARNESS_STATE:-${XDG_STATE_HOME:-$HOME/.local/state}/harness}/USAGE_7D"`
(the **real** state root; in tests `$T/state`), using `lib/config.sh`'s function. Past `WEEKLY_STOP_AT`: print its
message (`7-day window at 90%, stop at 85%; resets …`) and exit 1. Before each further task the same test runs on the
real file and on `$E/state/USAGE_7D` (the eval's own sessions write that one); past it, the eval stops starting
tasks and records the message in `eval.json.weekly`. Inside a task the driver already ends a run before its next
session on `$E/state/USAGE_7D`. Usage limits inside a task are the driver's (it waits within `HOURS`).

The usage-limit window is box-wide in real runs (`LIMIT_UNTIL` in the state root, `driver.sh:38`), but the eval's
driver reads `$E/state/LIMIT_UNTIL`. So before each task the eval copies the real `LIMIT_UNTIL` into `$E/state/` when
it is later than the eval's own (the driver then waits it out as a real run would). The other direction (a real run
seeing a limit the eval hit) is not covered: NEXT.md says to run evals when no harness run is going.

The eval's own configuration: `harness_config "$E0"` where `$E0` is a directory with no `.harness/config.sh` (as
`tests/run.sh` does), not `$HARNESS_HOME`: the harness repo's own `.harness/config.sh` sets `CHECK_CMD` and
`MERGE_POLICY=pr` for runs **on** the harness and must not leak into the eval command.

## 4. `harness eval compare` (E2-05)

`loadResult(dir)` (bash reads files, passes JSON; or the CLI reads them): `{ tasks: { <id>: [summary, …repeats] } }`.
`compare(a, b)` (pure) → rows `{ task, metric, a, b, verdict }` for every task in both (tasks in only one are listed
under the table as `only in A: …`), plus `task: "total"`.

| Metric (row name) | Per repeat, from summary.json | Better |
|---|---|---|
| `pass rate` | 1 if `features.verified == features.total`, else 0 | higher |
| `$ per verified feature` | `per_verified_feature.cost` | lower |
| `tokens per verified feature` | `per_verified_feature.tokens` | lower |
| `cache hit rate` | `tokens.cache_hit_rate` | higher |
| `orientation tokens` | `orientation.tokens` | lower |
| `context peak` | `tokens.context_peak` | lower |
| `wall time (h)` | `time.wall_h` | lower |
| `rework` | `rework.length` | lower |

(E2-05's builder confirms each key path against `lib/summary.mjs build`; E1-06 named them.)

- **Task value**: pass rate is **pass^N** (1 only if every repeat passed; shown as `pass^N 1 (2/2)`); the others are
  the mean over repeats, nulls dropped.
- **Total**: computed per repeat index r over all tasks (pass rate = share of tasks passing in r; $ and tokens per
  verified feature = sums over tasks / verified features in r; the rest = mean over tasks), then summarized like a
  task (pass rate total = share of tasks with pass^N 1).
- **Verdict**: either side with one repeat → `one sample`; a side with no values → `no data` (a fifth verdict, an
  addition to E2-05's four: `$ per verified feature` is null when nothing verified); otherwise
  noise = max(spread A, spread B), spread = max − min of the per-repeat values; |B − A| ≤ noise → `within noise`;
  else `better`/`worse` for **B relative to A** in the metric's direction. (Spread is coarse with N=2 or 3; it is the
  spec's rule and it errs towards "within noise".)

Output: a markdown table `| task | metric | A | B | verdict |`, one line per task and metric, the totals block, then
one line per metric: `<metric>: <verdict> (A <a>, B <b>)`. Numbers: cost 2 decimals, rates 2, tokens rounded.

## 5. `harness eval probes` (E2-06)

### 5.1 Questions and their answers (pure `questions(list, rows, commits)`)

The **target** is the task's first non-passing feature, else its last feature: the probe asks what a session for the
target would know at its start. `eval run`'s Collect step (§3.2) writes `commits.json` from the clone:
`git -C <clone> log --reverse --name-only --format='%x00%H%x09%s' main..harness/<run>`, parsed into
`[{ subject, files }]`; `probes` reads it from the result dir (never the clone, which `/tmp` may have lost). Questions, in this order:

1. `Which files did <F> change?` for each non-target feature F with commits: the union of `files` of the commits whose
   subject starts `<F>:`, minus `.harness/runs/` paths (the stub's flip of `passes` rides in the same commit). Score
   key: the set of paths.
2. `What does <target> depend on?`, when it depends on anything: `deps(list, target)` from `features.mjs` (its
   `after`, or every feature before it). Key: the ids.
3. `What did the last attempt at <F> fail on?` for each feature with a non-passing, non-environmental coding row in
   `metrics.jsonl`: the source is the `final` text of its last such row; the key is its first sentence (≤ 80
   characters).

Each `{ q, kind, feature, answer, key }` goes into `probes.json` in the task result dir.

### 5.2 The prompt the probe sees

The probe must see exactly the handoff a session for the target would get. To keep that from drifting from the
driver, E2-06 moves the prompt assembly into **`lib/prompt.sh`**, sourced by the driver:

- `prompt_env`: the `export HARNESS_RUN_ID=… HARNESS_CHECK_CACHE=…` block that `load_config` has today;
  `load_config` calls it.
- `prompt_render <template> [extra env…]` → stdout: today's `prompt()` body (brief, CLAUDE.md, project.md, policy,
  `HARNESS_INIT_OUTPUT` from `$SCRATCH/init.out`); the driver's `prompt()` becomes
  `prompt_render "$1" > "$STATE/prompt.md"` plus its `cp`.
- CLI: `lib/prompt.sh <worktree> <state dir> <template> <feature>` (only when executed, not sourced:
  `[[ ${BASH_SOURCE[0]} == "$0" ]]`) reads `PROJECT_DIR` and `RUN_ID` from `<state>/meta.env`, derives `RUN_DIR`,
  `BRANCH`, `PORT`, `SCRATCH`, `CHECK`, `PROJECT_NAME` and the `LIVE_LOCK` default exactly as the driver's top and
  `load_config` do, runs `harness_config "$WT" "$STATE"`, `prompt_env`, sets `HARNESS_FEATURE` and
  `HARNESS_MILESTONE`, and renders. The eval calls it with the §3.3 environment (`HARNESS_SCRATCH_ROOT`,
  `HARNESS_CONFIG`, …), or `{{SCRATCH}}` and friends differ from the driver's prompt.

`eval run` calls the **ref's** `$E/harness/lib/prompt.sh "$wt" "$state" coding "<target>"` while that worktree
exists and saves `probe-prompt.md` with the results, so probes judge the prompt of the version that ran (a ref
without `lib/prompt.sh` gets no probe prompt; `probes` then exits 1 saying so). **E4 contract**: the probe has no
tools, so from E4 on `prompt_render` (or this CLI) must paste the target's `context.md` into the prompt; E4's plan
owns that.

The probe session: prompt = `# Probe session` + a blank line + `probe-prompt.md` + `---` + "Answer from what is
above only. One line per question: `Q<n>: <answer>`." + the numbered questions. Run once, in the task's run
worktree when it still exists (CLAUDE.md auto-loads as for the real session), else in an empty temp dir (the line
`probes: run worktree gone; CLAUDE.md not auto-loaded` goes in probes.json and the output):
`${HARNESS_CLAUDE:-claude} -p "$p" --model "$PROBE_MODEL" --max-turns 1 --tools "" --allowedTools "" --permission-mode dontAsk --strict-mcp-config --max-budget-usd 0.5 --output-format stream-json --verbose`
(the flags exist in `claude --help` today). The answer text is `metrics.mjs final`.

### 5.3 Scoring (pure `score(probes, text)`)

Answers are the `Q<n>:` lines. Normalize: lowercase, strip `` ` `` `"` `'`, collapse whitespace, drop a trailing
`.`. **exact** (1): the normalized answer equals the key (for sets: same items, split on commas and spaces);
**contains** (1): every key item (or the key sentence) appears in the answer; else **miss** (0). No LLM judge.
Prints one line per question (`Q1 exact · Which files did T2a change? · work-T2a.txt`) and `score <n>/<m>`;
`probes.json` gets `answers`, per-question `score`/`match`, `score`, `model`, `cost`.
