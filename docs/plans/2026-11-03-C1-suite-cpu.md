## 2. A constraint every cut meets: the memo lives in the shell that stored it

bash here is 5.2.21: no `${ cmd; }` (the current-shell command substitution came in 5.3; tried: `bad substitution`).
A memo entry written inside `$( … )`, `< <( … )` or a pipeline stage dies with that subshell. Most answer-reading
calls are written that way: `lib/lane.sh` has 11 `$(F model …)`, 3 `$(F ids …)`, `$(F next …)`, `$(F summary …)`;
`lib/driver.sh` 7 `$(F summary …)`, 7 `$(F model …)`, `for m in $(F milestones …)` (3, one of them `rebase_due`,
called every poll inside `< <(rebase_due; F lanes …)`), `$(record F unpark … "$(answers_hash)")`. `F passes` and
`F milestone-done` are conditions (`if F passes …`, `F milestone-done … ||`) and run in the current shell. A subshell
**reads** its parent's array, so an entry the parent holds is a hit anywhere below it. Two ways to get entries into
the parent, both C1-02's:

- **`F model`**: the table is a constant (`modelId`), so the memo is filled for every alias at once by one node start
  in the current shell the first time `F model` runs there (*default*: a `models` subcommand printing
  `<alias>\t<id>` for `fable`, `opus`, `sonnet`, `haiku`, composed from `modelId`; `run_paths` calls `F model
  "$INIT_MODEL"` once in the current shell, so every later `$(F model …)` of the process is a hit). A `claude-…` id
  is answered by `modelId` as is, so bash may return it without node (`[[ $1 == claude-* ]]`); any other alias (empty,
  unknown: `modelId` falls back to opus) is a miss and goes to node as today.
- **The list readers**: `Fv <var> <sub> <args…>` (*default* name) runs `F` in the current shell, stores the entry and
  assigns `<var>` with `printf -v`; C1-02 converts the sites whose first call is in a subshell, in the order of §3's
  rows (a site after a converted one in the same process needs no change: its subshell hits).

## 4. C1-03: what it collapses

- **The coordinator's idle poll** (`lib/driver.sh`'s `while :`, `alive < MAX_LANES`): five node starts per poll
  today, `F unpark`, `inbox.mjs answers` (in `answers_hash`), `needs.mjs sweep` (`needs_sweep`), `F milestones`
  (`rebase_due`) and `F lanes`. With §3's memo held in the coordinator's shell, `unpark`, `answers` and `milestones` hit
  on an unchanged `parked.json`, `INBOX.md` and list. `needs.mjs sweep` stays (it writes `needs.md` and resolves by
  the state dir; skipping it when `needs/` holds no item would leave a synthesized card stale: rejected). So the step's
  bound (at most one node start per idle poll) needs `F lanes` off the idle path too: *default*, the coordinator
  memoizes `F lanes` on its full input, the list, `attempts.json` and `parked.json` hashes plus a fingerprint bash
  builds from exactly what `laneState` reads (the `verified-*` and `needs-*` names, each lane's pid and whether
  `lane_alive` holds, the non-empty `review-escalate` files, `meta.env`'s `RUN_ID`), so any change to them is a new
  key. C1-06 reads this key hardest. The calls move out of their subshells: `answers_hash` and `F unpark` read into
  variables in the current shell, `rebase_due` reads the memoized `milestones`, and `F lanes` is read with `Fv` into
  an array before the `while read` loop.
- **The coordinator's end check** (`! opened && alive == 0`): `F summary`, `F parked`, `F blocked`, `F next` on one
  unchanged list → **`F poll <list> <att> <max> <parked> [<lane>]`**, one start, labelled lines read with `mapfile`,
  composed from the same exported functions (`schedule`, `laneBlocked`, the `summary` and `parked` code moved into
  exported functions); the five subcommands stay. Per file the end check is rare (`parked` 7, `blocked` 7): the gain is
  small, and the subcommand is what the lane loop uses next.
- **The lane loop** (`lib/lane.sh`, one iteration): `F milestone-done "$LIST" "$M"` (272) and `F next … "$M"` (285)
  on the same list: one `F poll … "$M"` (its `milestone-done` line) or two memo hits. Per file: `milestone-done` 83,
  `next` 35 in the lanes.
- **The session-log reads** (`metrics.mjs` in the lane, third of the top five, 314 per file): after every session
  `MET usage <log>` and `MET usage <log> five_hour` (`lib/record.sh` 291–292), `MET limit` (two or three times on the
  same log and arguments: `lib/record.sh` 307 and 346, `lib/lane.sh` 339) and `MET final`. *Default:* `MET limit` is
  memoized on the log's hash plus wall and exit (a finished session's log no longer changes), and the two `usage`
  calls become one start printing both windows. C1-03's steps don't name `metrics.mjs`: it is done there only if it
  fits beside the named items, else it is the next fix (said in the C1-03 entry).
- **`treekey.mjs` in `lib/check.sh`**: `--partial` ran 82 times per file, `--names` **0** (no partial run in file 13).
  Merging the two saves nothing in this file; C1-03 merges them only as the step asks (one start when both are
  needed), with no expected gain here.
- **Builtins**: none (§1).

## 5. Left alone, and why

- **The stub's** `node -e` (48 per file, 1.3 CPU-s; `tests/stub-claude.sh` edits the list and INBOX.md as a session
  does): the fake's edits stay the fake's (fakes mirror the live side; a change there moves every check that reads
  the list after a session), and 1.5 % of node is not worth the risk.
- **`tests/lib.sh`'s and the checks' own** (9 per file: `$F summary`, a rendered prompt, `summary.mjs report`): each
  is a check's assertion, and a check's own process is its own.
- **The harness CLI the checks call** (162 per file: `status.mjs card` 22, `needs.mjs list` 30, the debrief's and
  desk's reads): commands with their own timing bounds (`decisions/2026-10-30-cpu-time-bound-and-stopped-files`); not
  in C1's scope.
- **`entries.mjs`** in the lane (191, fifth): one call of each subcommand per session, each writes or reads what the
  session wrote; nothing repeats within a process.

## 6. The prediction against the spec's target

The spec's target is suite CPU −20 % (C1-04, against the *before* row). File 13 alone, without strace and outside the
runner: 185.0 s wall, user 107.12 + sys 63.48 = **170.6 CPU-s**, of which node is 84.4 (**49 %**, the first per-file
share measured; the load curve's §3 could not state one). §3 and §4 together are a guess of 700–1,000 fewer starts per
file, 19–27 CPU-s: **11–16 % of file 13's CPU**. If the other files are like file 13, C1 alone lands under the
spec's −20 %; C1-04 records the miss with its number if it is one (the spec: the target is a prediction, the fixes
stand on their checks). The next lever, if C1-04 is short, is §4's `metrics.mjs` collapse (if C1-03 left it) and
`testcount.mjs` (150 per file in the lanes, 54 in the driver: after every `check.sh` call).
