## 1. The entry

A session writes **one** JSON object to the run directory's `entry.json` before it finishes. The driver is the only
writer of `entries.jsonl` (§3). Field order in the file is free; the driver writes the keys in the order below.

### 1.1 Written by the session

| Field | Type | Rule |
|---|---|---|
| `feature` | string | required, non-empty. Coding: the feature id. Verify: the milestone id. Initializer: `"init"`. The driver checks it against the session it ran (`feature: expected C, got B`) |
| `kind` | string | required: `coding` · `verify` · `init` (the session's kind, not the feature's `kind`); must match the session |
| `outcome` | string | required: `passes` · `not yet` · `parked` |
| `summary` | string | required, 1–400 characters (code points: `[...s].length`) |
| `files` | string[] | the paths it changed (default `[]`) |
| `verified_how` | string | real commands, names and numbers (default `""`) |
| `tests_before`, `tests_after` | integer ≥ 0 or null | the suite's passing count before and after (default `null`) |
| `dead_ends` | `{ tried, why }[]` | what was tried and why it failed; both non-empty strings (default `[]`) |
| `discoveries` | `{ text, affects }[]` | `text` non-empty; `affects` a non-empty array of feature ids, milestone ids or `"run"` (default `[]`) |
| `questions` | string[] | for Michael (default `[]`) |
| `proposed_changes` | string[] | to the feature list, the spec or the harness (default `[]`) |
| `evidence` | `{ feature, step, ran, saw, holds }[]` | verify only (an error on other kinds): `feature` a non-empty string (a feature id; not checked against the list, which `validate` doesn't get), `step` an integer ≥ 1, `ran`/`saw` strings, `holds` boolean (default `[]`) |
| `header` | string | init only (an error on other kinds), ≤ 2000 characters: progress.md's header text (§4.1) |

Unknown keys are dropped without an error (a session's extra `notes` doesn't cost it its entry). `validate` returns
one error per problem as `<field>: <what is wrong>`, e.g. `summary: 401 characters (at most 400)`,
`outcome: missing`, `outcome: "done" is not passes · not yet · parked`, `evidence[2].holds: not a boolean`. A file that
isn't JSON, or JSON that isn't an object, gives the single error `not JSON: <parser message>` /
`not an object` (from the CLI, before `validate`).

Examples (shown to the sessions in their prompts, §7):

```json
{ "feature": "C", "kind": "coding", "outcome": "not yet",
  "summary": "Added the parser and its check; the suite is red on the fixture's trailing blank line.",
  "files": ["lib/parse.mjs", "tests/run.sh"], "verified_how": "bash tests/run.sh: 211/212, the new check fails on …",
  "tests_before": 211, "tests_after": 212,
  "dead_ends": [{ "tried": "trimming in render.mjs", "why": "the prompt prefix check then fails" }],
  "discoveries": [{ "text": "render.mjs keeps trailing blank lines", "affects": ["D", "run"] }],
  "questions": ["Should X default to off?"], "proposed_changes": ["C step 2 should name tests/run.sh"] }
{ "feature": "M1", "kind": "verify", "outcome": "not yet", "summary": "A step 2 fails: …; B holds.",
  "evidence": [{ "feature": "A", "step": 1, "ran": "node --test …", "saw": "7/7 pass", "holds": true },
               { "feature": "A", "step": 2, "ran": "curl :7804/x", "saw": "500", "holds": false }] }
{ "feature": "init", "kind": "init", "outcome": "passes", "summary": "12 features: E1 4, E2 5, E3 3.",
  "header": "# Progress — run `x` (project)\n\nWhat this file is: …",
  "discoveries": [{ "text": "the suite needs port 7804 free", "affects": ["run"] }] }
```

### 1.2 Stamped by the driver

`at` (`YYYY-MM-DD HH:MM`, local time at ingest), `session` (the transcript's name without `.jsonl`: `05-C`,
`153012-verify-M1`, `00-init`), `model` (the full model id the session ran on). A session's own values for these are
overwritten. A minimal entry also gets `minimal`: `"missing"` or `"invalid: <first error>"`.

### 1.3 The minimal entry

`minimal({ feature, kind, outcome, files, final })` → `{ feature, kind, outcome, summary, files, verified_how: "",
tests_before: null, tests_after: null, dead_ends: [], discoveries: [], questions: [], proposed_changes: [] }` (verify:
`evidence: []`), where `summary` is the session's final message with whitespace runs collapsed to one space, cut to
400 characters (`…` as the 400th when cut), or `(no final message)`. The driver supplies `outcome` (§3.2) and `files`
(the paths changed since the session's start commit, the run directory excluded). It always validates.

## 2. `lib/entries.mjs`

One-line usage header listing the verbs (as `features.mjs` does), node standard library only, pure functions exported:

| Export | Does |
|---|---|
| `validate(obj, { feature, kind } = {})` | → `string[]` errors, `[]` when valid (§1.1). With `feature`/`kind`, also checks they match |
| `normalize(obj)` | → the entry with defaults filled and unknown keys dropped (keys in §1.1 order) |
| `minimal({ feature, kind, outcome, files, final })` | → §1.3 |
| `renderEntry(entry, line)` | → one entry in full (§4.2), markdown ending in `\n` |
| `renderProgress(entries, { full = 15, header })` | → progress.md (§4.3) |
| `renderArchive(entries, header, legacy = "")` | → progress-archive.md (§4.4) |
| `legacyOf(archiveText)` | → the pre-journal part of an existing archive (§4.4) |
| `headerOf(entries, legacy, runId)` | → the header: the newest `init` entry's `header`, else `legacy` up to its first `### ` line (trimmed), else the default (§4.1) |
| `pack(entries, { feature, list, answers, cap })` | → context.md text, `≤ cap` bytes (§5) |

`entries` is always the parsed `entries.jsonl` in file order; an entry's line is its index + 1.

CLI (`node lib/entries.mjs <verb> …`):

- `validate <entry.json> [<feature> <kind>]` → the errors one per line, exit 1 when there are any.
- `ingest <run dir> <kind> <feature> <session> <model> <outcome> <files file> <final file>` → reads
  `<run dir>/entry.json`; valid → normalized, stamped, appended as one line to `<run dir>/entries.jsonl` (created if
  missing), exit 0. Missing, not JSON or invalid → `minimal(…)` from the two files and `<outcome>`, stamped with
  `minimal`, appended; prints `missing` or `invalid (<first error>)`, exit 3; `entry.json` is deleted on exit 0 and 3.
  Any other failure (e.g. entries.jsonl not writable): a message, exit 1, nothing appended, `entry.json` left; `journal`
  then moves it to `$SCRATCH/entry-failed-<session>.json`, so the next session's ingest can't take it for its own.
- `render <run dir>` → no `entries.jsonl`: does nothing, exit 0 (a legacy run, §6). Else writes `progress.md` and
  `progress-archive.md` (each through a temp file and `rename`, so a crash leaves the old file).
- `pack <run dir> <feature> [<cap>]` → context.md on stdout (`list` from `<run dir>/feature_list.json`, `answers`
  from `<run dir>/INBOX.md` after its `## Answers` line, `cap` default 8192). No `entries.jsonl`: the pack of zero
  entries.

## 3. The driver

### 3.1 `journal` (E4-03), next to `session()`

```bash
# <kind> <feature> <transcript> <model> <start commit> → the session's entry.json into entries.jsonl: the driver is its
# only writer (decisions/<date>-journal-single-writer). Missing or invalid: a note and a minimal entry from git and the
# final message. Then progress.md is rendered from it (E4-04).
journal() {
  local kind=$1 id=$2 who=$2 outcome="not yet" out rc
  git diff --name-only --no-renames "$5" HEAD -- . ":!$RUN_DIR" > "$SCRATCH/entry-files"
  MET final "$3" > "$SCRATCH/entry-final" 2> /dev/null
  case $kind in
    coding) if F passes "$LIST" "$id"; then outcome=passes
            elif sed -n 's/^[[:space:]*`>-]*PARKED:[[:space:]]*//p' "$SCRATCH/entry-final" | grep -q .; then outcome=parked; fi ;;
    verify) who="verify $id"; F milestone-done "$LIST" "$id" && outcome=passes ;;
    init)   F summary "$LIST" > /dev/null 2>&1 && outcome=passes ;;
  esac
  out=$(node "$HARNESS_HOME/lib/entries.mjs" ingest "$RUN_DIR" "$kind" "$id" "$(basename "$3" .jsonl)" "$4" "$outcome" \
    "$SCRATCH/entry-files" "$SCRATCH/entry-final"); rc=$?
  (( rc == 3 )) && note "$who: entry.json $out; recorded a minimal entry"
  (( rc == 0 || rc == 3 )) || { note "$who: the journal append failed (exit $rc): $out"
    mv -f "$RUN_DIR/entry.json" "$SCRATCH/entry-failed-$(basename "$3" .jsonl).json" 2> /dev/null; }
}
```

The note is exactly E4-03's `<id>: entry.json missing|invalid (<first error>); recorded a minimal entry`. `outcome`
is only used for a minimal entry; a valid entry keeps the session's own.

### 3.2 The exact points (E4-03)

- **Coding**: `sstart=$(git rev-parse HEAD)` just before `session coding` (`:535`); `journal coding "$id" "$slog"
  "$mdl" "$sstart"` **right after** `commit_all "WIP: $id — …"` (`:536`), so before the usage-limit branch and before
  `F repair` (`:559`). A refused session is journaled too: the journal is the complete record, and its minimal entry's
  summary is the refusal (the final message), and its outcome is what the list says at that moment (`not yet`, or
  `passes` when it flipped its feature before the cut, as `STUB_PASS_THEN_LIMIT` does). An entry's outcome is always the
  session's claim, taken before the driver's checks: the driver's verdicts (list restored, un-passed on a red suite, given back after a limit) stay
  `note`s in `harness-log.md`, as today when a session's progress entry said `passes`.
- **Verify**: inside the model loop, `journal verify "$m" "$vlog" "$(F model "$model")" "$vstart"` **right after**
  `restrict` and its note (`:279–280`), so before the limit branch (`:281`), before `F repair-verify` (`:289`) and before
  the `<= before` count and `F evidence` (`:293–294`), which go on reading `progress.md` (rendered there from E4-04
  on). `restrict "$vstart" record verify` keeps `entry.json` (it is in the run record).
- **Initializer**: `istart=$(git rev-parse HEAD)` before `session init` (`:478`); `journal init init
  "$LOGS/00-init.jsonl" "$(F model "$INIT_MODEL")" "$istart"` **right after** `commit_all "WIP: initializer — …"`
  (`:479`), before the `F summary` check, so a failed or refused initializer is journaled too.
- The retro, the desk, the supervisor and the debrief write no entry.

### 3.3 Commits

`entry.json` sits in the run directory, so a session's `git add -A` may commit it, and the `WIP` commit takes it if
not. `ingest` deletes it; the next `commit_all` (`HARNESS: after <id>`, `HARNESS: usage limit`, `HARNESS: verify <m>`,
`HARNESS: initializer done` or `finish`'s) records the deletion together with the appended `entries.jsonl` line (and,
from E4-04, the rendered files). One extra commit, in verify only (built, from the E4-03 review): `HARNESS: journal
verify <m>` right after `journal`, because a milestone that holds is tagged before `HARNESS: <m> verified`, and the
tagged tree is what merges into main.

### 3.4 What E4-03 leaves alone

The prompts still ask for a progress.md entry and the driver doesn't render yet: progress.md is the sessions' as today,
and verify's count and `F evidence` read what the verify session wrote. `entries.jsonl` fills up in parallel.

### 3.5 Rendering (E4-04)

`journal` ends with `node "$HARNESS_HOME/lib/entries.mjs" render "$RUN_DIR"`, so progress.md and progress-archive.md
are regenerated right after each append (initializer, coding, verify). `F evidence` reads the rendered progress.md
after the session's append, where the verify entry is the newest, so always among the 15 in full.

**The `before` count moves to the journal.** Counting `^### .*verify $m\b` in the rendered file breaks twice: an
earlier `verify <m>` entry that is 15th newest drops into the one-line section at the next append (after = before), and
on a just-continued legacy run `before` is counted on the old progress.md (any number of verify entries) and after on
the first rendered one (one). Both read as "no new verify entry" and waste an escalated verify. So from E4-04, with
`entries.jsonl` present, `before` and the after-count are the number of `kind == "verify"`, `feature == $m` lines in
`entries.jsonl` (`vcount`: `jq -c --arg m "$m" 'select(.kind == "verify" and .feature == $m)' … | wc -l`; without the
file, the progress.md grep as today). Every verify session appends one (a minimal one when it wrote none), so the
`no new verify entry` branch fires only on a failed append; a verify with no `evidence` gets `F evidence`'s shortfall
(`A 0/2; B 0/1`) and is escalated as before. E4-04 step 1's "verify's `before` count … read[s] the rendered file" is
amended accordingly (proposed in the E4-01 progress entry).

**`pr_body`** (`:197`) reads `progress-archive.md` when it exists, else progress.md: a held milestone, or one merged
later by `harness merge`, merges after more entries were added, and its verify entry may have left progress.md's 15.
The archive has every entry in full, newest first, so the awk finds the newest `verify <m>`.

### 3.6 Starting the journal on a legacy run (E4-04)

After the `HARNESS_MERGE_ONLY` exit (`:451`) and before `deploy_check` (`:472`):

```bash
# A run from before the journal (a feature list, no entries.jsonl): its progress.md is kept, byte for byte, as
# progress-archive.md and the journal starts here (decisions/<date>-rendered-progress). Nothing is rendered until the
# first entry, so a start-up that ends at once leaves progress.md as it was.
if [[ -f $LIST && ! -f $RUN_DIR/entries.jsonl ]]; then
  : > "$RUN_DIR/entries.jsonl"
  if [[ -f $RUN_DIR/progress.md ]]; then cp "$RUN_DIR/progress.md" "$RUN_DIR/progress-archive.md"
    note "journal started; progress.md kept as progress-archive.md"
  else note "journal started (no progress.md to keep)"; fi   # then the default header, no legacy part
  commit_all "HARNESS: journal started"; sync
fi
```

A fresh run creates `entries.jsonl` at the initializer's append. `harness merge` (merge-only) exits before this, so it
never touches a legacy record.

### 3.7 The context pack (E4-05)

- `lib/config.sh` defaults: `CONTEXT_PACK_BYTES=8192   # context.md's cap (E4): the pack a session reads first`.
- **Coding**: after `run_init` (`:530`), before `prompt coding`: `node "$HARNESS_HOME/lib/entries.mjs" pack "$RUN_DIR"
  "$id" "$CONTEXT_PACK_BYTES" > "$RUN_DIR/context.md"`.
- **Verify**: inside the model loop, before `prompt verify` (`:275`), the same with `"$m"` (so the escalated round's pack
  has the first round's entry).
- `session()` copies it beside the prompt for coding and verify: `[[ $1 == coding || $1 == verify ]] && cp
  "$RUN_DIR/context.md" "${3%.jsonl}.context.md"` (as `logs/05-C.context.md`), so the pack each session got can be read
  afterwards. In the run directory it is committed with the run record (the session's commits or the driver's next
  one). No initializer pack.

## 4. The rendered files

### 4.1 Header

`headerOf`: the newest `init` entry's `header`; else, for a continued legacy run, the legacy text up to its first `### `
line; else the default:

```
# Progress — run `<run id>`

Rendered by the harness from `entries.jsonl` after every session (sessions write `entry.json`; edits here are
overwritten). Newest first: the 15 newest entries in full, older ones one line each, every entry in full in
`progress-archive.md`. Steer from `INBOX.md` (first line `status: run|pause|stop`; answers under `## Answers`).
```

### 4.2 One entry in full (`renderEntry`)

```
### <at> · <feature> · <outcome>            (coding, init: `### 2026-10-22 01:10 · C · not yet`)
### <at> · verify <m> · <outcome>           (verify: `### 2026-10-22 01:30 · verify M1 · not yet`)

<summary>

| Feature | Step | What you ran or read | What you saw | Holds |     (verify with evidence only)
|---|---|---|---|---|
| A | 1 | node --test … | 7/7 pass | yes |

- **Files:** a, b, c (the first 12, then `+N more`)
- **Verified:** <verified_how>
- **Tests:** 211 → 212                     (either side `?` when null; the line is left out when both are)
- **Dead end:** <tried> — <why>            (one line each)
- **Discovery** (affects C, run): <text>   (one line each)
- **Question for Michael:** <question>     (one line each; `debrief.sh` greps `question`)
- **Proposed change:** <change>            (one line each)
- *<session> · <model>*                    (minimal entries add ` · recorded by the harness: entry.json <missing|invalid: …>`)
```

Empty fields leave their lines out. Every text field but `header` is rendered on one line (whitespace runs, newlines included, become one space), and a `header` line starting `### ` or `|` gets a leading `\`, so no entry text can fake an entry header or an evidence row. The table is the five-column shape `verify.md` asks for today. Evidence cells: `|` becomes `\|`, newlines become spaces, `holds` renders `yes`/`no`,
the feature cell is the bare id, so `F evidence` counts each row (`^\|\s*\**A\**\s*\|`) and finds the entry
(`^### .*\bverify M1\b`). `pr_body`'s awk (`index($0, "verify M1")` on a `### ` line) finds it too.

### 4.3 progress.md (`renderProgress`)

```
<!-- harness: rendered from entries.jsonl after every session; edits here are overwritten -->
<header>

<the 15 newest entries in full, newest first (file order reversed), one blank line apart>

## Older entries (in full in progress-archive.md)

- <at> · <feature or verify m> · <outcome> · <summary, first 100 characters, … when cut> ([in full](progress-archive.md))
```

The older section is left out when there are ≤ 15 entries. Older lines never start with `### `, so the verify count and
`F evidence` see only the 15 newest (a verify entry is always the newest when they read it).

### 4.4 progress-archive.md (`renderArchive`)

```
<!-- harness: rendered from entries.jsonl after every session; edits here are overwritten -->
<header>

<every entry in full, newest first>
<!-- harness: progress.md before the journal, kept as it was -->      (continued legacy runs only, then:)
<the legacy text, verbatim>
```

`legacyOf(text)`: a text whose first line isn't the `<!-- harness: rendered …` line is all legacy (the archive as §3.6
copied it); otherwise the text after the first `<!-- harness: progress.md before the journal, kept as it was -->` line,
or `""`. The `render` CLI reads the existing archive (none: `legacy` is `""`), takes `legacyOf` it, and passes it to `headerOf` and
`renderArchive`. So the pre-journal record survives every render byte for byte (at the end), and right after the
journal starts (§3.6, no entry yet) the archive *is* the old progress.md.

## 5. The context pack (`pack`)

Deterministic, no LLM. Inputs: `entries` (file order), `feature` (a feature id, or a milestone id for verify), `list`
(the parsed feature list), `answers` (INBOX.md after `## Answers`), `cap` (bytes, `Buffer.byteLength`).

**Targets** `T`: `{feature}`; for a milestone id, the milestone and its feature ids. **Dependencies** `D`: the target
feature's `after`, a milestone id expanded to its features, in list order (for a milestone: its own features). No
`after`: `D` is empty (part 5 covers the run's recent work).

**Items**, in this priority order; within a part, newest entry first:

1. **This feature's earlier attempts**: for each entry whose `feature` is in `T`: each dead end (`Dead end (<feature>,
   <session>): <tried> — <why>`); then, scanning **every verify entry** (their `feature` is a milestone id, so they
   aren't among those entries), each `evidence` row whose `feature` is in `T` and that didn't hold (`Verify <m> found
   (<id> step <n>): ran <ran>; saw <saw>`); then each question (`Question (<feature>): …`); then the entry itself (`<header
   line without ###>: <summary>; tests <b> → <a>; files <first 5>`).
2. **Michael's answers**: one item, the text under `## Answers`; when it doesn't fit whole, its **last** bytes (newest
   answers are at the bottom) after `…`. Ends with `→ INBOX.md`.
3. **Discoveries for this feature**: every discovery, from any entry, whose `affects` meets `T ∪ {"run"}`
   (`Discovery (<feature>, affects …): <text>`).
4. **What it builds on**: for each id in `D`, its newest entry, as in part 1's entry item.
5. **Lately in the run**: the last 3 entries of the run, as in part 1's entry item.

An entry shown as an entry item in an earlier part isn't repeated in a later one (dead ends, rows, questions and
discoveries are items of their own). Every item is one markdown bullet whose text has whitespace runs collapsed, cut to
1024 bytes with `…`, and ending ` → entries.jsonl:<line>` (part 2: ` → INBOX.md`).

**Assembly**: `# Context pack for \`<feature>\``, a line `Chosen by the harness from entries.jsonl in a fixed order;
each item names its line. The full record is entries.jsonl / progress-archive.md.`, then a `## <part title>` before
the first item of each non-empty part. Items are added in order while the total (headings included) stays within
`cap − 160` bytes; the **first item that doesn't fit stops the pack** (lower parts never jump a cut higher one), except
part 2, which is cut to the room left when at least 256 bytes remain. If anything was left out, a last line
`_<k> items left out at <cap> bytes: entries.jsonl has them all._` (the 160 reserved bytes hold it). Output ≤ `cap`.

## 6. The legacy rule

- **Legacy run** = a run directory with `feature_list.json` and no `entries.jsonl` (every run before E4, and eval clones
  seeded by a pre-E4 `eval run`). Until it is continued, nothing in E4 touches it: `render` does nothing without
  `entries.jsonl`, `harness merge` exits before §3.6, and every reader of progress.md (§11) reads it as today.
- **Continuing it** (`harness continue`, or a queued continuation: any start-up that drives sessions) runs §3.6 once:
  `progress-archive.md` = the old progress.md byte for byte, an empty `entries.jsonl`, the note
  `journal started; progress.md kept as progress-archive.md`. progress.md stays as it was until the first append
  renders it (header from the legacy text, §4.1; the old record at the archive's end, §4.4).
- A run that ended before its feature list (no list) isn't legacy: its next initializer starts the journal.
- **Eval clones** (`lib/eval.sh:106` seeds progress.md and a feature list, no `entries.jsonl`) are legacy by this rule:
  an E4 driver starts their journal at once and notes it. Harmless and unchanged code; older refs ignore it.

## 14. Review (E4-07)

`git diff 0e2cc33..HEAD > $HARNESS_SCRATCH/E4.diff` for an Opus reviewer; `docs/plans/2026-10-21-E4-review.md`.

**A tension the review must settle.** E4-07 step 2 asks that a legacy record be byte-identical "after a driver
start-up that ends at once"; E4-04 step 3 asks that `harness continue` on a finished legacy run (which ends at once:
every feature passes) start the journal. Both hold only if "a start-up that ends at once" means `harness merge`
(merge-only, which exits before §3.6). That is how this plan reads it. A start-up that drives sessions and then stops
at once (`status: stop`, deadline, weekly window) starts the journal: it adds `progress-archive.md`, an empty
`entries.jsonl` and the note, and leaves progress.md as it was. The review confirms by commands: (a) `harness merge` on a
fresh legacy record (run 14's has a journal by the time `harness merge` runs there: build one the way §10 does, in a
run of its own) with nothing to merge leaves `progress.md` byte-identical and creates no `entries.jsonl`;
(b) `harness continue` with `status: stop` leaves `progress.md` byte-identical; (c) `harness report demo` and
`pr_body` on a legacy record still read its progress.md (`pr_body`'s verify entry is the legacy one).

## 15. Defaults taken here (Michael's to overrule)

1. Refused (usage-limit) sessions get a journal entry (minimal, the refusal as summary). Alternative: skip them.
2. The entry's `outcome` is the session's claim; the driver's verdicts stay in harness-log.md, as today.
3. A legacy run's journal starts at any session-driving start-up, not lazily before its first session (E4-04's check
   needs `harness continue` on a finished run to start it).
4. The pre-journal record lives at the end of progress-archive.md, found by a marker line, not in a third file.
5. The eval probe gets context.md pasted in (§9), so E4's comparison can see it at all.
