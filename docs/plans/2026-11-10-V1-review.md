## Minor

**M1. A record's `memory-event.json` can belong to another segment, or go missing** (`lib/record.sh:486-487`, with
`lib/driver.sh:291`, `:392`, `:432`). The only removal is at the top of `memory_pr`. A continue segment that never
reaches `memory_pr` (`MEMORY_POLICY=off` skips `curator` at driver.sh:432; `curator: wrote no memory-ops.json` returns at
:291; `memory_base` failing returns at :277) keeps the earlier segment's card in `.harness/runs/<run>/`, beside a segment
whose `$STATE/memory.json` `finish` removed at :392. The inverse: segment 2 reaches `memory_pr` with `curator: no
operations`, the `rm` takes segment 1's card out of the record, and on the ntfy path (`EVENT_V2` unset, today's default)
that file was the only copy of what was sent (`events/<id>/event.json` is written only by `notify_event`).
Impact today: none. `grep -rn memory-event lib bin` finds no reader, and the spec's V2 does not read it either. This is the
same lifecycle `memory-review.json` already has ("removed at the next segment's curation", architecture.md:142).
Fix: no code change. Write the lifecycle down in the *Memory curation* state row (M2). If the record must say "this
segment sent nothing", add `rm -f "$REC/memory-event.json"` beside driver.sh:392's `memory.json` removal. That edits
`finish`, so do it in its own change and keep invariant 3's "finish not in the diff" check honest.

**M2. Docs lag the code in four places** (`docs/architecture.md`).
- :142, the *Memory curation* state row, lists every record file of the curation (`memory-review-input.json`,
  `memory-review.json`, …) and their removal. It does not list `memory-event.json`.
- :166, the *Routed events* row, now names `memory-event.json` in the run record. Its writer column still says only
  `notify_event`, lib/context.sh. The writer is `memory_event` in lib/record.sh.
- :97, the `lib/memreview.mjs` row, is still sized `~130`. `wc -l` gives 156.
- :97 (`line` "the F3d card will carry") and :346 ("the F3d card's text") are both in the future tense, though the card
  ships in this milestone.

Failure: a reader looking for the record's memory files, or for who writes the card, is pointed at the wrong component.
Fix: add `memory-event.json` (with M1's lifecycle) to :142, add `memory_event` (lib/record.sh) to :166's writers, change
`~130` to `~155`, and put both F3d phrases in the present tense.

**M3. `EVENT_V2` other than exactly `1` is silent** (`lib/notify.sh:34`, `lib/config.sh:73`). `EVENT_V2=true`, `yes`, or
`1 ` with a trailing space routes nothing. This is the safe direction, and invariant 2 holds for every value. But no line
says it happened. Scenario: Michael finishes the n8n-home checklist, writes `EVENT_V2=true`, and keeps getting the ntfy
line. n8n stores no card, and nothing in `run.log` or `harness-log.md` tells him why. Fix: say "`1` exactly" in config.sh:73's
comment and in architecture.md:583. Optionally, follow the `MEMORY_POLICY` precedent (driver.sh:272, "is none of pr, auto,
off"): in `memory_event`, note `EVENT_V2=<v> is not 1; the memory event went to ntfy` once when the value is non-empty
and not `1`.

**M4. `ROUTED` and `ROUTED_V2` are read by nothing** (`lib/notify.mjs:116-117`). The routing that actually runs is
notify.sh:33-34's `case` line. `grep -rn ROUTED lib bin` finds only the definitions, and the unit test pins the constants,
not the routing. Scenario: a later spec adds a kind to `ROUTED_V2`, the unit test passes, and the kind never routes. The
gap is older than this milestone (`ROUTED` was already unread); V1 widens it. Fix: one comment at notify.sh:33 naming
`ROUTED`/`ROUTED_V2` as its mirror. Or add a unit assertion that reads notify.sh, takes the `case` line's two
alternations, and compares them with `ROUTED` and `ROUTED_V2 \ ROUTED`. No stub run is needed.
