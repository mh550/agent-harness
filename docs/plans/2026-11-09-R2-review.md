## Important

### I1. A continue that reuses a PR replaces its `memory.jsonl` row with the last segment's review alone, so the PR's earlier ops vanish from the counts and the overrides

- **Where:** `lib/summary.mjs:708-709` (`memory-line`: rows with the same url are dropped, then this summary's rows
  are pushed), `lib/summary.mjs:304-310` (`tierReview` reads only this segment's `reviewed_ids`/`failed_ids`),
  `lib/record.sh:487` (`memory_pr` resets every review variable per segment), and `lib/record.sh:524` (the
  landing-differs path writes `memory.json` with `pr: $MEM_URL`, the earlier segment's PR).
- **What's wrong:** a reused facts PR carries every segment's commits (`harness-memory/<run>` moves forward), and
  `memoryState` reads it as `merged unchanged` when all of them are the driver's. The ledger row, though, holds only the
  latest segment's `reviewed`, `held`, `failed`, `failed_ids` and `fails_dropped`. The suite already shows this:
  `tests/checks/memory-branch.sh:120` expects `mp · proj · facts · 1/3/0 · held 1 · failed 0` after mp's continue,
  where the first segment's line read `held 2 · failed 0`. And `tests/checks/memory-review.sh:174` builds the case
  where the PR keeps an unreviewed commit (mn: no review in segment 1, then `fact-b` held in segment 2); its row then
  reads `held 1 · failed 0`, reviewed.
- **Failure scenario (confirmed in `/tmp` with the CLI):**
  1. Segment 1 under `pr`: two facts, `facts/2` fails q2. The row is `reviewed 2 · held 1 · failed 1`.
  2. The run continues and reuses the PR. Segment 2 reviews one new fact, which holds. `memory-line` replaces the row:
     `reviewed 1 · held 1 · failed 0 · failed_ids []`.
  3. Michael merges the PR, failed eviction included. `harness memory p` prints `mn · p · facts · 1/0/0 · held 1 ·
     failed 0 · u1 · merged unchanged` with no `override:`, `review: … overrides 0`, and the `auto:` line counts a
     clean PR.
  The reverse also happens: when the PR still holds segment 1's failed or unreviewed op and Michael closes it,
  `memoryOverride` returns `closed against a hold`, which counts against the reviewer. The same thing happens in the mn
  case, where an unreviewed commit is counted as reviewed and held. A landing-differs segment
  (`record.sh:524`) replaces a reviewed row with an unreviewed `0 applied` one. The rule the spec says "cannot be
  moved that way" (a merge over a fail) moves on any continue.
- **Suggested fix (smallest, fails closed):** in `memory-line`, when a row with the same url exists, merge instead of
  replacing it. Sum `reviewed`/`held`/`failed`, concatenate `failed_ids` and set `fails_dropped` to the AND of both.
  If either side is unreviewed (no fields, or `review` not `ok`), write the merged row without review fields, so it
  reads `unreviewed`. To make a rerun of one segment's `ledger()` idempotent, key each segment's part by its facts
  commit (`fhead`, carried in `memory.json`), for example `segments: {<sha>: {reviewed_ids, failed_ids, review,
  fails_dropped}}`, and derive the counts from that map.
- **Test:** `tests/unit/summary.test.mjs`: `memory-line` on a summary with `failed_ids ["facts/2:q2"]`, then on a
  second summary for the same url with one held fact, gives `reviewed 3 · held 2 · failed 1`. A first summary with
  `review: "the reviewer wrote no memory-review.json"` makes the merged row unreviewed. Update
  `memory-branch.sh:120`'s expected `held 1` to the summed counts.

## Minor

### M1. The `auto:` line fails open when gh cannot answer: unknown states count as no override

- **Where:** `lib/summary.mjs:360` (`overrides = w.filter(r => memoryOverride(r, states[r.url], …))`) and
  `lib/summary.mjs:344-349` (an `unknown` or missing state is neither override).
- **What's wrong / failure scenario (confirmed):** 8 reviewed PRs, 22 of 24 held, and two that Michael merged over a
  fail. With gh unauthenticated or offline, `memory.sh` collects no answers, and `graduation` prints `auto: earned (held
  22 of 24 · 92 % · overrides 0 of 8 reviewed PRs · window 8)`. With gh's answers it prints `not yet … overrides 2 of
  8`. The tally line shows `unknown 8`, but the last line, the one Michael reads for the rule, says `earned`.
- **Fix:** count the window's PRs whose state is `unknown` or missing. With any, the word is `not yet` and the line
  adds ` · unknown <k>`. `revisit` stays computable, since it reads only the rows.
- **Test:** a `graduation(earn, {}, [], "p")` case in the graduation unit test expects `not yet` with `unknown 8`.

### M2. An R1-era summary prints a false `$0.00 · 0 min` reviewer cost

- **Where:** `lib/summary.mjs:291-292` (`reviewTail`: `money(m.review_cost_usd ?? 0)`, `Math.round((m.review_s ??
  0) / 60)`), `lib/summary.mjs:280-289` (`memoryOf` defaults them to 0). The unit test enshrines it:
  `tests/unit/summary.test.mjs:578`.
- **What's wrong:** a `summary.json` written between R1 and R2 (the ledger's or the state dir's copy, which `harness
  report` reads directly) has `reviewed` but no cost keys. Its `Memory` row changes from `· review 3 held · 0 failed`
  to `· review 3 held · 0 failed · $0.00 · 0 min`. That is a cost the session did not have: its real cost is in
  `Spend by role`. The decision gives `0, 0, null` for "no session ran", and here one did. The spec's "an old report
  prints as before" is not met for this generation.
- **Fix:** in `memoryOf`, keep `review_cost_usd`/`review_s` only when the file has them. In `reviewTail`, print the
  cost and minutes only when `Number.isFinite(m.review_cost_usd)`.
- **Test:** change line 578's expectation to `… · review 3 held · 0 failed` (no cost part).

### M3. Rounded figures can contradict the word: `90 %` with `not yet`, equal dollars "over" each other

- **Where:** `lib/summary.mjs:360` (`Math.round`) and `lib/record.sh:642` (`%.2f` on both sides of an exact `r > c`).
- **Failure scenario (confirmed):** 26 of 29 held prints `auto: not yet (held 26 of 29 · 90 % · …)`. Under `auto`,
  35 of 44 held prints `revisit … 80 %`. A reviewer at $0.4512 and a curator at $0.4498 give `memory review: cost
  $0.45 over the curator's $0.45`. The decision says "the per cent rounded; the thresholds compared exactly", so this
  is as designed, but the line then reads as wrong.
- **Fix:** `Math.floor` for `pct`, which is never above the threshold it was compared with. For the note, compare at
  cents (`printf "%.2f"` on both, then compare), or print three decimals when the two-decimal figures are equal.

## Resolution (R2-03)

One round: the review found nothing Critical. Each finding, test first:

- **I1 fixed.** `memoryMerge` (`lib/summary.mjs`) merges a reused PR's row with the earlier segments' parts, kept under
  `segments` and keyed by the summary's `continuations`, so a rerun of one segment replaces its own. Only segments
  that landed a commit on the PR count. One unreviewed segment makes the row unreviewed, and `fails_dropped` is true
  only when every failed op was dropped. New unit test: `summary.mjs memory: memory-line on a continue's reused PR sums
  …` (red first: `[1,1,0,"ok",[],false]` against `[3,2,1,"ok",["facts/2:q2"],false]`). `memory-branch.sh`'s mp
  expectations now read `held 3` for the facts row, `held 1` for the rules row (its segment 2 landed no rule),
  `review: held 4` and `held 3 of 3`. They had encoded the bug. `memory-review.sh`'s mn check now also asserts that
  mn's one facts row reads unreviewed (`the reviewer wrote no memory-review.json`) after the held continue.
- **M1 fixed.** `graduation` counts the window's PRs with no gh state. With any, the word is `not yet` and the line
  ends `· unknown <k>` (unit: `graduation(earn, {}, …)` reads `unknown 8`, one missing state `unknown 1`).
- **M2 fixed.** `memoryOf` keeps `review_cost_usd`/`review_s` only when the file has them, and `reviewTail` prints
  the cost and minutes only then. The unit test's R1-era case now expects no cost part.
- **M3 half fixed.** The per cent is `Math.floor` (unit: 26 of 29 reads `89 %`; 7 of 8 and 21 of 24 now read `87 %`).
  The cost note at equal cents is unchanged: the reviewer did cost more at full precision, and changing the note would
