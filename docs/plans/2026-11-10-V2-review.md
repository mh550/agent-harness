## Important

**I1. A card action that fails once can never be retried from the card, and a tap before `ledger()` fails once**
(`lib/requests.mjs:64`, `:159-162`, `:91`; `lib/requests.sh:113-115`; `docs/2026-11-10-review-surface-n8n-home.md:69-71`).
The checklist's id rule makes the id `1-<sha256(event id, verb, PR, note)>`, so "a double tap writes the same name"
(§3, spec §V2-02.4). `doneIds` counts any `done/<id>.json`, and every outcome writes one: a refusal, and also an
unreadable gh answer (`ok` false). So the second tap of the same action is `duplicate id`, and the first result stands
for ever. That breaks two things the code and spec rely on:
- **gh down.** requests.sh:113's comment and spec §V2-02.1 say an unreadable gh answer is "not a refusal, since the
  next tap may find GitHub back". The next tap never gets to gh. It is a duplicate, and the card shows the old failure.
  A merge has no note field, so Michael cannot vary the id. The only way left is GitHub.
- **The card arrives before the ledger row.** `memory_event` fires inside `curator` (driver.sh:438). `ledger()` writes
  the `memory.jsonl` row (driver.sh:346) at the very end of `finish` (:464), after `SUM build`, `report`, a
  `sync_record` push and `record_pr`'s gh calls with their retries. That is tens of seconds, and longer when gh retries.
  If the run is killed between the two, the row never comes until a continue. Scenario: the ntfy arrives, Michael opens
  the card at once and taps **Merge**. `validate` refuses `pr <url> is not a memory PR the ledger knows`, which
  writes `done/<id>.json`. A minute later the row is there, but every new tap of Merge on that card is a duplicate of
  the refusal. The checklist already knows about this window: its `## Review` table shows "not in the ledger yet"
  (§2.4), yet it still offers the buttons.

Fix: this side's docs only, and n8n-home builds the change. (a) Checklist §2.7: show the actions only once
`HARNESS_LEDGER_DIR/<project>/<run>/memory.md` exists. The card already reads that file when it is served, and
`ledger()` copies the record (`cp -r`, driver.sh:334) moments before it writes the row, under the same call. Until then,
show "the actions come when the run's record is in the ledger". (b) Checklist §3: the hash also takes an attempt number.
The result page offers **Try again** with attempt + 1 when the result is `ok` false with `refused` null (gh ran and
failed), or when it is refused `… is not a memory PR the ledger knows …`. A double tap still writes one name. (c) Change
requests.sh:113's comment and the decision file's "the next tap may find GitHub back" to the retry the card actually
has. Whether `harness requests` should leave an unknown-PR request of a live run pending instead of refusing it is a
behaviour change, so it needs its own decision. It is not needed once (a) holds.

## Minor

**M1. A merge from an earlier segment's card lands later segments' commits, and the decision says those read as
`merged edited`. They read as `merged unchanged`** (`journal/decisions/2026-11-10-review-surface-verbs.md`, the
"No `--match-head-commit`" bullet; spec §V2-02.1; `lib/summary.mjs:337-344`). A continue reuses the facts PR and adds
one driver commit per segment, `memory: <run>: <n> facts`. `memoryState` counts those as the driver's own, so the merge
is `merged unchanged`. Scenario: segment 1's card (all held) is still on the phone. The auto-continue's segment 2 pushes
a commit with a failed op onto the same PR. Michael taps segment 1's **Merge**, and the failed op lands unseen. The
count is right once segment 2's `ledger()` has run: the row sums both segments, and the merge reads `merged against a
fail`. Before that run, the row still carries segment 1's `review: ok` (requests.mjs:95), so a segment 2 whose
reviewer did not run also passes the review rule. Fix: correct the sentence in the decision file and say what does
happen (later driver commits ride along unseen; the count reads them once the ledger has the segment). Optionally,
refuse a v2 `merge` whose `event` is not the run's newest memory event id (`$STATE/events/*/event.json` of kind
`memory`), with the reason `the card is from an earlier segment: open the newest one`. That is a new rule with a check,
so give it its own decision.

**M2. After a continue, closing the rules PR with a why declines only the last segment's rules**
(`lib/requests.mjs:107-112`, `:230`; `lib/driver.sh:303`). `declineItems` reads `rules[]` from the ledger's
`<project>/<run>/memory-result.json`, and each segment's curation overwrites that file. Scenario: segment 1 lands rules
r/1 and r/2 on `harness-rules/<run>`, then segment 2 lands r/1' on the same PR. A close with "not for this repo" writes
declined rows only for segment 2's item. Segment 1's two rules are on the closed PR but never declined, so `apply`
drops them by nothing and a later curator may propose them again. The spec chose this file, and `harness memory
proposals` has the same limit, so this is not a code bug. Fix: one line in the decision's decline bullet and in the
README (*a continue's earlier rules are not in the ledger's result: decline them by hand*). If it matters later, derive
the items from the rules PR's body instead, since it numbers every rule it carries.

**M3. `docs/architecture.md` lags the code in three rows.**
- :57 `lib/memory.mjs`: `answerRow` is still "the row, or why not: no such `<n>`, a bad why", and `upsert` is still
  "one row per `<run>/<n>`". Neither mentions the run-level row (no `n`, decline only) or the `(run, n, key)` upsert.
- :96 `lib/curator.mjs`: no `runLevel`, no `badWhy` (now shared with memory.mjs and requests.mjs), no `answersText`
  run-level line, and no mention that `apply` leaves run-level rows out of its matches.
- :176 *Memory answers*: "one row per answered `<run>/<n>`", written by `harness memory accept|decline`. It now also
  holds the run-level row (`n`, `file`, `section`, `text`, `key` null), and the card's close with a why writes it
  (`harness requests` → `harness memory decline`).

Also, the `lib/requests.mjs` row is sized `~210` and `wc -l` gives 240. Failure: a reader of the state table looking for
what writes `memory-answers.jsonl`, or what its rows can look like, misses the card and the null row. Fix: one clause per
row, and `~240`.

**M4. With two ledger rows for one URL, validate and declines read the first row, and the ledger's writer treats the
last as current** (`lib/requests.mjs:90`, `:226`; `lib/summary.mjs:735`). `memory-line` keeps one row per URL, so this
happens only after a hand edit or a hand-resolved ledger merge. In that case an older `review: ok` row would let a
merge through past a newer `review: <none>` row. Fix: `findLast` at both places, as `memory-line` reads it. No new
check is needed beyond one unit assertion with two rows.

## The eight checks

1. **No request merges a PR the ledger does not know, or one whose review did not run: holds** (with I1 and M4 as the
   caveats on timing and duplicates).
   - The order in node: `validateRequest` (requests.mjs:58-72) checks the object, NUL, `v` 1|2, the id, the duplicate,
     v2's verb set, then the run pattern and a real run, then `memoryRequest`. `memoryRequest` (:89-101) checks
     `PR_RULE` and at most 200 characters, then an exact `x?.url === q.pr` match (no prefix match and no normalisation:
     `…/pull/12/` is not `…/pull/12`), then `row.run !== q.run` → refused. Only after that are `r.pr` and `r.review`
     set.
   - The order in bash: `one()` reaches `pr_verb` only from the `ok)` arm (requests.sh:85-88), after the claim. A
     node crash gives no `verdict` line (`captured` prints only at the end), and the file is left. `pr_verb` asks gh's
     state (:112), then applies the review rule (`$review != ok` for a merge, :119), then makes the call (:124-128).
   - Labelled-line spoofing: no value that bash reads can hold a newline or an unvalidated byte. `name`/`id` pass
     `ID_RULE`, `verb` the verb set, `run` `RUN_RULE`, and `pr` `PR_RULE` (JS `$` is end of string; the unit test
     tries `…/pr/1\nwhy=x`). `review` goes through `oneLine` from the ledger, never from the request. `reason` goes
     through `oneLine` and is printed last. The why is never printed (`why 1|0`; the text goes to `<out>/why`).
   - The suite: `memory-requests.sh:131-134` asserts no gh call for an unknown PR, and exactly one `pr view` (the
     norev request's) for the three refusals. `:128-130` asserts nothing is merged on `review` not `ok`.
