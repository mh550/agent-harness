the events that need him, with enough context to explain them in plain words, and let his answers come back. Three

exactly as today when nothing new is configured.

notification or a real HTTP request** (the event hook is tested against a stub through `HARNESS_CURL`, like ntfy),

every behaviour visible in `harness-log.md` or `runner.log` and checked in `tests/run.sh` (written first, watched

## Contracts (v1; `mh550/n8n-home` builds to these, so change nothing without a new `v`)

Event JSON, POSTed to `EVENT_URL` with `Content-Type: application/json`:
```json
{ "v": 1, "id": "<uuid>", "at": "<ISO 8601>", "kind": "park|needs_michael|blocked|ended|debrief|verified|merged|started|limit|other",
  "project": "dj-crate-streaming", "run": "dj-2026-10-17", "feature": "N1-03 or null",
  "title": "...", "body": "...", "priority": "high|", "click": "<url or null>", "actions": "<ntfy actions or null>",
  "context": "<absolute path of the context bundle, or null>" }
```
`title`/`body`/`click`/`actions`/`priority` are exactly what the ntfy post would have carried, so n8n's error path can
send the same plain alert. For the `debrief` event, `run` and `feature` are null and `project` is null.

Request JSON, written by n8n as `<STATE_ROOT>/requests/<id>.json`:
```json
{ "v": 1, "id": "<uuid>", "at": "<ISO 8601>", "verb": "answer|continue", "run": "<run id>",
  "text": "<answer text, for answer>", "brief": "<optional, for continue>", "source": "n8n-card|n8n-report", "event": "<event id or null>" }
```
Result JSON, written by the harness as `<STATE_ROOT>/requests/done/<id>.json`:
```json
{ "v": 1, "id": "<request id>", "at": "<ISO 8601>", "verb": "answer|continue|null", "run": "<run id or null>",
  "ok": true, "exit": 0, "output": "<the command's output, capped at 2000 bytes>",
  "runner_started": false, "refused": "<why, or null>" }
```
Paths are host paths; the n8n container mounts them at the same paths, read-only except `requests/`.

## A1 · Event hook with an ntfy fallback

**Finding.** `notify()` (`lib/notify.sh`) posts to `NTFY_URL`, or calls `NOTIFY_CMD` only when `NTFY_URL` is unset.
Nothing tells a call site's *kind*, and nothing can hand an event to another service while keeping ntfy as the
safety net.

**Choice.**
- New user settings in `lib/config.sh` defaults and `templates/user/config.sh`: `EVENT_URL=""` and
  `EVENT_TIMEOUT=5` (seconds). Unset `EVENT_URL` → behaviour byte-for-byte unchanged (a check proves the stub sees
  the same ntfy calls as before).
- `notify` accepts `kind=<kind>` and `feature=<id>` like its other `key=value` fields. Call sites pass them:

  | Kind | Call site today |
  |---|---|
  | `park` | `notify_park` (`lib/driver.sh`, the park's notification) |
  | `needs_michael` | `needs_you` (a milestone needs Michael) and the merge-refused notification (`lib/driver.sh`) |
  | `blocked` | the run-end notification when the end reason is one Michael must act on (`"blocked on"*`, `"waiting on Michael"*`, `"feature-list edits"*`, `"initializer failed"*`, the `pri=high` case in `lib/driver.sh`) |
  | `debrief` | the debrief's headline notification (`lib/debrief.sh`, after the note is written) |
  | `ended`, `verified`, `merged`, `started`, `paused`, `limit` | the other driver notifications |
  | `other` | everything else (desk, debrief failures); no `kind` given means `other` |

- **Only `park`, `needs_michael`, `blocked`, `debrief` are routed to `EVENT_URL`**; every other kind goes to ntfy (or
  `NOTIFY_CMD`) exactly as today. For a routed kind with `EVENT_URL` set: write the context bundle (A2), build the
  event JSON in node (a new `lib/notify.mjs event` subcommand: no JSON built in bash), POST it through
  `${HARNESS_CURL:-curl}` with `--max-time $EVENT_TIMEOUT`, no retries, never with `NTFY_TOKEN`. **2xx = received;
  n8n now owns telling Michael**: no ntfy, and `log "event → n8n: <kind> <id>"`. Non-2xx, timeout or curl error →
  `note "event hook failed (<code or curl exit>): <kind>; sent to ntfy"` and the ntfy post goes out exactly as
  today. `notify` still always returns 0.
- Each routed event is also kept at `<STATE_ROOT>/events/<id>/event.json` (with the bundle beside it), so the record
  of what was sent survives n8n.
- Default (record it): routed events are best-effort synchronous; the 5 s cap bounds how long a dead n8n can hold
  the driver.

**Checks** (stub curl records each call's URL and body): unset → ntfy only, unchanged; routed kind + stub 200 → one
POST to `EVENT_URL` with valid v1 JSON and no ntfy; stub 500 / stub timeout → the POST and then the same ntfy post as
without `EVENT_URL`, and the `note`; non-routed kind with `EVENT_URL` set → ntfy only; the token never appears in the
event POST; `title`/`body`/`click`/`actions` in the event equal what ntfy got in the fallback case.

## A2 · Context bundle and ID glossary

**Finding.** The debrief's gatherer (`lib/debrief.sh`, `run_context()` and the block that writes `$CTX`) is the only
code that collects a run's state for a reader, and it is inline: it covers "every run since the last debrief" and
can't be scoped to one run. Its output, and every report Michael reads, is full of bare IDs (`D35`, `E2-02`, `M8`,
`H3-04`, `D-H32`) that only someone who was there understands.

**Choice.**
- Move the gatherer into `lib/context.sh` (sourced by `lib/debrief.sh`): `context_runs <state dir>…` writes the same
  markdown the debrief writes today for those runs. The debrief calls it; its `--dry-run` output stays the same
  apart from the new glossary section (a check diffs it).
- A new read-only CLI, `harness context <run-id> | --since <YYYY-MM-DD HH:MM:SS> [--out <dir>]`, writes a bundle for
  one run or for every run since a time, so the bundle can be built and inspected by hand. It never writes
  `summary.json` (don't call `harness report`).
- **Bundle** = a directory `<STATE_ROOT>/events/<event id>/` (or `--out`) holding:
  - `context.md`: the gatherer's markdown, then `## Glossary` (each ID, what kind it is, its text, where it is written).
  - `context.json`: `{ "v": 1, "id", "generated_at", "scope": {"runs": [...], "since": "<ts or null>"},
    "runs": [{ "run", "project", "ended", "running", "features": "<F summary>", "paths": {"record", "worktree",
    "state", "report", "inbox", "progress"}, "summary": <summary.json or null>, "parked": [{"feature", "why",
    "question"}], "open_questions": ["<from progress.md>"] }],
    "glossary": [{ "id", "kind": "decision|feature|milestone", "text", "source": "<path>:<line>" }],
    "unresolved": ["<IDs found but not resolved>"] }`
  - For the event of one run, scope is that run; for `debrief`, scope is the debrief's runs.
- **Glossary, by code (no model).** Collect IDs from the bundle's own text (the gatherer's markdown, the parked
  questions, the INBOX and progress excerpts) and resolve them against the run's worktree (else the ledger copy):
  - features, `\b[A-Z]{1,2}\d+-\d+\b` (`E2-02`, `N1-03`, `H3-04`) → `feature_list.json` (`description`, first 300
    chars, and its `milestone`);
  - milestones, `\b[A-Z]{1,2}\d+\b` not followed by `-\d` (`M8`, `H3`, `N1`, `S1`) → the feature list's milestone
    ids, then headings in the project's docs
    (`# M9`, `## 9. M8`, `## H1 · …`);
  - decisions, `\bD\d+\b` and `\bD-H\d+\b`, classified before milestones (`D35`, `D-H32`, `D24 *default*`; a
    project whose milestones start with D resolves against both and keeps what matches) → markdown table rows `| D24 | … |` and headings `### D-H1 · …` in
    the project's `CLAUDE.md`, `README.md`, `docs/**/*.md`, `journal/decisions.md`, and `journal/decisions/*.md`
    titles; the first 300 chars of the row's text, markdown stripped.
  - An ID written differently in two places → every match, newest file first. An ID nothing resolves → `unresolved`
    (never guessed). Put the regexes and resolution in `lib/glossary.mjs` as pure exported functions with unit checks.
- Retention (default, record it): `events/` entries older than 30 days are removed when a new one is written.

**Checks:** fixtures copied from a real dj run record (a `feature_list.json`, a pivot spec decision table, a park
INBOX), sanitised; `harness context` on the fixture run gives a `context.json` that validates against the shape above,
resolves `D24`, `N1-01`, `M8`, `D-H1`, and lists a planted `Q99` as unresolved; the debrief's `--dry-run` matches the
old output apart from the glossary; a routed event's `context` path exists when the POST is made.

## A3 · Request inbox

**Finding.** Michael's answers reach a run through `harness answer` (appends to `<state>/inbox.md`; the driver moves
it into `INBOX.md` and unparks the feature only while a driver runs, `take_answers` in `lib/driver.sh`) or by editing
`INBOX.md`. A re-queue is `harness queue add --continue`, which never starts the runner by itself (`cmd_queue add` in
`bin/harness`). n8n can't run host commands, and must not.

**Choice.**
- n8n writes request files into `<STATE_ROOT>/requests/` (created by the harness, mode 700, owned by Michael; the n8n
  container runs as the same uid). A new CLI `harness requests` processes every pending `*.json` there, oldest first,
  under `flock` on `requests/.lock`:
  - **Validate**: parses as JSON; `v == 1`; `id` matches `^[A-Za-z0-9-]{8,64}$` and has no result yet (an id already
    in `done/` is ignored: idempotent); `verb` is `answer` or `continue`; `run` matches `^[A-Za-z0-9._-]+$` **and** is
    a real run (`state_of`); `text` 1–4000 chars for `answer`; `brief` ≤ 2000 chars; no NUL bytes. A file that
    doesn't parse and is younger than 10 s is left for the next pass (n8n may still be writing it); older → rejected.
  - **`answer`** → `harness answer <run> "<text>"`, text passed as one argument (an array, never through a shell or
    `eval`).
  - **`continue`** → `harness queue add --continue <run> [--brief "<brief>"]`, then, if the queue runner isn't up,
    `harness queue start` — **except between 03:15 and 04:30 local time** (the backup window), when the entry stays
    queued and the result says `refused: "backup window 03:15–04:30: queued, runner not started"`.
  - Anything else → rejected: the request moves to `requests/rejected/`, the result says why.
  - Every request gets a result file `requests/done/<id>.json` (contract above; written to a temp name and renamed),
    the request itself moves to `requests/done/<id>.request.json`, and one line goes to `requests/requests.log`
    (time, id, verb, run, ok/refused, exit; **not** the answer text).
- A **`systemd --user` path unit** runs it: ship `systemd/harness-requests.path` (`DirectoryNotEmpty=` /
  `PathExistsGlob=` on the requests dir) and `systemd/harness-requests.service` (`Type=oneshot`, `ExecStart=` the
  repo's `bin/harness requests`, the PATH it needs for node). Don't install them (no `~/.config` writes): the README
  gives Michael the two commands (`systemctl --user link …` / `enable --now`). A path unit, not the queue runner,
  because the runner exits when the queue is empty.
- Defaults (record them): no third verb; no batching of answers; a `continue` for a run whose driver is alive is
  accepted by `queue add` as today (it waits until the run ends).

**Checks** (in the suite's throwaway state root): a valid `answer` lands in `<state>/inbox.md` verbatim (including
quotes, `$(…)`, backticks and newlines, proving no shell); a valid `continue` queues the entry and starts the
(stubbed) runner; the same at a faked 03:30 queues but refuses to start the runner; unknown verb, unknown run,
`run: "../x"`, oversize text, `v: 2`, and a duplicate id are rejected with results; a half-written file younger than
10 s is left alone; `requests.log` never contains the answer text; `systemd-analyze --user verify` on the units when
available (skipped with a PASS note otherwise).
