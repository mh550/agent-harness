# Lanes: independent milestones run side by side, each on its own branch, verified and merged on its own (2026-10-26)

**Goal.** The driver runs a run's independent milestones at the same time. Each milestone is a **lane**: its
features in list order, then its verify, then its merge, on its own branch, in its own worktree slot, port, scratch
and memory scope. The run keeps one **record branch** written by the driver alone. `MAX_LANES=1` (the default) is
today's behaviour in structure: one lane at a time, the same code. Two milestones, P1 then P2.

**Source.** `docs/specs/2026-10-25-throughput-and-memory-design.md` §4 (approved 2026-10-26 on its §10
defaults; Michael's six answers of 00:40 are in `docs/plans/2026-10-25-throughput-rollout.md`); its §1 has the
measurements. This run starts right after the lifecycle run, from `main` as it stands: L1–L4 (scopes, stop
points, scratch, gc) are the base. **Its first milestone, P0, is the suite split** (`docs/specs/2026-10-26-suite-split.md`
S1–S3, S4 optional), so that P1 and P2 add their checks to `tests/checks/` files by topic, never to a monolith.
Three milestones: P0, then P1, then P2.

**Rules.** `CLAUDE.md` binds: worktree only; never touch real runs or real state; fakes mirror the live API; every
behaviour visible in `harness-log.md` (`note`) and checked test-first; `bash -n` and `node --check`; a decision file
per behaviour change; `docs/architecture.md` (§3 components, §4 state, §5 the life of a run, §7 guards, §8
branches, §12 parallelism, §15) and `README.md` in the same milestone. Proceed on the defaults below and record them;
never park. Two invariants hold throughout and get a check each: **what lands on `main` is byte for byte what was
verified**, and **the driver is the only writer of refs, merges and the run record**.

**Names.** Record branch `harness/<run>` (as today). Lane branch `harness-lane/<run>/<m>` (git forbids
`harness/<run>/<m>` beside `harness/<run>`). Tag `run/<run>/<m>` (as today). PR head `harness-merge/<run>-<m>` (as
today). Slot worktree `~/worktrees/<p>/lanes/<run>/slot-<k>`, `k < MAX_LANES`. Units `harness-<run>-<m>-s<n>`,
`harness-<run>-<m>-check-<pid>`, `harness-<run>-<m>-svc`; `scope_owns` learns the `<m>-` prefix (the role regex
becomes `^([A-Za-z0-9_]+-)?(s[0-9]+|check-[0-9]+|svc)$`), so L2's `gc` reaps lane units. Scratch
`$SCRATCH/lanes/<m>`. Lane state `$STATE/lanes/<m>/{pid,port,slot,exit}`.

**Config** (`lib/config.sh` defaults, `templates/user/config.sh` commented): `MAX_LANES=1`, `LANE_RESERVE_GB=4`,
`LANE_OPEN_BELOW_5H=70`, `LANE_REBASE=suite` (`verify` = a verify session every time), `MAX_REBASE_ROUNDS=1`,
`RECORD_PR=end` (`off` = none), `HARNESS_LANE_POLL=10` (seconds; the suite sets 1).

## P1 · One lane at a time: the lane process, the record lock, the scheduler, the coordinator

**Finding.** `lib/driver.sh:567-650` is one loop: pick the next feature, init, context, session, bookkeeping,
repeat; `verify_ready` runs before each pick and blocks it. Every counter is a shell variable. The record and the
code share one branch, so a milestone's tag contains every earlier commit (`docs/architecture.md` §7 "Tainted tag",
§8), and the record reaches `main` inside every milestone PR.

1. **`lib/lane.sh <m>`**: one milestone, one process, started by the coordinator with the driver's environment
   plus `LANE`, `LANE_SLOT`, `LANE_PORT`. It sources `config.sh`, `prompt.sh`, `scope.sh`, `notify.sh`; `prompt_vars`
   sees the slot as `WT` and the lane's port. Its loop is the per-feature body of today's driver, moved: `control`
   (pause: wait; stop: exit `stopped`), `limit_wait`, the weekly gate, `F next` **restricted to this milestone**,
   `run_init` (the lane's `svc` scope on the lane's port), the record materialized (item 3), `context`, the clock
   line, the coding session in `harness-<run>-<m>-s<n>`, `WIP:` commit, journal, the environmental branch (attempt
   back, `LIMIT_UNTIL`), repair, red-suite un-pass, metrics (with `lane: "<m>"`), park. When `F milestone-done`
   holds, the same process runs `verify` (item 5), then exits. Its exit code is one of: `0` verified and merged (or
   proposed under `pr`); `10` given up `<id>`; `11` parked `<id>`; `12` needs Michael (verify or merge); `13` limit
   ended; `14` stopped; `15` deadline. The reason is also written to `$STATE/lanes/<m>/exit`. The EXIT trap runs
   `services_down` for the lane's scope, so a killed lane leaves no server.
2. **The record lock.** Every write to the record branch's worktree (`~/worktrees/<p>/<run>`, `RUN_DIR` there)
   happens under `flock "$STATE/record.lock"` in one helper, `record() { flock 9; "$@"; } 9> "$STATE/record.lock"`:
   `take_answers`, the record `sync` (fetch and merge Michael's phone edits, push), `journal` (ingest, render),
   `note`, metrics append, the `passes` flip, the session counter (`$STATE/sessions`, replaces `n`;
   `MAX_SESSIONS` is checked against it), the limit-hits counter (`$STATE/limits`), `commit_all` and the push.
   Each critical section is seconds; sessions run outside it.
3. **Materialization.** Before a session the lane copies `.harness/runs/<run>/` from the record worktree into the
   slot and excludes it for that worktree only: `git config extensions.worktreeConfig true` once per repository,
   then `git config --worktree core.excludesFile "$STATE/lanes/<m>/exclude"` with the one line `.harness/runs/`.
   (`.git/info/exclude` is shared by every worktree and would hide the record from the record worktree's own `git
   add -A`.) After the session, under the lock: take `entry.json`; run `F repair` on the slot's list against the
   pre-session snapshot and apply the flip to the record's list with a new `F pass <list> <id>` (the mirror of
   `unpass`), never copying the file (another lane may have flipped its own feature meanwhile); append the lines the
   session added above `## Answers` to the record's `INBOX.md` (`notify.mjs question` computes them); then `rm -rf`
   the slot's copy. A lane commit that touches `.harness/runs/` anyway is reverted by a new commit, as `restrict`
   does, with `note "<id>: a lane commit touched the run record; reverted"`.
4. **The scheduler** (`features.mjs`, pure, unit-checkable): `lanes <list> <attempts> <max> <parked> <state dir>`
   prints, in list order, one line per milestone that can open now (`<m>\t<base tags>`), and `next` gains an
   optional milestone argument. A milestone can open when it has a feature left to try, isn't verified, `needs-<m>`
   or open (`$STATE/lanes/<m>/pid` alive), and every milestone it depends on has `verified-<dep>` in `$STATE`. Its
   dependencies are the milestones named by its first feature's `after` plus any milestone another of its features'
   `after` points into; a first feature with no `after` depends on **every earlier milestone** (D-H25 as today), so
   only declared independence runs in parallel. Inside a lane, a feature with no `after` depends on the earlier
   features of its own milestone (R10's change 1, now the rule). Features with no milestone form one lane
   `default`, opened first. `blocked` keeps its meaning across lanes.
5. **Verify and merge from the lane.** `verify` moves to `lane.sh` as it is (merge `origin/main` in first; the
   verify session in the lane's scope; the evidence count; the escalation; `green` on that tree; the tag pushed),
   then `merge_one`. The tag is the lane tip, so it contains the lane's base and the milestone's commits only; the
   `tainted-<m>` and `held` logic and the "stop at the first unverified milestone" rule are deleted. One rule
   replaces them: a lane's PR is **opened** at verify and **merged** only once every dependency has `merged-<dep>`;
   until then `note "<m> verified; its PR waits for <dep> to merge"` once. `merge_milestones` becomes "try every
   verified, unmerged lane in list order"; `harness merge <run>` calls the same.
6. **The lane's base.** At open: `git worktree add` (first use of the slot) or `git checkout -B
   harness-lane/<run>/<m>` (reuse) at `origin/main`; then `git merge --no-edit run/<run>/<dep>` for every
   dependency whose tag isn't an ancestor of `origin/main` yet (a `pr`-held or refused dependency). A conflict there
   is `note "<m>: its base conflicts (<dep> vs main); needs Michael"`, `needs-<m>`, and the lane doesn't open.
   `--base <ref>` on `harness start` replaces `origin/main` for the record branch and every lane.
7. **The coordinator** (`lib/driver.sh`, replacing the loop): start-up as today (record worktree, INBOX, brief,
   deploy check, initializer in the record worktree, `deps-noted`); then every `HARNESS_LANE_POLL` seconds:
   `control` (pause: lanes pause themselves between sessions; the coordinator logs once and opens nothing; stop:
   opens nothing, waits for lanes to exit, `finish "stopped by Michael"`), deadline, `limit_wait` (box-wide; lanes
   wait too), `weekly_over`; reap lanes whose pid is gone (read `exit`, `note "lane <m> closed (<why>)"`, free the
   slot); `F lanes` for candidates; admission (P2 item 1; in P1 only `lanes alive < MAX_LANES`); open each
   (`note "lane <m> opened (slot <k>, port <n>, from <sha>)"`). When no lane is alive and no candidate opens, the end
   reason is computed as today (`done` · `blocked on <ids>` · `waiting on Michael: <ids>` · `no feature left to
   try`), and `finish` runs. `MAX_SESSIONS` and `MAX_LIMIT_HITS` end the run from the coordinator when a lane's
   exit reports them.
8. **`finish`** as today (summary, notification, retro in the record worktree, ledger, continuation), plus: wait for
   every lane to exit; remove every slot (`git worktree remove --force`); delete the lane branches of **merged**
   milestones locally and on origin; keep the branches of unverified ones. Then the record PR (P2 item 4).
9. **`harness continue`** reopens lanes from `origin/harness-lane/<run>/<m>` when the branch exists (the slot's
   `checkout -B` takes `origin/harness-lane/<run>/<m>` instead of the base), with attempts reset as today.
10. **The existing checks' intent.** Checks that assert the record on a tag or on `main` (`run/demo/M2:
    .harness/runs/demo/entries.jsonl`, `…/context.md`, `on_main run/demo/M2` for record files, the gc "record-only"
    block) are rewritten to assert the record on the record branch and that no code PR touches `.harness/runs/`.
    Every other check keeps its text. The desk, debrief, eval, parked and queue checks run unchanged.
11. **Legacy runs.** `harness continue` on a run whose branch has commits outside `.harness/runs/` beyond
    `origin/main` prints the three ways forward and exits 1: `harness merge <run>` for its verified milestones; a
    new run with `--brief` naming the old branch as the source for what is left; or finishing by hand. A run with
    no such commits (n8n-home-2026-10-22) continues as a lanes run: its branch already is a record branch.

**Checks (written first):** `features.mjs lanes` unit checks (an undeclared first feature waits on every earlier
milestone; `after: []` opens at once; a feature's `after` into another milestone makes the lane wait for it; a
`needs-<m>` milestone never opens; a feature with no `after` waits on its milestone's earlier features only). A stub
run with `MAX_LANES=1` and today's three-feature list ends `done` with `M1` and `M2` merged by two PRs, each PR's
diff touching no `.harness/runs/` path, the record on `harness/<run>` with every entry, `metrics.jsonl` rows
carrying `lane`, and the `lane M1 opened/closed` notes. The lane materialization: a stub session that commits
`.harness/runs/x` in the slot gets the revert note and the record branch is unchanged by it; a stub session that
writes a question above `## Answers` has it on the record's `INBOX.md`; two sessions' `passes` flips both land
(the stub flips in a slot while the record moved). The record lock: two lanes' bookkeeping interleaved by a stub
delay never lose an entry (line count equals session count). A verified lane whose dependency is `pr`-held opens
from the dependency's tag, its PR is opened and not merged, with the note. `harness continue` on a legacy branch is
refused with the three options; on n8n-style record-only branch it runs. `harness pause` pauses between sessions
and `harness stop` ends with every lane exited and no slot left. `finish` leaves one worktree per run.

## P2 · Two lanes and more: admission, the re-base rule, slots, cleanup, status, the record PR

1. **Admission.** Before each open: lanes alive `< MAX_LANES`; `mem_available_gb ≥ MEM_MIN_AVAILABLE_GB +
   LANE_RESERVE_GB × lanes alive` (`scope.sh`'s reader, `HARNESS_MEMINFO` in tests); when the newest session
   reported a five-hour window (`USAGE_5H`, written beside `USAGE_7D` by `MET usage`), its utilization under
   `LANE_OPEN_BELOW_5H`. A refused open is `note "lane <m> waiting: <reason>"` once per reason, retried next poll.
   Ports: the lane's port is the first free from `BASE_PORT` not held by any lane or run (`port_taken` over
   `$STATE_ROOT/*/*/port` and `*/lanes/*/port`), allocated under the record lock.
2. **The re-base rule** (`LANE_REBASE=suite`). When `merge_one` finds the tag no longer satisfies the invariant
   because `main` moved (the merge-tree differs from the tag's tree), the lane: merges `origin/main` into its
   branch (a conflict → `needs Michael`, today's path); computes the files `main` brought in (`git diff
   --name-only <tag>..HEAD`) and the milestone's own files (`git diff --name-only <base>..<tag>`); if they are
   **disjoint**, runs the suite on the merged tree in the lane's check scope and, when green, creates a new annotated
   tag `run/<run>/<m>` at the merged commit (`git tag -f -a`, pushed with `--force` to the tag ref only; the old
   commit stays reachable from the PR), notes `"<m> re-based on <main>: <n> files, disjoint, suite green;
   re-tagged"` and merges; if they **overlap**, one more verify round on the merged tree under its own counter
   (`MAX_REBASE_ROUNDS`), then tag and merge, else `needs Michael`. `LANE_REBASE=verify` makes every case the verify
   round. Decision file: `2026-10-26-lane-rebase-disjoint`. Under `pr`, `harness merge <run>` opens a slot from the
   tag and runs the same.
3. **Slots and cleanup.** A lane opens in the lowest free slot; a slot's worktree is created once per run and
   reused by `checkout -B`, so ignored install and build directories survive across milestones (one slot = today's
   one worktree). When a lane's PR merges: `git branch -D` and `git push origin --delete harness-lane/<run>/<m>`,
   the slot freed. Under `pr`: slot freed at verify, branch kept until `gc` sees it merged. `cmd_gc`: the
   `harness-lane/` prefix joins the `harness/` and `harness-merge/` passes; slots under `lanes/` of an ended,
   dead-driver run are removed by the worktree pass; `--deps` covers slots. `harness gc` of a run with a live
   driver touches no slot.
4. **The record PR** (`RECORD_PR=end`). The last step of `finish`, after the retro and the ledger: push the record
   branch; `gh pr create --base main --head harness/<run> --title "<run>: run record"` (or reuse the open one), body
   = the report; under `auto`, `gh pr merge --merge` and the PR head is gone with it; under `pr`, left for Michael,
   noted. The branch is record-only, so this merge can't conflict. Michael's rule (2026-10-26): the PR is merged and
   nothing stale stays behind. So `cmd_gc`'s `record_only` keeps its meaning, and the queue runner's end-of-queue
   `gc --all-merged --deps` (L4) deletes a merged run's record branch, locally and on origin, and its record
   worktree, the ledger keeping the record. It is not deleted at `finish` itself, so a `harness continue` the same
   night still finds the branch.
5. **Visibility.** `harness status <run>` prints one line per open lane: `lane <m> · <feature> · session <n> · port
   <p> · slot <k> · <units and MemoryCurrent>`. `summary.json` gains `lanes: {max_open, lane_hours, wall_hours}`
   (lane hours = the sum of each lane's open-to-close time), and `report.md` a line. `harness trends` is unchanged.
6. **Prompts.** `prompts/initializer.md`: milestones that may run side by side should touch different files, and
   shared docs (`README.md`, `docs/architecture.md`) are edited in a milestone's closing review feature; a feature
   independent of its predecessors in the same milestone gets `after` (R10's change 2, moved here). `prompts/parts/
   run.md`: the lane's worktree and port are what `WT`/`PORT` already render; one line says other lanes of this run
   work in other slots.
7. **Decisions and docs.** `journal/decisions/2026-10-26-lanes.md` (finding · choice · rejected: lanes from the run
   branch, a frozen legacy driver, a worktree per milestone, feature-level lanes now); `2026-10-26-parallel-runs-headroom.md`
   superseding D-H18 with 2026-10-25's usage figures (five-hour at 12 %, seven-day 82→83 % in 4.5 h) and the rule
   that admission is by headroom; `docs/architecture.md` §3, §4 (lane state, slots, record lock, `USAGE_5H`), §5 (the
   coordinator diagram), §7 (the record guard replaces the taint rows), §8 (lane branches; the record PR), §12
   (lanes beside `MAX_PARALLEL_RUNS`), §15 (the first bullet replaced); `README.md` (`MAX_LANES`, slots, the record
   PR, what `harness continue` says to a legacy run); `templates/user/config.sh`.

**Checks (written first):** with `MAX_LANES=2` and a list whose M2 is `after: []`, the stub run opens M1 and M2
together (two `opened` notes before any `closed`), both merge, `summary.json` has `max_open: 2`; with a
`HARNESS_MEMINFO` fixture under the reserve the second lane waits with the note and opens once the fixture changes;
with a stub `USAGE_5H` at 80 % it waits. The re-base: lane A merges a file B never touched while B is verifying →
B's note says disjoint, the suite ran, B re-tagged and merged, and the tree on `main` after B equals B's merged tree
(the invariant check); A touching a file B changed → B's verify round, then merge; `LANE_REBASE=verify` → the round
in the disjoint case too. Slots: a second milestone in `slot-0` keeps an ignored directory the first left; after
`finish` no `lanes/` directory remains and the merged lane branches are gone locally and on the origin while an
unverified one stays; `gc` on an ended run with a leftover slot (a killed driver) removes it and reaps a stub lane
unit, and leaves a live run's alone. The record PR: a PR whose diff is only `.harness/runs/<run>/` is opened and
merged under `auto`, left under `pr`, skipped with `off`; `gc` then deletes the record branch. `harness status`
shows the lane lines; the initializer prompt has the two new lines.
