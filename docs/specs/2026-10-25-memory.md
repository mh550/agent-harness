# Memory: a retro backlog the harness keeps, one routing rule, gotchas in place, memlint (2026-10-25)

**Goal.** Two kinds of memory the harness doesn't keep today. **Its own:** each retro proposal is promoted by the
driver into one deduplicated, status-tracked backlog in this repo, and the debrief reads that instead of 20 raw
retros. **The projects':** every session is told where a fact goes, durable gotchas are edited in place in
`CLAUDE.md`, the context pack carries the current rules, and a deterministic lint keeps the files in line. Then two
follow-ons to the retro-fixes run: a test-count contract (after R1) and a measured review gate (after R2).

**Sources, folded in here.** `docs/specs/2026-10-22-retro-followups.md` §C–§F and `docs/specs/2026-10-24-memory-model.md`
K1–K3 (both superseded by this spec; their findings and evidence stay there and are cited, not repeated). K4, the
one-time tidy of each project, was done by hand in chunk 3 Part 2 (`prompts/project-catchup.md`), so memlint (M4)
confirms it rather than driving it.

**Rules.** `CLAUDE.md` binds: work only in the worktree, never touch real runs or real state, fakes mirror reality
(fixtures copied from real `check.out` files, retros and project files, trimmed, never typed from memory), every
behaviour visible in `harness-log.md` and checked in `tests/run.sh` (written first, watched failing), `bash -n` and
`node --check` on every file touched, a decision file per behaviour change, `docs/architecture.md` and `README.md` in
the same milestone. **Sessions never write `ledger/`:** what is stored there is written by the driver or the `harness`
CLI (bash), never by a session. No LLM curator, no vector search, no blocking guard. Proceed on the defaults below and
record them; never park.

**Depends on.** This run starts after the resource-lifecycle and retro-fixes runs, from `main` as it stands. M5 builds
on R1 and M6 on R2: if either was given up there, drop that milestone and say so in the decision file. The parked
n8n-events run (A2) moves the debrief's gatherer later; M1 changes what it gathers, so keep that change inside the
gatherer block (`lib/debrief.sh:164-165`) so A2's move stays mechanical.

## M1 · The retro backlog (retro-followups §E)

**Finding.** Retros re-propose fixes that are already specced or built, because nothing records a proposal's status:
the review cap was proposed in 8 retros and the test counter in 6, both specced since 2026-10-21, and "a parked
feature shouldn't block unrelated milestones" (4 retros) was specced nowhere until R10. The debrief re-derives it each
time from the 20 newest `retro.md` files (`lib/debrief.sh:164-165`). That is how "retro proposals never became work"
(the handoff's first line).

1. **The store:** `ledger/retro-backlog.jsonl`, one object per proposal: `{id, title, first_seen: {run, date},
   runs_seen: [run ids], status: proposed|specced|queued|merged|dropped, spec, pr, note}`. `id` is a kebab-case
   slug. The driver commits it with the ledger, under the ledger's existing flock.
2. **The retro emits proposals as data.** Beside `retro.md` it writes `<run dir>/retro-proposals.json`, a list of
   `{id, title, evidence}`. Its prompt is given the current backlog (`HARNESS_BACKLOG`, as `HARNESS_LEDGER` is now) and
   told to reuse an existing id when it re-raises one, to cite its status instead of re-arguing a
   `specced`/`queued`/`merged` item, and to coin a new slug only for a new proposal.
3. **The driver merges them** in `finish()`, right after the retro and inside the ledger commit: a new id is appended
   as `proposed`; a known id gets this run added to `runs_seen`, status unchanged. Bad JSON is logged and skipped and
   the run goes on, as with E4's `entry.json`. `restrict` reverts a retro that edits the backlog file itself.
4. **The CLI moves status:** `harness backlog [list]` (id, title, status, runs seen, links; `proposed` first, most
   seen first) and `harness backlog set <id> <status> [--spec <path>] [--pr <url>] [--note <text>]`, with flock and a
   commit. `harness backlog import <file.jsonl>` merges rows by id, the same way, for seeding.
5. **The seed.** The build writes `docs/specs/2026-10-25-memory.backlog-seed.jsonl` from the table below (rows only,
   statuses as given) and README gives Michael the one command, `harness backlog import <that file>`, run on the live
   checkout. The build never imports it into the real ledger.

   | id | title | status | spec |
   |---|---|---|---|
   | `test-counts` | real test counts per runner | queued | retro-fixes R1, this spec M5 |
   | `review-cost` | size and route the milestone review | queued | retro-fixes R2, this spec M6 |
   | `step-lint` | lint feature steps at init | queued | retro-fixes R3 |
   | `carry-on-past-given-up` | a given-up feature doesn't end the run | queued | retro-fixes R10 |
   | `verify-fresh-suite` | verify never trusts the cache | queued | retro-fixes R4 |
   | `merge-before-deadline` | verify and merge a finished milestone at the deadline | queued | retro-fixes R5 |
   | `no-retry-on-denial` | don't retry a session that stopped on a permission question with nothing changed | proposed | — |
   | `session-memory-cap` | cap and stop each session's processes | queued | resource-lifecycle L1–L2 |
6. **The debrief reads the backlog**, not the raw retros: the gatherer block puts `retro-backlog.jsonl` in its
   context, and its "For the next interactive session" section lists open `proposed` items by times seen and flags
   any re-raised though already `specced` or `queued`.

**Checks (written first):** a stub retro with a new id appends a `proposed` row; a second stub run with the same id
adds its run to `runs_seen` without a second row or a status change; a malformed `retro-proposals.json` is logged and
the run finishes; `backlog set … specced --spec <p>` flips the status and `backlog list` shows it; `backlog import`
of the seed file into the suite's ledger gives eight rows and is idempotent; the rendered retro prompt contains a
backlog line for a `specced` id; `restrict` reverts a retro's edit to the backlog; the debrief's gathered context has
the backlog and no "Earlier retros" block.

## M3 · Gotchas in place, and the pack carries the current rules (K2, §F2, §F3)

1. **K2 as written:** the coding prompt's *Finish* step adds or edits one `## Gotchas` line (≤ 160 characters,
   ending `(<run> <date>)`, 15 lines at most, never a wholesale rewrite), and the driver logs
   `note "<feature>: gotchas +<a> ~<e> -<d>"` when the section changed between the session's start and end commits.
2. **§F2:** an answered question (INBOX `## Answers`, or a decision that settles it) is marked resolved in the
   session's entry, and the context-pack selector drops resolved questions.
3. **§F3:** `context.md` gains a bounded slice of the decisions store's current lines (headings and their one-line
   rule, newest first, within `CONTEXT_PACK_BYTES`), read through `decisionsStore()`. No model summarizes it.

**Checks:** K2's three checks; F's: a stub session that resolves a question has it gone from the next `context.md`;
the pack has the store's current lines and respects `CONTEXT_PACK_BYTES`; a legacy run without E4's journal is
untouched; E4's existing context-pack checks still pass.

## M5 · A test-count contract, and correct counts on a continued run (retro-followups §C; after R1)

## M6 · The milestone review, measured and gated (retro-followups §D; after R2; droppable)

§D as written: the driver measures the milestone diff and passes `{{REVIEW_DIFF}}`; below `REVIEW_OPUS_LINES`
(default 400 changed lines) the review runs on Sonnet, above it on Opus; a Sonnet review that reports a Critical or
Important escalates one round to `REVIEW_ESCALATE_MODEL` (default `opus`); `summary.json` adds review cost as a % of
the run and the count of reviews that found nothing. **No cost claim without E2 evals, which Michael runs:** the build
writes the before/after `harness eval compare` commands into `evals/NEXT.md` and never runs them. If time is short,
this milestone goes first.
