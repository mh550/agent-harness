## Q1 · A run never starts on a spec file that isn't there

**Finding.** F named `docs/specs/2026-10-30-suite-cpu-and-flakes.md` and wrote no file. `harness queue add
~/projects/agent-harness --spec <that path>` accepted it: `cmd_queue add` passes the arguments to `queue_add` unread,
and `cmd_start`'s only test is that `--spec` or `--brief` was given. The runner started the run; the initializer found
the path on no branch (`git fetch --all`, every ref checked), read the title, and built the flakes half as F1
(`docs/plans/2026-10-30-F1-flakes.md`, PR #71), a night on half a scope. The run's worktree is made from `origin/main`
(or `--base`), so what a session can read is what that ref holds, not what Michael's working tree holds.

**Choice.**

1. **The check**, one function in `lib/config.sh` (or a new `lib/spec.sh`, sourced by `bin/harness` and `lib/queue.sh`):
   `spec_missing <project dir> <ref> <path>…` fetches `origin` (`git -C <p> fetch -q origin`; a failed fetch is said on
   stderr and the check reads the last fetched ref) and prints, for the first path not in the ref (`git cat-file -e
   <ref>:<path>`), one line: `spec <path>: not in <ref> (fetched now); commit and push it, or name its ref with --base`.
   The ref is `--base` when given, else `origin/$MAIN_BRANCH`. *Default:* the project's `origin/main`, not the working
   tree, because the run's worktree is made from that ref (`cmd_start`'s `git worktree add … origin/main`), `queue add`
   may be called from anywhere by project name, and a file in the working tree that is not pushed is exactly what the
   initializer cannot read. The `--spec` value is split as `SPEC_FILES` is, on spaces: each word is one path.
2. **`harness start`** refuses before it queues or starts: with a `--spec`, or with `SPEC_FILES` from `.harness/config.sh`
   and no `--spec`, and only for a new run (a resume, `-d $wt`, skips it: the spec persists in `run.env` and was checked
   then), `die` with the line. The check sits before the first `queue_add` in `cmd_start` (the busy-project and
   `MAX_PARALLEL_RUNS` paths queue before the worktree exists), so a queued entry is a checked one. `--brief` alone is not
   checked.
3. **`harness queue add`** refuses the same way, before `queue_add`. `queue add --continue` is not checked (the run has
   its spec).
4. **The runner re-checks at dequeue** (`lib/queue.sh`, after the entry is chosen and before `mv` to `done/`): for a
   `start` entry with `--spec` (or whose project config names `SPEC_FILES`), `spec_missing` with the entry's `--base` if
   any; on a miss the entry moves to `queue/held/` with a `.why` holding the line and the time (the shape `harness queue
   park` writes), one `parked <entry>: <line>` log line, and the loop goes on to the next entry. A branch deleted or a
   spec moved between `queue add` and the start therefore parks, and a spec pushed after `queue add` passes. `harness queue
   list` already lists parked entries with their reason; `unpark` puts it back once the file is pushed. *Default:* no
   notification (the runner's log and the queue list carry it; the debrief reads the runner's log).
5. **Visible.** `harness start` and `queue add`: the line, exit 1. The runner: `parked <entry>: spec <path>: not in
   <ref> …` in `runner.log`. No `harness-log.md` change (no run exists).
6. **Decision and docs.** `journal/decisions/2026-10-31-spec-must-exist.md` (finding · choice · rejected: the working
   tree as the reference (above); checking only at `queue add` (the ref moves between queueing and the start); failing the
   runner's start and leaving the entry in `done/` (today: the run is lost silently, `failed:` in a log nobody reads at
   night); the initializer guessing from the title (what happened)). `README.md`'s `harness start` and `harness queue`
   rows (the refusal and the park); `docs/architecture.md` §3 (`bin/harness`, `lib/queue.sh` rows), §12 (the runner's
   dequeue), §7 (the guard table: a missing spec parks, never starts).

**Checks (written first)**, in a new `tests/checks/83-spec-must-exist.sh` with a throwaway repo and origin (as
`tests/lib.sh` builds them): `harness start <p> --spec docs/missing.md` exits 1 with `spec docs/missing.md: not in
origin/main` and makes no worktree, no state dir and no queue entry; the same with the file committed locally but not
pushed → the same refusal (the working tree is not the reference); pushed → the start proceeds (the stub run's worktree
exists); `--spec "a.md b.md"` with `b.md` missing names `b.md`; `--base <branch>` with the file on that branch only →
proceeds, and without `--base` → refused naming `origin/main`; `SPEC_FILES=docs/missing.md` in the stub's
`.harness/config.sh` and no `--spec` → refused; `--brief` alone → not checked; a resume of an existing run worktree →
not checked; `harness queue add <p> --spec docs/missing.md` → the line, exit 1, no `.args` file; the runner: an entry
queued with the file present, the file then removed from `origin/main` (a commit that deletes it, pushed; no rewrite) →
at dequeue the entry is in `queue/held/` with its `.why` holding the line, `runner.log` has `parked`, no run started, and
the next entry (another project, or a `--brief` entry) starts; an entry planted by hand in `queue/` naming a missing
file (queueing one is now impossible) → parked at dequeue; `harness queue list` shows the parked entry with the reason;
`bash -n bin/harness lib/queue.sh`.

## C1 · Fewer process starts, then one full run per session

### Fix 6: fewer process starts in the suite

**Finding** (load curve §3, plan §2 row 6). Per large check file: 3,128–3,516 successful `node` execs at 26.9 ms each
on the idle box, 84–95 CPU-s against 182–208 s of file wall at `TEST_JOBS=4` solo: about 45 % of the file's CPU, over
the plan's "a third or more" bar for fix 6. `git`'s 7,600–8,400 execs at 1.1 ms cost about 9 s; `cat` and `date`
(2,400–6,400 each at 0.8 ms) 2–5 s. The suite is CPU-bound (4.04 cores busy at 4 jobs; CPU rises from 2,810 s at 1 job
to 4,144 s at 8), so CPU cut is wall cut, and lower load at the same `TEST_JOBS` is the one lever on flakes the data
supports (every flake row of 10-29-2 had another suite running; the load curve's reds were at `some avg60` above 24 %).
Where the node starts come from is **not measured**: the counts are by basename. The driver calls node through `F`
(`lib/features.mjs`: `model` on 17 lines of `lib/lane.sh`, `lib/driver.sh`, `lib/prompt.sh`, `lib/desk.sh`; `summary`
on 11; `lanes`, `next`, `parked`, `blocked`, `milestone-done` in the loops), `MET`, `SUM`, `treekey.mjs` (every prompt,
twice per `check.sh` call, `run_init`, `green`, the pathspec test), `testcount.mjs`, `entries.mjs`, `inbox.mjs`,
`memlint.mjs`, `notify.mjs`; the coordinator's poll (`lib/driver.sh`'s `while :` loop, `HARNESS_LANE_POLL` 1 s in the
suite) runs `F unpark`, `F lanes` and, at the end check, `F summary` twice, `F parked`, `F blocked` and `F next` on the
same unchanged `feature_list.json`. The stub (`tests/stub-claude.sh`) and `tests/lib.sh` start node too.

**Choice.**

1. **Measure first, one feature (C1-01), no code change.** `strace -f -e trace=execve -o <file>` on one stub `harness
   start` in the suite's environment: `KEEP=1 bash tests/run.sh <file>` for one of the three large files (`08`, `13`,
   `15`), then that file's first `harness start` by hand in the kept `$T`, the way the load curve's §4 did (same exports,
   `--foreground`). Node execs grouped by script and subcommand (`features.mjs model`, `features.mjs summary`,
   `treekey.mjs --partial`, …), and by caller: the driver's (`lib/*.sh`, by the parent's command line), the stub's, and
   `tests/lib.sh`'s; `git`, `date`, `cat` and `bash` counts beside them. The table goes in
   `journal/decisions/2026-10-31-fewer-node-starts.md` under *Finding*, with the one run's wall and `time -v` CPU, and
   names the top five callers by execs × 26.9 ms. The feature's step is the table's presence and shape (script,
   subcommand, caller, count, CPU-s), not a number. *Default:* one start, the file's cheapest kind, as §4 did; the
   session may add a second file's start if the first takes under 10 minutes.
2. **Cut the top callers (C1-02, and C1-03 if the table splits them).** In the order the table gives, until the top
   callers that are the driver's are covered:
   - **Memoize the pure answers per process.** `F model <alias>` is pure in its argument: one lookup per alias per
     process (a bash associative array in `lib/record.sh`'s `F`, keyed `model:<alias>`). `F summary <list>` and the other
     list readers are pure in the list's content: keyed `<sub>:<sha1 of the list file>:<other args>`, the hash by
     `sha1sum` (0.8 ms) or `git hash-object` (1.1 ms), so a changed list is a new key and the old answer is never
     served; the memo lives in the process (the driver's, a lane's), never on disk, never keyed on mtime or path alone.
     Only subcommands the session has read as pure (no clock, no state dir, no network) are memoized; `MET append`,
     `entries.mjs ingest|render|pack`, `inbox.mjs insert|repair`, `notify.mjs` are not.
   - **Collapse the poll loop's calls to one node start per iteration.** The coordinator's end check asks `features.mjs`
     five questions of one unchanged list; one subcommand (say `F poll <list> <att> <max> <parked> <state>`) prints them
     as labelled lines, read with one `mapfile`; the lane loop's `F next` and `F milestone-done` the same way where they
     sit in one iteration. The memo above makes the second and later polls on an unchanged list free as well. *Default:*
     the existing subcommands stay (the checks and `harness` commands call them); the new one is a composition of the
     same exported functions, unit-checked with `node --input-type=module -e`.
   - **`treekey.mjs`** is the content key itself and is not memoized across calls (a tree changes between them); its two
     calls inside one `check.sh` call (`--partial`, then `--names`) may become one.
   - **Bash builtins for `date` and `cat`** where the table says they are the driver's (`$EPOCHSECONDS`, `printf
     '%(%F %T)T'`, `$(< file)`), only in `lib/`, never in the checks' own lines (a check's clock is its own). *Default:*
     only if the table puts them in the top five; git is not a target (9 s).
   - **No harness-log.md line changes**: `note`'s text and order are untouched; the lines are what every check compares.
3. **Prove it on the runner's own `wall` line (C1-04, before fix 4's feature).** Two full suites, each `systemd-run
   --user --scope -p MemoryMax=3G /usr/bin/time -v env TEST_JOBS=4 bash tests/run.sh` run by the session directly (not
   through the suite command, whose cache would answer, and not inside its own full run): *before* in a scratch worktree
   of the run's base commit (`git worktree add <scratch>/before <base>`), *after* on the feature's tree; no other suite
   alive (`harness status`, read-only, before each). The decision file gets both rows (wall from the runner's own `wall`
   line, user+sys from `time -v`, checks passed, red files) beside the load curve's 4-solo row (805 s, 3,249 s at
   1,077 checks) and §11's harness runs (817–835 s, 3,322–3,355 s at 1,081–1,084). **Target: CPU −20 % against the
   *before* row; solo wall ≤ 650 s at the then check count.** A miss is recorded as a miss with the number, and the
   feature still passes on its other steps: the target is the spec's prediction, not a step (the fixes stand on the
   checks). The *before* worktree is removed after.
4. **Decision and docs.** `journal/decisions/2026-10-31-fewer-node-starts.md` (title, provenance, finding with the
   table, choice with every default, the before/after rows, rejected: a disk cache of node answers (a stale answer
   outlives the process; the invariant); keying on mtime or path (the invariant: content only); rewriting the `.mjs`
   helpers in bash (the pure functions are what the unit checks hold); a long-lived node server the driver talks to
   (a process to supervise, a socket per run; the memo gets most of the gain); `TEST_JOBS=8` (599 s solo over the 582 s
   bar, 4,144 CPU-s, 8 paired unusable: fix 7's variant, plan §6)). `docs/architecture.md` §3 (`lib/record.sh`'s `F`
   memo, the poll subcommand), §11 (the measurement rows); `README.md` only if a command's output changes (none
   expected).

**Checks (written first)**, in a new `tests/checks/84-node-memo.sh` and the existing files the collapsed calls touch:
a `node` shim on `PATH` that counts execs into a file and execs the real node (as `tests/stub-claude.sh` stands in for
`claude`) shows, in a check that sources `lib/record.sh` (`HARNESS_HOME=$HH`): two `F model opus` calls start node once;
`F summary` twice on one list starts node once, and after one byte of the list changes starts it again and prints the
new answer (**a changed input invalidates the cached answer**); a list restored to its first content answers from the
memo again (content, not mtime); `F poll` on a fixture list prints the same lines the five subcommands print, in the
unit check (`node --input-type=module -e`, the exported functions compared); a stub run with the shim: the coordinator's
poll on an idle list (one lane open, nothing to decide) starts node at most once per iteration, read from the shim's
counts against the `HARNESS_LANE_POLL` count in `run.log`; every existing check that compares `harness-log.md` or
`run.log` lines passes unchanged (the suite is the check; a changed note is a red file); `bash -n` on every `lib/*.sh`
touched, `node --check` on `lib/features.mjs`; and the measurement feature's step: the decision file holds a *before*
and an *after* row with wall, CPU and the check count, each from a run the session ran (the output files kept in scratch
and named in its entry).

### Fix 4: one full run per coding session, last

**Finding** (budget §10, §11; plan §2 row 4). 10-29-3: 19 full scopes in 11 coding sessions, 1.73 each, 1,393 s of suite
per session, mostly red-driven (a red full run, a fix, another full run); 10-30: 1.3 per session, 1,112 s. The prompt's
rule is "run it in full once before you flip `passes`", and §3's order puts the `## Gotchas` line (step 3) after the
suite (step 2), so a session that follows it edits `CLAUDE.md` after its last full run and the post-session tree is a
new key (S2's partial map now runs `memlint` alone for that, seconds, but only when the session's last full run was on
the tree before the line). 10-28 paid about 20,000 s for a session's `TEST_JOBS=2` proposal, rejected since
(`decisions/2026-10-29-check-timeout-25m`), and nothing in the prompt says so. 0.1 full run per session is about
1,610 s per 20 sessions (805 s × 2).

**Choice.**

1. **`prompts/coding.md`.** The *The suite* ground rule: "While iterating, pass arguments for a subset: `<suite> <args>`.
   Run it in full **once, last**, after your final edit of any file, `CLAUDE.md` included: a full run before that is a
   full run you pay twice. A red check that check.sh reran green is a flake it has already recorded: never rerun the suite
   by hand for it; a red after its rerun is real. Never lower the suite's parallelism to make room for other lanes
   (`TEST_JOBS=2` on this box: slower and as flaky, 2026-10-28; `decisions/2026-10-29-check-timeout-25m`)." The timeout
   clause stays. §3 *Finish* reorders: the `## Gotchas` line (today's step 3) comes before the full run (today's step 2),
   with one sentence saying why ("so the tree you tested is the tree that ends the session"); `entry.json` and the
   commit after, as today (the run directory is outside the key). *Default:* the `TEST_JOBS=2` sentence is in the shared
   prompt, phrased as the general rule with this box's measurement as its example, because `prompts/coding.md` is the
   file the check reads and the lesson is every project's (a lane's suite is never slowed for another lane's); the
   alternative, this repo's `.harness/project.md`, does not exist and would reach only this project.
2. **The count.** `lib/lane.sh` already reads the session's `check-runs.log` rows between `t0` and `t1` for the `<id>:
   suite ran <n>x (<s> s) in the session` note (R3-04; `n` counts every non-`cached` row). It also counts the rows whose
   kind is `full` and passes `suite_runs` and `suite_full` to `MET append` as two more trailing arguments; `metrics.mjs
   metricsRow` writes them on the coding row (`null` when the log is missing). **The note's text is unchanged** (the rule
   above). `summary.mjs` gains `suite_runs: { sessions, full, runs, full_per_session }` from the coding rows and one
   `reportView` row `Suite runs` · `1.4 full per coding session (16 in 11; 42 runs in all)`, `0` for none, placed after
   `Flakes`; `harness report` prints it (`--md` and the TTY view), and the retro prompt sees it in `summary.json`
   (`HARNESS_SUMMARY`). *Default:* a row in the report and a field in the summary, not a new note or a `trends`
   column; `trends` is unchanged.
3. **Decision and docs.** `journal/decisions/2026-10-31-one-full-run.md` (finding · choice · rejected: a driver-enforced
   cap on full runs per session (the session's judgment is what the rule asks for; a cap would turn a needed second run
   into a red end); counting from `harness-log.md`'s note (the line would have to change; the rule); the rule in
   `CLAUDE.md` alone (one project)). `docs/architecture.md` §3 (`lib/lane.sh`: the two metrics fields; `summary.mjs`: the
   row), §11 (the measure); `README.md`'s `harness report` row (the `Suite runs` row).

**Checks (written first)**, in `tests/checks/79-suite-length.sh` (the prompt's suite rule; it already renders a stub
run's `prompt-coding.md`) and `tests/checks/77-leftovers.sh` (R3-04's rows) or a new file by topic: a stub run's rendered
`prompt-coding.md` has `once, last, after your final edit of any file` and `TEST_JOBS=2` with `slower and as flaky`, and

no longer has `Run it in full once before you flip`; a stub run whose session makes two full calls and one subset call

session with no call → `0` and `0`; `summary.json`'s `suite_runs.full_per_session` is `2` for a run of one such session,
`harness report --md` prints `Suite runs | 2 full per coding session (2 in 1; 3 runs in all)`, and the TTY view the same
row; the retro's rendered prompt (`prompt-retro.md`) carries the number (the summary is rendered into it); the report of
