# Sandboxing autonomous coding agents on a single Linux box (Pop!_OS / Ubuntu, systemd, one user) — state as of 2026-10-26

Scope note for the writer: the person runs a bash orchestrator that launches headless `claude -p --permission-mode auto` workers, one per git worktree, each wrapped in `systemd-run --user --scope` with memory caps. Same box hosts live services (n8n, a streaming app under /srv, docker compose stacks) and secrets (.env, ~/.config, ~/.livekit). Current safety = Claude Code deny rules in settings.json + conventions. Material older than ~12 months is marked "(older)".

Overall takeaway up front: Anthropic's own docs now draw the line clearly — the built-in Bash sandbox only covers shell commands; for unattended runs (auto mode or bypass) they say to put the *whole* Claude Code process inside a boundary (srt, container, or VM). On Linux the cheapest boundary that covers the whole process is bubblewrap, either via `srt claude` or a hand-written `bwrap` wrapper, plus Claude Code's built-in Bash sandbox nested inside it for network allowlisting. `systemd-run --scope` (what the orchestrator uses now) gives resource control only; sandboxing directives need a *service* unit, and most of them work for `--user` units only with `PrivateUsers=` implied. Docker-based test stacks are the main friction point for every option.

## Key question 1: What does Anthropic provide, and how does it interact with `--permission-mode auto` / bypass?

### Takeaway
Anthropic ships three things: (a) the built-in sandboxed Bash tool (bubblewrap + socat + optional seccomp on Linux, network via a host-side proxy over a Unix socket), (b) the open-source `@anthropic-ai/sandbox-runtime` (`srt`) that wraps a whole process in the same mechanism, and (c) a reference devcontainer with a default-deny iptables firewall. The built-in sandbox makes sandboxed Bash run without prompts in any mode but leaves file tools, MCP servers, hooks and `excludedCommands` on the host; the docs say that for `--dangerously-skip-permissions` you must use srt/container/VM, and that for auto mode an outer boundary is "defense in depth" rather than required.

### Cited Findings

**Built-in sandboxed Bash tool (Claude Code docs, current, 2026)**
- Linux and WSL2 use bubblewrap for filesystem isolation; macOS uses Seatbelt; native Windows is unsupported. Network isolation: the command runs in a separate network namespace with no route out; Claude Code runs a proxy on the host and points commands at it via `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`; `socat` relays traffic. A seccomp filter is optional and "adds Unix domain socket blocking"; it is installed with `npm install -g @anthropic-ai/sandbox-runtime` if `/sandbox` reports it missing. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Linux deps: `sudo apt-get install bubblewrap socat`. Ubuntu 24.04+ may need an AppArmor profile for `bwrap` (`sysctl kernel.apparmor_restrict_unprivileged_userns`). Inside a container bubblewrap may fail to mount `/proc`; `enableWeakerNestedSandbox: true` works around it "at a security cost". — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Default filesystem boundary: writes to the working directory, `$TMPDIR`, and `--add-dir`/`permissions.additionalDirectories`; **reads to the entire computer except denied directories** — `~/.ssh` and `~/.aws/credentials` are readable unless you deny them. Protected paths are write-denied even inside writable dirs: `.claude` settings, `.mcp.json`, `.bashrc`/`.zshrc`, `.gitconfig`, `.git/hooks`, `.git/config`. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Verbatim example of narrowing reads to the project only:
  ```json
  { "sandbox": { "enabled": true, "filesystem": { "denyRead": ["~/"], "allowRead": ["."] } } }
  ```
  and credential handling:
  ```json
  { "sandbox": { "enabled": true, "credentials": {
      "files": [ { "path": "~/.aws/credentials", "mode": "deny" }, { "path": "~/.ssh", "mode": "deny" } ],
      "envVars": [ { "name": "GITHUB_TOKEN", "mode": "deny" }, { "name": "NPM_TOKEN", "mode": "deny" } ] } } }
  ```
  Path convention: `/tmp/build` absolute, `~/.kube` home-relative (differs from `//path` in Read/Edit rules). — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Network: `allowedDomains` starts empty; proxy checks hostname against `allowedDomains`/`deniedDomains`. Tools that ignore proxy vars (plain `ssh`, most DB drivers) can't connect; UDP, QUIC, ICMP can't leave. Hostnames that resolve to loopback/link-local/the machine's own addresses are refused. TLS is not terminated unless `network.tlsTerminate` (experimental). — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Behaviour for a host outside the allowlist depends on mode: `bypassPermissions` → allowed without prompt; manual/`acceptEdits` → prompt; **auto → refused unless the command listed the host and the classifier approved**; `dontAsk` → refused; `deniedDomains` refused everywhere. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Permission interaction: with `autoAllowBashIfSandboxed` (default `true`), sandboxed Bash runs without a prompt "regardless of permission mode", except plan mode, per-command domain listings in auto mode, and server-side classifier review in auto mode. Still enforced in auto-allow: `Bash` deny rules, `rm`/`rmdir` on critical paths, content-scoped ask rules such as `Bash(git push *)`. Unsandboxed retry (`dangerouslyDisableSandbox`): bypass → no prompt; manual/acceptEdits → prompt; **auto → classifier**; dontAsk → denied. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- `excludedCommands` (pattern syntax `Bash(...)`, e.g. `"excludedCommands": ["docker compose *"]`) run **outside** the sandbox with no FS restriction and no proxy; every command in a compound call must match; calls with redirects, `cd`, or `$(...)` stay sandboxed; excluded commands still go through the permission flow. Known incompatibilities: `docker`, `watchman` (use `jest --no-watchman`); Chromium and rootless Podman need workarounds. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- What runs outside the sandbox regardless: hooks, MCP servers, plugin monitors, LSP servers, status line, `apiKeyHelper`. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Documented weakenings/escapes: broad `excludedCommands` let Claude write then run a script; the `!` shell prompt runs unsandboxed; an allow rule matching a command can approve an unsandboxed retry; `filesystem.disabled: true` lets commands write shell startup files or executables on `$PATH`; `allowNestedUserNamespaces: true` "turn[s] off a security boundary"; `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `allowAllUnixSockets`, `allowLocalBinding` all weaken it; without the seccomp filter, Unix-socket blocking is not active; `httpProxyPort`/`socksProxyPort` hand filtering to your own proxy. Sandbox can be enabled at launch with `claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'`. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- If the sandbox can't start, Claude Code falls back to running commands unsandboxed unless `failIfUnavailable` is set. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing) (via search summary of the same page)

**Choosing an environment (Claude Code docs, current)**
- Comparison table: Sandboxed Bash tool isolates "Bash, PowerShell, and Monitor tool commands and their child processes" (no Docker, low setup on Linux); Sandbox runtime isolates "the whole Claude Code process, including file tools, MCP servers, and hooks" (no Docker, low setup); dev container / custom container need Docker, medium–high setup; VM is highest. — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary. On Linux and macOS, Claude Code refuses to start with this flag when running as root." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- "Auto mode replaces the prompt with a classifier that reviews actions. The classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth for unattended runs, and is not required the way it is for `--dangerously-skip-permissions`." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- "The sandboxed Bash tool on its own constrains only shell commands, so it is not sufficient for fully unattended runs in either mode. You can layer approaches: running the sandboxed Bash tool inside a container or VM gives you OS-level command restrictions on top of the outer environment boundary." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Warning: "Any approach that allows network egress can still leak data the agent can read, and any approach that mounts your project directory writable can still modify that code." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Docker Sandboxes (docs.docker.com/ai/sandboxes) is named as a microVM option "with its own Docker daemon and workspace sync... a free, standalone product from Docker that does not require Docker Desktop." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)

**`srt` / `@anthropic-ai/sandbox-runtime` (GitHub README + docs, current)**
- Beta research preview; Apache-2.0; Linux uses bubblewrap with network namespace removed entirely; proxies on the host reached via Unix sockets bind-mounted in; HTTP(S) via HTTP proxy, other TCP via SOCKS5; `socat` bridges. Unix sockets blocked by seccomp (x64/arm64 only); if seccomp unavailable, sockets are unrestricted with a warning. Requires bubblewrap ≥ 0.4.0 (≥ 0.5.0 for `denyRead` on fifos/sockets/devices), socat, ripgrep. — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Config in `~/.srt-settings.json` or `--settings`. Example schema:
  ```json
  { "network": { "allowedDomains": ["github.com", "*.github.com", "api.github.com:443"], "deniedDomains": ["malicious.com"], "allowUnixSockets": ["/var/run/docker.sock"], "allowLocalBinding": false },
    "filesystem": { "denyRead": ["~/.ssh"], "allowRead": [], "allowWrite": [".", "src/", "/tmp"], "denyWrite": [".env", "config/production.json"] } }
  ```
  Network is allow-only (empty = no network). Writes allow-only, `denyWrite` wins. Reads deny-then-allow, everything readable by default. — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- **Linux-specific limits**: `allowWrite`/`denyWrite` take literal paths only (globs skipped); `denyRead`/`allowRead` globs expand at wrap time; a pattern whose first component is a wildcard (e.g. `/**/*.pem`) is skipped and "a skipped pattern hides nothing"; `**/.env` is skipped on Linux (a literal `./secrets` or `~/.ssh` works); a `denyRead` directory with contents becomes an empty writable tmpfs inside the sandbox; files created after wrap time are not covered; a `denyRead` for a non-existent path hides nothing; `allowUnixSockets` is **ignored on Linux** (seccomp can't filter by path) so Docker socket access on Linux needs `allowAllUnixSockets: true`; `allowLocalBinding` ignored on Linux (sandbox has its own loopback). — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Mandatory denies are read-only bind mounts that only hold within the mount namespace they were made in; enabling `allowNestedUserNamespaces` weakens `denyWrite` and the mandatory denies. — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Resolved-address check refuses loopback, link-local, metadata and the host's own addresses; a 1:1-NAT public IP reaching the host is not covered. — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Credentials: `credentials.envVars`/`files` with `mode: "deny"` or `mode: "mask"` (sentinel substituted, real value injected by the proxy on egress to `injectHosts`; requires `network.tlsTerminate`; file masking is Linux-only). — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Ubuntu 24.04+: `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` or grant `userns` to the binaries. — [anthropics/sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Running Claude Code under srt (`srt claude`): by default the runtime denies network and confines writes to built-in runtime paths. You must allow writes to the project dir, `~/.claude`, `~/.claude.json`, and `/tmp` (or `CLAUDE_CODE_TMPDIR`); allow domains `api.anthropic.com` (plus `claude.ai` and `platform.claude.com` for OAuth; API-key runs can drop those two). On Linux write grants apply only to paths that already exist (`mkdir -p ~/.claude && { [ -f ~/.claude.json ] || echo '{}' > ~/.claude.json; }`). Install srt under a prefix outside every path you allow writes to. — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- srt's own mandatory denies at the project root: `.git/hooks`, `.git/config` (unless `filesystem.allowGitConfig: true`), `.mcp.json`, `.claude/commands`, `.claude/agents`, shell startup files. On Linux the deny list is built once at launch and does not cover repos created later (`git init`, `git clone`). Starting with no settings file is silent (network blocked, writes to runtime paths only) — "Don't take a clean start as proof your settings loaded." Empty/invalid settings file → refuses to start. "A sandboxed session that can write [config paths] can persist hooks, permission rules, or MCP servers that run unsandboxed the next time you launch Claude Code." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)

**Anthropic engineering blog (2025-10-20, older but foundational)**
- Announced the sandbox; two primitives (filesystem, network) both required; Linux bubblewrap, macOS Seatbelt; network only via Unix socket to a host proxy that enforces domain restrictions; internally "safely reduces permission prompts by 84%"; threat model assumes a prompt-injected Claude Code and aims for it to be unable to steal SSH keys or contact an attacker's server; Claude Code on the web keeps git credentials outside the sandbox with a proxy issuing scoped credentials. — [Anthropic: Beyond permission prompts: making Claude Code more secure and autonomous](https://www.anthropic.com/engineering/claude-code-sandboxing)

**Reference devcontainer (Claude Code docs, current)**
- Includes `init-firewall.sh` (default-deny outbound, requires `NET_ADMIN` and `NET_RAW` via `runArgs`). Warning: "When executed with `--dangerously-skip-permissions`, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`." Advises not mounting `~/.ssh` or cloud credential files; prefer repository-scoped or short-lived tokens. Non-root `remoteUser` required for the flag. Suggests auto mode as the alternative to the flag. — [Claude Code: Development containers](https://code.claude.com/docs/en/devcontainer.md)

### Inferences
- For this orchestrator (auto mode, headless), Anthropic's position maps to: enable the built-in Bash sandbox for the network allowlist and default write boundary, AND put the whole worker process inside srt (or an equivalent bwrap wrapper) so Read/Edit/WebFetch tools, hooks and MCP servers cannot read `~/.livekit`, `.env`, `~/.config/x`. The built-in sandbox alone leaves the file tools able to read anything the user can.
- In auto mode, the built-in sandbox already removes the Bash prompt path entirely; the only residual approval points are the classifier (server-side, no human) for unsandboxed retries and per-command domain additions. That is the "no-friction" combination the person asked about, and it is documented behaviour, not a hack.
- `excludedCommands: ["docker compose *"]` is the documented way to keep docker-based test stacks working, at the cost that those commands run with the worker's full host access. If the whole process is under srt, the docker socket is reachable only with `allowAllUnixSockets: true`, which removes socket blocking for everything.

### Gaps
- The sandboxing doc does not explicitly say whether `/sandbox`-panel behaviours (prompts, unsandboxed retry UI) differ in `claude -p` headless mode; the settings keys are documented as working via `--settings`, and auto mode's classifier path is non-interactive, but I found no page stating "-p + sandbox" semantics directly.
- No published escape/CVE for the bubblewrap-based sandbox itself was found; all "escapes" listed are documented configuration weakenings.
- The engineering blog's 84% figure is an internal Anthropic number; no external replication.

## Key question 2: Lightweight Linux tools — bubblewrap, firejail, systemd-run sandboxing properties, user namespaces, Landlock, seccomp, nsjail

### Takeaway
On an unprivileged single-user Ubuntu-family box, bubblewrap is the tool with the most working examples for whole-process agent sandboxing (hide everything but the worktree, scratch, and `~/.claude`; `--clearenv`; optional `--unshare-net`). systemd's filesystem/network sandboxing directives do work for `--user` *service* units (they implicitly enable `PrivateUsers=`), but not for `--scope` units, and several (`ProtectProc`, `ProtectControlGroups`, `DynamicUser`) are system-only. Landlock-based wrappers (nono, Landrun) are newer and still pre-1.0. Ubuntu 24.04+'s AppArmor restriction on unprivileged user namespaces is the recurring setup snag for all namespace-based tools.

### Cited Findings

**bubblewrap, whole-process wrappers by individual developers**
- Esokia (2026-03-18, Kubuntu 24.04, bwrap 0.9.0, Claude Code 2.1.78): two layers — an outer `claude-safe` bwrap wrapper around the whole Claude process plus Claude Code's native Bash sandbox inside. Outer wrapper: `--ro-bind` `/usr`, `/etc`, `~/.local/bin`, `~/.local/share/claude`, the resolved `/etc/resolv.conf`; writable: project dir at its own path, `~/.claude/`, `~/.claude.json`; `/tmp` tmpfs with XDG dirs under it; `$HOME` an empty 0555 dir; nothing from `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config`; `--clearenv` then set only `HOME PWD PATH TERM LANG XDG_* DISABLE_AUTOUPDATER=1` (+ proxy/TLS vars and `ANTHROPIC_API_KEY` if set); `--unshare-pid --unshare-uts --unshare-ipc --new-session --die-with-parent`; **no `--unshare-net`/`--unshare-user` in baseline** (host network incl. localhost shared). Mounting only `~/.claude/` without `~/.claude.json` can break sign-in. — [Esokia Labs: Sandboxing the Claude Code CLI on Linux](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/)
- Esokia problems: AppArmor on Ubuntu 24.04 made plain `bwrap` fail with "Permission denied"; fix was a per-binary AppArmor profile with `flags=(unconfined)` + `allow userns create` (author stresses it "adds no real confinement"). Nested-sandbox bookkeeping errors (`/tmp/claude-UID/cwd-*: Read-only file system`) appear even when commands succeed. `getent hosts` fails while `curl` works inside the nested sandbox (traffic goes via proxy vars). Author's conclusions: outer wrapper alone doesn't enforce egress; `allowedDomains` must be validated empirically on the exact version ("Anthropic service endpoints such as api.anthropic.com remained reachable even when not listed"); hard egress guarantees need host firewall, egress proxy, or VM/container. — [Esokia Labs](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/)
- Juan Bretti (2026-08-09, updated 2026-04-22) one-liner wrapping the whole agent with `--dangerously-skip-permissions`:
  ```
  bwrap --ro-bind /usr /usr --bind "$PROJECT_DIR" "$PROJECT_DIR" --bind "$HOME/.claude" "$HOME/.claude" --ro-bind /dev/null "$PROJECT_DIR/.env" --ro-bind /dev/null "$PROJECT_DIR/.env.local" --share-net --unshare-pid --die-with-parent "$(command -v claude)" --dangerously-skip-permissions "..."
  ```
  i.e. `.env` files are masked by binding `/dev/null` over them; network shared with host. — [Juan Bretti: Bubblewrap: Sandboxing AI Agents Without Trusting Anyone](https://blog.juanbretti.com/en/posts/2026-08-09_bubblewrap_sandboxing_ai_agents/)
- Other bubblewrap write-ups exist with the same shape (install bubblewrap + socat, `/sandbox`, or outer wrapper): [whereistayuplate: Sandboxing Claude Code with bubblewrap](https://whereistayuplate.com/posts/sandboxing_claude_code_with_bubblewrap/); third-party guides [claudefa.st sandboxing guide](https://claudefa.st/blog/guide/sandboxing-guide), [agent37: Claude Code Sandbox: Every Option Compared](https://www.agent37.com/blog/claude-code-sandbox). (Not fetched in full; cited from search summaries.)
- A HN-posted tool `sx` (macOS Seatbelt wrapper) was motivated by the fact that "Claude's built-in sandbox permits reads across the filesystem, so sensitive folders like ~/.ssh stay readable" when running with permission checks disabled. — [HN user dev3o threads](https://news.ycombinator.com/threads?id=dev3o) (macOS; cited for the motivation only)

**systemd-run / systemd.exec(5) for `--user` units (current man page)**
- `ProtectHome=`, `ReadOnlyPaths=`/`ReadWritePaths=`/`InaccessiblePaths=`, `TemporaryFileSystem=`, `PrivateTmp=`, `RootDirectory=`, `PrivateNetwork=`, `NetworkNamespacePath=`, `PrivateDevices=`, `ProtectKernelTunables=`, `ProtectHostname=`, `PrivateMounts=`, `ProtectClock=`: each is "only available for system services, or for services running in per-user instances of the service manager" with `PrivateUsers=` implicitly enabled. The Sandboxing intro: "most namespacing settings, that will not work on their own in user services, will work when used in conjunction with `PrivateUsers=true`", and "the various settings requiring file system namespacing support (such as `ProtectSystem=`) are not available" to user services on their own. — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- Not supported in per-user instances: `ProtectProc=`, `ProtectControlGroups=`, and the User/Group identity settings incl. `DynamicUser=`. `PrivateUsers=` in the per-user case: "the user namespace will be set up before most other namespaces". `BindPaths=` "implies that a mount namespace is allocated". `NoNewPrivileges=` has no stated restriction. `ReadWritePaths` docs advise combining with `CapabilityBoundingSet=~CAP_SYS_ADMIN` or `SystemCallFilter=~@mount` for effective sandboxing. — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- `SystemCallFilter=` "makes use of the Secure Computing Mode 2 interfaces of the kernel ('seccomp filtering')"; `RestrictSUIDSGID=` "is implemented using seccomp filtering". The man page text I retrieved did not contain an explicit per-user availability statement for the seccomp-based directives (`SystemCallFilter`, `RestrictAddressFamilies`, `RestrictNamespaces`, `LockPersonality`, `MemoryDenyWriteExecute`). — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- **Scope units**: "Unlike service units, scope units manage externally created processes, and do not fork off processes on their own." The `[Scope]` section's shared options are documented in systemd.kill(5) and systemd.resource-control(5); the page does not state that systemd.exec options apply to scopes (its only systemd.exec reference is `OOMScoreAdjust`). `systemd-run --scope` "may be used to easily launch a command in a new scope unit from the command line." — [systemd.scope(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.scope.html)
- ArchWiki (community, undated) claims "user units can not be hardened or sandboxed properly since this would make privilege escalation issues possible" — this conflicts with the current man page's `PrivateUsers=`-implied availability above; treat the man page as authoritative and the wiki as older. — [ArchWiki: systemd/Sandboxing](https://wiki.archlinux.org/title/Systemd/Sandboxing)
- General Ubuntu systemd sandboxing how-to (2026-03-02, system services): [OneUptime: How to Configure systemd Service Sandboxing on Ubuntu](https://oneuptime.com/blog/post/2026-03-02-configure-systemd-service-sandboxing-ubuntu/markdown)

- nono (Luke Hinds / nolabs; Help Net Security 2026-07-27): Landlock on Linux, Seatbelt on macOS; built-in profiles for Claude Code, Codex, OpenCode; credential-injection proxy keeps API keys outside the sandbox; >3,100 GitHub stars; self-described "early alpha", "not had a comprehensive security audit and is not recommended for production"; Windows only via WSL2. — [Help Net Security: Nono: Open-source sandbox for AI agents](https://helpnetsecurity.com/2026/07/27/nono-open-source-ai-agent-sandboxing/); [nono-rs on docs.rs](https://docs.rs/nono-rs)
- rywalker.com review (checks dated 2026-09-15/16) compares srt, nono, Landrun, Fence, yolobox, Litterbox, Shai, Docker Sandboxes, OpenShell plus built-ins of Codex/Claude Code/Copilot/Grok Build. Findings: OS-level wrappers (srt, nono, Fence, Landrun) restrict a command and its descendants but trust the host kernel; Fence denies network unless allowed and targets "semi-trusted commands, not hostile malware"; Landrun's TCP controls are port-based; "mounts and sockets can bypass isolation"; for a separate wrapper on native Linux the author points to Landrun "after checking kernel ABI support"; "Start with the agent's built-in sandbox and check that it covers the tools and exception paths you use." — [rywalker.com: Local agent sandboxes](https://rywalker.com/research/local-agent-sandboxes)
- OpenAI Codex CLI on Linux (current docs): requires `bubblewrap` (`bwrap`); uses the first `bwrap` on PATH, else a bundled helper needing unprivileged userns; on Ubuntu 24.04 recommends the `bwrap-userns-restrict` AppArmor profile over the global sysctl. Modes: `read-only`, `workspace-write` (default low-friction), `danger-full-access`; `sandbox_workspace_write.writable_roots` in `config.toml`; approvals `on-request` (default) / `never`; `untrusted` retired; full access = `danger-full-access` + `never`; "lower-risk automation preset is `workspace-write` with `on-request`". — [Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md) (developers.openai.com/codex/sandboxing now 308-redirects here). Note: the wincent gist (2026-05) lists Codex Linux as "Landlock + seccomp"; the current Codex doc page describes bubblewrap and does not mention Landlock, so Codex appears to have moved to bwrap on Linux sometime in 2026 — I could not find a changelog confirming the date.

### Inferences
- The orchestrator's current `systemd-run --user --scope` wrapper cannot carry `ProtectHome=`/`ReadWritePaths=`/`PrivateNetwork=` etc.; those need `systemd-run --user` *without* `--scope` (a transient service) and will be applied with `PrivateUsers=` implied. A transient user service also detaches from the orchestrator's tty/stdio, which matters for a bash orchestrator that reads worker stdout; `--pty`/`--pipe`/`--wait` options of systemd-run exist but I did not verify their interaction with the sandboxing directives.
- Because `--user` sandboxing runs inside a user namespace, it provides the same class of guarantee as bubblewrap (which also uses an unprivileged userns) — both are subject to the Ubuntu 24.04+ AppArmor userns restriction, and neither hides anything from a process that can create a nested userns unless nesting is blocked (bwrap `--disable-userns`, srt's default, systemd `RestrictNamespaces=`).
- Secret hiding is cheapest with bubblewrap: don't bind `~/.config`, `~/.livekit`, `/srv`; bind `/dev/null` over `.env*` inside the worktree. srt's Linux glob limits (`**/.env` skipped) mean per-repo `.env` masking must be listed as literal paths or handled by a hand-rolled bwrap wrapper.
- Network allowlisting on Linux with least setup is Claude Code's built-in proxy (`sandbox.network.allowedDomains`), since it is hostname-based and already integrated; bubblewrap/systemd give only all-or-nothing (`--unshare-net` / `PrivateNetwork=`), and Landrun/Fence are port-based or binary.

### Gaps
- No source directly tested `systemd-run --user -p ProtectHome=... -p PrivateUsers=yes` with Claude Code; availability is from the man page, not an agent-specific write-up.
- firejail and nsjail: listed in surveys but I found no 2025–2026 write-up of either used specifically with Claude Code; no evidence on their friction.
- Whether the seccomp-based systemd directives are allowed in per-user units is not stated in the portion of the man page I read.

## Key question 3: Containers and microVMs — when is a container worth it for a solo dev vs bubblewrap, and what is the test-tooling cost?

### Takeaway
Containers buy a separate root filesystem, a writable overlay, and a straightforward way to keep host secrets out; they do not buy a separate kernel (only microVMs do). The sources consistently say the decisive costs are docker-in-docker for test stacks, mounts/sockets that reintroduce host access, and credentials copied into the container. Docker Sandboxes (free, microVM, own Docker daemon per sandbox) and Podman rootless wrappers are the most-cited solo-dev container paths in 2026; Anthropic's docs reserve "VM/microVM" for untrusted repos or compliance.

### Cited Findings
- Anthropic: dev container (Docker, medium setup) and custom container isolate the "full development environment"; VM/microVM (Firecracker) is for "evaluating untrusted code, when your security policy requires kernel-level separation... or when no host-level approach meets your compliance requirements". Built-in Bash sandbox can be layered inside a container but unprivileged containers need `enableWeakerNestedSandbox`. — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Dev container caveat: with `--dangerously-skip-permissions` a malicious project can exfiltrate anything in the container including `~/.claude` credentials; don't mount `~/.ssh`/cloud creds; use repo-scoped or short-lived tokens. Firewall needs `NET_ADMIN`/`NET_RAW`. — [Claude Code: Development containers](https://code.claude.com/docs/en/devcontainer.md)
- Docker Sandboxes: "microVM isolation", managed with the `sbx` CLI, local sandboxes and CLI "free, including for commercial work"; cloud compute pay-as-you-go; org governance paid. Overview page does not name the Linux hypervisor or state docker-in-sandbox details. — [Docker docs: Sandboxes](https://docs.docker.com/ai/sandboxes/); Anthropic says it "provides a microVM with its own Docker daemon and workspace sync... does not require Docker Desktop". — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Podman-based community wrappers (2025–2026): claude-podman (project dir RW, keeps Claude login inside the container), claude-container (rootless Podman, SELinux), claude-pod (Docker/Podman, mounts only the project folder), marchiore/claude-sandbox (Podman, domain-restricted network, needs nested-sandbox setting for bwrap inside unprivileged container). textcortex/claude-code-sandbox is archived. — [tjemke/claude-pod](https://github.com/tjemke/claude-pod); [tvardema/claude-container](https://github.com/tvardema/claude-container); [surfmikko/claude-podman](https://github.com/surfmikko/claude-podman); [marchiore/claude-sandbox](https://github.com/marchiore/claude-sandbox); [textcortex/claude-code-sandbox (archived)](https://github.com/textcortex/claude-code-sandbox); [End Point: Containerizing Claude Code with Podman (2026-03)](https://www.endpointdev.com/blog/2026/03/claude-code-cli-in-container/)
- Survey: Docker/OCI = shared-kernel container; Sysbox = "safer Docker-in-Docker"; Docker Sandboxes = microVM with own Docker daemon per sandbox; microsandbox = libkrun microVM with MCP server and ephemeral mode; container-use (Dagger) = containers + git worktrees, parallel agents via MCP; Kata = container in its own microVM; gVisor = user-space kernel. Node_modules friction not mentioned anywhere in the list. — [wincent gist](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e)
- rywalker: "Containers haven't lost to OS-policy wrappers. Both approaches remain viable, and microVMs are now an option too." Containers share the host kernel; Docker Sandboxes and OpenShell's MicroVM driver use a separate Linux kernel; "In Docker's clone mode, a readable `.env` remains exposed"; Docker's proxy substitutes credentials on the host. For a separate kernel "consider Docker Sandboxes or OpenShell's MicroVM driver, weighing mounts, authentication, and overhead." — [rywalker.com](https://rywalker.com/research/local-agent-sandboxes)
- Firecracker: KVM microVM, "<150ms" boot, "<5MB" overhead (vendor-blog figures, inconsistent across sources); E2B and Vercel Sandbox run on Firecracker. — [Northflank: best microVM sandboxes for AI coding agents](https://northflank.com/blog/best-microvm-sandboxes-for-ai-coding-agents); [reinvently: Firecracker, OpenSandbox, Docker, SmolVM and nono compared](https://reinvently.co.uk/blog/microvm-sandbox-options-firecracker-opensandbox-smolvm-nono/)
- Community tools that keep git credentials host-side: AgentBox (local Docker + FUSE overlay, "keeps git credentials on the host"); Fletch (`git clone --shared` per agent; push/PR run host-side so tokens stay out of the sandbox). — [wincent gist comments](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e)
- Anthropic's srt README lists `/var/run/docker.sock` in `allowUnixSockets` but notes the option is ignored on Linux; Docker is a known incompatibility of the built-in sandbox. — [sandbox-runtime README](https://github.com/anthropics/sandbox-runtime); [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)

### Inferences
- For this box, the test stacks that need `docker compose` are the deciding factor. Options, in rising cost: (1) keep workers on the host under bwrap/srt and exclude `docker compose *` from the Bash sandbox (documented, but those commands run with host access and the docker socket is root-equivalent on the host); (2) run workers under rootless Podman with the project and a per-worker compose project, accepting that bwrap inside needs `enableWeakerNestedSandbox`; (3) Docker Sandboxes microVM with its own daemon (free, but adds workspace sync and a second Docker daemon per worker; Linux-without-Desktop support is stated by Anthropic's page, not confirmed in detail on Docker's overview page).
- A container is "worth it" for a solo dev mainly when the agent must drive Docker itself or when the host has live services that must not be reachable from the sandbox at all (a container with its own network and no host socket satisfies both). Otherwise bubblewrap gives the same filesystem/secret isolation with far less tooling friction (node_modules and .venv live in the worktree, which is bound RW anyway).
- The docker socket is the single biggest hole: any sandbox that grants it is equivalent to root on the host.

### Gaps
- No source quantified build/test friction (node_modules, .venv, cache dirs) for bwrap vs Podman; the gist explicitly says node_modules is not mentioned.
- Docker Sandboxes' Linux hypervisor, docker-in-sandbox and Linux-host support details were not on the overview page I fetched; the deeper Architecture/Agents pages were not fetched.
- Dagger container-use: no 2026 coverage found beyond the gist's one-line entry.

## Key question 4: What threat model do people guard against, and which layer stops which?

### Takeaway
The threats named across Anthropic docs, research notes, and practitioner posts are: prompt injection via repo/PR/web/MCP content leading to (a) credential exfiltration, (b) persistence by writing agent config/hooks/git hooks, (c) destructive git/rm on the project or host, and (d) reaching production/live services. Real 2026 incidents were credential exfiltration through prompt injection, not sandbox escapes. Network allowlisting stops exfiltration; read-deny / not-mounting stops credential access; write-deny on config paths stops persistence; harness deny rules and git conventions stop destructive git; separate network namespace or firewall stops reaching live services on localhost.

### Cited Findings
- Anthropic's stated threat model: assume prompt injection can compromise Claude Code; sandboxing ensures a successful injection "cannot steal SSH keys or contact an attacker's server"; both FS and network isolation are needed because "without network isolation, a compromised agent could exfiltrate files like SSH keys, and without filesystem isolation, it could escape the sandbox and gain network access". — [Anthropic engineering blog, 2025-10-20](https://www.anthropic.com/engineering/claude-code-sandboxing); [sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Persistence threat: "A sandboxed session that can write [config paths] can persist hooks, permission rules, or MCP servers that run unsandboxed the next time you launch Claude Code"; srt mandatorily denies `.git/hooks`, `.git/config`, `.mcp.json`, `.claude/commands`, `.claude/agents`, shell startup files. — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Even with isolation, "any approach that allows network egress can still leak data the agent can read, and any approach that mounts your project directory writable can still modify that code." Isolation "does not change what is sent to the model." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- "Comment and Control" (disclosed 2026-04-15): Claude Code Security Review, Gemini CLI Action and GitHub Copilot Agent hijacked via prompt injection in PR titles/issue bodies/comments; in the Claude case a malicious PR title led the agent to post its own API key as a comment; Anthropic rated it CVSS 9.4; no external server needed since exfil went through GitHub itself. — [CSA research note: Comment and Control](https://labs.cloudsecurityalliance.org/research/csa-research-note-comment-control-github-prompt-injection-20/); [VentureBeat (2026)](https://venturebeat.com/security/ai-agent-runtime-security-system-card-audit-comment-and-control-2026)
- January 2026: RyotaK (GMO Flatt Security) reported an authorization bypass + indirect prompt injection + env-var exfiltration chain in `claude-code-action`; reported 2026-01-12, primary fix within four days. — [CSA research note: Claude Code GitHub Action prompt injection](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)
- Study of 17,022 agent skills: 520 (3.1%) contain 1,708 credential-leakage issues, 84% from developer negligence. — [arXiv 2604.03070: Credential Leakage in LLM Agent Skills](https://arxiv.org/html/2604.03070v1)
- Research framing of OS-level policy for agent harnesses: [arXiv 2606.25189: ActPlane: Programmable OS-Level Policy Enforcement for Agent Harnesses](https://arxiv.org/pdf/2606.25189); [arXiv 2605.18991: Agent Security is a Systems Problem](https://arxiv.org/pdf/2605.18991) (not fetched; titles only).
- Which layer does what (rywalker): "Claude's permission rules are enforced by the harness, while filesystem and network confinement comes from the sandbox"; credential proxies keep selected secrets out of the child process but env-injected secrets are exposed; "Mounts and sockets can bypass isolation." — [rywalker.com](https://rywalker.com/research/local-agent-sandboxes)
- Harness-level protections that survive sandboxing in auto-allow: `Bash` deny rules, `rm`/`rmdir` on critical paths, content-scoped ask rules like `Bash(git push *)`; `--dangerously-skip-permissions` skips protected-path checks but "actions no mode auto-approves" still apply. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Codex's analogous layering: sandbox (`workspace-write`) + approval policy (`on-request`) is the "lower-risk automation preset"; full access = `danger-full-access` + `never`. — [Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md)

### Inferences
- Mapping to this box's assets: `.env`, `~/.config/*`, `~/.livekit`, `/etc/restic` → not bound into the worker's mount namespace (bwrap/srt `denyRead` or simply not mounted) stops both read and exfil at the source, independent of the model. `/srv` and docker compose stacks → make `/srv` invisible or read-only in the worker namespace; the live n8n/streaming services on localhost are reachable only if the worker shares the host network namespace — the built-in sandbox's netns and srt's netns both refuse loopback targets by design.
- The current settings.json deny rules remain the only layer that understands *git semantics* (no push to main, no force-push); no OS sandbox distinguishes `git push` from `git fetch`. Keep them; they continue to apply inside the sandbox.
- The persistence vector (writing `~/.claude/settings.json`, hooks, `.mcp.json`) is specific to the worker having `~/.claude` writable, which srt requires for sign-in state; srt's mandatory denies and the built-in sandbox's protected paths cover the project-level files, but `~/.claude/settings.json` itself must be protected by `denyWrite` or by giving workers a separate `CLAUDE_CONFIG_DIR`.

### Gaps
- No public incident of a local Claude Code worker on a developer machine exfiltrating via network was found; the documented incidents are CI/GitHub-Action contexts.
- No source measured how often auto mode's classifier blocks an unsandboxed retry or domain addition in practice.

## Key question 5: Scope — does anyone sandbox the orchestrator itself? What is the common pattern?

### Takeaway
I found no write-up that sandboxes a bash orchestrator; the universal pattern is a trusted host-side controller (holds git credentials, does push/PR, allocates worktrees) and sandboxed workers, with test runs inheriting the worker's sandbox. Anthropic's cloud product and the community tools that address the question (Fletch, AgentBox, Claude Code on the web's credential proxy) all keep credentials and privileged git operations on the trusted side.

### Cited Findings
- Claude Code on the web: "A network proxy enforces a default allowlist, and a separate proxy holds your GitHub token outside the sandbox while issuing scoped credentials for repository access inside it." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments); the engineering blog: "credentials such as git credentials or signing keys stay outside the sandbox, and a custom proxy validates scoped credentials and git operations (e.g., the configured branch) before attaching authentication." — [Anthropic engineering blog](https://www.anthropic.com/engineering/claude-code-sandboxing)
- Fletch: "Gives each agent its own `git clone --shared`. Push and PR operations run host-side so tokens stay out of the sandbox." AgentBox: "Keeps git credentials on the host." container-use (Dagger): "Containers + Git worktrees; parallel agents via MCP." Conductor: git worktrees, runs Claude Code and Codex. — [wincent gist and comments](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e)
- srt docs: "The same `srt` command works for sandboxing standalone MCP servers or other helper processes." — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- The Bash sandbox covers "Bash, PowerShell, and Monitor tool commands and their child processes" — i.e. test suites launched by the agent are inside the per-command sandbox automatically. — [Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- rywalker: orchestrators vs workers "not discussed as a separate architecture". — [rywalker.com](https://rywalker.com/research/local-agent-sandboxes)

### Inferences
- Recommended scope for this setup: **do not** sandbox the orchestrator (it needs to create worktrees, merge, push, delete branches, run `harness gc`, and hold the GitHub token); **do** sandbox each worker's whole process (bwrap/srt) and enable the built-in Bash sandbox inside it so tests and build commands inherit a network allowlist and the write boundary. Tests are then covered by inheritance with no extra mechanism; the one exception is docker-based test stacks, which need either `excludedCommands` (host access) or a container/microVM per worker.
- The orchestrator is the natural place for a credential proxy pattern: workers get no GitHub token; the orchestrator pushes and opens PRs after the worker exits (what Fletch and Claude Code on the web do). This also removes the need for `claude.ai`/`platform.claude.com` in the worker allowlist if workers authenticate with an API key or a `claude setup-token` long-lived token passed via env.

### Gaps
- No published example of a bash/systemd orchestrator plus sandboxed `claude -p` workers on one host; the closest analogues are the cloud product and the container-based multi-agent tools.

## Key question 6: How do people avoid permission prompts entirely by combining a sandbox with "allow everything inside it"? Good write-ups

### Takeaway
The documented recipe is: enable the built-in sandbox (sandboxed Bash auto-allowed in every mode by default), run under auto mode (classifier instead of human for exceptions) or bypass (no exceptions at all), and wrap the whole process in srt/bwrap/container so the exceptions can't hurt. Anthropic reports 84% fewer prompts from the Bash sandbox alone; practitioners pair bwrap with `--dangerously-skip-permissions`. Codex's equivalent is `workspace-write` + `on-request` (or `never`).

### Cited Findings
- "Auto-allow mode: sandboxed Bash commands run without a prompt, regardless of permission mode" (`autoAllowBashIfSandboxed` defaults to `true`); in auto mode, out-of-allowlist hosts are refused unless listed by the command and approved by the classifier; unsandboxed retry in auto mode uses the classifier. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Internal Anthropic measurement: sandboxing "safely reduces permission prompts by 84%". — [Anthropic engineering blog, 2025-10-20](https://www.anthropic.com/engineering/claude-code-sandboxing)
- Dev container doc: "Because the container runs Claude Code as a non-root user and confines command execution to the container, you can pass `--dangerously-skip-permissions` for unattended operation... Pair this flag with the network egress restrictions". Alternative: auto mode. `permissions.disableBypassPermissionsMode: "disable"` in managed settings forbids bypass. — [Claude Code: Development containers](https://code.claude.com/docs/en/devcontainer.md)
- Practitioner one-liner combining bwrap and `--dangerously-skip-permissions` (Bretti, 2026-08-09). — [Juan Bretti](https://blog.juanbretti.com/en/posts/2026-08-09_bubblewrap_sandboxing_ai_agents/)
- Esokia's two-layer approach (outer bwrap + inner native sandbox, 2026-03-18) and its empirical warning that `allowedDomains` must be validated per Claude version. — [Esokia Labs](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/)
- Codex: `--sandbox workspace-write --ask-for-approval on-request` as the "lower-risk automation preset"; `never` + `danger-full-access` = full access. — [Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md)
- Third-party overviews of the "every option" landscape for Claude Code (2026): [agent37](https://www.agent37.com/blog/claude-code-sandbox); [claudefa.st](https://claudefa.st/blog/guide/sandboxing-guide); [TrueFoundry on Claude Code sandboxing](https://www.truefoundry.com/es/blog/claude-code-sandboxing) (argues built-in sandbox insufficient for enterprise; recommends containers, egress controls, credential scoping). (Secondary; not fetched in full.)
- A secrets-focused approach (daily.dev repost, 2026): "A better way to limit Claude Code (and other coding agents!) access to Secrets" — [daily.dev](https://daily.dev/posts/a-better-way-to-limit-claude-code-and-other-coding-agents-access-to-secrets-blog-yu0vomcjx) (not fetched; title only).

### Inferences — recommended layering for this box (synthesis; each element traces to the findings above)
1. **Keep the orchestrator trusted and unsandboxed**; keep it as the only holder of git push credentials; keep `systemd-run --user --scope` for memory caps (scopes do resource control; they can't carry exec sandboxing directives).
2. **Per worker, wrap the whole `claude -p` process** in bubblewrap — either `srt claude` with a per-worker `--settings` file (allowWrite: worktree, `/tmp/<worker>`, `~/.claude`, `~/.claude.json`; denyRead: `~/.config`, `~/.livekit`, `/srv`, `/etc/restic`, and literal paths of `.env*`; allowedDomains: `api.anthropic.com`, `github.com`, `*.github.com`, `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org`), or a hand-written bwrap wrapper in the Esokia shape (`--ro-bind /usr /etc`, bind the worktree, `~/.claude`, tmpfs `/tmp`, `--clearenv`, `--unshare-pid --unshare-ipc --unshare-uts --new-session --die-with-parent`, `/dev/null` over `.env*`). Hand-rolled bwrap is simpler for secret hiding (srt's Linux glob limits) but offers no hostname allowlist; srt gives the allowlist and credential masking but needs `~/.claude` writable and literal deny paths.
3. **Enable the built-in Bash sandbox inside the worker** via `--settings '{"sandbox":{"enabled":true,"failIfUnavailable":true,"network":{"allowedDomains":[...]}}}'` so Bash, tests and builds get the netns + proxy allowlist, and so auto mode never prompts for sandboxed Bash. Add `"excludedCommands": ["docker compose *"]` only if the worker must drive compose; otherwise move compose-based tests to a container/microVM per worker or run them from the orchestrator after the worker exits.
4. **Keep settings.json deny rules** for git semantics (force-push, main) and the protected-path behaviour; give workers a separate `CLAUDE_CONFIG_DIR` or `denyWrite` on `~/.claude/settings.json` so a compromised worker cannot persist hooks/MCP servers for the next run.
5. **One-time host prep**: `apt install bubblewrap socat`, `npm i -g @anthropic-ai/sandbox-runtime` (seccomp filter), AppArmor userns profile for `bwrap` on 24.04+ (per-binary profile rather than the global sysctl, per both Anthropic and Codex docs).
6. **Not worth it for this box yet**: Firecracker/Kata/gVisor (compliance-grade, high setup), Kubernetes, paid cloud sandboxes. Docker Sandboxes (free microVM with own daemon) is the one to revisit if compose-driven tests must run inside the worker boundary.

### Gaps
- No HN thread on the Anthropic sandbox announcement was located by my searches (only an HN user page); the writer should not cite an HN discussion unless they find one.
- No source gives a worked `srt` settings file for a multi-worker, per-worktree layout; the per-worker `--settings` idea is my inference from srt's `--settings` flag and the docs' write-grant requirements.
- I did not verify that `claude -p` honours `--settings` identically to interactive mode for the `sandbox` keys (expected, not confirmed).
