# Agent/model interchangeability, protocols, frameworks and durable-execution runtimes for a home-built coding-agent orchestrator (state as of 2026-10-26)

Scope note: the orchestrator under discussion is bash + node stdlib, shelling out to `claude -p … --output-format stream-json`, parsing the transcript for cost/tokens/tool calls and the agent's final `entry.json`, relying on CLAUDE.md, Claude Code hooks/skills/settings deny rules, and `claude --remote-control` as the human desk. Older material (2024–2025) is marked where it matters. "Documented" = taken from a primary doc or source file fetched during this research; "inferred" = my reading of the documented facts.

## Key question 0: What in the current architecture is Claude-specific, and what would an adapter boundary look like?

### Takeaway
Almost everything the orchestrator touches is a Claude Code-specific surface (flag names, stream-json schema, `total_cost_usd`, permission modes, CLAUDE.md, hooks/settings deny rules, Remote Control). The parts that generalise are the shape of the contract, not the fields: "run a prompt in a cwd with a model, a budget/turn cap and a permission policy; stream events; return a final text/structured artifact plus usage; be resumable by session id". Every other agent CLI offers some subset of that contract, and two projects (Vibe Kanban, acpx) show two different ways to draw the line: a per-agent executor trait, or an ACP wrapper around every agent.

### Cited Findings
- `claude -p` offers: `--output-format text|json|stream-json`, `--json-schema` structured output (`structured_output` field, absent if the run ends without valid output), `--max-budget-usd` (on cap, remaining background work is stopped), `--permission-mode auto|dontAsk|acceptEdits|…`, `--permission-prompts none`, `--allowedTools`, `--settings`, `--mcp-config`, `--continue`/`--resume <id|transcript path>`, `--bare` (skip hooks/skills/CLAUDE.md/MCP auto-discovery; "recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release"), SIGTERM exit code 143 with the in-progress turn unrecorded — [Claude Code headless docs](https://code.claude.com/docs/en/headless) (fetched 2026-10-26).
- stream-json carries `system/init` (model, tools, `mcp_servers`, `plugins`, `capabilities` array for feature-detection), `system/api_retry`, `permission_denied` system messages, `assistant`/`user` messages with `parent_tool_use_id` for subagents, and a final `result` with "final response text, cost, and session metadata"; `--output-format json` includes `total_cost_usd` and a per-model cost breakdown that are "client-side estimates" — [Claude Code headless docs](https://code.claude.com/docs/en/headless).
- Result-level fields: `total_cost_usd`, `usage` (main loop only; excludes subagents), `modelUsage`/`model_usage` (per model: `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costUSD`, `costBasis` from v2.1.246), `duration_api_ms`, result `subtype` values `success`, `error_max_budget_usd`, `error_during_execution` (may be zeroed after a crash); cost is computed "from a price table bundled at build time" and must not be used for billing; since v2.1.277 a resumed session's results include earlier spend — [Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md).
- Remote Control requires a claude.ai subscription ("API keys are not supported"), activates only via `claude remote-control`, `claude --remote-control` or `/remote-control`, and `claude --remote-control` "starts an interactive session"; server mode (`claude remote-control`) supports `--spawn worktree`, `--capacity N` (default 32), and sessions can be brought back with `--continue`/`--session-id` for about four hours — [Remote Control docs](https://code.claude.com/docs/en/remote-control).
- Vibe Kanban (BloopAI, Rust) abstracts agents behind a `StandardCodingAgentExecutor` trait with `spawn(current_dir, prompt, env)`, `spawn_follow_up(current_dir, prompt, session_id, reset_to_message_id, env)`, `normalize_logs(raw_logs, worktree_path)`, `default_mcp_config_path()`, `get_availability_info()`, `discover_options()`, `get_preset_options()`; the `CodingAgent` enum has variants `ClaudeCode, Amp, Gemini, Codex, Opencode, CursorAgent, QwenCode, Copilot, Droid`, plus an `acp/` module directory — [executors/mod.rs](https://raw.githubusercontent.com/BloopAI/vibe-kanban/main/crates/executors/src/executors/mod.rs), [directory listing](https://github.com/BloopAI/vibe-kanban/tree/main/crates/executors/src/executors).
- acpx (openclaw, MIT, "alpha") is a headless ACP client that runs Claude (via `claude-agent-acp`), Codex (via `codex-acp`), Gemini (`gemini --acp`), Copilot (`copilot --acp --stdio`), Droid (`droid exec --output-format acp`), OpenCode (`npx -y opencode-ai acp`), Qwen, Kimi, Cursor and others; it has `exec` one-shot mode, persistent per-repo sessions, `--approve-all|--approve-reads|--deny-all`, `--non-interactive-permissions <deny|fail>`, `--policy <json>`, `--format text|json|quiet`, `--timeout`, and a `compare` command that "summarizes timing, token usage, permissions, and final output across agents"; it does not mention cost — [acpx README](https://cdn.jsdelivr.net/npm/acpx@0.11.2/README.md).
- OpenAI's Symphony spec abstracts the *tracker*, not the agent: it is "built around the Codex app-server protocol", launches the agent via a configurable `codex.command` (default `codex app-server`), and "doesn't describe support for other agents" — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md).

### Inferences
- Claude-specific in the current design (inferred from the docs above): flag names; the stream-json event vocabulary; `total_cost_usd`/`modelUsage`; `--permission-mode auto` (classifier-based) and `--permission-prompts none`; settings deny rules and hooks (`PreToolUse` etc.) as the safety layer; CLAUDE.md as instruction file; `--resume` semantics; Remote Control as the desk. Of these, the hardest to replace are (a) dollar cost (only Claude reports it; Codex, Gemini, OpenCode, Goose report tokens only), (b) hooks as deny gates (ACP gives the client a permission callback instead, which is a different mechanism), and (c) Remote Control (subscription-only, interactive-only).
- A reasonable adapter boundary, modelled on Vibe Kanban's trait and the fields the CLIs actually share: `spawn(cwd, prompt, model, limits{turns,budget?,timeout}, policy) -> stream of normalised events {init, text, tool_call, tool_result, permission_denied, error, result{stop_reason, tokens{in,out,cached}, cost?, session_id, structured_output?}}`, plus `resume(session_id, prompt)` and `instructions_file()` per agent. `entry.json` (the agent writing a file in the worktree) is already agent-neutral and should stay the primary result channel, since structured-output flags differ (`--json-schema` in Claude, `--output-schema` in Codex, none in Gemini/Goose).
- Budget in dollars cannot be a portable contract; a token cap (plus a per-model price table the orchestrator owns) is the portable equivalent, which is also what Claude itself does internally.

### Gaps
- I did not find a document describing how Vibe Kanban normalises each agent's log stream into its common format (the `normalize_logs` implementations live per agent in `claude.rs`, `codex.rs`, etc., which I did not read).
- Whether `claude -p` sessions can be attached to Remote Control after the fact is not documented; the docs only describe interactive and server-mode entry points.

## Key question 1: Agent Client Protocol (ACP) and other protocols

### Takeaway
ACP (Zed, launched August 2025, JSON-RPC over stdio) is now the de facto editor–agent protocol with ~43 registry entries including adapters for Claude Code and Codex and native support in Gemini CLI, Goose, OpenCode, Copilot and Cursor; it covers sessions, prompt turns, tool-call reporting, permission requests, client-side file and terminal access, modes and (optionally) a `usage_update` with tokens and an optional cost. It is usable headless (acpx, acpc, acp-cli exist), but it does not carry budgets, turn caps or instruction-file semantics, and the Claude adapter is a wrapper over the Agent SDK rather than a native Anthropic surface.

### Cited Findings
- ACP's stated goal is to do for agent–editor integration what LSP did for language servers; local agents run as subprocesses speaking JSON-RPC over stdio, remote agents over HTTP/WebSocket are "a work in progress"; it reuses MCP JSON types where possible and assumes "the user is mainly working in their editor" — [ACP introduction](https://agentclientprotocol.com/overview/introduction).
- Protocol structure (v1): agent methods `initialize`, `authenticate`, `session/new`, `session/prompt`, optional `session/load`, `session/set_mode`, `logout`, notification `session/cancel`; client methods `session/request_permission` (baseline), optional `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|release|wait_for_exit|kill`, `elicitation/create`; notification `session/update`. Extensibility via `_meta`, `_`-prefixed methods, custom capabilities. Minimum client: drive `initialize`, `session/new`, `session/prompt` and handle `session/request_permission` and `session/update`; clients "are typically code editors" but "can also be other UIs for interacting with agents" — [ACP protocol overview](https://agentclientprotocol.com/protocol/overview).
- Prompt turn: `session/prompt` returns a `stopReason` in `end_turn | max_tokens | max_turn_requests | refusal | cancelled`; `session/update` kinds include `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update`, `notice`, `compaction_update`. `usage_update` carries `used` and `size` (context tokens) and an optional `cost {amount, currency}`; the `PromptResponse` itself has no usage — [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn).
- Registry (fetched 2026-10-26) lists 43 agents, including "Claude Agent: ACP wrapper for Claude" (`agentclientprotocol/claude-agent-acp`), "Codex: ACP adapter" (`agentclientprotocol/codex-acp`), Gemini CLI, goose, OpenCode and "OpenCode V2", Copilot, Cursor, Devin, Junie, Qwen Code, Kimi CLI, Mistral Vibe, DeepAgents (LangChain), Harn ("runs agent pipelines as a native ACP coding agent over stdio"); it is curated to agents "that support authentication" and is fetchable at `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json` — [ACP registry](https://agentclientprotocol.com/registry).
- Zed's progress report (2025-10-02; older) listed Gemini CLI (launch partner), Claude Code (via Zed's SDK adapter) and Goose as available, Codex/Aider/Cursor in progress, and Neovim, Emacs, marimo as clients; no governance body was named — [Zed ACP progress report](https://zed.dev/blog/acp-progress-report).
- Zed's Claude Code integration is "an adapter that wraps Claude Code's SDK and translates its interactions into ACP's JSON RPC format", Apache-licensed, beta from 2025-09-03; a Taiwanese report noted it was built on Zed's side rather than Anthropic adding native ACP — [Zed: Claude Code via ACP](https://zed.dev/blog/claude-code-via-acp) (older, 2025); summary of the ithome note via search.
- The current `claude-agent-acp` README says it is built on the Claude Agent SDK; supports permission requests, diffs, subagent transcripts, terminals, client MCP servers, `/mcp`, and "experimental ACP v2" (session list, resume with replay, close, delete, fork, plans, compaction); it does not document hooks, skills, usage/cost reporting, or authentication — [claude-agent-acp README](https://raw.githubusercontent.com/agentclientprotocol/claude-agent-acp/main/README.md).
- Headless ACP clients: acpx (npm, openclaw, alpha; one-shot `exec`, sessions, permission policies, NDJSON output); acpc (PyPI, "headless Python CLI for ACP, built on top of the official agent-client-protocol SDK", alpha, each call pays an adapter cold start); acp-cli (Rust port of acpx) — [acpx README](https://cdn.jsdelivr.net/npm/acpx@0.11.2/README.md), [acpc on PyPI](https://pypi.org/project/acpc), [acp-cli](https://docs.rs/crate/acp-cli/0.3.1).
- ACP has reached non-editor hosts: JetBrains AI Assistant 2026.1/2026.2 docs describe ACP agent support — [JetBrains ACP help](https://www.jetbrains.com/help/ai-assistant/2026.2/acp.html); a June 2026 post reports ACP arriving in Microsoft's terminal — [codex.danielvaughan.com, 2026-06-10](https://codex.danielvaughan.com/2026/06/10/agent-client-protocol-microsoft-intelligent-terminal-codex-cli-multi-agent-ide-ecosystem/) (secondary).
- Other protocols: A2A (Google) was donated to the Linux Foundation on 2025-06-23 and is agent-to-agent, not client-to-agent — [Linux Foundation press release](https://linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents). AGENTS.md was released by OpenAI in August 2025 and moved to the Linux Foundation's Agentic AI Foundation in late 2025; one April 2026 table counts 25+ tools reading it natively; Codex truncates past `project_doc_max_bytes` (32 KiB default) — [codex.danielvaughan.com, 2026-04-07](https://codex.danielvaughan.com/2026/04/07/agents-md-open-standard-cross-tool-portability) (secondary). Vercel AI SDK 6 added a `ToolLoopAgent` class; docs now mention AI SDK 7 — [dev.to write-up](https://dev.to/curioustore_48788631d0e2e/vercel-ai-sdk-6-an-agent-is-just-a-while-loop-4kf3) (secondary), [AI SDK docs](https://ai-sdk.dev/docs/reference/ai-sdk-tui).
- Codex's own equivalent is the Codex app-server: JSON-RPC over stdio (also unix socket; WebSocket experimental), `initialize`/`initialized` handshake, thread/turn/item model, `thread/start|resume|fork`, `turn/start|steer|interrupt`, approval requests `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`, usage via `thread/tokenUsage/updated`, `account/rateLimits/read|updated`, `account/usage/read`; schema generated with `codex app-server generate-ts|generate-json-schema`; the docs point "automation and CI users to the Codex SDK" — [Codex app-server docs](https://learn.chatgpt.com/docs/app-server.md).

### Inferences
- ACP is the only cross-vendor protocol that matches the orchestrator's needs (sessions, permissions, tool-call stream, stop reasons), and acpx already proves it can be driven headless from a shell. What it lacks relative to `claude -p`: a budget/turn cap request (stop reasons exist for `max_tokens`/`max_turn_requests` but limits are set agent-side), cost (optional, agent-dependent), hooks/deny rules (replaced by the client answering `session/request_permission`), and instruction-file loading (left to each agent's own conventions).
- Going through ACP for Claude means going through a third-party wrapper (claude-agent-acp) over the Agent SDK, which adds a layer that Anthropic does not maintain and that does not surface hooks or cost; for the Claude path, `claude -p` or the SDK is the more direct interface. ACP earns its place as the second adapter, covering many agents at once, not as the primary one.
- The permission model inverts: with ACP, the *orchestrator* is the permission host and must implement the deny policy itself (acpx's `--policy <json>` is one example), rather than relying on Claude's settings.

### Gaps
- I could not confirm which registered agents emit `usage_update` with `cost`; the field is optional and the Claude adapter README is silent.
- ACP governance (foundation, versioning cadence) is not stated on the pages fetched; the registry notes its format "may change".
- No official statement on whether Anthropic intends native ACP in Claude Code.

## Key question 2: Headless interfaces of each CLI, what they report, their permission modes and instruction files

### Takeaway
Every major CLI now has a non-interactive mode with JSON or JSONL output and a session-resume flag, but only Claude Code reports dollar cost and only Claude and Codex offer structured-output schemas; permission/sandbox models differ fundamentally (Claude: classifier/auto mode + rules + hooks; Codex: OS sandbox levels + approval policy; Gemini: approval modes; OpenCode: allow-list + `--auto`; Goose: `GOOSE_MODE`; Aider: `--yes`), and instruction files are converging on AGENTS.md everywhere except Claude Code.

### Cited Findings
Claude Code (`claude -p`)
- Flags, stream-json contents, exit behaviour, `--bare`, `--max-budget-usd` behaviour, `--permission-mode` semantics and `--resume` as described under Key question 0 — [headless docs](https://code.claude.com/docs/en/headless); result fields and cost estimation — [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md).
- Instruction files: CLAUDE.md at project/parent/child/user levels, `.claude/rules/*.md`, CLAUDE.local.md — [SDK Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features.md). Community reports conflict on whether Claude Code reads AGENTS.md; the common workaround is importing it with `@AGENTS.md` from CLAUDE.md — [search summary of blogs and a Manifold market](https://manifold.markets/bessarabov/will-claude-code-support-agentsmd-i) (secondary; unverified against Anthropic docs).
- A third-party guide claims `--max-budget-usd` only applies in `-p` mode, that executed tool calls are not undone when the cap hits, and that `num_turns` is not a reliable measure of completed actions — [mer.vin](https://mer.vin/news/what-max-budget-usd-actually-kills-mid-agent-loop/) (secondary opinion).

OpenAI Codex CLI (`codex exec`)
- `codex exec "<task>"`: progress on stderr, final message on stdout; `--json` makes stdout a JSONL stream of `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*`, `error`; item types: agent messages, reasoning, command executions, file changes, MCP tool calls, web searches, plan updates; `turn.completed` carries `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens` (no cost); `-o/--output-last-message <path>`; `--output-schema <file>`; `--ephemeral`; default sandbox read-only, `--sandbox workspace-write|danger-full-access`; `--full-auto` is "no longer supported", replaced by `--sandbox workspace-write` or `--approve-for-me`; `--ignore-user-config`, `--ignore-rules`; a required MCP server failing makes exec exit with an error; `--skip-git-repo-check`; `CODEX_API_KEY`; `codex exec resume --last | <SESSION_ID>` — [Codex non-interactive docs](https://learn.chatgpt.com/docs/non-interactive-mode) (fetched 2026-10-26; the old developers.openai.com URL now redirects here).
- A community reference (2026-04-08, updated 2026-10-26) adds `-m`, `-c` config overrides, notes "the stream has no version indicator", no cost, no turn counter, and that `item_type`→`type` and `assistant_message`→`agent_message` renames happened before v0.44.0 — [codex exec JSONL reference](https://codex.danielvaughan.com/2026/04/08/codex-exec-jsonl-reference/) (secondary). A Mintlify mirror shows a different `method`/`params` shape (`turn/started`, `item/agentMessage/delta`), i.e. app-server framing; sources conflict, so verify against the installed version.
- Instruction file: AGENTS.md (origin OpenAI, Aug 2025; `project_doc_max_bytes` 32 KiB default) — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/05/27/agent-instruction-files-agents-md-claude-md-cross-tool-portability-codex-cli/) (secondary).

Gemini CLI
- Headless via `-p/--prompt` or automatically in a non-TTY; `--output-format json` returns one object `{response, stats, error?}` where `stats` is "token usage and API latency metrics"; `--output-format stream-json` emits `init`, `message`, `tool_use`, `tool_result`, `error`, `result` (final outcome "with aggregated statistics and per-model token usage breakdowns"); exit codes 0 success, 1 general/API error, 42 input error, 53 "Turn limit exceeded"; no dollar cost — [Gemini CLI headless reference](https://geminicli.com/docs/cli/headless.md).
- Community sources show `stats.models.<model>.tokens.{prompt,response|candidates,cached,total}` and `api` blocks, with an older flat `inputTokens/outputTokens` form on a Mintlify mirror; field names are inconsistent across sources — [gc.bytenote mirror](https://gc.bytenote.net/docs/cli/headless), [Mintlify mirror](https://www.mintlify.com/google-gemini/gemini-cli/advanced/headless) (secondary; verify locally).
- `--approval-mode default|auto_edit|yolo|plan`; standalone `--yolo` deprecated; GEMINI.md loads hierarchically (global, project, subdirectory) with `@./path` imports — [developersdigest CLI reference](https://www.developersdigest.tech/reference/gemini-cli), [computingforgeeks cheat sheet](https://computingforgeeks.com/gemini-cli-cheat-sheet/) (secondary). Whether Gemini reads AGENTS.md natively or needs `context.fileName` is contested in secondary sources.
- Gemini CLI is ACP-native (`gemini --acp`) — [acpx README](https://cdn.jsdelivr.net/npm/acpx@0.11.2/README.md); listed in the ACP registry.

OpenCode (anomalyco/opencode)
- `opencode run` flags: `--format default|json` ("raw JSON events"; schema not documented on the page), `-m provider/model`, `--agent`, `-s/--session`, `-c/--continue`, `--fork`, `-f/--file`, `--title`, `--attach <url>` (to a running `opencode serve`, avoiding MCP cold boot), `--dir`, `--variant` (reasoning effort), `--auto` ("Auto-approve permissions that are not explicitly denied"); `opencode serve` is a headless HTTP server with basic auth; `OPENCODE_PERMISSION` inline JSON; `agent create --permissions` allow-list of `bash, read, edit, glob, grep, webfetch, task, todowrite, websearch, lsp, skill` — [OpenCode CLI docs](https://opencode.ai/docs/cli/). A third-party cheat sheet also names `--dangerously-skip-permissions`; the official page does not — [computingforgeeks](https://computingforgeeks.com/opencode-cli-cheat-sheet/) (secondary; conflicts).
- Instruction files: project `AGENTS.md`, falling back to `CLAUDE.md`; global `~/.config/opencode/AGENTS.md`, falling back to `~/.claude/CLAUDE.md`; `instructions` array in `opencode.json` accepts paths, globs (e.g. `.cursor/rules/*.md`) and URLs; "the first matching file wins in each category"; `~/.claude/skills/` also read; `OPENCODE_DISABLE_CLAUDE_CODE=1` and finer env vars disable the Claude fallbacks — [OpenCode rules docs](https://opencode.ai/docs/rules/).
- ACP: `opencode acp` command exists (acpx launches `npx -y opencode-ai acp`) — [acpx README](https://cdn.jsdelivr.net/npm/acpx@0.11.2/README.md).

Goose (Block)
- `goose run` flags: `-i <file|->`, `-t <text>`, `--recipe`, `--params`, `--no-session` ("Useful for automated runs"), `--max-turns`, `--output-format text|json|stream-json`, `-q`, `--provider`, `--model`, `--with-extension`, `--with-builtin`, `-r/--resume`, `-n/--name`, `--session-id`, `--system`, `--stats` ("Prints generation statistics after the run"), `--max-tool-repetitions`, `--container <id>` (run extensions inside a container) — [goose-run man page](https://www.mankier.com/1/goose-run) (undated). Providers listed include `claude-code` and `gemini-cli`, i.e. Goose can drive other CLIs as its model backend (same source).
- `GOOSE_MODE` values `auto` (default, including for headless and scheduled sessions), `approve`, `smart_approve`, `chat`; resolution order env var → `config.yaml` → session `/mode` — [DeepWiki on block/goose](https://deepwiki.com/block/goose/6.2-permission-modes-and-tool-approval) (secondary), [goose permission docs](https://goose-docs.ai/docs/guides/goose-permissions).
- Instruction files: global `~/.config/goose/.goosehints`, local `.goosehints` or `AGENTS.md`; local wins on conflict — [thepromptshelf guide](https://thepromptshelf.dev/blog/goose-agents-md-goosehints-guide-2026) (secondary). Goose is in the ACP registry.

Aider
- `--message/--msg/-m` runs one instruction and exits; `--message-file`; `--yes`; `--auto-commits`/`--no-auto-commits`, `--dry-run`; Python API (`Coder.create`, `coder.run`) is "not officially supported or documented" — [aider scripting docs](https://aider.chat/docs/scripting.html).
- Conventions load only via `--read CONVENTIONS.md`/`/read` or a `read:` entry in `.aider.conf.yml`; no automatic AGENTS.md/CLAUDE.md — [aider conventions docs](https://aider.chat/docs/usage/conventions.html). Aider was "in progress" for ACP in Zed's Oct 2025 report and is absent from the current registry — [Zed progress report](https://zed.dev/blog/acp-progress-report), [ACP registry](https://agentclientprotocol.com/registry).

How Vibe Kanban and Symphony abstract across agents
- Vibe Kanban: per-agent executor modules (`amp.rs, claude.rs, codex.rs, copilot.rs, cursor.rs, droid.rs, gemini.rs, opencode.rs, qwen.rs` plus `acp/`), one trait with `spawn`/`spawn_follow_up`/`normalize_logs`; each attempt gets its own git worktree; a VirtusLab review described the trait as "how to locate the binary, how to format the prompt, and how to parse stdout" — [mod.rs](https://raw.githubusercontent.com/BloopAI/vibe-kanban/main/crates/executors/src/executors/mod.rs), [VirtusLab blog](https://virtuslab.com/blog/ai/vibe-kanban/) (secondary).
- Symphony (OpenAI, released 2026-04-28, Apache-2.0, Elixir reference implementation, "low-key engineering preview"): targets the Codex app-server only; tracker-agnostic (`active_states`, `terminal_states`, `required_labels`); repo-owned `WORKFLOW.md` with YAML front matter + prompt template; worker lifecycle with `before_run`/`after_run` hooks, per-issue persistent workspaces, `max_turns`; retries with `min(10000 × 2^(attempt−1), max_retry_backoff_ms)` and a 5-minute stall timeout; `max_concurrent_agents` default 10; scheduler state in memory, "requires no database", restart re-polls the tracker; tracks tokens and rate-limit payloads but "does not calculate monetary cost"; no sandbox mandated, tracker credentials stay host-side — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md), [README](https://raw.githubusercontent.com/openai/symphony/main/README.md), [Help Net Security, 2026-04-28](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/).

### Inferences
- The lowest common denominator across the six CLIs is: prompt in, JSON(L) events out, token counts (not dollars), a session id for resume, an exit code, and an agent-specific way to disable prompts. An adapter that needs more than that (budget in USD, structured output, deny hooks) will have per-agent branches, exactly as Vibe Kanban's per-agent modules show.
- Instruction-file portability: writing AGENTS.md as the canonical file and having CLAUDE.md `@AGENTS.md` it covers Codex, Gemini (possibly with config), OpenCode (native), Goose (native) and Claude (via import); Aider needs an explicit `--read`.
- Symphony is the most relevant "someone else did this" example: it is a scheduler around one agent protocol with the state machine in the tracker and in-memory scheduler state, deliberately without a database or durable runtime; its WORKFLOW.md is the analogue of the current per-role prompts.

### Gaps
- Official schemas for OpenCode's `--format json` events, Gemini's `stats` object and Goose's `json`/`stream-json` output were not found; all three need a local test run before writing a parser.
- `codex exec` exit codes and a documented stop reason are not covered by the official non-interactive page.
- Whether Gemini CLI reads AGENTS.md without configuration remains contested in the sources found.

## Key question 3: Claude Agent SDK versus `claude -p` for an orchestrator

### Takeaway
The SDK is "a library that runs the Claude Code binary" and exposes the same stream-json message objects, so it does not add a different engine; what it adds is in-process programmatic hooks and permission callbacks (`canUseTool`), typed messages, in-process custom MCP tools, explicit `settingSources` control, and streaming-input multi-turn sessions. It is Python/TypeScript only, bound to Anthropic's commercial terms and API-key auth (no claude.ai login for third-party products), so it locks you in to Claude at least as much as the CLI, while the CLI's JSONL stays the only language-neutral surface.

### Cited Findings
- "Embed Claude Code's agent in your own Python or TypeScript application … A library that runs the Claude Code binary, with Claude Code's capabilities, such as built-in tools, permissions, sessions, and hooks"; "To drive the same agent loop from a language other than Python or TypeScript, run the CLI as a subprocess with the `-p` flag and `--output-format json`" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).
- "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods"; use is governed by Anthropic's Commercial Terms; branding rules forbid calling the product "Claude Code" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).
- `settingSources` (default equivalent to `["user","project","local"]`) controls loading of CLAUDE.md, `.claude/rules`, skills, commands, subagents and filesystem hooks; `settingSources: []` limits the agent to programmatic config; managed policy, `~/.claude.json`, auto memory and claude.ai MCP connectors are read regardless; multi-tenant guidance: `settingSources: []` plus `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and per-tenant filesystems — [Claude Code features in the SDK](https://code.claude.com/docs/en/agent-sdk/claude-code-features.md).
- Hooks: filesystem hooks (`command`, `http`, `mcp_tool`, `prompt`, `agent` types) and programmatic callbacks run side by side; callbacks return `hookSpecificOutput.permissionDecision: "deny"` with a reason; TypeScript supports extra events (`SessionStart`, `SessionEnd`, `TeammateIdle`, `TaskCompleted`); skills have no programmatic registration API — [same page](https://code.claude.com/docs/en/agent-sdk/claude-code-features.md).
- Capabilities table: built-in tools, hooks, subagents, MCP, permissions, sessions ("resume or fork later"), skills/commands/memory, plugins — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview). The headless page states the Python/TypeScript packages add "structured outputs, tool approval callbacks, and native message objects"; `--permission-prompts none` matters "most when your run has a permission host: an Agent SDK app with a `canUseTool` callback, or an MCP tool you pass with `--permission-prompt-tool`" — [headless docs](https://code.claude.com/docs/en/headless).
- Cost semantics are identical in CLI and SDK (same `total_cost_usd`, `modelUsage`, streaming-input running totals, `maxBudgetUsd` counts only the call's own spend) — [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md).
- A community article describes the SDK as spawning `claude -p` as a subprocess over a JSON-lines stdin/stdout stream — [Medium: Claude Code deep dive, the SDK strikes back](https://medium.com/@the.gigi/claude-code-deep-dive-the-sdk-strikes-back-03b8d501ec38) (secondary, member-only).

### Inferences
- For a bash+node orchestrator, the SDK's concrete gains are (1) in-process deny logic with structured reasons instead of shell hook scripts, (2) a `canUseTool` permission host (which `--permission-prompt-tool` can approximate from the CLI via an MCP tool), (3) typed access to the same messages, and (4) streaming-input sessions where the orchestrator can send follow-up turns without respawning. None of these change what the model can do; they change where the control code lives.
- Lock-in: the SDK ties the orchestrator's control code to a Claude-specific API and to the Commercial Terms/API-key path; the CLI ties it only to a JSONL schema that an adapter can normalise. If interchangeability is the goal, the CLI (or ACP) is the less-locked surface; if deep Claude integration is the goal, the SDK is where hooks and permissions are richest. Using the SDK only inside a Claude adapter (behind the orchestrator's own interface) keeps both options open.
- `--bare` is the CLI's path to deterministic, machine-independent runs and the docs say it will become the default for `-p`; an orchestrator relying on project hooks and CLAUDE.md auto-discovery should pass them explicitly (`--settings`, `--append-system-prompt-file`, `--mcp-config`) so a future default flip does not silently remove the deny rules.

### Gaps
- No official statement on whether Remote Control can attach to an SDK-driven session (the Remote Control docs cover interactive and server mode only).
- No independent measurements of SDK vs CLI overhead or reliability were found.

## Key question 4: Do agent frameworks (LangGraph, CrewAI, AutoGen/AG2, OpenAI Agents SDK, Google ADK, Mastra, Pydantic AI, smolagents) add anything when the workers are full coding agents?

### Takeaway
These frameworks model an agent as an LLM call loop with tools inside the framework's process; a coding-agent orchestrator's "worker" is an opaque subprocess, so the frameworks' core (tool loop, state graph, role/handoff abstractions) does not apply to the worker and would only be a second, redundant loop. Their defensible niche in this design is the small roles that are themselves LLM calls (an initializer that plans, a verify judge that reads a diff and emits a verdict), and even there the primary vendor advice is to start with the raw API. No practitioner write-up was found that uses LangGraph/CrewAI/AutoGen to drive Claude Code or Codex as workers.

### Cited Findings
- Anthropic (2024-12-19; older): "start by using LLM APIs directly"; frameworks "often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug"; workflows are "systems where LLMs and tools are orchestrated through predefined code paths", agents are "systems where LLMs dynamically direct their own processes and tool usage" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- A 2026 comparison argues "Claude Code vs LangGraph is a comparison that sounds like a direct matchup but isn't. These tools operate on completely different layers of your stack" (development time vs runtime) — [lowcode.agency](https://www.lowcode.agency/blog/claude-code-vs-langgraph) (secondary opinion).
- LangGraph's edge over CrewAI is "arbitrary state transitions, parallel fan-out, conditional looping, and stateful pause-and-resume", at the cost of a more verbose graph API; CrewAI is "role-based teams… fastest to prototype" — [leanware](https://leanware.co/insights/langgraph-vs-crewai-comparison), [stacknotice](https://stacknotice.com/blog/langgraph-vs-crewai-vs-claude-agents) (secondary).
- Framework convergence on durable runtimes rather than on coding agents: Temporal lists integrations for OpenAI Agents SDK (Python, TypeScript), Vercel AI SDK, Deep Agents, Google ADK, Google GenAI, LangGraph, Mastra, Pydantic AI, Spring AI and Strands — [Temporal durable AI docs](https://docs.temporal.io/ai.md); Pydantic AI integrates with Temporal, DBOS, Prefect, Restate, AWS Lambda, Absurd, pgtask and Airflow, journaling model requests and tool calls as durable units — [Pydantic AI durable execution overview](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/); Restate has posts for OpenAI Agents SDK (2026-01-15), Google ADK (2026-01-12), Vercel AI SDK (2025-11-13), Pydantic AI (2026-04-02) — [Restate blog tag AI](https://www.restate.dev/blog/tags/AI).
- LangChain's DeepAgents is itself registered as an ACP *agent* (`langchain-ai/deepagentsjs`), i.e. the framework side is adopting the coding-agent protocol rather than the reverse — [ACP registry](https://agentclientprotocol.com/registry).
- Older HN criticism of OpenAI Swarm (Oct 2024): dividing work into subtasks "takes a lot of trial and error, plus custom code to parse outputs and reconnect them"; "agent ensembles tend to diverge over time" — [InfoQ on Swarm](https://www.infoq.com/news/2024/10/openai-swarm-orchestration) (secondary; opinion, 2024).
- A 2026 piece argues that hand-rolling orchestration for a few parallel tasks is reasonable, but "once multiple concurrent local agents become routine, the overhead of hand-rolling (lost sessions, stale worktrees, unreviewed diffs) usually exceeds the cost of adopting a purpose-built workspace" — [superset.sh](https://superset.sh/agent-orchestration) (vendor opinion).
- Anthropic's own multi-agent story inside Claude Code is "agent teams" and "dynamic workflows", a CLI feature "not directly configured via SDK options" — [Claude Code features in the SDK](https://code.claude.com/docs/en/agent-sdk/claude-code-features.md), [Anthropic blog: a harness for every task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (linked from SDK overview; not fetched).

### Inferences
- Where a framework *could* fit: the verify judge (one model call over a diff + test output, returning a typed verdict) and the init planner are "workflow" steps in Anthropic's sense; Pydantic AI or the OpenAI Agents SDK give typed outputs and retries for such steps with little code. But the orchestrator already gets typed output from `claude -p --json-schema` (or `codex exec --output-schema`), so a framework there buys a second model-provider abstraction at the price of a Python/TS dependency the bash+node design does not have.
- The one framework feature that does map onto this orchestrator is LangGraph's "stateful pause-and-resume" graph; that is a durable-execution concern (Key question 5), not an agent-modelling one, and the same property is available from Temporal/Restate/Inngest without adopting the LLM-loop abstractions.
- No evidence was found of practitioners wrapping coding-agent subprocesses in CrewAI/AutoGen/LangGraph nodes; the orchestrators that do exist (Symphony, Vibe Kanban, Clancy, orc, cc-ci-orchestrator, Chipp's harness) are plain schedulers in Elixir, Rust, Go, Python or bash.

### Gaps
- No HN thread from 2026 specifically on "frameworks for coding-agent orchestration" was found; the opinion evidence is vendor blogs and a 2024 Swarm thread.
- AutoGen/AG2, smolagents, Mastra and Google ADK were not individually researched beyond the Temporal/Restate integration lists; nothing found suggests any of them targets subprocess coding agents.

## Key question 5: Durable execution (Temporal, Inngest, Restate, Dagger, Prefect, Nix) and separating orchestration from execution

### Takeaway
Durable-execution runtimes give journaled steps, replay-based resume, retries, durable timers and human-approval waits, and in 2025–2026 they all pivoted to agents (Temporal–OpenAI Agents SDK integration July 2025, Restate's durable coding agent Oct 2025, Inngest Feb 2026, Cloudflare Apr 2026); the published coding-agent examples all journal an in-process agent loop, not an opaque subprocess, so for a subprocess-based orchestrator the runtime would only journal "spawn agent / wait / collect result", which a file-state machine already does. Symphony, the closest published analogue, explicitly keeps scheduler state in memory and re-polls the tracker on restart, and separates orchestration (scheduler/tracker reader) from execution (workspaces, agent process) by contract rather than by adopting a runtime.

### Cited Findings
- Temporal: positions itself so "a Workflow resumes after crashes, network timeouts, or multi-day waits for human approval"; approval via Signals; integrations listed above; the AI page does not cover coding agents or long-running sandboxes — [Temporal durable AI](https://docs.temporal.io/ai.md). Temporal–OpenAI Agents SDK integration launched 2025-07-30 — [BusinessWire](https://www.businesswire.com/news/home/20250730783559/en/Temporal-and-OpenAI-Launch-Integration-for-Enterprises-Developing-Production-Agents). A May 2026 Replay talk "How OpenAI uses Temporal" describes a "paved road" with managed workers; claims that Codex itself runs on Temporal appear only in third-party/analyst pieces — [Replay schedule](https://replay.temporal.io/schedule/how-openai-uses-temporal), [Forkast](https://forkast.news/durable-execution-is-the-next-agent-infrastructure-sub-sector) (secondary, unverified).
- Restate "durable coding agent with Restate and Modal" (2025-10-16): the agent is a custom GPT-5 loop; each LLM call and tool run is wrapped in `restate.run(...)` and journaled; on crash Restate retries and "continues from the latest completed step"; a per-session Virtual Object holds history and cancels the running workflow when a new message arrives; a per-sandbox Virtual Object schedules snapshot-and-restart with durable timers to beat Modal sandbox TTLs; scalability "primarily from Modal and Restate" and Restate's durable functions "replace hand-built queues, locks, and K/V stores" — [Restate blog](https://restate.dev/blog/durable-coding-agent-with-restate-and-modal). Restate's model: the server "sits in front of your agent process, similar to a message broker or a reverse proxy", journaling LLM/db/tool steps and replaying them after a crash (2025-06-19) — [Restate durable AI loops](https://restate.dev/blog/durable-ai-loops-fault-tolerance-across-frameworks-and-without-handcuffs); custom loops can wrap LLM calls in a run block — [Restate resilient serverless agents](https://restate.dev/blog/resilient-serverless-agents).
- Inngest (2026-02-19, Charly Poly): agents add failure points ordinary retry logic cannot handle; `step.run` checkpoints so completed steps "don't re-run after a restart, which avoids paying for repeated LLM calls"; `step.waitForEvent` with timeouts like `"7d"` for approvals; example of a coding agent that "reads files, runs tests, queries documentation, and executes commands dozens of times per task, each needing independent retry handling" — [Inngest blog](https://www.inngest.com/blog/durable-execution-key-to-harnessing-ai-agents) (vendor).
- Cloudflare "Project Think" (Apr 2026) previews an Agents SDK with durable execution, crash recovery and checkpointing, and argues coding agents are "ephemeral: they run for a session, tied to a single process or device" — via search summary of Cloudflare blog (not fetched; vendor).
- Pydantic AI distinguishes durability (surviving process stops, waiting hours/days) from persistence ("saving, resuming, or forking a run from an earlier step doesn't require an engine") — [Pydantic AI durable execution overview](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/).
- Prefect 3 provides transactional task semantics with persisted result records so reruns are idempotent; Pydantic AI routes model/tool/MCP calls through Prefect tasks when run inside a `@flow`; ControlFlow (PrefectHQ) is at 0.8.1 with no 2026 release found — [Pydantic AI Prefect docs](https://pydantic.dev/docs/ai/integrations/durable_execution/prefect/), [ControlFlow on PyPI](https://pypi.org/project/controlflow/0.8.1).
- Dagger's relevant project is Container Use: an MCP server that gives "each agent its own container and its own git branch", works with Claude Code/Cursor via MCP, logs executed commands, lets you drop into an agent's terminal; v0.4.2 published 2025-08-15, described as early-stage; no 2026 news found — [pkg.go.dev container-use](https://pkg.go.dev/github.com/dagger/container-use), [InfoQ Aug 2025](https://www.infoq.com/news/2025/08/container-use) (older).
- Nix: 2026 posts argue agents "inherit their shell environment", so a flake-pinned devShell fixes every tool version; Nix is complementary to Codex's Seatbelt/Landlock sandbox ("Nix addresses a different problem: making sure the agent has the right tools"); microvm.nix for ephemeral VMs — [codex.danielvaughan.com 2026-05-13](https://codex.danielvaughan.com/2026/05/13/codex-cli-nix-flakes-reproducible-agent-environments-declarative-toolchains/), [2026-05-30](https://codex.danielvaughan.com/2026/05/30/codex-cli-nix-development-mcp-nixos-flakes-reproducible-agent-environments/) (secondary, one blog).
- Symphony's separation: "Symphony is a scheduler/runner and tracker reader"; "The orchestrator is the only component that mutates scheduling state"; scheduler state in memory, no database required, restart re-polls the tracker and reuses preserved workspaces; "retry timers and live sessions are not restored"; the dashboard "MUST NOT become REQUIRED for orchestrator correctness"; stall timeout kills and reschedules; the SSH appendix runs commands remotely while "the orchestrator stays the source of truth" — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md).
- Restate's "Agentic workflows are just code" post title frames the position that orchestration should be ordinary code made durable, not a DSL — [Restate blog](https://restate.dev/blog/agentic-workflows-are-just-code-treat-them-that-way) (title only; not fetched).

### Inferences
- What a durable runtime would add over files + flock + systemd for this orchestrator: exactly-once step semantics across crashes, durable timers (retry backoff, stall detection) that survive a reboot, a built-in UI/history for each run, and typed signals for the human desk. What it would not add: durability *inside* a worker (a crashed `claude -p` loses its in-progress turn regardless; the recovery path is `--resume <session_id>`, which the runtime can call but not improve).
- The published coding-agent examples (Restate+Modal, Inngest) get most of their value because they own the LLM loop and can journal every model call; with Claude Code/Codex as a subprocess, that granularity is not available to the runtime. The journaled unit would be "one worker run", which is already what a state file records.
- Separating orchestration from execution is what both Symphony (tracker + in-memory scheduler vs. per-issue workspace + app-server) and Restate+Modal (durable functions vs. sandboxes) do; the pattern is to keep orchestration state small, re-derivable from an external source of truth (tracker, git, state files), and keep the execution environment disposable. A bash state machine already fits that pattern if its state is in files/git and it re-derives on restart rather than trusting in-memory state.
- The strongest argument for adopting a runtime later is operational (visibility, retries, multi-host) rather than correctness; Symphony shows a serious orchestrator shipping without one.

### Gaps
- No primary source confirms that OpenAI's Codex product runs on Temporal; treat it as unverified.
- No write-up was found of an orchestrator that wraps `claude -p`/`codex exec` subprocesses as Temporal/Restate/Inngest steps; the examples all own the loop.
- Dagger's current (2026) agent story beyond Container Use was not researched.

## Key question 6: Bash as the orchestrator language, its limits, and migration paths

### Takeaway
Practitioners who run unattended `claude -p` loops split into two camps: those who keep bash deliberately (Chipp's 312-line harness: process control, auditability, no deps, TypeScript "took about ten times as long to debug") and those who moved the logic to Go or Python while keeping bash as thin wrappers (cc-ci-orchestrator: "exec python3 <script>.py "$@"", pure stdlib; Clancy, orc, orchestra in Go). The documented pain points are runaway cost/time, hang detection, destructive-command backstops, worktree/process debris, and parsing structured output; the migration pattern that recurs is "keep the shell for process/git/systemd plumbing, move the state machine and JSON handling to a real language with no dependencies".

### Cited Findings
- Chipp "The bash harness" (2026-05-12, updated 2026-08-14, Hunter Hodnett): runs `claude -p` with `--dangerously-skip-permissions`; wall-clock timeout cut from 8h to 2h because runaway sessions cost too much; hang detection on tool-output silence (2→5 minutes); greps the command stream for `git reset --hard`, `--no-verify` pushes, `rm -rf` because the agent "sometimes issued destructive commands despite CLAUDE.md rules"; cleans worktrees and orphaned processes; enforces the push step; first version in TypeScript was "more elegant but took about ten times as long to debug"; bash chosen because it "manages Unix processes, is easy to audit on a production box, and has no dependencies"; harness is 312 lines, "most of them comments"; argues against adding frameworks to this deterministic layer — [chipp.ai](https://chipp.ai/blog/the-bash-harness) (practitioner opinion).
- cc-ci-orchestrator (autonomic.zone): commit "refactor: rewrite launchers as Python; add orchestrator JOURNAL.md"; bash scripts became one-liner `exec python3 <script>.py "$@"` wrappers; Python is "pure stdlib, no deps"; keeps `--resume <id>` so "conversation survives reboots" — [git.autonomic.zone commit](https://git.autonomic.zone/recipe-maintainers/cc-ci-orchestrator/src/commit/bca51071bd70b6cd36454b519371b57b5b98c6ae).
- Go loop orchestrators around coding-agent CLIs: Clancy ("Ralph Wiggum"-style loop over opencode/claude code with max iterations and global timeout) — [pkg.go.dev clancy](https://pkg.go.dev/github.com/eduardolat/clancy); orc ("invokes claude -p for agent phases", exit codes for timeout, cost limit, rate limit) — [pkg.go.dev orc](https://pkg.go.dev/github.com/jorge-barreto/orc); orchestra (circuit breakers: 2 empty cycles, 3 all-fail, 6h timeout; agents "spawned via claude -p") — [pkg.go.dev orchestra](https://pkg.go.dev/github.com/MochaCosine1206/orchestra).
- "Loop engineering" (2026-06) argues the loop primitives are moving into the tools themselves (Claude Code, Codex app) "instead of bespoke bash you maintain forever" — [mer.vin](https://mer.vin/2026/06/loop-engineering-design-coding-agent-systems-instead-of-prompting-every-turn/) (opinion).
- Claude Code itself now covers several things harnesses used to do: `--max-budget-usd`, `--max-turns`, `--permission-prompts none`, SIGTERM handling with `SessionEnd` hooks, background-work wait ceiling `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, `system/api_retry` events, `--resume` by transcript path — [headless docs](https://code.claude.com/docs/en/headless).
- Symphony's reference implementation chose Elixir "for its concurrency model" and the spec is "language-agnostic"; the README's Option 1 is to have a coding agent build Symphony from `SPEC.md` in any language — [Symphony README](https://raw.githubusercontent.com/openai/symphony/main/README.md), [Help Net Security](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/).
- Vibe Kanban is Rust (Axum + SQLite) with a React front end; each attempt gets a branch, worktree, terminal and dev server — [VirtusLab](https://virtuslab.com/blog/ai/vibe-kanban/), [OpenApps listing](https://openapps.pro/apps/vibe-kanban) (secondary).

### Inferences
- The limits people actually hit are not bash syntax but: no native JSON (every orchestrator above either shells to `jq`/node or moved to a language with a JSON library), no typed state (hence Symphony's explicit claim states and orc's exit-code taxonomy), concurrency across hosts (Symphony's per-host caps, SSH appendix), and testability of the state machine. The bash+node-stdlib split already in use is the same shape as cc-ci-orchestrator's bash+python-stdlib split; the migration path with least churn is to move the state machine and JSONL parsing fully into the node side and leave bash for `systemd`/`tmux`/`git`/`flock`.
- Because Claude Code has absorbed budget, turn and prompt-suppression limits, a bash harness's remaining jobs are the ones Chipp lists: wall-clock and silence timeouts, destructive-command backstops independent of the agent, debris cleanup, and enforcing the commit/push contract. Those are agent-neutral and belong in the orchestrator regardless of language or agent.
- A Go/Rust rewrite (Clancy/orc/Vibe Kanban style) buys a single static binary and typed concurrency; the evidence does not show it buying better agent control, which comes from the agent's own flags and from the adapter.

### Gaps
- No controlled comparison of bash vs Go/Python orchestrators (reliability, time-to-fix) exists; the "10x debug time" figure is one author's experience.
- The Go projects' maintenance status and real-world usage were not verified.
