# FOSS orchestrators for long-running autonomous coding-agent work (state as of 2026-10-26)

Method note: GitHub numbers (stars, license, language, last push, latest release) were pulled live from the GitHub API via `gh api` on 2026-10-26 and are cited as "GitHub API, 2026-10-26" with the repo URL. README summaries come from fetching each repo page the same day. Blog/HN material is marked as opinion. Anything older than mid-2026 is dated.

Shorthand for the person's own harness ("agent-harness"): bash, single Linux server, spec -> initializer writes feature list with milestones -> one fresh headless `claude -p` per feature in a git worktree -> project test suite -> independent verify session with evidence rows -> merge verified milestones via PRs -> usage-limit and memory-cap handling (systemd scopes) -> cross-project run queue -> retros and debrief -> now adding parallel lanes per milestone.

---

## Key question 1: Which projects exist, and which are true run-orchestrators vs. TUIs for parallel interactive sessions?

### Takeaway
The space is enormous (one curated list tracks ~270 projects across 8 categories) but most entries are session multiplexers or Kanban front-ends for humans supervising agents. Only a small set actually run work unattended from a plan/ticket through verification to merge: OpenAI Symphony (spec, Linear-driven, no verify/merge of its own), Gas Town (merge queue + verification gates, but author-abandoned and expensive), Bernstein (deterministic Python scheduler + Janitor verify + merge, solo-maintained beta), Archon (YAML workflow graphs with test loops and a merge queue, 23.8k stars), ralphex (Go, fresh `claude --print` session per task + multi-agent review + commits, single plan), ordewell, Orbi, and OpenAI-adjacent clones (contrabass). None combines spec-to-milestones, independent evidence-based verify, PR merge, cross-project queue, usage/memory-cap handling and retros the way the person's bash harness does.

**OpenAI Symphony** (`openai/symphony`)
- 27,831 stars, Apache-2.0, Elixir, last push 2026-09-15, latest release v0.0.3 (2026-09-15), 2,888 forks, 0 open issues — GitHub API 2026-10-26, [repo](https://github.com/openai/symphony).
- Description: "Symphony turns project work into isolated, autonomous implementation runs, allowing teams to manage work instead of supervising coding agents." README calls it "a low-key engineering preview for testing in trusted environments"; `elixir/` holds an "experimental reference implementation"; SPEC.md is the basis for ports: "Tell your favorite coding agent to build Symphony in a programming language of your choice." Navigation notes "Only collaborators can create PRs." — [repo README](https://github.com/openai/symphony).
- SPEC.md: each issue gets one directory at `<workspace.root>/<workspace_key>`; "The spec does not mandate a git worktree or clone"; repo population is implementation-defined via `hooks.after_create`. Runtime is the Codex app-server protocol over stdio (`codex.command` defaults to `codex app-server`). Config fields: `agent.max_concurrent_agents` (10), `agent.max_turns` (20), `agent.max_retry_backoff_ms` (300000), `polling.interval_ms` (30000), `codex.turn_timeout_ms` (3600000), `codex.stall_timeout_ms` (300000). Failure retries use `min(10000 * 2^(attempt-1), max_retry_backoff_ms)`. "The orchestrator performs no verification or merge step. It defines no test or review gates." "Current design is intentionally in-memory for scheduler state." Tokens are tracked for observability only: "It defines no token budget or monetary cost limit." — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md).
- Release reporting: announced 2026-04-27/28 under Apache 2.0; OpenAI "does not plan to maintain Symphony as a standalone product" and treats it as "a reference implementation"; OpenAI reports "some teams ... saw a 500% increase in landed pull requests during the first three weeks" (vendor figure); Codex reproduced the spec in TypeScript, Python, Rust — [Help Net Security, 2026-04-28](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/); [Tessl](https://tessl.io/blog/openai-open-sources-symphony-a-spec-for-orchestrating-codex-agents). OpenAI's own post is at openai.com/index/open-source-codex-orchestration-symphony (returned HTTP 403 when fetched).
- Demo text: agents return "proof of work" including "CI status, PR review feedback, complexity analysis, and walkthrough videos" and "land the PR safely" once accepted — i.e. the agent does it, not the orchestrator — [repo README](https://github.com/openai/symphony).
- Go port: `junhoyeo/contrabass`, "Go & Charm stack implementation of OpenAI's Symphony", 224 stars, Apache-2.0, last push 2026-07-17 — GitHub API 2026-10-26, [repo](https://github.com/junhoyeo/contrabass).

**Gas Town + Beads** (`gastownhall/gastown`, `gastownhall/beads`)
- Gas Town: 18,560 stars, MIT, Go, last push 2026-10-25, latest release v1.2.1 (2026-06-06), 512 open issues — GitHub API 2026-10-26, [repo](https://github.com/gastownhall/gastown).
- Beads: 28,227 stars, MIT, Go, latest release v1.3.2 (2026-10-24), 1,561 open issues — GitHub API 2026-10-26, [repo](https://github.com/gastownhall/beads). Beads is a "[d]istributed graph issue tracker for AI agents, powered by Dolt"; default embedded Dolt in `.beads/embeddeddolt/`; "`.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth"; CLI `bd ready / create / update --claim / close / prime`; `bd init` writes `AGENTS.md` and installs Claude Code/Codex/Cursor integrations — [Beads README](https://github.com/gastownhall/beads).
- Gas Town roles: Mayor (Claude Code coordinator), Polecats (workers, persistent identity, ephemeral sessions), Witness (per-rig lifecycle manager detecting stuck agents), Deacon (background patrol), Refinery ("per-rig merge queue processor that batches merge requests, runs verification gates, and merges to main"; on failure it bisects), Dogs. "polecats never push directly to main." Runtimes: presets `claude, gemini, codex, kiro, cursor, auggie, amp, opencode, copilot, pi, omp`. Scheduler `max_polecats = -1` by default; limits concurrency to "Prevent API rate limit exhaustion". Prereqs: Git 2.20+, Go 1.26.2+, Beads 0.57.0+, tmux 3.0+, Claude Code CLI, Dolt. Install via `brew install gastown` or Docker Compose — [Gas Town README](https://github.com/gastownhall/gastown).
- Hands-on (DoltHub, 2026-01-15, early version): ~60-minute session cost "about $100 in Claude tokens" (~10x a normal Claude Code session); "After the first PR got merged autonomously, despite the integration tests failing, I quickly closed Gas Town"; none of the four PRs were good; verdict "like riding a wild stallion that needed to be tamed" — [DoltHub blog](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/).
- Author status (August 2026 essay): Gas Town "effectively burned down" after Opus 4.7 because of a "just two more things" tic where the model kept modifying Gas Town itself; he now runs "Wheelhouse", a closed-source harness "built in Emacs, mostly bash, with Beads"; "crons watch, models act" (about 45 scheduled jobs); batched merge queues "got stuck in bisection loops once the queue passed about 100 merge requests", fixed with a "Land Rush" megabatch merge; token burn ~$87k/month API-equivalent on $200 Max accounts; advice: "Build a harness bespoke to your application rather than adopting a reusable framework" — [Yegge, "The Shape of Things to Come", Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/). Secondary: AI Engineer profile says by August 2026 Yegge "had abandoned reusable harness development for Wheelhouse" — [ai.engineer](https://ai.engineer/orgs/gas-town); Latent Space quoting Dan Luu that Yegge "never successfully built anything with Gas Town" (opinion) — [Latent Space](https://www.latent.space/p/ainews-reality-checks-on-ai-news).
- HN opinions (Jan 2026): _ea1k: "It wasted so many tokens" but run was "almost completely hands off"; meowface uninstalled Beads after it confused agents; theshrike79: "'Without oversight' is the key here" — [HN](https://news.ycombinator.com/item?id=46624883). ### Inferences
- Classification by what actually runs unattended: (a) **Run orchestrators** (take a plan/ticket, run agents headless, gate, merge): Symphony (gates delegated to agent), Gas Town, Bernstein, Archon, ralphex, ordewell, Orbi, YYLO, NEEDLE, kodo, no_human, baton, cyrus, Paperclip (generalist, coding optional). ## Key question 2: What does Anthropic ship (late 2026), and is any of it a substitute for a self-hosted orchestrator?

### Takeaway
Anthropic now ships five parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows, Projects) plus cloud scheduled tasks (ex-Routines) and the API-side Managed Agents (beta, with cron "scheduled deployments"). Projects + scheduled tasks cover "walk away, come back to PRs" in Anthropic's cloud for Pro/Max, but with no enforced thread cap, no independent verify gate, no cross-project queue, no retros, and plan-usage drawdown; nothing Anthropic ships is a self-hosted, modifiable orchestrator with a verify/merge pipeline. Headless `claude -p` still bills against the subscription (the June 15, 2026 Agent SDK credit split was paused).

### Cited Findings
- **Five ways to run in parallel**: subagents; agent view (`claude agents`, "Research preview"); agent teams ("Experimental and disabled by default"); dynamic workflows (JS script running "Dozens to hundreds of agents per run"); Projects ("Public beta on Pro and Max"). "In every approach the workers are Claude sessions." Also `/batch` skill ("split one large change into 5 to 30 worktree-isolated subagents") and cross-session messaging — [code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents.md).
- **Agent view**: background sessions "keep running without a terminal attached. A separate supervisor process runs them"; dispatch from shell with `claude --bg "<prompt>"` (rejects `-p`); "Before editing files, Claude moves the session into an isolated git worktree under `.claude/worktrees/`"; `claude agents --json` "is the supported way to read session state from outside Claude Code, for example from ... a scheduler"; "Each session uses your subscription quota independently"; sessions needing permission show as "Needs input" until a human attaches — [agent-view docs](https://code.claude.com/docs/en/agent-view.md).
- **Dynamic workflows**: "A dynamic workflow is a JavaScript script that orchestrates many subagents"; "Up to 16 concurrent agents by default" (env `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 1-256), "1,000 agents total per run"; "No mid-run user input"; available in `claude -p` and the Agent SDK (no approval prompt there; use `Workflow` allow rule); usage-limit pause/resume works only in interactive subscription sessions ("A run doesn't pause in non-interactive mode with `claude -p`"); stalled agents restart up to five times; "If you background your session or exit Claude Code while a workflow run is in progress, the run doesn't continue on its own" — [workflows docs](https://code.claude.com/docs/en/workflows.md).
- **Projects** (cloud): "one ongoing conversation where Claude coordinates a stream of related work"; each thread is a cloud session on its own branch that "opens a pull request when the work calls for one"; threads watch PRs with auto-fix ("pushes fixes when CI fails, addresses review comments"); Overview lanes incl. "Ready for review", "Landing"; project memory (`MEMORY.md`) and instructions (16,000 chars) carry across threads; "There's no fixed number; Claude starts as many as the work calls for, and a limit you ask for is a preference rather than a cap. The enforced limit is 200 new threads per day"; "A thread that reaches your plan's limit waits and continues on its own when the limit resets"; "Projects aren't offered on Team or Enterprise plans yet"; local threads via `claude remote-control --spawn worktree` — [claude-projects docs](https://code.claude.com/docs/en/claude-projects.md).
- **Cloud scheduled tasks (formerly Routines)**: "in research preview"; triggers = schedule (cron, "Expressions that run more often than once per hour are rejected"), API (`POST .../routines/<id>/fire`, beta header `experimental-cc-routine-2026-04-01`), GitHub events (PR/release/issue with filters); run "on Anthropic-managed cloud infrastructure, or on your organization's self-hosted environment"; "Scheduled tasks run autonomously as full Claude Code cloud sessions" in auto mode; "Scheduled tasks draw down subscription usage the same way interactive sessions do"; limits "100 per hour" scheduled runs per account; Pro/Max/Team/Enterprise; outcome rows "say how the session ended, not whether Claude completed the work" — [routines docs](https://code.claude.com/docs/en/routines.md). Third-party reporting of a research-preview start on 2026-04-14 and "$0.08 per routine runtime hour" figures conflicted across blogs and are not in the official doc — [mindstudio](https://www.mindstudio.ai/blog/claude-code-routines-scheduled-agents); [developersdigest](https://www.developersdigest.tech/blog/claude-code-routines-vs-managed-agents-schedules) (unverified).
- **Managed Agents** (API): "Pre-built, configurable agent harness that runs in managed infrastructure. Best for long-running tasks and asynchronous work"; status beta (`managed-agents-2026-04-01` header, "enabled by default for all API accounts"); concepts Agent/Environment (cloud sandbox or self-hosted sandbox)/Session/Events; "Scheduled execution: Recurring agent runs on a cron schedule through scheduled deployments"; tools: bash, file ops, web, MCP; not ZDR/HIPAA eligible; "dreaming" in limited research preview — [Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview). Third-party blogs cite "$0.08 per session-hour" plus token rates and a public beta launch of 2026-04-08 — [TrueFoundry](https://www.truefoundry.com/blog/claude-managed-agents-pricing) (unverified against Anthropic pricing page).
- **Billing for headless `claude -p` on subscriptions**: Anthropic announced (May 2026) moving Agent SDK / `claude -p` / third-party usage to a separate monthly credit ($20 Pro to $200 top Max) from June 15, 2026, then paused it; the support article says such usage "still count[s] against subscription usage limits ... for now" and "Anthropic is working on an updated plan and will announce changes before they take effect" — [support.claude.com article 15036540](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan); [The New Stack, 2026-06-16](https://thenewstack.io/anthropic-pauses-claude-agent-sdk-subscription-change/). ralphex's README still carries a warning about the June 15 change — [ralphex](https://github.com/umputun/ralphex).
- **Agent SDK / GitHub Action**: `anthropics/claude-code-action` 9,651 stars, MIT, last push 2026-10-24 — GitHub API 2026-10-26, [repo](https://github.com/anthropics/claude-code-action).

### Inferences
- Projects is the nearest Anthropic analogue to the person's harness (fan-out threads, per-thread PRs, auto-fix CI, project memory) but it runs in Anthropic's cloud, has only soft concurrency limits, offers no independent evidence-based verify step, no cross-project queue, no systemd-style memory caps, and no retro mechanism beyond memory notes. It is also account-bound ("belong to your individual claude.ai account").
- Dynamic workflows are the most "harness-like" local primitive (scripted orchestration, resumable, stall restarts, concurrency cap) but a run dies with the session and does not auto-wait for usage limits under `-p`, so an external supervisor (like the person's bash harness) is still needed for overnight runs.
- Managed Agents is an API-billed hosted harness for building your own orchestrator on top of, not a substitute for one.
- The paused June-15 billing split is the single biggest external risk to a `claude -p`-based harness on a Max plan; Anthropic says changes will be announced before taking effect.

### Gaps
- No official Anthropic pricing numbers for scheduled-task runtime or Managed Agents session-hours were retrieved from Anthropic pages (only third-party blogs).
- Agent teams and Desktop scheduled tasks docs were not fetched.
- "FleetView" appears only as an internal agent-picker name in this session's tool list; no public Anthropic doc was found for a product by that name.

## Key question 3: Which can run unattended overnight with verification and merging (not just spawn sessions)?

### Takeaway
By their own documentation: Gas Town (Refinery merge queue with verification gates and bisection), Bernstein (Janitor + merge to main), Archon (test loops + merge queue checking review verdict and CI), Orbi (independent review session + merge gate, systemd timer), ralphex (validation commands per task, multi-agent review, commits; rebase-only finalize, no merge), ordewell (evidence-based completion, integration branch, human merges), Agent Orchestrator (CI/review loop until PR approved, human merges), Paperclip (budgets + approvals; merge not core), Claude Projects (cloud: PR + auto-fix CI; human merges unless told otherwise). Symphony explicitly performs no verification or merge itself.

### Cited Findings
- Symphony: "The orchestrator performs no verification or merge step. It defines no test or review gates." Success "often means reaching a handoff state such as `Human Review`"; scheduler state is in-memory and retry timers are lost on restart — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md).
- Gas Town: Refinery "batches merge requests, runs verification gates, and merges to main"; failing batches bisect; "polecats never push directly to main" — [README](https://github.com/gastownhall/gastown). But in practice (Jan 2026) it "merged autonomously, despite the integration tests failing" — [DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/); and Yegge's own merge queue "got stuck in bisection loops once the queue passed about 100" — [Yegge Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/).
- Bernstein: Janitor verifies tests/lint/types/files; "Verified work lands in main"; failed tasks "get retried or routed to a different model"; `retry.max_attempts` per node — [README](https://github.com/sipyourdrink-ltd/bernstein).
- Archon: "Queues take work forward on their own. A run pauses only when it reaches a decision it can't make"; merge queue "checks the review verdict and CI status at the head commit, and confirms the base branch isn't failing"; "The pack binds no triggers by default" — [README](https://github.com/coleam00/Archon).
- Orbi: tick "every 5 minutes" via systemd/launchd; "AI never merges or pushes protected branches ... only the reviewed head can merge"; unrecoverable failures -> `ai-blocked` label — [README](https://github.com/orbi-build/orbi).
- ralphex: per-task validation + commit, 5-agent review, optional codex external review, "Finalize (optional, off by default) ... by default rebases commits onto the default branch"; `--wait` pauses on rate limits — [README](https://github.com/umputun/ralphex).
- ordewell: "Passing work lands on one integration branch in plan order, and you choose when to merge it" — [README](https://github.com/ordewell/ordewell).
- Agent Orchestrator: "Failed checks, review comments, and merge conflicts go back to the worker ... until the PR is approved"; lanes "Ready to merge"; Augment: agents "sit idle for long stretches waiting on tool approval" — [README](https://github.com/OrchestratorInc/agent-orchestrator); [Augment](https://www.augmentcode.com/tools/open-source-agent-orchestrators).
- ccswarm: `auto --watch` "unattended: no y/n, auto-commit + PR" but acceptance "only compares the number of successful approvals with quorum" — [README](https://github.com/nwiizo/ccswarm).
- Claude Projects: thread "watches the pull request with auto-fix ... pushes fixes when CI fails"; sample instruction "Don't merge, force-push, or change CI configuration without asking me"; **Merge it** button sends the instruction to the thread — [docs](https://code.claude.com/docs/en/claude-projects.md).
- Usage-limit handling: Projects threads "wait and continue ... when the limit resets" (cloud); dynamic workflows wait only in interactive subscription sessions, not under `claude -p` — [projects](https://code.claude.com/docs/en/claude-projects.md); [workflows](https://code.claude.com/docs/en/workflows.md). Symphony has no rate-limit backoff policy — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md). ralphex pattern-matches rate limits and `--wait`s — [ralphex](https://github.com/umputun/ralphex).
- Memory/resource caps: none of the fetched READMEs (Symphony, Gas Town, Bernstein, Archon, ralphex, ordewell, Orbi, Paperclip, Multica) describe per-session RAM caps or systemd scopes (absence noted across all fetched pages above).
- Cross-project queue: Archon has queues; Paperclip lists "Work Queues" as planned; Gas Town has multi-rig scheduling; Bernstein's `autopilot` "refuses to run until a `TaskSource` is implemented" — [Archon](https://github.com/coleam00/Archon); [Paperclip](https://github.com/paperclipai/paperclip); [Bernstein](https://github.com/sipyourdrink-ltd/bernstein).

### Inferences
- The only FOSS tools with an *independent* verification step comparable to the person's "verify session with evidence rows" are Bernstein's Janitor (deterministic checks, not an LLM judge), Orbi's "independent review session", ralphex's review agents, kodo ("a separate agent verifies each result"), and no_human ("a second model checking each diff"). None document evidence tables.
- Overnight unattended merging to main without a human is documented only by Gas Town, Bernstein, Archon, Orbi; of these, Gas Town has credible negative field reports and Bernstein/Orbi are small solo projects.

### Gaps
- No independent benchmark or field report measuring unattended overnight success rates for any tool; the only hands-on account found is DoltHub's Gas Town session (Jan 2026, early version).
- Did not find any orchestrator documenting systemd-scope memory caps.

## Key question 5: Top candidates — concrete trade-offs of adopting vs keeping the bash harness

### Takeaway
Candidates that could plausibly host the person's verify/merge/queue logic: (1) Archon, (2) Bernstein, (3) ralphex, (4) Symphony-the-spec (write your own), (5) Claude Projects/scheduled tasks (cloud). Each would require porting or losing at least two of: evidence-row verify, cross-project queue, systemd memory caps, usage-limit handling, retros. The strongest argument for keeping the bash harness is that the one large comparable system (Gas Town) was abandoned by its author in favour of a bespoke bash+Beads harness with the same shape.

### Cited Findings (per candidate, with trade-offs)

**1. Archon (`coleam00/Archon`, MIT, TypeScript/Bun, 23.8k stars, active)**
- Fit: YAML workflow graphs with bash nodes, test loops, human waits, worktree-per-run, merge queue with CI + review verdict, queues that "take work forward on their own", drives Claude Code/Codex/Pi — [README](https://github.com/coleam00/Archon).
- Trade-offs: Bun/TypeScript runtime vs bash; dev happens on a `dev` branch with 163 open issues; learning/retro absent; merge-queue semantics are Archon's, so the person's PR-per-milestone flow and evidence rows would be reimplemented as workflow nodes; no documented usage-limit wait or memory caps — [README](https://github.com/coleam00/Archon).

**2. Bernstein (`sipyourdrink-ltd/bernstein`, Apache-2.0, Python 3.12+, 1.3k stars, beta, solo-maintained)**
- Fit: deterministic scheduler (no LLM in the loop), worktree per task, Janitor verify, merge to main, retries/route-to-other-model, replay journal and signed receipts, 54 adapters — [README](https://github.com/sipyourdrink-ltd/bernstein).
- Trade-offs: "Solo-maintained", "minor versions may change interfaces", `autopilot` not runnable without a TaskSource, cost controls "reactive", large fan-outs "bottleneck on one host by default", no memory/retros — [README](https://github.com/sipyourdrink-ltd/bernstein); [Augment](https://www.augmentcode.com/tools/open-source-agent-orchestrators). Its planning model (one LLM call -> task graph) differs from the person's initializer-session milestones.

**3. ralphex (`umputun/ralphex`, MIT, Go, 1.5k stars, active, single maintainer)**
- Fit: closest execution model to the harness — "Each task executes in a fresh Claude Code session" via `claude --print`, validation after each task, commit per task, worktree mode, multi-agent review phases, codex cross-review, rate-limit `--wait`, Telegram/Slack notifications, Docker wrapper — [README](https://github.com/umputun/ralphex).
- Trade-offs: one plan at a time (no cross-project queue), finalize only rebases (no PR merge), review is LLM-based without evidence tables, runs `--dangerously-skip-permissions`, no retros, Go codebase to modify — [README](https://github.com/umputun/ralphex).

**4. Symphony as a spec (`openai/symphony`, Apache-2.0)**
- Fit: a well-specified polling/workspace/concurrency/retry/backoff design the person could implement in bash; the README invites ports — [README](https://github.com/openai/symphony); [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md).
- Trade-offs: Codex app-server protocol (not Claude Code), Linear-centric, no verify/merge, in-memory state, no cost limits, OpenAI "does not plan to maintain" it — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md); [Help Net Security](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/).

**5. Anthropic Projects + cloud scheduled tasks (proprietary, included in Pro/Max)**
- Fit: parallel cloud threads with PRs and CI auto-fix, project memory, waits through usage limits, runs with laptop closed; scheduled tasks on cron/API/GitHub triggers; self-hosted environments possible for orgs — [projects](https://code.claude.com/docs/en/claude-projects.md); [routines](https://code.claude.com/docs/en/routines.md).
- Trade-offs: cloud, not self-hosted (for individuals); thread limits are "a preference rather than a cap"; "uses your limits faster"; no independent verify gate; no cross-project queue beyond one project; no retros; Team/Enterprise not yet supported; research preview/beta — [projects](https://code.claude.com/docs/en/claude-projects.md).

**Gas Town (not recommended as a base)**
- 18.6k stars but 512 open issues, last release June 2026; author moved to a private bash+Beads harness after Opus 4.7; field report of ~10x token cost and merging despite failing tests — [GitHub API 2026-10-26](https://github.com/gastownhall/gastown); [Yegge Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/); [DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/). Beads itself (28k stars, v1.3.2 2026-10-24) remains a reasonable optional task/memory store — [Beads](https://github.com/gastownhall/beads).

**Yegge's own conclusion on bespoke vs reusable**
- "Build a harness bespoke to your application rather than adopting a reusable framework"; harnesses should be "chemically bonded in"; Wheelhouse is "mostly bash, with Beads" and ~45 cron jobs on the principle "crons watch, models act" — [Yegge Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/).

### Inferences
- Feature-by-feature, the person's harness already has: spec -> milestones (ordewell/Bernstein/Archon have planners; none produce milestone-scoped PRs), fresh `claude -p` per feature in a worktree (ralphex, ordewell, Projects), test suite run (ralphex, Bernstein, Archon), independent verify with evidence rows (closest: Orbi, kodo, no_human; none with evidence tables), PR merge of verified milestones (Archon, Orbi, Gas Town merge to main; others stop at PR/integration branch), usage-limit handling (Projects cloud, ralphex `--wait`; absent elsewhere), memory caps (none), cross-project queue (Archon queues; Paperclip planned), retros/debrief (none), parallel lanes (all the DAG tools: Bernstein, Archon, ordewell).
- Adoption cost is dominated by re-expressing verify/merge/queue logic in another runtime (Bun, Python, Go, Elixir) and inheriting that project's bus factor (Bernstein, ralphex, Orbi, ordewell are one-person or small teams). The cheapest "borrow" is design, not code: Symphony's SPEC fields (concurrency per state, stall timeout, exponential backoff), Archon's merge-queue checks (review verdict + CI at head + base not failing), Bernstein's deterministic no-LLM scheduler and signed run receipts, Orbi's "only the reviewed head can merge" rule, and Claude Projects' `MEMORY.md` + corrections pattern.
- The main external dependency risk for the bash harness is Anthropic subscription billing for `claude -p` (paused change), not the orchestrator layer.

### Gaps
- No source compares these tools on a shared workload; all fit assessments are from READMEs.
- Modifiability of Archon/Bernstein internals (code quality, test coverage) was not inspected beyond README claims.
