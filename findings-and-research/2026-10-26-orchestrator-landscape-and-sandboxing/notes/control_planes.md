# Control planes for autonomous coding-agent runs (state as of 2026-10-26)

Scope note: "control plane" here means the human-facing surface over a set of agent runs: run list, log/transcript view, a way to answer a blocked agent, queue/park/continue, settings such as parallelism. The person's own harness already has: `harness status` CLI, `INBOX.md` per run, ntfy push, a tmux window per run, and an optional `claude --remote-control` "desk". Star counts and version numbers below are what the fetched pages showed on 2026-10-26 unless a date is given; several GitHub pages showed no release date, so "latest release" is often a gap. Where a source is a vendor or a third-party blog that is flagged.

## Key question 1: Which FOSS (and proprietary) projects provide this, and what does each actually provide?

### Takeaway
There is no FOSS project that is a thin control plane over someone else's orchestrator state. Every well-known project (Paperclip, Vibe Kanban, Multica, T3 Code, HumanLayer, OpenHands, Mux) is a full orchestrator that owns the run; the few that can sit over external state are either Gas Town's "Minimal Mode", small read-only JSONL viewers for `~/.claude/projects`, Onako (tmux-window discovery), or Claude Code's own Agent View / Remote Control, which only see sessions Claude Code itself supervises.

- Marketing page: runs local agents in parallel with automatic git worktree creation and setup scripts; review and comment on changes; start dev servers; issues and sub-issues. — [vibekanban.com](https://www.vibekanban.com/)

**OpenAI Symphony — Apache-2.0, Elixir reference implementation, Linear as the UI**
- Released April 28, 2026 as an open-source spec plus reference implementation; treats a Linear board as the control plane, each open task gets a dedicated agent workspace, agents restart on crash/stall, ticket statuses are the state machine; built on Codex App Server; OpenAI-reported "500% increase in landed PRs" for some internal teams (company figure). — [Help Net Security 2026-04-28](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/); [openai.com announcement](https://openai.com/it-IT/index/open-source-codex-orchestration-symphony/)

### Inferences
- The market split in 2026 is: (a) full orchestrator-plus-UI products that want to own the run (Paperclip, Multica, Vibe Kanban, T3 Code, HumanLayer, OpenHands, Paradev, Mux), (b) thin viewers over Claude Code's own session files, and (c) Anthropic's first-party surfaces. None is a drop-in UI over a bash orchestrator's JSON/JSONL and `INBOX.md` files.
- Vibe Kanban's shutdown (free users, no business model) and Agent Inbox's archiving are evidence that standalone free control-plane UIs are hard to sustain; licenses are drifting toward source-available (Multica License, Elastic 2.0 for Paradev).
- Symphony's spec is the closest published design to what the person already has: tracker/state file as the source of truth, an optional loopback dashboard with a JSON API, and an explicit policy for "agent needs input".

## Key question 2: Which can be pointed at an external orchestrator's state (files, JSONL, git branches) versus requiring you to run agents through them?

### Takeaway
Only a handful can observe runs they did not start: Gas Town "Minimal Mode", Onako (discovers foreign tmux windows), the read-only JSONL viewers over `~/.claude/projects`, and Symphony (whose state is the issue tracker). Paperclip can wrap a custom process or HTTP endpoint as an "agent" but it then owns scheduling, heartbeats and budgets. Claude Code's Agent View and Remote Control only see sessions Claude Code supervises, and Anthropic says `~/.claude/jobs/<id>/` is not a stable interface.

### Cited Findings
- Gas Town "Minimal Mode": "you launch runtimes yourself and Gas Town just tracks state" (but it still requires Dolt, Beads and its HQ layout). — [GitHub steveyegge/gastown](https://github.com/steveyegge/gastown)
- Onako discovers tmux windows created outside it as "external" tasks with view/send/kill, and users can `tmux move-window` existing windows into its session. — [PyPI onako](https://pypi.org/project/onako/)
- Read-only JSONL viewers over `~/.claude/projects`: Stargx/claude-code-dashboard (chokidar file watch, Express API, single-HTML React via CDN, 2 production dependencies, frontend polls every 2 s, no WebSockets, no build step, MIT, 16 stars, 4 commits, read-only); dlupiak/claude-session-dashboard (`npx`, read-only, delegation timeline, token use); delexw/claude-code-trace (live tail, desktop/web/TUI); hoangsonww Claude-Code-Agent-Monitor (SQLite, covers Claude Code, Cursor, Codex). — [GitHub Stargx/claude-code-dashboard](https://github.com/Stargx/claude-code-dashboard); [GitHub dlupiak/claude-session-dashboard](https://github.com/dlupiak/claude-session-dashboard); [GitHub delexw/claude-code-trace](https://github.com/delexw/claude-code-trace); [Claude-Code-Agent-Monitor](https://hoangsonww.github.io/Claude-Code-Agent-Monitor/)

### Inferences
- For the person's harness, the only adoptable "over external state" pieces are: Onako's tmux-window discovery model (small, MIT, Python), the JSONL-tail pattern of Stargx's dashboard, and the git-heartbeat pattern. All are read-only or tmux-send only; none understands an `INBOX.md` question/answer protocol or a project queue.
- Backlog.md could serve as a queue/board file format (Markdown in git, web UI, MCP) if the harness wrote its queue as Backlog tasks, but it adds no run supervision.
- If the orchestrator launched each run as `claude remote-control --name <run>` (server mode) or `claude --rc`, the claude.ai/code session list and the Claude app become a free run list + transcript + question-answering surface with push, at the cost of subscription-auth only (no API key, no gateway) and no view of non-Claude steps (bash phases, queue, park/continue, parallelism).

### Gaps

## Key question 3: What human-in-the-loop patterns do they use for "the agent is blocked, answer this", and which work well on a phone?

### Takeaway
Four patterns recur: (1) an inbox/interrupt object with fixed responses (accept/edit/respond/ignore), (2) the issue tracker or PR as the conversation (state changes and comments), (3) chat-style steering of the live session from a phone app, and (4) push notifications with action buttons. For a phone, the Claude app with Remote Control (questions and permission prompts stay open until answered, pushes on "actions required") and ntfy's `http` action buttons (up to three, POST with body) are the lightest working options; most FOSS boards only offer a mobile web UI or an unreleased native app.

### Cited Findings
- Interrupt/inbox: Agent Inbox exposes accept / edit / respond / ignore per interrupt with per-interrupt config; LangGraph `interrupt` persists state and resumes with a value. — [GitHub langchain-ai/agent-inbox](https://github.com/langchain-ai/agent-inbox); [LangChain changelog](https://changelog.langchain.com/announcements/interrupt-simplifying-human-in-the-loop-agents)
- Multica: Inbox notifies when an agent "needs a call"; reply to a running agent; agents can raise blockers; Slack/Telegram etc. channels; Expo iPhone/iPad app built from source. — [GitHub multica-ai/multica](https://github.com/multica-ai/multica)
- Paperclip: configurable review/approval stages, pause/reassign/stop, gateway actions "Allowed / Ask first / Off", issues carry inbox state; "Mobile Ready" web UI; Tailscale bind. — [GitHub paperclipai/paperclip](https://github.com/paperclipai/paperclip)
- Tracker-as-conversation: Symphony leaves user-input handling to implementation policy (fail, surface to operator, approved channel, auto-resolve) and lets operators intervene by moving the issue's tracker state; agents comment on tickets via tracker tools. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Vibe Kanban: inline diff comments and "send feedback to the agent"; GitHub PR review for merge. — [GitHub BloopAI/vibe-kanban](https://github.com/BloopAI/vibe-kanban)
- Cursor: steer via Slack, GitHub/Bitbucket comments, Linear, web, iOS app, Android PWA. Devin: responds in Slack threads with "updates and questions". — [cursor.com/docs/cloud-agent](https://cursor.com/docs/cloud-agent); [docs.devin.ai](https://docs.devin.ai/fr/integrations/slack)
- Claude Code Remote Control from the phone: "Claude Code keeps permission prompts and `AskUserQuestion` questions open until you answer them"; push notification "when it needs a decision from you"; `/config` "Push when actions required"; attach photos/files from the phone; Bypass permissions cannot be chosen from the app. — [code.claude.com remote-control](https://code.claude.com/docs/en/remote-control); [code.claude.com mobile](https://code.claude.com/docs/en/mobile)
- Claude Code Channels: ask Claude via Telegram, Discord or iMessage while work runs on your machine. — [code.claude.com mobile](https://code.claude.com/docs/en/mobile)
- Agent View (terminal only): `Needs input` rows for "a question, permission decision, sandbox prompt, or MCP input request"; peek shows the exact question and "waiting 3m"; replies to questions can be typed in the peek panel, but permission/sandbox prompts require attaching; `Notification` hook fires `agent_needs_input`. — [code.claude.com agent-view](https://code.claude.com/docs/en/agent-view)
- Paradev: "working indicators, completion chimes, and dock badges show when an agent needs attention"; inline tool approvals and plan review in built-in chat; iPhone/iPad requires Pro. Nimbalyst: native iOS app to "review, resume, and monitor sessions" (vendor claim). T3 Code: iOS and Android apps. — [superset](https://github.com/superset-sh/superset); [Nimbalyst](https://nimbalyst.com/blog/best-agent-management-tools-2026/); [t3code](https://github.com/pingdotgg/t3code)
- ntfy action buttons: `view` (open URL), `http` ("By default, this action sends a POST request (not GET!)" with optional `body`, `method`, `headers`, `clear`), `broadcast` (Android only); "up to three user actions" per notification; priority 1–5 via `X-Priority`; tags/emoji. ntfy is dual-licensed Apache-2.0 / GPLv2, self-hostable, with open-source Android (Play, F-Droid) and iOS (App Store) apps; 35.1k stars. — [docs.ntfy.sh/publish](https://docs.ntfy.sh/publish/); [GitHub binwiederhier/ntfy](https://github.com/binwiederhier/ntfy)
- Onako: tasks started from an iOS Shortcut or the mobile-friendly dashboard; send messages to a tmux window. — [PyPI onako](https://pypi.org/project/onako/)
- Artem Zhutov (2026-03-16, blog): Obsidian Base dashboard grouping session files by status (blocked, done, in-progress, review); he adds comments on the dashboard and an orchestrator agent relays them to the right worker via cmux `send`. — [artemxtech substack](https://artemxtech.substack.com/p/how-i-manage-10-claude-code-agents)
- Addy Osmani (2026-03-26, talk): check progress every 5–10 minutes, keep WIP to 3–5 agents, kill criteria for agents stuck on the same error for 3+ iterations; "human review isn't optional overhead"; plan approval before code. — [addyosmani.com](https://addyosmani.com/blog/code-agent-orchestra/)

### Inferences
- The person's `INBOX.md` + ntfy design is the same shape as Symphony's "surface the request to an operator via an approved channel" and Agent Inbox's "respond" action; what it lacks on the phone is a one-tap answer. ntfy `http` actions can close that gap for yes/no or pick-one questions (three buttons max, POST with a body to a small endpoint), while free-text answers need a web page or the Claude app.
- Among phone-native options, only the Claude app (Remote Control) is both free-with-subscription and able to answer a blocking `AskUserQuestion`; the FOSS boards either need a tunnel/Tailscale to a responsive web UI (Paperclip, Multica, Gas Town/City read-only) or an app that is Pro-gated or unreleased.

### Gaps
- No source measured how well any of these work on a phone; "mobile-friendly" claims are vendor statements.
- Multica's Inbox reply semantics (does the reply reach the agent mid-turn or at next heartbeat?) not found.

## Key question 4: Realistic effort of building a minimal control plane versus adopting one; precedents of individuals doing exactly that

### Takeaway
Several individuals built exactly this in 2026 as single-person, dependency-light projects (Onako: 94 kB Python over tmux + SQLite, 17 releases in three weeks; Stargx dashboard: Express + chokidar + one HTML file, 2 dependencies; a zero-dependency git-heartbeat board; an Obsidian Bases dashboard). None of the sources states hours spent. Adopting a full orchestrator (Paperclip, Multica, Gas Town) means re-hosting runs inside it and taking on Postgres/Dolt/daemons; adopting a viewer gives read-only state with no answer/park/queue controls.

### Cited Findings
- Stargx/claude-code-dashboard: Node backend (Express, chokidar) watching `~/.claude/projects/` JSONL, single-HTML React frontend via CDN, polls every 2 s, no WebSockets, no build step, "2 production dependencies", 4 commits, MIT; read-only. — [GitHub Stargx/claude-code-dashboard](https://github.com/Stargx/claude-code-dashboard)
- Onako: Python ≥3.10 + tmux + SQLite, 94 kB, MIT, single maintainer, v0.6.1 on Feb 19, 2026 after first release Jan 31, 2026; spawns Claude Code in tmux, discovers external windows, mobile web dashboard, iOS Shortcut dispatch, Tailscale for remote. — [PyPI onako](https://pypi.org/project/onako/)
- Git-heartbeat board (2026-07-11): collector + zero-dependency local server, git as the only backend, scheduled every minute via launchd/cron; the guide supplies a prompt to have Claude Code build it; read-only. — [aiwithamirthan guide](https://aiwithamirthan.com/guides/a-dashboard-for-every-agent-you-run/)
- Artem Zhutov (2026-03-16): session file per workspace + Obsidian Base query as dashboard; orchestrator agent relays comments; provides a "cmux skill + orchestrator setup" download; effort not stated. — [artemxtech substack](https://artemxtech.substack.com/p/how-i-manage-10-claude-code-agents)
- lbacik/agent-dashboard (status "specified, not yet built" per README, 178 commits, 0 stars): Python, polls containers via `docker exec agentctl telemetry --json`, five controls (`stop`, `stop --after N`, `resume`, `handoff now`, `next issue <n>`) each with review-and-confirm, append-only `control-audit.jsonl`, read-only mode auto-enabled on non-loopback binds; an issue describes SSE `GET /stream` with htmx swapping table content and auto-reconnect. — [GitHub lbacik/agent-dashboard](https://github.com/lbacik/agent-dashboard); [issue #3](https://github.com/lbacik/agent-dashboard/issues/3)
- Gas City's dashboard security model for a tiny server: loopback bind by default, CSRF header on mutations, read-only unless `allow_mutations` when bound elsewhere. — [docs.gascity.com dashboard](https://docs.gascity.com/getting-started/dashboard)
- Symphony's spec: a status surface is optional and "must not be required for correctness"; loopback HTTP with `GET /api/v1/state` and a human-readable `/`; rich web UI a non-goal. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Addy Osmani: three shell aliases, "roughly 12 lines of bash", as the DIY alternative to Conductor's worktree management; recommends starting simple and adopting tools as needs grow. — [addyosmani.com](https://addyosmani.com/blog/code-agent-orchestra/)
- Vendor comparison lists "tmux + session-manager scripts" as a legitimate DIY pattern: "scripted panes; worktree creation; session resume; branch tracking. Your team maintains it." — [Nimbalyst comparison](https://nimbalyst.com/blog/best-agent-management-tools-2026/)
- Adoption cost markers: Paperclip needs Node ≥24.11 and Postgres (embedded locally); Multica needs Postgres 17 + Go backend + daemon and has a non-OSI license; Gas Town needs Dolt, Beads, tmux and a Gas Town HQ layout; Gas City dashboard is read-only off-loopback by default; T3 Code is "very very early"; Paradev is macOS-first with Linux experimental; OpenHands brings its own agent server and Docker runtime. — [paperclip](https://github.com/paperclipai/paperclip); [multica](https://github.com/multica-ai/multica); [gastown](https://github.com/steveyegge/gastown); [gascity dashboard](https://docs.gascity.com/getting-started/dashboard); [t3code](https://github.com/pingdotgg/t3code); [superset](https://github.com/superset-sh/superset); [OpenHands](https://github.com/OpenHands/OpenHands)
- Project longevity signals: Vibe Kanban company shut down 2026-04-10; Agent Inbox archived 2026-09-20; Opcode "no longer actively developed". — [vibekanban shutdown](https://vibekanban.com/blog/shutdown); [agent-inbox](https://github.com/langchain-ai/agent-inbox); [Nimbalyst comparison](https://nimbalyst.com/blog/best-agent-management-tools-2026/)

### Inferences
- Evidence-based build-vs-buy: the person's requirements (run list over existing JSON/JSONL, INBOX answer, park/continue, queue in/out, parallelism setting, phone-usable) map to one static page + SSE or 2-second polling + four or five POST endpoints. The closest precedents (Onako, Stargx, git-heartbeat board) are each under ~100 kB and one person's work over days to weeks, and all stop short of write controls; the control side is a thin wrapper around commands the harness CLI already exposes (`harness status`, answering `INBOX.md`, queue files).
- The pieces worth copying rather than adopting: Gas City/Symphony/lbacik's loopback-by-default + read-only-off-loopback + confirm-then-append-audit pattern; Agent View's state vocabulary (`working`/`blocked`/`done`/`failed`/`stopped`, `waitingFor`); ntfy `http` action buttons for one-tap answers; Tailscale or an SSH tunnel for phone access (what Paperclip and Onako recommend).
- Adopting a full orchestrator UI would mean moving run ownership (tmux, worktrees, merges) into Paperclip/Multica/Gas Town; the person would lose their existing bash harness or run two schedulers. Adopting a viewer only duplicates `harness status`.
- Risk on the "buy FOSS" side is maintenance: two of the named projects died or were archived within 2026.

### Gaps
- No source gives hours or days of effort for any of the DIY dashboards; the size and dependency counts are the only proxies.
- No precedent was found that combines an `INBOX.md`-style question file with a web answer form; the DIY precedents are read-only or tmux-send.
- lbacik/agent-dashboard README says "specified, not yet built", so its control design is a spec, not proven software.

## Key question 5: For "buy": are there free tiers of hosted control planes that work with a self-hosted runner?

### Takeaway
The only hosted control plane that is free with an existing subscription and drives a runner on the person's own Linux server is Anthropic's claude.ai/code + Claude app via Remote Control (server mode supports 32 concurrent sessions by default), but it only shows Claude Code sessions, needs claude.ai subscription auth (no API key, no gateway), and has no queue/park/parallelism controls. HumanLayer Cloud has a free Starter tier (3 members, 200 sessions/month) with local daemons; Cursor supports self-hosted machines but not on Free/Plus; Codex Cloud has no self-hosted runner; Paperclip, Gas Town/City and Vibe Kanban have no hosted tier (Vibe Kanban's was shut down).

- Claude Code Projects (cloud) coordinate parallel cloud threads and report "which need you"; self-hosted environments for cloud sessions are Team/Enterprise only. — [code.claude.com mobile](https://code.claude.com/docs/en/mobile); [code.claude.com remote-control](https://code.claude.com/docs/en/remote-control)

This only works if the harness authenticates with claude.ai login rather than an API key or gateway.
- No hosted free tier was found that ingests arbitrary orchestrator state; every hosted option requires its own daemon or agent CLI on the runner.

### Gaps
- Multica managed-cloud pricing and OpenHands Cloud free credits were not located.

- Whether Claude Code's `claude remote-control` server mode is compatible with sessions the person's harness runs as `claude -p` (headless) is not stated in the docs read; the docs say `--bg` cannot combine with `-p`, and Remote Control is described for interactive or server-mode sessions.
