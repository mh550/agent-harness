# Agent memory by type and scope: current practice (as of 2026-10-26) for a git-file coding orchestrator and a LiveKit/SQLite voice agent

Scope note: Research done 2026-10-26 with ~17 web calls. Primary sources (vendor docs, arXiv) are preferred; third-party blogs are flagged as such. Older material (pre-2025) is marked "(older)". The person's own design (CoALA buckets x session/lane/run/project/orchestrator/user scopes, one writer kind per store, append-only episodic, in-place semantic with dated line, PR-reviewed procedural, derived working memory with a per-role byte budget) is referred to below as "the proposed model".

## KQ1. How CoALA's working/episodic/semantic/procedural buckets are used in 2025-2026 systems, and which use explicit scopes, single-writer, or append-only vs in-place rules

### Takeaway
The four CoALA buckets are the de facto vocabulary (LangMem, Mem-alpha, Hindsight, and most commentary use them or close variants), but production systems organise storage by *scope and writer* more than by bucket: Claude Code splits memory by who writes it (human CLAUDE.md vs Claude-written auto memory) and by scope (managed/user/project/local, per-repo); mem0 scopes by `user_id/agent_id/app_id/run_id`; Zep by user graph vs group graph; LangMem by namespace tuples. Explicit "append-only vs edit-in-place" rules exist in practice (Claude Code auto memory `type` field + `modified` stamp; mem0 "additive" adds with explicit update/delete; Hindsight "mark invalid, never delete"; memd's append-only `mistakes.md` vs rewritten `state.md`), so the proposed model is consistent with the field, and ahead of most of it in making the rules explicit per store.

### Cited Findings

**CoALA itself (older: v1 Sep 2023, v3/TMLR camera-ready 15 Mar 2024)**
- Working memory "maintains active and readily available information as symbolic variables" for the current decision cycle; episodic memory stores "experience from earlier decision cycles"; semantic memory stores "knowledge about the world and itself", including knowledge produced by LLM reasoning; procedural memory has implicit (weights) and explicit (agent code, prompts, decision procedures) forms — [CoALA v3 HTML](https://arxiv.org/html/2309.02427v3); [abstract/versions](https://arxiv.org/abs/2309.02427)
- Learning actions: write experiences to episodic; reason over raw experience and store inferences as semantic (Reflexion cited); update weights/prompt templates/code for procedural. The paper warns writing to procedural memory is "significantly riskier than writing to episodic or semantic memory" because it can introduce bugs or let the agent subvert designers' intentions — [CoALA v3](https://arxiv.org/html/2309.02427v3). (This is the direct precedent for "procedural stores reviewed via PR".)
- CoALA does not use the word "derived" for working memory; it just describes it as active variables that persist across LLM calls within a cycle — [CoALA v3](https://arxiv.org/html/2309.02427v3)

**Anthropic: memory tool, context editing, context engineering (Sep 2025 onward)**
- Memory tool (`memory_20250818`) is file-based and client-side: Claude issues `view/create/str_replace/insert/delete/rename` against a `/memories` prefix that "your handler maps onto real storage, such as a per-user directory or keys in a database"; available on Claude 4+ models — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The API auto-injects a system prompt: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE ... ASSUME INTERRUPTION: Your context window might be reset at any moment"; the tool description tells Claude to keep the directory organised, and the docs suggest adding "Only write down information relevant to <topic>" to constrain what is stored — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Security/hygiene guidance: cap file sizes, cap `view` output and page with `view_range`, "periodically delete memory files that haven't been accessed in a long time", strip sensitive data before write, path-traversal validation — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- "Multisession software development pattern": an initializer session sets up a progress log, a feature checklist and a startup-script reference; each later session reads them first and updates the progress log at end; mark features complete only after end-to-end verification — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) (This is a published episodic/progress-log convention with one writer: the session that did the work.)
- Memory tool + context editing launched in public beta 29 Sep 2025; Anthropic reports memory tool + context editing improved agentic search performance 39% over baseline and context editing alone cut token use 84% in a 100-turn eval — [Anthropic news: context management](https://www.anthropic.com/news/context-management) (vendor claim)
- Anthropic's "Effective context engineering" (29 Sep 2025) names three techniques for long-horizon work: compaction (summarise and restart; Claude Code keeps architectural decisions, open bugs, implementation details, drops redundant tool output, carries five most recently accessed files), structured note-taking (NOTES.md, to-do lists; "notes outside the context window"), and sub-agent isolation (sub-agents return 1,000-2,000-token summaries). Goal: "the smallest set of high-signal tokens". Hybrid: CLAUDE.md loaded up front, glob/grep for just-in-time retrieval — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Claude Code: CLAUDE.md / rules / AGENTS.md / auto memory (docs current as of Oct 2026)**
- Two systems, both "context, not enforced configuration": CLAUDE.md (written by you; instructions and rules; scope project/user/org; whole file loaded up to 4 MiB) and auto memory (written by Claude; "your preferences, corrections you give Claude, project context Claude can't derive from the code"; scope per repository shared across worktrees; first 200 lines or 25 KB of `MEMORY.md` loaded) — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md scopes: managed policy (`/etc/claude-code/CLAUDE.md` on Linux, or `claudeMd` key in managed settings), user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`), local (`./CLAUDE.local.md`, gitignored). Files up the tree are concatenated root-down; subdirectory files load on demand; `@path` imports; external imports need one-time approval — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md` with YAML `paths:` globs load only when matching files are touched; `~/.claude/rules/` for personal rules; symlinks allowed; per-file on-demand limit 40,000 chars at 200K context — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Auto memory records four typed notes with a `type` frontmatter field: `user` (role, preferences), `feedback` (corrections and confirmed approaches), `project` (ongoing work, deadlines, decisions "Claude can't derive from the code or git history"), `reference` (where to find info outside the project). "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Layout: `~/.claude/projects/<project>/memory/MEMORY.md` (index, one line per memory) plus topic files (`user_role.md`, `feedback_testing.md`); topic files load on demand; machine-local; excluded from `cleanupPeriodDays` sweep. After each write Claude Code measures `MEMORY.md` against the 200-line/25 KB limit and reminds Claude to shorten (one line per entry, move detail to topic files, "merge or drop stale entries"); over the limit the write succeeds but an error tells Claude to rewrite the index — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- When a memory file begins with YAML frontmatter, Claude Code stamps a `modified` ISO 8601 field "so the timestamp shows how current the fact is" — [Claude Code memory docs](https://code.claude.com/docs/en/memory) (a vendor implementation of the "dated line" rule)
- Subagent memory: `memory: user|project|local` frontmatter writes to `~/.claude/agent-memory/<name>/`, `.claude/agent-memory/<name>/` (versioned), or `.claude/agent-memory-local/<name>/`; first 200 lines/25 KB of its `MEMORY.md` injected; subagent "instructed to curate it" when over; docs recommend `project` scope and body text like "Update your agent memory as you discover codepaths, patterns, library locations, and key architectural decisions" — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents.md)
- AGENTS.md is read in place of CLAUDE.md when no CLAUDE.md exists (v2.1.277+), or alongside with the `claude-md-and-agents-md` setting — [Claude Code memory docs](https://code.claude.com/docs/en/memory). The AGENTS.md spec (Agentic AI Foundation / Linux Foundation, 60k+ projects, read by Codex, Cursor, Copilot, Gemini CLI, etc.) is a plain-Markdown "README for agents"; nearest file to the edited file wins; it defines no memory mechanism and says nothing about where agents write learnings — [agents.md](https://agents.md/)
- Related: Claude Code `/doctor prompt-audit` audits CLAUDE.md/rules/skills for conflicts, and `/doctor` "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions" — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

**Letta / MemGPT**
- Memory blocks have `label`, `description` ("the agent uses it to decide how to read and write it"), `value`, and a character `limit` (examples 4,000-6,000); blocks are pinned in context; `read_only: true` prevents agent edits (example: company policies); blocks can be shared across agents via `block_ids`; external `value` writes replace whole content and with concurrent writers "the last write wins", so docs recommend read-only blocks where agents shouldn't write — [Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks)
- Legacy V1 docs: core memory (in-context blocks, agent edits via memory tools, developer edits via API), full message history persisted and retrievable after eviction, archival searched by tool — [Letta stateful agents (V1 legacy)](https://docs.letta.com/guides/agents/memory); [MemGPT architecture](https://docs.letta.com/guides/agents/architectures/memgpt)
- Current docs describe "dreaming" (`/sleeptime` in CLI): background subagents review recent conversations, consolidate lessons and update memory in MemFS, "a git-backed memory filesystem shared across the agent's conversations", triggered after N agent steps or on context compaction, with an optional "agent reviews before applying" second pass — [Letta sleeptime/dreaming](https://docs.letta.com/guides/agents/architectures/sleeptime)
- Letta's own docs do not use the episodic/semantic/procedural labels; those mappings are third-party — [search summary citing docs.letta.com and mcp.directory](https://mcp.directory/blog/mem0-vs-letta-vs-zep-vs-cognee-2026) (third-party)

**mem0**
- Scoping fields: `user_id`, `agent_id`, `app_id`, `run_id`, plus metadata filters (workspace, tenant, feature area); "always scope searches" — [mem0 memory types page](https://docs.mem0.ai/core-concepts/memory-types); [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add)
- Add pipeline is "additive": extraction, dedupe against existing memories, store "without overwriting or deleting existing memories"; corrections require "explicit `update` or `delete` operations"; `infer=False` stores raw payload; `expiration_date` (YYYY-MM-DD) hides memories from search/get_all unless `show_expired` — [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add); [mem0 memory types](https://docs.mem0.ai/core-concepts/memory-types)
- mem0 blog (vendor): recency re-rank boosts recent memories, demotes idle ones; A/B moved the correct memory to rank 1 in 3 of 4 cases — [mem0 memory decay post](https://mem0.ai/blog/memory-decay-for-long-running-agents-how-recency-aware-ranking-fixes-retrieval-staleness)

**LangMem / LangGraph**
- LangMem's launch post maps semantic = facts/knowledge, episodic = past experiences used as few-shot examples, procedural = system behaviour/prompt rules updated by "prompt optimization"; every memory has a namespace, commonly including a user ID, and namespaces can be scoped to app routes, individual users, or shared teams — [LangMem SDK launch (Feb 2025)](https://blog.langchain.com/langmem-sdk-launch)
- Maturity: still pre-1.0, latest release 0.0.30 (Oct 2025) per a third-party summary — [rywalker.com LangMem notes](https://rywalker.com/research/langmem) (third-party)

**Zep / Graphiti**
- Zep builds a knowledge graph per user ("user graph") and lets developers create "group graphs" for shared memory across users; default entity/edge types apply to user graphs only; API reads by `user_id` or `group_id` — [Zep key concepts](https://help.getzep.com); [Zep graph overview](https://help.getzep.com/graph-overview)
- Graphiti: entities with evolving summaries, facts as triplets with validity windows, episodes as raw ingested data that every fact traces back to; contradictions handled by temporal edge invalidation; bi-temporal (occurred vs ingested) — [graphiti-core on PyPI](https://pypi.org/project/graphiti-core)

**Research systems 2025-2026**
- Hindsight (arXiv 2512.12818, 14 Dec 2025; ACL 2026 demo): four logical networks separating world facts, agent experiences, synthesized entity summaries, and evolving beliefs; three operations retain/recall/reflect; reports 39% -> 83.6% on LongMemEval/LoCoMo with a 20B open model vs full-context baseline — [Hindsight arXiv](https://arxiv.org/abs/2512.12818)
- A-MEM (NeurIPS 2025, arXiv 2502.12110): Zettelkasten-style notes with descriptions/keywords/tags, links to related memories, "memory evolution" where new memories update attributes of old ones — [A-Mem NeurIPS page](https://neurips.cc/virtual/2025/poster/119020); [arXiv](https://arxiv.org/html/2502.12110v8)
- Mem-alpha (arXiv 2509.25911, 30 Sep 2025): RL-trained memory construction over "core, episodic, and semantic" components; argues hand-written fixed update rules leave agents unable to decide what to keep; generalises from 30k to 400k tokens — [Mem-alpha arXiv](https://arxiv.org/abs/2509.25911v1)

**OpenAI (consumer)**
- ChatGPT has two switches: "Reference saved memories" (details you explicitly asked it to keep) and "Reference chat history"; manage/delete individually or tell it to forget; deleting a chat does not delete a memory made from it; logs of deleted memories may be kept up to 30 days — [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq); [saved memories](https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work)

**Single-writer / append-only precedents in small tools (all third-party, small projects)**
- memd 0.5.0 (released 2026-10-26, beta): `./.memory/state.md` is present-tense, "stale facts are replaced, not kept"; `decisions.md` entries "must constrain future work"; `mistakes.md` is strictly append-only; overflow moves to `archive/YYYY-MM.md`, never deleted; per-file character budgets (state 10,000; decisions 12,000; todo 10,000; mistakes 22,000); rejects a distill that deletes >60% of a file unless archived; a single "curator" rewrites the files, and agents are told "not to edit the memory files, and to send new facts through `memd note` or the inbox"; wired via Claude Code SessionStart/SessionEnd/PreCompact hooks and a 30-minute sweep for other tools; writes AGENTS.md/CLAUDE.md/GEMINI.md instruction stubs — [memd on PyPI](https://pypi.org/project/memd/)
- xChuCx/agent-memory keeps Markdown as source of truth and "stages durable changes for human review instead of landing silently", scanning secrets/PII before write — [agent-memory on pkg.go.dev](https://pkg.go.dev/github.com/xChuCx/agent-memory)
- repo-memory keeps a decisions folder (context, options, reasoning) and gotchas file, synced via git — [repo-memory MCP](https://glama.ai/mcp/servers/yubinkim444/repo-memory)

### Inferences
- The proposed bucket x scope table is sound and slightly more explicit than any single vendor system. The closest published analogues are: Claude Code's writer split (human-authored CLAUDE.md = procedural; Claude-authored typed auto memory = semantic/episodic with `modified` stamps and a derive-don't-store rule), Hindsight's four networks (facts / experiences / entity summaries / beliefs is roughly semantic / episodic / derived-semantic / derived-semantic), and memd's per-file mutation rules (replace-in-place state, append-only mistakes, archive instead of delete).
- "One writer kind per store" is implemented in the field mostly as *read-only vs writable* (Letta `read_only` blocks; memd curator; agent-memory human review gate) rather than as a per-store writer-kind column. Letta's "last write wins" note on shared blocks is direct evidence of why a single-writer rule matters.
- "Append-only episodic" matches Anthropic's progress-log pattern, mem0's additive adds, and Graphiti's immutable episodes; "semantic edited in place with a dated line" matches Claude Code's `modified` frontmatter and mem0's explicit `update`; "procedural via PR" matches CoALA's risk warning and agent-memory's human-review staging. Nobody found appears to have all three rules written down in one table; that is the gap the proposed model fills.
- "Working memory derived, never stored, with a byte budget per role" matches Anthropic's "smallest set of high-signal tokens", the 1,000-2,000-token sub-agent return budget, Claude Code's 200-line/25 KB index cap and 40,000-char on-demand file cap, Letta's per-block character `limit`, and memd's per-file budgets. Byte budgets per role are thus mainstream, though usually expressed per file/block rather than per role.
- Scope vocabulary in the field is user / agent / app / run (mem0), user / group (Zep), managed / user / project / local (Claude Code), namespace tuples (LangMem). The proposed "session, lane, run, project, orchestrator, user" maps cleanly: run <-> `run_id`/thread; project <-> project/app; orchestrator <-> agent/managed; user <-> user; "lane" has no direct analogue and should be defined in the policy document.

### Gaps
- Letta's current (non-legacy) docs on memory tiers and the MemFS/dreaming model were only partially read; whether Letta documents per-file mutation rules for MemFS is unknown.
- mem0's "memory types" page did not contain a factual/episodic/semantic/procedural taxonomy at fetch time; I could not confirm whether mem0 publishes one elsewhere.
- No source was found that benchmarks "append-only vs edit-in-place" or "single-writer" policies against each other; the evidence is design precedent, not measurement.
- LangMem's current API names (`create_memory_manager`, etc.) were not verified against official docs.

## KQ2. Mechanisms that make future agent sessions respect memory rules (put new memory in the right store), and evidence on what works

### Takeaway
Documented practice combines (1) instruction files that state where each kind of fact goes, (2) typed schemas or frontmatter the tool itself checks after each write, (3) lifecycle hooks that inject the policy at session start, deny or lint writes, and run a distill at session end/pre-compaction, and (4) a human-review or curator gate for durable/procedural stores. Vendors are explicit that instructions alone are "context, not enforced configuration"; enforcement needs hooks or tool-side validation. Quantitative evidence on which mechanism works best is absent; the evidence is vendor design guidance plus the direction of travel (Claude Code added post-write limit checks and typed frontmatter rather than relying on prompts).

### Cited Findings
- Claude Code docs: CLAUDE.md and auto memory are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." Also: "If the instruction is something that must run at a specific point, such as before every commit or after each file edit, write it as a hook instead. Hooks execute as shell commands at fixed lifecycle events and apply regardless of what Claude decides to do." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Hook mechanics: `PreToolUse` can `deny`/`allow`/`ask` and rewrite inputs via `updatedInput`; matchers like `Edit|Write` and `if: "Edit(*.md)"` permission-rule syntax filter by path; `PostToolUse` cannot block but feeds `additionalContext`/`decision: block` + `reason` back to Claude; exit code 2 = blocking error with stderr fed to Claude (exit 1 is not blocking); `SessionStart` injects `additionalContext` (10,000-char cap) and supports `watchPaths`; `PreCompact` can block compaction, `PostCompact` runs side effects; `SessionEnd` has a 1.5 s default budget (raisable to 60 s); `InstructionsLoaded` logs which CLAUDE.md/rules files loaded; hooks live in user, project (committable), local, managed, plugin, skill or subagent frontmatter and merge — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Claude Code's own enforcement of memory hygiene is tool-side, not prompt-side: after each `MEMORY.md` write it measures the file and reminds or errors; it stamps `modified` on frontmatter files; it records a `type` field per memory; `/doctor` proposes trims of derivable content; `/doctor prompt-audit` finds conflicting instructions — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Anthropic memory tool: the API injects the memory protocol into the system prompt automatically; developers constrain content with prompt lines such as "Only write down information relevant to <topic>" and are told to implement size caps, expiry and sensitive-data stripping in the handler — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Letta: `description` on each block is the mechanism that tells the agent "how to read and write it"; `read_only` is the hard gate; shared blocks are "last write wins" — [Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks)
- mem0: scope is enforced by requiring `user_id/agent_id/run_id` on every add/search; corrections are explicit `update`/`delete` calls, not re-adds — [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add)
- Claude Code subagents: docs tell you to write the memory discipline into the subagent body ("check its memory before starting work, and save what it learned afterward"), and auto-enable Read/Write/Edit on the memory dir — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents.md)
- memd: agents are told to read memory before work and "not to edit the memory files"; new facts go through `memd note` or an `inbox/` folder; a curator folds them in under per-file budgets; integration is SessionStart brief injection + SessionEnd/PreCompact `memd sync`; a distill deleting >60% of a file is rejected — [memd on PyPI](https://pypi.org/project/memd/) (third-party, beta)
- xChuCx/agent-memory: durable changes are staged for human review; secrets/PII scanned out before write — [agent-memory](https://pkg.go.dev/github.com/xChuCx/agent-memory) (third-party)
- One gist proposes agents may only initialise/update a `.agents/` context folder when a human explicitly instructs them — [gist](https://gist.github.com/Jakob-98/ebfbe38a4218b9f339d664ef863b6568) (opinion)
- Third-party hook write-ups split the roles: "CLAUDE.md as holding judgment and guidance, with hooks handling deterministic automation and enforcement"; PostToolUse `Edit|Write` lint hooks are the common example — [morphllm hooks examples](https://www.morphllm.com/claude-code-hooks-examples); [israynotarray hooks guide, 31 May 2026](https://israynotarray.com/en/ai/2026/05/31/claude-code-hooks-complete-guide/) (third-party)
- Anthropic's harness guidance: compaction prompts should "maximize recall" first; sub-agents return condensed summaries; "do the simplest thing that works" — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Memory tool multisession pattern: initializer session creates the progress log and feature checklist deliberately "instead of writing them ad hoc as work progresses" — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

### Inferences
- A concrete enforcement stack for a git-file orchestrator, assembled from the documented mechanisms above (each piece is documented; the combination is my synthesis):
  1. **Policy file** (procedural, PR-reviewed): a short table in CLAUDE.md or `.claude/rules/memory.md` listing bucket, scope, path glob, writer kind, mutation rule, and "put X here" examples. Claude Code loads it every session; `.claude/rules/` with `paths:` can make it load only when memory paths are touched.
  2. **Schema**: YAML frontmatter per memory file (`type`, `scope`, `writer`, `modified`, `supersedes`), mirroring Claude Code's `type`/`modified` fields and memd's required frontmatter. A validator script checks required fields, the writer kind against the store, and that episodic files only grow (compare to git HEAD) while procedural files change only on a branch.
  3. **Hooks**: `PreToolUse` on `Edit|Write` with `if: "Edit(memory/**)"`-style filters to deny edits to append-only or PR-only stores from the wrong role (exit 2 or `permissionDecision: deny`); `PostToolUse` to run the validator and return `additionalContext` with the fix; `SessionStart` to inject the policy table and a byte-budgeted "pack" per role; `PreCompact`/`SessionEnd` to distill the session into the episodic store (memd pattern); `InstructionsLoaded` to log that the policy loaded.
  4. **CI**: the same validator as a pre-commit hook and a CI job, so PR-reviewed procedural changes and append-only episodic logs are checked at merge, not just in-session.
  5. **Promote-to workflow**: an `inbox/` or "proposals" file as the only place a session may add candidate semantic/procedural facts; a curator (human or a dedicated session) promotes them. This is the memd/agent-memory pattern and matches the proposed "one writer kind per store".
- Because the subagent `memory:` field gives each role its own `MEMORY.md` with a 200-line/25 KB cap, the proposed "byte budget per role" can piggyback on Claude Code's existing mechanism rather than a custom one.
- The field's consistent message is that prompts set intent and tools/hooks enforce; a lint that fails loudly in `PostToolUse` plus a hard `PreToolUse` deny for the PR-only store is the documented way to make the rules stick.

### Gaps
- No study or engineering post measured how often agents write memory to the wrong file under instruction-only vs hook-enforced regimes; all "what works" evidence is vendor design guidance and small-tool practice.
- No published example of a hook that validates memory-file frontmatter or append-only semantics specifically was found; the lint-on-edit pattern is documented, the memory-specific validator is an extrapolation.
- The exact text of Claude Code's auto-memory and subagent-memory curation instructions is not published in the docs.

## KQ3. Known failure modes (bloat, stale facts, duplicates, wrong file, over-storage) and how teams bound working-memory size per role

### Takeaway
2025-2026 writing converges on: unbounded growth and stale-but-high-relevance facts are the main failures; the responses are (a) store less ("skip anything derivable"), (b) typed write policies with per-class lifetimes, (c) supersede/invalidate with tombstones instead of delete, (d) hard caps per file/block/index with forced curation, and (e) provenance links so invalidation can propagate. Per-role working-memory bounds are implemented as per-block, per-file or per-return token/character limits.

### Cited Findings
- Claude Code: auto memory "skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" and anything already in CLAUDE.md; index capped at 200 lines/25 KB with a post-write reminder to "merge or drop stale entries"; CLAUDE.md target under 200 lines because "longer files consume more context and reduce adherence"; conflicting instructions mean "Claude may pick one arbitrarily" — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Anthropic memory tool: cap file sizes, cap `view` output, expire files not accessed for a long time — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Anthropic context engineering: treat context as finite; sub-agents return 1,000-2,000-token summaries; compaction keeps decisions/open bugs and the five most recent files — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Letta: per-block character `limit`; last-write-wins on shared blocks — [Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks)
- Hindsight blog (21 May 2026, vendor): "Agents that remember everything remember nothing useful"; four consolidation levers — importance (what becomes a memory), merge (entity resolution, dedupe, recency-wins with explicit invalidation: "old facts are marked invalid rather than deleted"), decay (exponential default), eviction ("a compliance tool, not a performance tool", used only for GDPR/PII); evaluation signals: multi-session accuracy, contradiction-detection accuracy, token cost per turn, which "should stay flat as the index grows" — [Hindsight consolidation post](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation)
- Tian Pan (16 May 2026, independent blog): "Agent memory is a cache with no invalidation policy"; TTL decay misses high-relevance facts that were true then became false; recommends provenance edges to source events, "write policy by class" (identity, stable preference, project state, transient mood, each with its own lifetime), recency bias plus preferring user-asserted over inferred facts at retrieval, tombstones (mark INVALID, keep audit trail), and adversarial "seed a fact, change the world" evals; cites a benchmark where the best system recognised outdated memories only ~55% of the time but does not name the paper — [Tian Pan post](https://tianpan.co/blog/2026-05-16-agent-memory-cache-without-invalidation-policy) (the 55% figure is unattributed; treat as unverified)
- Tian Pan (Apr 2026): "garbage collection" framing with decay tiers and freshness thresholds — [agent memory GC post](https://tianpan.co/blog/2026/04/14/agent-memory-garbage-collection) (opinion)
- HackerNoon (2026): memories need lifecycle states (active/superseded) and validity windows — [HackerNoon](https://hackernoon.com/the-most-dangerous-memory-in-an-ai-agent-is-the-one-that-used-to-be-true) (opinion)
- mem0: duplicates arise when `infer=True` and `infer=False` are mixed for the same fact; `expiration_date` hides expired memories from search — [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add)
- Graphiti: bi-temporal validity windows and edge invalidation rather than summarisation judgments — [graphiti-core](https://pypi.org/project/graphiti-core)
- memd: per-file budgets, archive-not-delete, distill guardrail (>60% deletion rejected) — [memd](https://pypi.org/project/memd/)
- Letta dreaming: consolidation offloaded to background subagents after N steps or on compaction — [Letta sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime)

### Inferences
- The proposed "derive, don't store" working-memory rule is now vendor policy in Claude Code (both auto memory and `/doctor` trims derivable content). The proposed "dated line" on semantic edits lines up with the `modified` stamp and the supersede/tombstone advice; adding a `supersedes:` reference (provenance) would close the invalidation-propagation gap Tian Pan describes.
- Duplicate proposals are best prevented by a single inbox with dedupe on promotion (memd/Hindsight "merge" lever) rather than by letting every session write semantic facts directly.
- Byte budgets per role in the field: Claude Code 200 lines/25 KB index per repo or per subagent; 40,000 chars per on-demand rules file; Letta 4-6k chars per block; sub-agent returns 1-2k tokens; memd 10-22k chars per file. A per-role budget of the same order (tens of KB) is in line with practice.

### Gaps
- The ~55% memory-validity benchmark could not be attributed to a specific paper.
- No controlled comparison of file-level caps vs semantic consolidation on downstream task accuracy was found for coding agents specifically.

## KQ4. Voice agents: LiveKit Agents memory patterns, mem0/Letta/Zep integrations, turn-path vs background-path, per-caller vs per-business scope, forgetting/consent, and a CoALA bucket x scope table for a voice concierge

### Takeaway
LiveKit Agents is at 1.8.x (1.8.9 released 24 Oct; no 2.0 or "threads" model was found in releases or docs), ships no memory layer, and documents three injection points (seed `ChatContext` before `session.start()`, add in `on_user_turn_completed` then `update_chat_ctx`, or tool calls) plus manual truncation/summarisation. Vendor integrations (mem0 example, zep-livekit) write in `on_user_turn_completed`, with the mem0 example awaiting the write in the turn path and Zep extracting asynchronously. Scope is `user_id`/thread (per caller, per call) or group graph (per business). The proposed model transfers directly; the voice-specific additions are a hard latency budget on the turn path, consent/forget handling, and treating the extracted-facts table as semantic with the transcript as the immutable episodic source.

### Cited Findings
- LiveKit Agents Python releases: 1.8.9 (24 Oct, marked Latest), 1.8.8 (15 Oct), 1.8.7 (14 Oct), 1.8.6 (9 Oct), 1.8.5 (6 Oct), 1.8.4 (1 Oct), 1.8.3 (26 Sep), 1.8.2 (15 Sep). No 2.0 release; the only "threads" mention is a `ThreadJobExecutor.aclose()` hang fix in 1.8.3; 1.8.4 changed `ChatContext.truncate()` to honour non-positive `max_items`; 1.8.7 fixed keeping earlier summaries when chat context is summarised again; 1.8.5 lists chat summaries among reliability items — [livekit/agents releases](https://github.com/livekit/agents/releases) (page shows no year; inferred 2026 from "Latest")
- The only "LiveKit Agent SDK v2.0" hit was an SEO-style page not matching documented architecture — [dailyaiworld](https://dailyaiworld.com/workflow/livekit-realtime-voice-agent-pipeline-guide-2026) (unreliable; do not cite)
- Chat context docs: each agent/task has its own `chat_ctx`; `session.history` holds the full cross-agent conversation; in-turn changes persist only via `await self.update_chat_ctx(turn_ctx)`; `on_user_turn_completed(self, turn_ctx, new_message)` is where to fetch data and `add_message`; `truncate(max_items=...)` keeps recent items and preserves system instructions; `copy()` with exclusion flags; `merge()` dedupes by item ID; no built-in `summarize`; for personalisation, "load user-specific data before the session starts by passing a seeded `ChatContext`" because it avoids an extra LLM round-trip; `ChatContext` can be passed to `llm.chat()` standalone for background work — [LiveKit chat context](https://docs.livekit.io/agents/logic/chat-context.md)
- Summarisation pattern: custom helper builds a `ChatContext` with a "summarise" system message, keeps only user/assistant messages, skips items with `item.extra.get("is_summary")`, calls `summarizer.chat(chat_ctx=...).collect()`; used on handoff; alternative `chat_ctx.copy().truncate(max_items=6)`; or store key facts in `userdata` and inject as a system message — [LiveKit agents & handoffs](https://docs.livekit.io/agents/logic/agents-handoffs.md)
- External data & RAG guide: (1) load before session via job metadata/room metadata/participant attributes, and do any network call before `ctx.connect()`; (2) RAG in `on_user_turn_completed` "avoids tool-call round trips, so it's typically faster" but only for STT-LLM-TTS pipelines; (3) tool-based retrieval with credentials via participant attributes; (4) background `asyncio.create_task` with cancellation, and `AsyncToolset` for progress; (5) latency feedback when an operation exceeds "a few hundred milliseconds": verbal status after ~0.5 s, pre-synthesised cached filler phrases, `BackgroundAudioPlayer` `thinking_sound`, frontend RPC popups. The guide lists Letta and Mem0 as external memory services but has no memory section of its own — [LiveKit external data & RAG](https://docs.livekit.io/agents/build/external-data.md)
- Turns doc: `on_user_turn_completed` can raise `StopResponse` to suppress a reply; `on_user_turn_exceeded` with `user_turn_limit` (`max_words`/`max_duration`); interruption truncates history to what the user heard — [LiveKit turns](https://docs.livekit.io/agents/build/turns/)
- mem0 LiveKit example: `AgentSession` + `Agent` subclass; in `on_user_turn_completed` it `await`s `mem0_client.add(...)` (turn path, before retrieval and reply), then `search`es and injects results via `turn_ctx.add_message` + `update_chat_ctx`; only user messages stored; a single hard-coded `RAG_USER_ID = "livekit-mem0"`, so no per-user isolation — [mem0 LiveKit integration](https://docs.mem0.ai/integrations/livekit)
- zep-livekit 1.0 (requires LiveKit Agents v1.0+, Python 3.11+, zep-cloud v4): `ZepUserAgent` (per `user_uuid` + `thread_uuid`; "new thread per room while keeping the same user") persists the user message on `on_user_turn_completed` and captures assistant replies via the `conversation_item_added` session event; `thread.add_messages(..., return_context=True)` persists and retrieves in one call; `ZepGraphAgent` writes to a shared `graph_uuid` (no user provisioning) via `graph.episode.add` then `graph.get_context`; Zep "extracts knowledge asynchronously, so facts from the current turn aren't searchable until later"; warning: automatic injection into a system message is "for fully trusted, application-authored content only", user/document/third-party content should be retrieved via SDK or a tool call — [Zep LiveKit integration](https://help.getzep.com/ecosystem/livekit-memory)
- Zep scopes: user graph per user, group graph shared across users — [Zep key concepts](https://help.getzep.com)
- Consent/forgetting precedents: ChatGPT lets users delete individual memories or "tell ChatGPT to forget"; deleting a chat does not delete derived memories; deleted-memory logs kept up to 30 days — [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq). Hindsight: eviction is for "GDPR deletion or PII redaction", handled by bank-level clearing; otherwise mark invalid and keep for audit — [Hindsight consolidation](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation). Anthropic memory tool: strip sensitive data before write; expire unused files — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool). mem0: `expiration_date` and explicit `delete` — [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add)
- Letta dreaming is the vendor precedent for background consolidation triggered after N steps or on compaction — [Letta sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime)

### Inferences
- **Turn-path vs background rule, as documented practice reads:** reads that must shape the next reply (caller facts, last-visit summary) go either into the seeded `ChatContext` before `session.start()` (cheapest) or into `on_user_turn_completed` with a strict time cap; writes (fact extraction, transcript persistence, summarisation) should be background (`asyncio.create_task`, or a post-call job), because LiveKit's own guidance treats anything over a few hundred ms as needing audible feedback and the mem0 example's awaited `add` in the turn path is the anti-pattern (Zep's async extraction and the person's existing background extraction are the better precedent). Facts extracted in the background are only visible from the next turn or next call; that is acceptable and is how Zep behaves.
- **CoALA bucket x scope table for a voice concierge (my synthesis of the sources; each cell's mechanism is documented above):**

  | Bucket | Store | Scope | Writer | Mutation rule | Budget / load path |
  | --- | --- | --- | --- | --- | --- |
  | Working | `chat_ctx` for the current call | call (room/thread) | the turn pipeline | derived each turn; `truncate(max_items)` or summary item with `is_summary`; never persisted as-is | seeded before `session.start()`; cap by items or tokens |
  | Episodic | transcripts (`session.history`) and per-call visit summaries in SQLite | call, keyed by caller + business | post-call background job (one writer) | append-only; summary rows immutable, new row per call | not loaded whole; last N summaries or a rolled-up line loaded at call start |
  | Semantic | caller facts table (preferences, name, past bookings) | caller (per business tenant) | background extractor only | upsert with `modified`/`valid_from`, `source_call_id` provenance, `superseded_by`; explicit delete for "forget me"; `expires_at` for transient facts | small per-caller pack (hundreds of tokens) seeded before session; shown in the memory panel |
  | Semantic (shared) | business facts (hours, menu, policies) | business | operator/human via config or admin UI | edited in place, versioned in git or a config table | loaded as instructions; treat as trusted (Zep's "application-authored" caveat) |
  | Procedural | system instructions, tool definitions, knowledge sources, extraction prompt | business or deployment | humans via PR | PR-reviewed; dated changelog | loaded at job start; byte-capped |

- **Per-caller vs per-business scope:** mem0's `user_id` + `agent_id`/`app_id` and Zep's user graph + group graph are the two vendor precedents; in SQLite that is a composite key `(tenant_id, caller_id)` for semantic facts and `(tenant_id)` for business facts. Caller identity should come from participant attributes/job metadata (LiveKit's documented channel), never from the transcript.
- **Forget me / consent:** the field's pattern is user-triggered delete of semantic facts plus retention policy on the episodic source (ChatGPT's "deleting a chat does not delete the memory" is the pitfall to avoid): a "forget me" tool should delete the caller's semantic rows *and* schedule deletion of their episodic transcripts/summaries, log the request (tombstone with timestamp, not the content), and the memory panel should show what is stored and when (the `modified`/provenance columns make that cheap). Hindsight's "eviction only for compliance" supports keeping deletion as a separate, rarely used path from normal supersession.
- **Compaction of working context** in LiveKit is manual (truncate or custom summary with `is_summary` markers, 1.8.7 fixed re-summarisation); treating the summary as derived working memory (recomputed, not stored as a fact) matches the proposed model.
- **Memory panel:** no vendor doc for voice agents describes one; ChatGPT's "Manage memories" and Claude Code's `/memory` are the UI precedents (list, open, delete; show timestamps).

## KQ5. Is there a case for one shared memory model/document across projects, and any precedent for a project-level "memory policy" file?

### Takeaway
There is no canonical "memory policy" file standard; AGENTS.md deliberately says nothing about memory, and Claude Code splits policy across CLAUDE.md, `.claude/rules/`, settings (`autoMemoryEnabled`, `autoMemoryDirectory`) and hooks. The nearest precedents are memd's `.memory/` layout with per-file mutation rules and budgets, Claude Code's typed-frontmatter auto memory, and Anthropic's initializer/progress-log pattern. A single shared model document is justified because the two systems already use the same buckets, scopes, writer and mutation concepts; what differs is the physical store (git files vs SQLite) and the latency budget.

### Cited Findings
- AGENTS.md defines no memory mechanism and does not say where agents write learnings — [agents.md](https://agents.md/)
- Claude Code's policy surface for memory is split: CLAUDE.md scopes, `.claude/rules/` with `paths`, `claudeMdExcludes`, `autoMemoryEnabled`, `autoMemoryDirectory` (settable at user/project/local/policy scope), `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, subagent `memory:` field, and hooks — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [subagents docs](https://code.claude.com/docs/en/sub-agents.md)
- Claude Code managed-settings guidance separates "technical enforcement" (settings: `permissions.deny`, sandbox) from "behavioral guidance" (CLAUDE.md) — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- memd's `.memory/` is the closest thing to a project-level memory policy: five files with stated mutation rules, budgets in `config.json`, archive rule, inbox, and auto-generated AGENTS.md/CLAUDE.md/GEMINI.md stubs — [memd](https://pypi.org/project/memd/) (third-party beta, released 2026-10-26)
- stax "memory" spec treats memory as mutable runtime output distinct from immutable author-supplied knowledge — [stax memory spec](https://stax.stakpak.dev/docs/spec/memory) (third-party)
- Anthropic memory tool's "multisession" pattern prescribes which files exist (progress log, feature checklist, init script reference) and who updates them when — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The person's own `~/.claude/CLAUDE.md` already uses the "one home for a policy, project files point here" pattern for permissions (`decisions/2026-10-24-permissions-policy`), per the instructions visible in this session (local file, not a web source).

### Inferences
- A shared "memory policy" document (one table: bucket, scope, store, writer kind, mutation rule, budget, load path, forget path) with two implementation appendices (git files for the orchestrator; SQLite tables for the voice agent) fits both the field's direction and the person's existing single-home policy convention. The orchestrator appendix maps to Claude Code's native stores (CLAUDE.md/rules = procedural, auto memory `type: feedback|project` = semantic, subagent `memory: project` dirs = per-role, hooks = enforcement); the voice appendix maps to SQLite tables with `tenant_id/caller_id`, `modified`, `source_call_id`, `superseded_by`, `expires_at`.
- Columns worth adding to the proposed row, based on the failure-mode literature: provenance (source session/call id), supersedes link, expiry class, and a "forget path". Columns the field does not bother with: per-store writer *kind* (they use read-only flags instead) — keeping it is a reasonable stricter choice.
- Precedent for the policy living in git and being PR-reviewed: CoALA's risk warning on procedural writes, agent-memory's human-review staging, and Claude Code's `project`-scoped subagent memory "shared through version control".

### Gaps
- No organisation-level "memory policy" standard (analogous to AGENTS.md) was found; the Agentic AI Foundation's AGENTS.md scope excludes it.
- No source compares outcomes of a shared vs per-project memory policy.
