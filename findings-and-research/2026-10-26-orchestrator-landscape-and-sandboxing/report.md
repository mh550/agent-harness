# Keep your harness, sandbox its workers

Nothing surveyed replaces agent-harness, and the one large project that tried to be the reusable version of it was abandoned by its own author in favour of a private bash harness. No FOSS orchestrator combines a fresh headless session per feature, an independent evidence-based verify step, PR merges of verified milestones, a cross-project queue, usage-limit and memory-cap handling and retros; the closest functional matches (Bernstein, ralphex, Archon, Orbi) each cover two or three of those and are one-person or small-team projects, while Steve Yegge's Gas Town "effectively burned down" and he now runs "Wheelhouse", a closed harness that is "mostly bash, with Beads" ([Yegge, Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/)). Three changes are worth making. First, an adapter boundary (spawn, resume, normalise events; token caps rather than dollar budgets; `entry.json` as the result channel; AGENTS.md as the canonical instruction file imported from CLAUDE.md) makes Codex, Gemini CLI, OpenCode, Goose or an API loop swappable later without touching the state machine. Second, each worker's whole `claude -p` process should run inside bubblewrap (`srt claude` or a hand-written `bwrap` wrapper) with Claude Code's built-in Bash sandbox nested inside for the network allowlist, the orchestrator left unsandboxed as the only holder of git credentials; this matters because settings.json deny rules are a Claude-only mechanism that does not port to other agents, `systemd-run --scope` gives resource control but cannot carry sandboxing directives, and Anthropic itself now says the classifier in auto mode "is a per-action control, not an isolation boundary" ([Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)). Third, the control plane should be built, not bought: no FOSS control plane sits over someone else's run state, and the precedents (Onako, a 2-dependency JSONL dashboard, a git-heartbeat board) are each one person's work under 100 kB. LangGraph/CrewAI, durable-execution runtimes and a framework/runtime split all solve a loop you do not own; bash remains the right language for process, git, tmux and systemd plumbing with the state machine and JSON in node. The CoALA bucket × scope memory model is ahead of shipped practice and should gain provenance, supersedes, expiry and forget-path columns, be enforced by hooks plus the deterministic `memlint`, and be reused as-is for the LiveKit voice agent with the transcript as the immutable episodic source, the background extractor as the only semantic writer, and no memory writes on the turn path.

## One adapter contract, token caps, AGENTS.md canonical

Almost everything the harness touches today is a Claude Code surface rather than a coding-agent surface: the flag names, the stream-json event vocabulary, `total_cost_usd` and `modelUsage`, `--permission-mode auto`, settings deny rules and hooks as the safety layer, CLAUDE.md as the instruction file, `--resume` semantics and Remote Control as the desk. What generalises is the shape of the contract: run a prompt in a cwd with a model, a cap and a policy; stream events; return final text or a structured artifact plus usage; be resumable by session id. Every major CLI now offers a subset of that. Codex `exec --json` emits `thread.started`, `turn.started`, `turn.completed` and `item.*` events with `input_tokens`, `cached_input_tokens`, `output_tokens` and `reasoning_output_tokens`, offers `--output-schema <file>` and `-o <path>` for the last message, and resumes with `codex exec resume <SESSION_ID>` ([Codex non-interactive docs](https://learn.chatgpt.com/docs/non-interactive-mode)). Gemini CLI's `--output-format stream-json` emits `init`, `message`, `tool_use`, `tool_result`, `error` and `result`, with exit code 53 for "Turn limit exceeded" ([Gemini CLI headless reference](https://geminicli.com/docs/cli/headless.md)). OpenCode has `opencode run --format json`, `--session`/`--continue` and `--auto` ("Auto-approve permissions that are not explicitly denied") ([OpenCode CLI docs](https://opencode.ai/docs/cli/)); Goose has `goose run --no-session --max-turns --output-format stream-json` and `GOOSE_MODE=auto` ([goose-run man page](https://www.mankier.com/1/goose-run)); Aider has `--message` and `--yes` and nothing else ([aider scripting docs](https://aider.chat/docs/scripting.html)). **The lowest common denominator is prompt in, JSON(L) events out, token counts, a session id, an exit code, and an agent-specific way to disable prompts.** Only Claude reports dollars, and even those are "client-side estimates" from "a price table bundled at build time" that must not be used for billing ([Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md)). A budget in USD therefore cannot be the portable contract; a token cap plus a per-model price table the orchestrator owns is, and that is what Claude does internally anyway.

The adapter boundary that fits is the one Vibe Kanban drew: a `StandardCodingAgentExecutor` trait with `spawn(current_dir, prompt, env)`, `spawn_follow_up(current_dir, prompt, session_id, ...)`, `normalize_logs(raw_logs, worktree_path)` and `get_availability_info()`, implemented once per agent in `claude.rs`, `codex.rs`, `gemini.rs`, `opencode.rs` and so on, plus an `acp/` module ([executors/mod.rs](https://raw.githubusercontent.com/BloopAI/vibe-kanban/main/crates/executors/src/executors/mod.rs)). For the harness this means a node module per agent exposing `spawn(cwd, prompt, model, limits{turns, tokens, timeout}, policy)` that yields normalised events (`init`, `text`, `tool_call`, `tool_result`, `permission_denied`, `error`, `result{stop_reason, tokens{in,out,cached}, cost?, session_id}`), a `resume(session_id, prompt)`, and an `instructions_file()`; bash invokes it and never parses a vendor stream directly. The `entry.json` the agent writes into the worktree is already agent-neutral and should stay the primary result channel, because structured-output flags differ (`--json-schema` in Claude, `--output-schema` in Codex, nothing in Gemini or Goose). Instruction files converge on AGENTS.md everywhere except Claude Code: OpenCode reads project `AGENTS.md` and falls back to `CLAUDE.md`, and `~/.config/opencode/AGENTS.md` falling back to `~/.claude/CLAUDE.md` ([OpenCode rules docs](https://opencode.ai/docs/rules/)); Claude Code reads AGENTS.md in place of CLAUDE.md when none exists (v2.1.277+) or alongside it with the `claude-md-and-agents-md` setting ([Claude Code memory docs](https://code.claude.com/docs/en/memory)); Aider only loads conventions via `--read` ([aider conventions docs](https://aider.chat/docs/usage/conventions.html)). Writing AGENTS.md as canonical and importing it from CLAUDE.md with `@AGENTS.md` covers everyone but Aider; whether Gemini CLI reads it without `context.fileName` configuration is contested in the sources and needs a local test. Note that Codex truncates past a 32 KiB `project_doc_max_bytes` default ([codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/07/agents-md-open-standard-cross-tool-portability), secondary), which argues for keeping the "Where things go" block short.

Two further decisions follow. The Agent Client Protocol is the only cross-vendor protocol that matches the harness's needs: JSON-RPC over stdio with `session/new`, `session/prompt`, `session/update` (tool calls, plan, `usage_update` with optional `cost`) and `session/request_permission`, a registry of 43 agents including adapters for Claude Code and Codex and native support in Gemini CLI, Goose and OpenCode ([ACP protocol overview](https://agentclientprotocol.com/protocol/overview); [ACP registry](https://agentclientprotocol.com/registry)); acpx already drives it headless from a shell with `--approve-all|--approve-reads|--deny-all` and `--policy <json>` ([acpx README](https://cdn.jsdelivr.net/npm/acpx@0.11.2/README.md)). But the Claude path through ACP is a third-party wrapper over the Agent SDK that does not surface hooks or cost ([claude-agent-acp README](https://raw.githubusercontent.com/agentclientprotocol/claude-agent-acp/main/README.md)), and ACP inverts the permission model: **the orchestrator becomes the permission host and must implement the deny policy itself**, because `session/request_permission` replaces settings.json. ACP is the right second adapter covering many agents at once, not the primary one. Likewise the Claude Agent SDK is "a library that runs the Claude Code binary" that adds in-process `canUseTool` callbacks and typed messages but is Python/TypeScript only and bound to API-key auth under the Commercial Terms ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)); it belongs inside the Claude adapter if anywhere, never above the boundary. One operational risk belongs in the adapter now: `--bare` skips hooks, skills, CLAUDE.md and MCP auto-discovery and "will become the default for `-p` in a future release" ([Claude Code headless docs](https://code.claude.com/docs/en/headless)), so the Claude adapter should pass `--settings`, `--append-system-prompt-file` and `--mcp-config` explicitly rather than rely on discovery, or a future default flip silently removes the deny rules.

## Nobody has built this combination; Gas Town's author went back to bash

The space is crowded but shallow. One curated list tracks roughly 270 projects in eight categories, and most are session multiplexers or Kanban front-ends for humans supervising agents ([awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)). Of those that run work unattended from a plan through verification to merge, each is missing something the harness has. OpenAI's Symphony (27,831 stars, Apache-2.0, Elixir) states outright that "the orchestrator performs no verification or merge step. It defines no test or review gates", keeps scheduler state "intentionally in-memory", "defines no token budget or monetary cost limit", and targets the Codex app-server only ([SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); OpenAI "does not plan to maintain Symphony as a standalone product" ([Help Net Security, 2026-04-28](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/)). Bernstein (1,327 stars, "Solo-maintained", "Status: beta") has a deterministic Python scheduler where "no model decides what happens next", a worktree per task behind merge gates and a Janitor that checks tests, lint, types and files, but its `autopilot` "refuses to run until a `TaskSource` is implemented" and it has no memory or retros ([Bernstein](https://github.com/sipyourdrink-ltd/bernstein)). ralphex (1,504 stars, Go) is the closest execution model, "each task executes in a fresh Claude Code session with minimal context", with validation per task, five review agents and rate-limit `--wait`, but handles one plan at a time, only rebases rather than merges, and runs `--dangerously-skip-permissions` ([ralphex](https://github.com/umputun/ralphex)). Archon (23,775 stars, TypeScript/Bun) has YAML workflow graphs, worktree-per-run, queues and a merge queue that "checks the review verdict and CI status at the head commit", but no learning across runs beyond `archon-discoveries` ([Archon](https://github.com/coleam00/Archon)). Orbi uses GitHub Issues as "the only state store—no database, queue, or daemon" with a systemd timer every five minutes and an independent review session before merge ([Orbi](https://github.com/orbi-build/orbi)). **None documents systemd-scope memory caps, evidence tables, a cross-project queue with usage-limit handling, or a retro that writes proposals into a backlog**; the retro loop appears in practitioner writing (Addy Osmani's factory model "ends with a retro step") rather than shipped tools ([addyosmani.com](https://addyosmani.com/blog/code-agent-orchestra/)).

The negative evidence is stronger than the positive. Gas Town (18,560 stars, 512 open issues, last release June 2026) is the one large project with the same ambitions, and a DoltHub hands-on found a sixty-minute session cost "about $100 in Claude tokens", that the first PR "got merged autonomously, despite the integration tests failing", and that none of four PRs were good ([DoltHub blog, 2026-01-15](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/)). Yegge's August essay reports the batched merge queue "got stuck in bisection loops once the queue passed about 100 merge requests", that Gas Town "effectively burned down" after Opus 4.7 kept modifying Gas Town itself, and advises "Build a harness bespoke to your application rather than adopting a reusable framework" ([Yegge, Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/)). Vibe Kanban (28,468 stars) is "sunsetting" because bloop "couldn't find a business model" ([vibekanban.com/shutdown](https://vibekanban.com/shutdown)); Aperant is in maintenance mode with pull requests paused ([Aperant](https://github.com/AndyMik90/Aperant)). The most-starred entries, Paperclip at 107,611 and OpenHands at 91,918, are generalist control planes rather than overnight verify-and-merge pipelines ([Paperclip](https://github.com/paperclipai/paperclip); [OpenHands](https://github.com/OpenHands/OpenHands)). Star counts correlate poorly with the property that matters here.

Anthropic's own surfaces are not substitutes either. Projects fans out cloud threads that open PRs and auto-fix CI, with project memory in `MEMORY.md`, but the thread count is "a preference rather than a cap" with an enforced 200 new threads per day, there is no independent verify gate or cross-project queue, and it runs in Anthropic's cloud against the individual account ([claude-projects docs](https://code.claude.com/docs/en/claude-projects.md)). Dynamic workflows are the most harness-like local primitive (up to 16 concurrent agents by default, stall restarts up to five times) but "a run doesn't pause in non-interactive mode with `claude -p`" when usage limits hit, and exiting Claude Code ends the run ([workflows docs](https://code.claude.com/docs/en/workflows.md)), so an external supervisor is still required overnight. The one external risk worth watching is billing: Anthropic announced a separate monthly credit for Agent SDK and `claude -p` usage from June 15, 2026, then paused it, and the support article says such usage "still count[s] against subscription usage limits ... for now" ([support.claude.com](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan); [The New Stack, 2026-06-16](https://thenewstack.io/anthropic-pauses-claude-agent-sdk-subscription-change/)). That risk attaches to the Claude adapter, not the orchestrator, which is one more reason to have the adapter boundary. The verdict on question two is to keep the harness and borrow design rather than code: Symphony's per-state concurrency caps, 300-second stall timeout and `min(10000 × 2^(attempt−1), max_retry_backoff_ms)` backoff ([SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); Archon's three merge-queue checks (review verdict, CI at head, base not failing); Bernstein's signed run receipts; Orbi's "only the reviewed head can merge" rule.

## No thin control plane exists; a loopback page plus ntfy buttons is the build

Every well-known control plane owns the run. Paperclip schedules heartbeats, budgets and approvals itself and needs Node ≥24.11 and Postgres ([Paperclip](https://github.com/paperclipai/paperclip)); Multica's agents "execute through the daemon, which spawns the agent CLI", on a Go backend with Postgres 17 under a licence the README calls both "open-source" and "source-available" ([Multica](https://github.com/multica-ai/multica)); T3 Code is "very very early" ([t3code](https://github.com/pingdotgg/t3code)); HumanLayer now runs agents through its own per-host daemon ([humanlayer](https://github.com/humanlayer/humanlayer)); LangChain's Agent Inbox, the one project that was purely an answer-the-blocked-agent UI, requires a LangGraph deployment and was archived on September 20, 2026 ([agent-inbox](https://github.com/langchain-ai/agent-inbox)). The handful that can observe runs they did not start are read-only or tmux-send only: Gas Town's "Minimal Mode" where "you launch runtimes yourself and Gas Town just tracks state" but still needs Dolt and Beads ([gastown](https://github.com/steveyegge/gastown)); Onako, 94 kB of Python over tmux and SQLite that discovers foreign tmux windows as "external" tasks with view, send and kill, started from an iOS Shortcut, with 17 releases in three weeks by one maintainer ([PyPI onako](https://pypi.org/project/onako/)); Stargx's dashboard, an Express plus chokidar watcher over `~/.claude/projects` JSONL with a single HTML page, "2 production dependencies" and 2-second polling ([Stargx/claude-code-dashboard](https://github.com/Stargx/claude-code-dashboard)); and a zero-dependency board where a collector writes a JSON heartbeat into a private git repo and a local server renders queued, doing, needs-input, done and failed columns ([aiwithamirthan guide](https://aiwithamirthan.com/guides/a-dashboard-for-every-agent-you-run/)). **None understands an `INBOX.md` question/answer protocol or a project queue**, and adopting a full product would mean moving tmux, worktrees and merges into it or running two schedulers.

The requirements (run list over existing state, answer an INBOX question, park and continue, queue in and out, change parallelism, usable from a phone) map onto one static page with SSE or 2-second polling and four or five POST endpoints wrapping commands `harness status` and the queue files already expose. The patterns worth copying are small and well documented. Gas City's dashboard binds `127.0.0.1` by default, runs read-only when bound elsewhere without `allow_mutations`, and requires an `X-GC-Request` header on mutations ([docs.gascity.com dashboard](https://docs.gascity.com/getting-started/dashboard)); Symphony's optional loopback server exposes `GET /api/v1/state` and insists the status surface "must not be required for correctness" with a "rich web UI" an explicit non-goal ([SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); the lbacik spec adds confirm-then-append to a `control-audit.jsonl` for every control ([lbacik/agent-dashboard](https://github.com/lbacik/agent-dashboard)). Agent View's state vocabulary (`working`/`blocked`/`done`/`failed`/`stopped`, with `waitingFor`) is a sensible schema to adopt because `claude agents --json` is now "the supported way to read session state from outside Claude Code, for example from ... a scheduler", even though `~/.claude/jobs/<id>/` is "not a stable interface" ([agent-view docs](https://code.claude.com/docs/en/agent-view)). For the phone, ntfy already carries up to three action buttons per notification, and the `http` action "sends a POST request (not GET!)" with an optional body ([docs.ntfy.sh/publish](https://docs.ntfy.sh/publish/)), which turns yes/no and pick-one INBOX questions into one tap against the same small endpoint; free-text answers need the page or the Claude app. Phone access to the page is a Tailscale or SSH tunnel, which is what Paperclip and Onako both recommend.

The hybrid "buy" is Remote Control. Server mode `claude remote-control --name <run> --spawn worktree --capacity N` (default 32) lists sessions at claude.ai/code and in the Claude app, keeps permission prompts and `AskUserQuestion` open until answered, and pushes "when actions required" ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). It is free with the subscription but requires claude.ai login ("API keys are not supported"), cannot sit behind an `ANTHROPIC_BASE_URL` gateway, sees only Claude sessions and not the bash phases, queue or parallelism, and the docs do not state whether a `claude -p` session can be attached after the fact; `--bg` explicitly rejects `-p` ([agent-view docs](https://code.claude.com/docs/en/agent-view)). The practical reading is that the optional desk stays optional, and the harness's own page covers what no vendor surface will: queue, park/continue and lane count.

## Bubblewrap around each worker closes the gap deny rules leave

Anthropic's current guidance draws the line the harness needs. The built-in sandboxed Bash tool uses bubblewrap on Linux with a separate network namespace and a host-side proxy that enforces `allowedDomains`, and by default it lets commands **read "the entire computer except denied directories"**, so `~/.ssh` and `~/.aws/credentials` stay readable unless denied; it also leaves file tools, MCP servers, hooks and `excludedCommands` on the host ([Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)). The environment-choice page says "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary", that in auto mode "the classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth for unattended runs", and that "the sandboxed Bash tool on its own constrains only shell commands, so it is not sufficient for fully unattended runs in either mode" ([Claude Code: Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)). The threat model behind this is prompt injection via repo, PR, web or MCP content, and the 2026 incidents were exactly that: "Comment and Control" (disclosed 2026-04-15) hijacked Claude Code Security Review, Gemini CLI Action and Copilot Agent through PR titles and comments, with the Claude case posting its own API key as a comment and rated CVSS 9.4 by Anthropic ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-comment-control-github-prompt-injection-20/)). No escape of the bubblewrap sandbox itself was found; every documented weakening is a configuration choice.

The current `systemd-run --user --scope` wrapper cannot become the sandbox. Scope units "manage externally created processes" and the scope page references systemd.exec only for `OOMScoreAdjust` ([systemd.scope(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.scope.html)); `ProtectHome=`, `ReadWritePaths=`, `InaccessiblePaths=`, `PrivateNetwork=` and the rest work for per-user *service* units with `PrivateUsers=` implicitly enabled, and `ProtectProc=`, `ProtectControlGroups=` and `DynamicUser=` are system-only ([systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)). A transient user service would also detach stdio from the orchestrator, and no source tested that path with Claude Code. Bubblewrap is the tool with working examples. Esokia's two-layer recipe on Kubuntu 24.04 ro-binds `/usr`, `/etc`, `~/.local/share/claude`, binds the project, `~/.claude/` and `~/.claude.json` writable, mounts `/tmp` as tmpfs with an empty `$HOME`, clears the environment and sets only `HOME PWD PATH TERM LANG XDG_*`, and runs `--unshare-pid --unshare-uts --unshare-ipc --new-session --die-with-parent` with Claude's native Bash sandbox nested inside ([Esokia Labs](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/)). Bretti's one-liner masks secrets by binding `/dev/null` over `$PROJECT_DIR/.env` and `.env.local` ([Juan Bretti](https://blog.juanbretti.com/en/posts/2026-08-09_bubblewrap_sandboxing_ai_agents/)). Anthropic's `srt` wraps the whole process the same way, with the network namespace removed and allow-only domains, but its Linux limits matter for this box: `allowWrite`/`denyWrite` take literal paths only, `**/.env` is skipped and "a skipped pattern hides nothing", a `denyRead` for a non-existent path hides nothing, and `allowUnixSockets` is ignored so Docker socket access needs `allowAllUnixSockets: true` ([sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)). Either way, on Ubuntu 24.04-family kernels the recurring snag is AppArmor's restriction on unprivileged user namespaces; both Anthropic and Codex recommend a per-binary `bwrap` profile over the global `kernel.apparmor_restrict_unprivileged_userns` sysctl ([sandbox-runtime README](https://github.com/anthropics/sandbox-runtime); [Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md)).

The scope question has a consistent answer across sources: **a trusted host-side controller and sandboxed workers, with test runs inheriting the worker's sandbox.** Claude Code on the web keeps the GitHub token in "a separate proxy ... outside the sandbox while issuing scoped credentials" ([Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)); Fletch runs "push and PR operations ... host-side so tokens stay out of the sandbox" and AgentBox "keeps git credentials on the host" ([wincent gist](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e)); no write-up sandboxes the orchestrator itself. For agent-harness that means: do not sandbox the orchestrator (it creates worktrees, merges, pushes, deletes branches, runs `harness gc`, and should be the only holder of the GitHub token, pushing and opening PRs after the worker exits); keep `systemd-run --scope` for memory caps; wrap each worker's whole process in `bwrap` or `srt` with the worktree, a per-worker `/tmp` and `~/.claude` writable and `~/.config`, `~/.livekit`, `/srv`, `/etc/restic` and literal `.env*` paths invisible; and enable the built-in Bash sandbox inside it with `failIfUnavailable` and an `allowedDomains` list so tests and builds inherit the network allowlist without any extra mechanism. In auto mode this removes the Bash prompt path entirely, since sandboxed Bash runs "without a prompt, regardless of permission mode" and out-of-allowlist hosts are refused unless the command listed them and the classifier approved ([Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)); Anthropic measured 84% fewer permission prompts from the Bash sandbox alone, an internal figure ([Anthropic engineering blog](https://www.anthropic.com/engineering/claude-code-sandboxing)). Esokia found `allowedDomains` must be validated empirically per version, since Anthropic endpoints "remained reachable even when not listed" ([Esokia Labs](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/)), and whether `claude -p` honours the `sandbox` keys via `--settings` identically to interactive mode is expected but unconfirmed in any doc.

Two things remain outside the sandbox's reach and need separate handling. The settings.json deny rules are the only layer that understands git semantics (no push to main, no force-push); no OS sandbox distinguishes `git push` from `git fetch`, and these rules keep applying inside the sandbox, so they stay. The persistence vector is specific: "A sandboxed session that can write [config paths] can persist hooks, permission rules, or MCP servers that run unsandboxed the next time you launch Claude Code" ([Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)), and because `srt` needs `~/.claude` writable for sign-in state, workers should get a separate `CLAUDE_CONFIG_DIR` or a `denyWrite` on `~/.claude/settings.json`. The decisive cost is docker compose. `excludedCommands: ["docker compose *"]` is the documented way to keep compose-based tests working, but excluded commands run with no filesystem restriction and no proxy ([Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)), the Docker socket is root-equivalent on the host, and granting it under `srt` on Linux removes socket blocking for everything. Given that `/srv` hosts live stacks, compose-driven tests should run from the orchestrator after the worker exits, or in a Docker Sandboxes microVM "with its own Docker daemon" that Anthropic says "does not require Docker Desktop" ([Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)) if they must run inside the worker boundary; Firecracker, Kata, gVisor and Kubernetes are compliance-grade and not worth it on one box. The sandbox also does what the deny rules cannot do for a non-Claude agent: once Codex or OpenCode is a worker, settings.json means nothing, Codex's `workspace-write` plus `on-request` is its own "lower-risk automation preset" ([Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md)), and the only agent-neutral safety layers are the OS boundary, the orchestrator holding credentials, and Chipp-style greps of the command stream for `git reset --hard`, `--no-verify` and `rm -rf` ([chipp.ai](https://chipp.ai/blog/the-bash-harness)).

## Frameworks and durable runtimes solve a loop you do not own; bash stays the plumbing

LangGraph, CrewAI, AutoGen and the rest model an agent as an LLM call loop with tools inside the framework's process. The harness's worker is an opaque subprocess, so the frameworks' core (tool loop, state graph, role and handoff abstractions) does not apply to it and would be a second, redundant loop. Anthropic's own advice is to "start by using LLM APIs directly" because frameworks "often create extra layers of abstraction that can obscure the underlying prompts and responses" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)), and the direction of travel runs the other way: LangChain's DeepAgents is itself registered as an ACP *agent* ([ACP registry](https://agentclientprotocol.com/registry)). No practitioner write-up was found that wraps Claude Code or Codex in a LangGraph or CrewAI node; the orchestrators that exist (Symphony, Vibe Kanban, Clancy, orc, cc-ci-orchestrator, Chipp's harness) are plain schedulers in Elixir, Rust, Go, Python or bash. The one niche where a framework could sit is the roles that are themselves single model calls, the init planner and the verify judge, and even there `claude -p --json-schema` or `codex exec --output-schema` already give typed output without a Python or TypeScript dependency the bash+node design does not have. LangGraph's genuinely useful property, "stateful pause-and-resume", is a durable-execution concern, not an agent-modelling one.

Durable-execution runtimes get their value from owning the loop. Restate's "durable coding agent" wraps each LLM call and tool run in `restate.run(...)` so a crash "continues from the latest completed step" ([Restate blog](https://restate.dev/blog/durable-coding-agent-with-restate-and-modal)); Inngest's `step.run` checkpoints "avoid paying for repeated LLM calls" ([Inngest blog](https://www.inngest.com/blog/durable-execution-key-to-harnessing-ai-agents)); Temporal lists integrations for OpenAI Agents SDK, LangGraph, Pydantic AI and others ([Temporal durable AI](https://docs.temporal.io/ai.md)). With `claude -p` as a subprocess, that granularity is unavailable: the journaled unit would be "one worker run", which a state file already records, and a crashed worker loses its in-progress turn regardless (SIGTERM gives exit 143 "with the in-progress turn unrecorded" ([headless docs](https://code.claude.com/docs/en/headless))), with `--resume <session_id>` the recovery path a runtime could call but not improve. Symphony, the closest published analogue, ships without one: "Symphony is a scheduler/runner and tracker reader", "the orchestrator is the only component that mutates scheduling state", state is in memory, and a restart re-polls the tracker and reuses preserved workspaces while "retry timers and live sessions are not restored" ([SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)). **Separating orchestration from execution is a contract, not a runtime**: keep orchestration state small and re-derivable from files and git, keep the execution environment disposable, and re-derive on restart instead of trusting memory. The harness already fits that pattern; a Temporal or Restate adoption would buy exactly-once steps across reboots, durable timers and a built-in run history, which are operational niceties on one box and only become arguments once runs span hosts.

Bash is the right language for exactly the jobs it still holds. Chipp's 312-line harness, "most of them comments", kept bash because it "manages Unix processes, is easy to audit on a production box, and has no dependencies", after a TypeScript version "took about ten times as long to debug"; its remaining jobs are the ones Claude Code has not absorbed, a wall-clock timeout cut from 8 to 2 hours because runaway sessions cost too much, hang detection on 2–5 minutes of tool-output silence, greps for destructive commands because the agent "sometimes issued destructive commands despite CLAUDE.md rules", worktree and orphan cleanup, and enforcing the push step ([chipp.ai](https://chipp.ai/blog/the-bash-harness)). The migration pattern that recurs when bash gets painful is not a rewrite but a split: cc-ci-orchestrator turned its launchers into one-liner `exec python3 <script>.py "$@"` wrappers around "pure stdlib, no deps" Python ([git.autonomic.zone commit](https://git.autonomic.zone/recipe-maintainers/cc-ci-orchestrator/src/commit/bca51071bd70b6cd36454b519371b57b5b98c6ae)), the same shape as the harness's bash+node split. The limits people actually hit are no native JSON, no typed state, and testability of the state machine, so the least-churn path is to move JSONL parsing and the per-run state machine fully into the node side (which is also where the agent adapters live) and keep bash for `systemd-run`, `tmux`, `git`, `flock` and `bwrap`. Claude Code now covers `--max-budget-usd`, `--max-turns`, `--permission-prompts none`, SIGTERM handling with `SessionEnd` hooks and `system/api_retry` events ([headless docs](https://code.claude.com/docs/en/headless)), so the harness-side backstops that remain are agent-neutral by construction and belong in the orchestrator whatever language or agent it fronts. A Go or Rust rewrite in the Clancy, orc or Vibe Kanban style buys a static binary and typed concurrency; the evidence does not show it buying better agent control.

## The memory table is ahead of practice; hooks and memlint make it stick

The four CoALA buckets are the de facto vocabulary, but production systems organise storage by scope and writer more than by bucket, which is what the bucket × scope table already does. Claude Code splits memory by who writes it: CLAUDE.md "written by you" versus auto memory "written by Claude", both "context, not enforced configuration", with auto memory records typed `user`, `feedback`, `project` or `reference`, an index capped at 200 lines or 25 KB with a post-write reminder to "merge or drop stale entries", and a `modified` ISO 8601 stamp on frontmatter files "so the timestamp shows how current the fact is"; it "skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Letta's memory blocks carry a `description` the agent uses "to decide how to read and write it", a character `limit` and a `read_only` flag, and the docs warn that on shared blocks "the last write wins" ([Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks)), which is direct evidence for the single-writer rule. mem0 scopes every add and search by `user_id`, `agent_id`, `app_id` and `run_id`, stores additively, and requires explicit `update` or `delete` for corrections ([mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add)). Hindsight marks old facts "invalid rather than deleted" and treats eviction as "a compliance tool, not a performance tool" ([Hindsight consolidation post](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation)). memd, released 2026-10-26 in beta, is the closest thing to a project-level memory policy: a present-tense `state.md` where "stale facts are replaced, not kept", a strictly append-only `mistakes.md`, per-file character budgets of 10,000 to 22,000, archive-never-delete, a single curator, agents told "not to edit the memory files" but to send facts through an inbox, and a guardrail that rejects any distill deleting more than 60% of a file ([memd on PyPI](https://pypi.org/project/memd/)). CoALA itself warned that writing to procedural memory "is significantly riskier than writing to episodic or semantic memory" ([CoALA v3](https://arxiv.org/html/2309.02427v3)), the direct precedent for PR-reviewed procedural stores. **Append-only episodic, in-place semantic with a dated line, PR-reviewed procedural and derived working memory with a byte budget each have a vendor precedent; nobody found has all four rules written in one table**, which is the gap the model fills. The design's rejection of an LLM curator, embeddings and a facts database is consistent with where the file-based systems landed (Anthropic's memory tool is file-based and client-side ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)); Yegge's core is "Beads plus a Markdown 'project brain'" ([Yegge, Aug 2026](https://yegge.ai/essays/the-shape-of-things-to-come/))), and the per-role byte budget is in line with the field's tens-of-KB caps (Claude Code's 25 KB index and 40,000-char on-demand rules file, Letta's 4–6k-char blocks, Anthropic's 1,000–2,000-token sub-agent returns ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))). Of the six scopes, session, run, project, orchestrator and user map onto mem0's `run_id`/app/agent/user and Claude Code's managed/user/project/local; "lane" has no analogue anywhere and needs defining in the policy document. The failure-mode literature suggests four columns the row should gain: provenance (source session or run id), a `supersedes` link so invalidation propagates, an expiry class per fact kind, and an explicit forget path; Tian Pan's framing is that "agent memory is a cache with no invalidation policy" and that TTL decay misses facts "that were true then became false" ([Tian Pan post](https://tianpan.co/blog/2026-05-16-agent-memory-cache-without-invalidation-policy)).

Making future sessions respect the table is a hooks-and-validator problem, not a prompt problem. Anthropic's docs are explicit: "To block an action regardless of what Claude decides, use a PreToolUse hook instead", and anything that "must run at a specific point ... write it as a hook" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The mechanics exist: `PreToolUse` can `deny` with filters like `if: "Edit(*.md)"`, `PostToolUse` cannot block but returns `additionalContext` and exit code 2 feeds stderr back to Claude, `SessionStart` injects up to 10,000 chars of context, `PreCompact` and `SessionEnd` run distills, and `InstructionsLoaded` logs which files loaded ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)). Mapped onto the queued memory run: the "Where things go" block is the policy file and can live in `.claude/rules/memory.md` with a `paths:` glob so it loads only when memory paths are touched; `memlint` is the tool-side validator the field converges on (Claude Code itself enforces its index cap after every write rather than by prompt), and should check frontmatter (`type`, `scope`, `writer`, `modified`, `supersedes`), that episodic files only grow against git HEAD, and that procedural files change only on a branch; a `PreToolUse` deny on `Edit|Write` to append-only and PR-only stores from the wrong role is the hard gate, `PostToolUse` running `memlint` and returning the fix is the soft one, and the same validator as a pre-commit hook and CI job catches what hooks miss when a non-Claude agent is the worker, since hooks are Claude-only and the adapter boundary means they will not always be present. The retro backlog is the inbox-then-promote pattern memd and xChuCx/agent-memory use (durable changes "staged for human review instead of landing silently" ([agent-memory](https://pkg.go.dev/github.com/xChuCx/agent-memory))), with dedupe on promotion rather than at write time. Per-role budgets can piggyback on Claude Code's subagent `memory: project` directories, each with its own 200-line/25 KB `MEMORY.md` and curation instruction ([subagents docs](https://code.claude.com/docs/en/sub-agents.md)), instead of a custom mechanism. No study measures how often agents write to the wrong file under instruction-only versus hook-enforced regimes; the evidence is design direction, and the direction is unanimous.

The voice agent takes the same table with a different physical store and a latency budget. LiveKit Agents is at 1.8.9 (no 2.0 or "threads" model exists in the releases or docs found) and ships no memory layer; its documented injection points are a seeded `ChatContext` before `session.start()` (cheapest, "avoids an extra LLM round-trip"), `on_user_turn_completed` with `update_chat_ctx`, and tool calls, with `truncate(max_items)` and a custom summary marked `is_summary` for compaction ([LiveKit chat context](https://docs.livekit.io/agents/logic/chat-context.md); [LiveKit agents & handoffs](https://docs.livekit.io/agents/logic/agents-handoffs.md)). Its latency guidance treats anything over "a few hundred milliseconds" as needing audible feedback ([LiveKit external data & RAG](https://docs.livekit.io/agents/build/external-data.md)). The two vendor integrations show the fork: mem0's example `await`s `mem0_client.add(...)` inside `on_user_turn_completed` with a single hard-coded `RAG_USER_ID`, so no per-user isolation and a write on the turn path ([mem0 LiveKit integration](https://docs.mem0.ai/integrations/livekit)); zep-livekit keys by `user_uuid` plus a new `thread_uuid` per room, writes to a group graph for shared business facts, and "extracts knowledge asynchronously, so facts from the current turn aren't searchable until later", with a warning that automatic injection into a system message is "for fully trusted, application-authored content only" ([Zep LiveKit integration](https://help.getzep.com/ecosystem/livekit-memory)). The existing background extraction is the right side of that fork. The table for the concierge is: working memory is `chat_ctx` for the call, derived each turn and never persisted as-is; episodic is the transcript and one immutable visit-summary row per call, written by the post-call job; semantic is the caller facts table keyed `(tenant_id, caller_id)` with `modified`, `source_call_id`, `superseded_by` and `expires_at`, written only by the extractor and seeded as a few hundred tokens before the session; shared semantic is business facts per tenant, edited by the operator and loaded as trusted instructions; procedural is the system prompt, tools and extraction prompt, changed by PR. Caller identity comes from participant attributes or job metadata, never from the transcript. "Forget me" must delete the caller's semantic rows *and* schedule deletion of their transcripts and summaries, because the pitfall to avoid is ChatGPT's, where "deleting a chat does not delete" the memory made from it and logs persist up to 30 days ([OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq)); log the request as a timestamped tombstone without the content, and keep deletion a separate, rare path from normal supersession as Hindsight does. Letta's "dreaming", background subagents that consolidate after N steps or on compaction ([Letta sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime)), is the vendor precedent for the background extractor and compaction, and the memory panel's UI precedents are ChatGPT's "Manage memories" and Claude Code's `/memory`: list, open, delete, timestamps. One shared policy document with two appendices (git files for the orchestrator, SQLite tables for the voice agent) matches the single-home convention the permissions policy already uses; no organisation-level memory-policy standard exists, as AGENTS.md "defines no memory mechanism" ([agents.md](https://agents.md/)).

## Adopt, borrow, leave alone

| Priority | Decision | Why |
| --- | --- | --- |
| 1 | Per-worker `bwrap`/`srt` wrapper with the built-in Bash sandbox nested inside; orchestrator unsandboxed and sole holder of the GitHub token; separate `CLAUDE_CONFIG_DIR` per worker; compose tests run from the orchestrator after exit | The only layer that is agent-neutral, closes the "reads the entire computer" default, and is what Anthropic now prescribes for unattended runs; `--scope` cannot do it |
| 2 | Agent adapter boundary in node: `spawn`/`resume`/`normalize`, token caps with an orchestrator-owned price table, `entry.json` as result, AGENTS.md canonical with `@AGENTS.md` in CLAUDE.md, explicit `--settings`/`--mcp-config` on the Claude path | Makes Codex/Gemini/OpenCode/Goose a per-agent module later, isolates the Claude billing risk, and survives the coming `--bare` default |
| 3 | Memory policy columns and enforcement: add provenance, `supersedes`, expiry class, forget path; `memlint` in `PostToolUse`, pre-commit and CI; `PreToolUse` deny on append-only and PR-only stores; retro backlog as inbox-then-promote with dedupe at promotion | The model is sound; this is the field's unanimous "prompts set intent, tools enforce" direction, and CI coverage is what still holds when a non-Claude worker has no hooks |
| 4 | Small loopback control page: one static page, SSE or 2-second polling, four or five POSTs wrapping `harness status`, INBOX answers, queue and lane count; loopback by default, read-only off-loopback, confirm-then-append audit; ntfy `http` action buttons for yes/no INBOX questions; Tailscale for the phone | No FOSS control plane sits over external state; the precedents are under 100 kB and one person's work; two named alternatives died in 2026 |
| 5 | Borrow designs: Symphony's stall timeout, per-state concurrency and backoff formula; Archon's three merge checks; Orbi's reviewed-head-only merge; Agent View's state vocabulary | Cheapest "adoption" available; all are spec-level and fit a file-state bash machine |
| 6 | Move JSONL parsing and the per-run state machine fully into node; keep bash for `systemd-run`, `tmux`, `git`, `flock`, `bwrap`; keep Chipp-style backstops (silence timeout, destructive-command grep, debris cleanup) | The recurring migration pattern; the limits people hit are JSON and typed state, not bash itself |
| 7 | Voice agent: same table with SQLite appendix, extractor as sole semantic writer, no writes on the turn path, "forget me" deleting semantic and episodic rows with a tombstone | Matches Zep's async shape and avoids mem0's awaited-write and ChatGPT's orphaned-memory pitfalls |
| Later | ACP as a second adapter via acpx; Remote Control server mode as the optional desk if `claude -p` sessions can be attached; Docker Sandboxes microVM if compose must run inside the worker boundary | Each depends on something unconfirmed (ACP cost reporting, `-p` attach, Linux microVM details) |
| Leave alone | Adopting Archon, Bernstein, ralphex, Gas Town, Paperclip, Multica or OpenHands; LangGraph/CrewAI/AutoGen; Temporal/Restate/Inngest; Go/Rust rewrite; Firecracker/Kata/gVisor/Kubernetes; LLM curator, embeddings, facts database; sandboxing the orchestrator | Each would re-express verify/merge/queue in another runtime, inherit a small team's bus factor, or add a loop or boundary that solves nothing on one box |

## Conclusion

The research reframes the question from "should I adopt something" to "which of my layers are accidentally Claude-shaped". The state machine, worktrees, verify-with-evidence, PR merges, queue, memory caps and retros are already agent-neutral and ahead of what ships; the Claude-shaped parts are the safety layer (deny rules, hooks, classifier), the result parsing (stream-json, dollar cost) and the desk (Remote Control). The sandbox and the adapter boundary are therefore one project viewed from two sides: the OS boundary is what lets a non-Claude worker run at all without settings.json, and the adapter is what lets the orchestrator stop knowing which agent produced the events. Doing them together, with the orchestrator as the trusted credential holder, is the architecture the cloud products (Claude Code on the web, Fletch, AgentBox) converged on independently.

The memory finding has a sharper implication than "sound". Because hooks are a Claude mechanism and the adapter plan makes workers interchangeable, the enforcement that matters most is the one that runs outside any agent: `memlint` in pre-commit and CI, append-only checked against git HEAD, procedural changes only via PR. The in-session hooks are a convenience layer on top. The same logic transfers to the voice agent, where the extractor and the post-call job are the only writers precisely because the turn path has a latency budget no memory system should spend; a single policy document with two store appendices keeps both systems honest with one set of rules.
