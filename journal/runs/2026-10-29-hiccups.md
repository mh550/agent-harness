## 2. 08:46: a step that contradicts git (run 1, N2-02)

Verify failed N2-02 on step 2. At 08:48 the session parked N2-02 with a question. Step 2 said an out-of-order side
makes the merge driver "exit 1 with A untouched (git reports the conflict as usual)". Those two halves can't both be
true. In git 2.43 a merge driver's `%A` is kept as the result whatever its exit. An untouched A is therefore a conflict
with no markers, and theirs' lines are lost without a word.

N2-06's Opus review had already changed the driver to fall back to `git merge-file`
(`lib/merge-sorted.sh:11` on `harness-lane/agent-harness-2026-10-29/N2`). The assisting session reproduced the
problem in a scratch repo (git 2.43.0): base `a b`, ours `b a`, theirs `b a c`, driver `exit 1`. git said CONFLICT; the
file was `b a`, with no `<<<<<<<` and no `c`.

**Handled:** Michael reworded the step with a `jq` command the session supplied (dry run checked first). The new text:
"…gets git's text merge (`git merge-file`): clean exits 0, a conflict exits 1 with its `<<<<<<<` markers in A". The
answer went in with `harness answer`: "N2-02: step 2 reworded". The lane has since re-verified it with no code change
(18972cb).

## 4. A wrong continue, caught by Michael

**Mistake.** The assisting session (harness-answer skill) advised `harness queue add --continue agent-harness-2026-10-29`
and said the runner had a free slot (`MAX_PARALLEL_RUNS=2`). It checked the parallel limit, but not the one-run-per-project
hold (`decisions/2026-10-21-queue-one-run-per-project`, `decisions/2026-10-27-same-project-starts`; `project_busy`,
`bin/harness:130`). The entry sat "held: agent-harness busy (agent-harness-2026-10-29-2)" (runner.log, 09:53). Run 1
would have waited for all 23 of -2's features, the reverse of the merge order planned. Michael caught it.

The same advice is written in two places, and both are wrong when another run of the same project is alive:
- the skill (`~/.claude/skills/harness-answer/SKILL.md:48-49`: "with a runner going, `harness queue add --continue <run>`");
- the parked card's `do` line (`lib/parked.mjs:22`).

A plain `harness continue` would have queued the same way (`bin/harness:372-381`). Only `--now` skips the hold (`bin/harness:373`).

**Fix.** `harness queue rm 1`, then `harness continue agent-harness-2026-10-29 --now`. Run 1 restarted at 10:21:
- The driver's first commit, "HARNESS: start run" (`rec_commit` before `sync_record`, `lib/driver.sh:391`), picked up
  the uncommitted `feature_list` edit.
- "merged main into harness/agent-harness-2026-10-29": clean.
- "N2-02 unparked: INBOX.md has new answers".
- "lane N2 opened (slot 0, port 7817, from 252aea6)". 252aea6 was the pushed N2 lane tip, so no work was lost.

The two runs are isolated from each other:
- state dirs: `~/.local/state/harness/agent-harness/<run>`;
- worktrees and branches;
- lane slots: `~/worktrees/agent-harness/lanes/<run>/slot-k`;
- ports: 7817 against 7818/7819, allocated under a box-wide lock (`lib/driver.sh:127-130`).

**Follow-ups (not done):** when another run of the same project is alive, the skill and the parked card should say
`harness continue <run> --now`, or at least name the hold.

## 5. Pausing -2

A second Claude session advised pausing -2, for two reasons:
- **Old code.** Both drivers run harness 3470da3 (the state's harness-version), which has no N2 conflict resolver. When
  -2's R1/R2 meet N2's changes at verify, today's code would park the conflict on Michael.
- **Load.** Three suites at once (load average about 9.8, 11.7 at 10:38) against `CHECK_TIMEOUT=25m`, which was sized
  for two (`decisions/2026-10-29-check-timeout-25m`).

Michael paused -2 at 3/23, about $14.

**Evaluation of that plan.** Pausing is right. It lets run 1 merge N2 first, and -2 then gets the resolver (N2's
`lib/config.sh:38` defaults `CONFLICTS=resolve`) instead of handing conflicts to Michael. The plan's later steps had a
gap, though: a paused driver stays alive and loops in `lane_wait` (`lib/driver.sh:527-533`). So:
- `harness continue` on -2 refuses while it is alive: "is running; continue it after it ends (or harness stop)"
  (`bin/harness:367`);
- a manual `harness sync` doesn't check for live runs. Only the queue runner waits for no run to be alive, because "a
  driver reads its scripts as it goes" (`lib/sync.sh:3-4`). Syncing under a live paused driver risks it running a mix
  of old and new code.

**The corrected sequence:**
1. Once -2's sessions in flight end, run `harness stop agent-harness-2026-10-29-2`. It stops after the current
   session; finish keeps the passed features and pushes the lane branches. A continue by hand later undoes the stop.
2. Wait until run 1 ends with N2 merged (`git log --oneline origin/main | grep -E 'harness-merge/.*-N2$'`) and no run
   is alive. Then run `harness sync`.
3. Run `harness continue agent-harness-2026-10-29-2`.

If N2 parks again, resume or continue -2 without syncing, and let -2 merge first.

## What this shows

- **An adviser checked one limit and missed the other.** "A slot is free" isn't enough: a run waits for both the
  parallel limit and the one-run-per-project hold. The tool's own text (skill, card) gives the same wrong advice, so
  the fix belongs there, not in the next session's memory.
- **A step can contradict the tool it describes.** The review found it, the verify caught it, and a scratch repro
  proved it in two minutes. The answer was to reword the step, not to change the code.
- **Pausing isn't stopping.** A paused driver is still alive. Anything that waits for "no run alive" (continue,
  a safe sync) needs a stop.
- **Ended isn't merged.** The series assumed run 2 would start on run 1's code. Run 1 ended parked, the queue started
  run 2 on the old harness, and nothing said so. A series has to wait on a merge, not an end.
