# `harness show`: where a run's work is, from local refs, one change counted once

*(2026-10-28, run agent-harness-2026-10-28, feature U3-04; spec `docs/specs/2026-10-27-status-ux.md` §U3 item 4, plan
`docs/plans/2026-10-28-U3-show-and-fixes.md` §4 and default 5)*

- **Finding:** "where are a run's changes, and do they conflict with main?" took `git -C ~/worktrees/… log`, `git diff
  --stat` and `git merge-tree` by hand. Since lanes a run's code is on `harness-lane/<run>/<m>` (local branches of the
  project repo; `harness/<run>` holds the record), so the worktree alone no longer answers it. A milestone that waits
  on another is opened on that one's branch: on the stub run M2's branch holds M1's commits too, so summing every lane
  branch's diff counted M1's files twice (`big-A.txt` +1000 for a 500-line file). Found in review: a bare `git log
  --grep '^A'` over the run's branches walks main's history too.
- **Choice:** `harness show <run> [<feature>] [--files] [--json]` (`cmd_show`, `lib/show.mjs`), read-only: git in the
  run's `PROJECT_DIR`, local refs only (no fetch, `GIT_OPTIONAL_LOCKS=0`, the config read in a subshell), so a removed worktree
  changes nothing. The run's branches are `harness/<run>` and every `harness-lane/<run>/*` (an origin copy without a
  local branch too); each is diffed from its merge-base with `origin/main` (`--numstat` and `--name-status`, both
  `--no-renames`, joined by path, `core.quotePath=false`; `.harness/runs/` left out). **A path whose blob at the tip is
  the same on two branches is one change, counted once** (a stacked lane carries its base lane's files; two lanes
  opened on one both do; a base lane that moved on after a stacked one opened still shares the unchanged ones);
  different results are summed per path (plan default 5). `✗ conflicts` on the paths `git merge-tree --write-tree
  --name-only origin/<main> <branch>` lists for any branch (exit 1; any other non-zero: no mark), run against a
  scratch object store with the repo's as an alternate, so the project's object store is untouched. The main branch is
  the project's `MAIN_BRANCH` (its config and the run's `run.env`, read in a subshell). No `origin/<main>` ref (never
  fetched, a project dir gone): `CHANGES vs origin/<main>: unknown (…)` and `changes: null`, never a `0` that reads
  as nothing waiting. Milestones from `harness-log.md`'s `merged into main` and `proposed for merging`
  notes (the ledger copy after gc); a merge note without a URL keeps the proposal's PR. The compare URL of every run
  branch with changes, GitHub-shaped origins only. The feature form: steps, sessions (`metrics.jsonl` rows), entry
  files made absolute against the worktree, commits whose subject matches `^(WIP: )?<id>` followed by a non-id
  character over the run branches and its `run/<run>/*` tags since the run started (ids like `A` and `F1` recur
  across a project's runs, and main holds the earlier ones; `--grep` alone would match a body line too), its open
  needs card. `--json` v1 with its key paths in
  `tests/fixtures/show-json-keys.txt` (a session row and a needs card are other files' shapes, left out of the
  comparison).
- **Visible:** the view itself (it writes nothing, so nothing goes to `harness-log.md`).
- **Rejected:** summing every lane branch (double counts stacked lanes, the common case); skipping a branch that is an
  ancestor of another (still double counts two lanes opened on one, and a base lane that moved on); taking each path's
  largest +/− (under-counts two independent lanes on one file); diffing the worktree (record only since lanes, and gone after
  gc); a `git fetch` first (a read view must not touch the network or the refs a live run's lanes use).
