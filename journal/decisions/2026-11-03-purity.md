## Finding

The riskiest decisions in the harness are written in bash and reached only by a whole stub run:

- **The suite runner's cache and rerun choices** (`lib/check.sh`): what a red exit means, whether a cached marker
  answers, whether a partial run may stand for the full one, and whether to rerun.
- **The lane's verify verdict and exit table** (`lib/lane.sh`, `lib/driver.sh`): hold, thin, red or fail, and which exit
  code and reason a finished lane gives.
- **How a run ends** (`lib/driver.sh`): which reason, which card, which notification priority.
- **Two formats written more than once.** The queue entry is encoded in one place and decoded in four: `queue_add` in
  `bin/harness` writes it, and `lib/queue.sh`, `lib/spec.sh`, `bin/harness` and `lib/status.mjs` each read it. No check
  holds its newline byte at all. INBOX.md's `status:` line is read three times, with `sed` and `grep`, through `| head`.

Each of these branches costs a stub run to test, and some have no test. The spec's candidates were read on the base tree;
the five below are the decision tables and the twice-written parsers, the spec's *default* order.

## Choice

Each move is the same shape. The logic becomes an exported pure function in the `.mjs` that owns the data, with one unit
test per behaviour. The bash calls it through `ask` (the resident helper, in a driver's or lane's shell) or one `node`
spawn (`lib/check.sh`, `bin/harness`, `lib/queue.sh`, which have no helper) and reads labelled lines. **Every note,
`check:` line, marker byte, flake row, card, exit reason, end reason, queue file byte and runner log line stays as it
is**: every `note "…"` literal stays in its bash file, and a function answers a branch and its values, never a note's
words.

- *Default:* the one queue decoder drops a CR at a line's end, as the queue view's reader always has. The runner's read

  harness writes changes.
- *Default:* the `sort -u` of the blocked ids stays in `lib/driver.sh`: it sorts by the driver's locale, and the end

- *Default:* moves 2 and 3 leave the bash barely shorter: 52 lines deleted and 51 added across `lib/lane.sh` and

**What proving each removal would cost**, by the trim's rule (`journal/decisions/2026-11-03-trim.md`):

- **A successor named.** One row per removed check, naming the unit test that makes its assertion now: five rows for
  these four starts (the five checks that read those runs), and a CLI check for `harness stop`'s empty `STOP`. The checks' names
  leave both fixtures in the same commit.
- **The coverage union not smaller.** One traced full suite on an empty box, then the reduction
  (`tests/tools/coverage.sh`). S1 measured a traced suite at 681.5 s wall and 2,563.9 CPU-s, with 8.8 GB of raw traces. It
  is one run for all four removals taken together, not one per removal. The moved lines are in `.mjs` now; S1's method
  covers node as well as bash, so they stay in the union.
- **The mutants still caught.** No check of these four starts is named as catching any of the forty
  (`findings-and-research/2026-11-03-suite-coverage.md`), so no mutant reruns.

action. **As Decision 16 (b) says, none is made.**

## Rejected

- **One spawn per function.** A red run would start node once for each function it reaches
  (at the start, at the rerun, at the end, each more than once); instead one question per moment answers everything known then.
- **The note's words in the `.mjs`.** The S4 proof reads `note "` literals in the bash diff, so a moved note would print
  as removed with no twin, and a reader of the bash would lose what the run says.
- **Removing the four stub starts now.** Decision 16 (b): the moves as the spec writes them, remove no check.
