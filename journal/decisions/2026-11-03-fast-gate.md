# The fast gate: `check.sh --fast` runs the fast tier, marks `fast-<key>`, and a fast-green is never read as a green

*(2026-11-04, run `agent-harness-2026-11-04`, T2-01 (`check.sh --fast`, `CHECK_FAST_CMD`); spec
`docs/specs/2026-11-03-suite-tiers.md` T2; plan `docs/plans/2026-11-03-test-suite-redesign.md` phase 3; Michael chose
this gate on 2026-11-03, the plan's question 2)*

## Finding

A coding session's `passes` stood on the full suite: about 805 s solo at 4 jobs, run 1.3–1.7 times a session, 58 % of
lane time (`findings-and-research/2026-10-29-run-time-budget.md` §2, §4). T1 split the suite into a fast tier
(`bash tests/run.sh --tier fast`, about 152 s, 537 checks) and a slow one
(`decisions/2026-11-03-suite-tiers`), but `lib/check.sh`, the one command the driver and every session call, knew only
the whole suite and its subsets. The markers it keeps (`green-<key>`, `red-<key>`, `part-<key>`) all mean "the whole
suite on this tree", and every count the driver reads (`tests-start`, `tests-end`, the prompt's Suite line) comes from
them or from `check.out`.

## Choice

- **`CHECK_FAST_CMD`** in the project layer of `lib/config.sh`, empty by default, exported as `HARNESS_CHECK_FAST_CMD`
  by `prompt_env`; `templates/project/config.sh` has it commented. This repo sets
  `CHECK_FAST_CMD="bash tests/run.sh --tier fast"`. No other project sets it, so nothing changes for them.
- **`check.sh --fast` with no fast command is the bare form, byte for byte** (the same markers, lines and rows): a
  one-tier project's `passes` still stands on its whole suite.
- **With one, in order:** a `green-<key>` answers with the full cached line (a full green satisfies the fast gate); a
  `red-<key>` with the cached RED and its exit (a full red stands); a `fast-<key>` with
  `check: fast green (cached for this code tree, <n> tests)`, row `cached`; else the fast command runs through `run()`,
  the same scope, cap and `HARNESS_CHECK_TIMEOUT`, to `check-fast.out`.
- **The rerun guard as for a full run:** a red's `HARNESS_FAILED=` files are rerun through the suite command (`CHECK_CMD
  <files>`, the subset form's way: a file name picks its file whatever its tier), else the fast tier again; to
  `check-fast-rerun.out`; never after a timeout or a cap kill. A green rerun is a flake: one `flakes.jsonl` row with
  `"tier": "fast"` (*default*: the key only on fast rows, so every existing row and reader stays as it was) and
  `check: fast green after a rerun (flaky: <names>), <n> tests`.
- **Green** writes `fast-<key>`: the fast run's `<n> tests` (a flake's first-run total) and `wall <s>`, the same two
  lines as `green-<key>`, and `check: fast green in <s> s, <n> tests`, row `fast`. It never writes `green-<key>`,
  `red-<key>` or `part-<key>`, and no call but `--fast` reads `fast-<key>`: **a fast-green is never read as a green**
  (a bare call on a fast-green tree runs the whole suite).
- **Red** prints `check: RED (fast: <why>[; red again on a rerun of …]) — last lines of <scratch>/check-fast.out:` and
  that file's tail, row `fast`, and writes **no marker** (*default*: a fast red costs about 150 s to find again; the
  red marker is for a 900 s run). The tail is the first run's (*default*: the whole tier's output, conformance
  included; a rerun's covers a few files, and `check-fast-rerun.out` is beside it).
- **`--fast` never reads the map or `part-<key>`**: the partial path is the full form's. The subset form is unchanged,
  and `--fast` takes no further arguments (usage, exit 2; *default*), with or without a fast command (before, `check.sh
  --fast x` passed both words to the suite as a subset).
- **`check.out` and `check-<key>.out` stay the last full run's** (*default*): every count the driver and the cached
  RED read from them is a whole suite's. A full run's sweep of older `check-*.out` files spares `check-fast*.out`, so a
  fast RED's pointer holds after a bare run.
- **`fast-<key>` is keyed by the tree only**, as `green-<key>` is: a fast command changed outside the tree (the user
  config, `run.env`) leaves an older fast-green standing (*default*; the same exposure `green-<key>` has to `CHECK_CMD`).
- **`--fast` is never the bare default** (*default*): the driver asks for it by name where `passes` is gated (T2-02).
- **The driver (T2-02).** `run_init` takes a mode: `run_init fast` (a coding session's pre-session init,
  `lib/lane.sh`) calls `check.sh --fast`; bare `run_init` and `run_init fresh` call the full form. The post-session gate
  is `green_fast` (`check.sh --fast`), its note `<id> un-passed: fast tier red after the session`, with or without a
  fast command (*default*: one note, one reader; without one the whole suite is the fast tier). The run's first init
  (the baseline, `tests-start`), the verify's `run_init fresh` and its `green` after a hold, the re-base's `run_init
  fresh` and `green`, and the driver's final `green` stay full: a slow-tier red passes the session and is found at
  verify (`verify_red`). `run_init fresh` removes `fast-<key>` with `green-`, `red-` and `part-`. `tests-start` and
  `tests-end` read `green-<key>` alone, so between sessions `tests-end` moves only on a full green (the verify's), never
  to a fast count. run.log keeps `suite red before the session` for a red pre-session init of either tier (*default*).
  `summary.mjs` reads both un-pass notes (`redUnpass`): an older run's `suite red after the session` still counts.

## Rejected

- **The full suite behind `passes`** (the plan's question 2, option a): safer, but it saves only 0.3–0.7 full runs a
  session; Michael chose the fast gate, with the full suite at verify and merge.
- **An LLM-chosen tier or subset**: the gate stays deterministic; no model picks what a verdict stands on.
- **A per-feature file subset**: budget §7: the files a feature's reds came from span 73 % of the suite, and 4 reds
  were missed by a name selection.
- **A fast red marker**: a fast red is cheap to rediscover, and a marker would be one more state for `run_init` to clear.
- **`--fast` as the bare default**: every existing caller and check reads the bare form as the full suite.
