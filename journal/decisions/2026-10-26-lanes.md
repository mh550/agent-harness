# The run record travels on its own branch; each milestone's code on a lane branch

*(2026-10-26, run agent-harness-2026-10-26, feature P1-03; spec `docs/specs/2026-10-26-lanes.md` P1, plan
`docs/plans/2026-10-26-P1-lanes-serial.md`. P1-04 and P1-05 added their parts below, P1-06 the P1 defaults, the
rejected designs and the P1 review (`docs/plans/2026-10-26-P1-review.md`); P2 completes this file.)*

- **Finding:** a run branch carried both the code and the run record, linearly. A milestone's tag carried every
  commit before it, so a later milestone verified first (or one whose features `after` points elsewhere) was "held"
  or "tainted" until an earlier one merged, and every milestone PR carried record commits into `main`
  (`.harness/runs/<run>/` on main, `gc`'s record-only rule). Two lanes could never share such a branch.
- **Choice:**
  - The record lives only on `harness/<run>` in the run's worktree; every write to it goes through `record` (one
    `flock` on `state/record.lock`, `lib/record.sh`), including desk.sh's note. The session counter and the
    limit-hits counter are files (`state/sessions`, `state/limits`), 0 at each segment's start, as the shell counters
    were.
  - Code lives on `harness-lane/<run>/<m>`, worked in `<worktrees>/<project>/lanes/<run>/slot-0` (one lane at a time
    in P1-03, still one driver loop). A lane starts from `--base` (persisted as `BASE_REF`) or `origin/main`, resumes
    its own branch if it exists, and merges the tag of each dependency (`F deps`) that main doesn't have yet.
  - A session sees a copy of the record (excluded in the slot by a per-worktree `core.excludesFile`; skip-worktree
    when the base tracks it). The driver judges the copy (repair, red suite, park) and takes back only the entry,
    the question above `## Answers` (inserted above that line, so `answers_hash` holds) and the flip (`F pass`).
    A lane commit touching `.harness/runs/` is reverted and noted. Updated in place 2026-10-30: reverted against
    the lane's merge-base with main, not the session's start, in the index only; `merge_one` undoes any that slip
    through (decisions/2026-10-30-lane-guard-base).
  - The loop picks the first milestone `F lanes` lets open: complete → its verify, else its next feature. Verify runs
    in the slot (main merged in), tags the lane tip, and merges through `merge_milestones <m>`: a milestone merges
    once every dependency has `merged-<dep>`, else its PR is opened and waits (noted once). Taint, held and
    "stop at the first unverified milestone" are gone; `harness merge` runs the same rule.
  - At `finish` the slot is removed and merged lanes' branches deleted (local and origin); unmerged ones stay.
- **Defaults taken** (Michael's to change):
  - **D1** *default*: a verified lane whose tag no longer equals `merge-tree main tag` (main moved since) is not
    merged and needs Michael, once per main commit (`moved-<m>`), until P2's re-base rule.
  - **D2** *default*: `gc`'s `record_only` is unchanged, so `gc` deletes a finished run's record branch and worktree
    before any record PR exists (P2 adds one); the ledger keeps the whole record.
  - **D3** *default*: the initializer runs in the record worktree and whatever it changes outside `.harness/runs/`
    is reverted and noted, so the record branch stays record-only (its prompt already says "write no feature code").
  - **D5** *default*: the end reason "waiting on Michael" also names `needs-<m>` milestones when features could run
    but their lane can't open past them.
  - **D6** *default*: `harness start` refuses the run id `lanes` (it would be `<worktrees>/<project>/lanes`).
  - **D7** *default*: the `default` lane (features with no milestone) is never verified, as before lanes: it holds
    the lanes after it only until its features pass, then never opens again (`laneDeps`, `lanes`). Its code stays on
    `harness-lane/<run>/default`; a lane opened once its features pass starts on that branch (`slot_open`, from the
    P1 review), so the next milestone's tag carries it to main, as before lanes.
  - **D8** *default*: the deploy guards stay `harness/**` (Vercel) and `harness/*` (Netlify), so a guarded project's
    lane branches `harness-lane/<run>/<m>` get a preview deploy per push until the guard covers them too.
  - A slot that can't be checked out (`worktree add`, `checkout -B`) needs Michael like a base conflict, and a lane
    reopened after another lane's failed open checks its own branch out again (review of P1-03).
- **P1-04, the lane process and the coordinator** (finding: one loop did a milestone's sessions, its verify and the
  run's bookkeeping, so two milestones could never run at once):
  - `lib/lane.sh <m>` is one milestone as its own process, the loop body moved out of the driver; `lib/driver.sh` is
    the coordinator: it reaps lanes whose pid is gone (`lane <m> closed (<reason>)`, the reason from
    `state/lanes/<m>/exit`), checks the run's ends, and opens what `F lanes` offers while `lanes alive < MAX_LANES`.
    What both need moved into `lib/record.sh`. A lane exits 0 (merged, proposed, its PR waiting), 10 given up,
    11 parked, 12 needs Michael, 13 cap/limit/weekly, 14 stopped, 15 deadline; 13 and `feature-list edits` end the run.
  - A lane has its own units (`harness-<run>-<m>-s<n>`, `-check-<pid>`, `-svc`), scratch (`<scratch>/lanes/<m>`),
    prompt, snapshot and question files (`state/lanes/<m>/`); it loads the configuration, `--settings` and `.mcp.json`
    from its slot. Its `BRANCH` stays the record's, so every link a notification carries points at the record.
  - The deadline is the coordinator's: lanes exit 15 between sessions without a note; the coordinator notes it once,
    waits for them, then opens one verify-only lane (`LANE_ONCE=1`) per complete, unverified milestone.
  - Pause: each lane tears its services down after its session and waits; the coordinator logs `paused` once and
    opens nothing. Stop: the coordinator opens nothing, waits for the lanes, then ends as before.
  - A lane's services stay up when it closes (D4 of the plan); the next lane in its slot stops them silently, `finish`
    tears down what is left with the end reason (one `services stopped (<reason>)` per run, as before).
  - From the review of P1-04: a lane's verify repairs against its own snapshot (`state/lanes/<m>/before.json`); the
    coordinator's TERM gives lanes 150 s (a teardown's `timeout -k 10s 2m`) and never tears down a live lane's
    services; a lane process a SIGKILLed coordinator left is stopped (noted) before the next segment reopens its
    slot; the deadline's verifies stop at a usage-limit window one of them raised; a pause or a long limit wait with
    no lane open also stops the services closed lanes left up. The `MAX_REPAIRS` streak is per lane now.
- **Defaults taken in P1-04** (Michael's to change):
  - **D9** *default*: the coordinator takes answers and syncs the record only when it may open a lane (or while
    paused), not every poll: with every slot busy, a fetch every 10 s would decide nothing. Lanes sync before each
    session, as the driver did.
  - **D10** *default*: a lane that exits without its exit line (a crash) gets `needs-<m>`, so the coordinator never
    reopens it in a loop.
  - **D11** *default*: `finish` also deletes a local lane branch that was never pushed and carries nothing beyond
    main (a lane opened, then the run stopped before its first session); a pushed lane branch stays for a continue.
  - **D12** *default*: a session's unit number stays `scope-seq` (every session of the run, under the record lock),
    not `state/sessions` (coding only), so a verify and a coding unit never share a name.
- **P1-05: continue, legacy runs, a `pr`-held dependency.**
  - A lane reopens its branch from whichever side is ahead: the origin's (Michael pushed a fix by hand; the box's
    copy is stale), the box's (a push failed), or the box's with the origin's merged in when they diverged (noted; a
    conflict is needs Michael). Before, a stale local branch won: every push of the lane was rejected, and the
    verified tag lacked the origin's commits. A reused slot's leftover work is committed (and its push tried) before
    that choice, so a failed push leaves the box's branch ahead and it is kept.
  - `harness continue` (and `harness start` resuming) refuses a run whose `harness/<run>` has code main doesn't:
    the branch merged into its base (`origin/main`, or the run's `--base`) with `git merge-tree`, then diffed outside
    `.harness/runs/`, so the base's own later changes and the record are never the run's code. It prints the three ways forward and exits 1 before it
    resets anything; `harness merge` is never refused. A record-only branch (its record on main too, n8n-home's
    shape) continues as a lanes run.
  - Under `pr`, a verified milestone whose dependency hasn't merged opens its PR and waits (`waits-<m>`, noted once),
    instead of being `proposed`; `harness merge` merges `proposed` milestones too, in list order, so both land with
    the dependency first. A `proposed` milestone whose tag is on main (Michael merged its PR on GitHub) is marked
    merged by the next `merge_milestones` (`<m> merged into main (by its PR)`), so a milestone waiting on it is then
    proposed and notified.
- **Defaults taken in P1-05** (Michael's to change):
  - **D13** *default*: the refusal is said on stderr, in `run.log` and in a high-priority notification
    (`[<run>] continue refused: a pre-lanes run`), not as a `harness-log.md` note: the CLI never writes the record
    (the driver is its only writer), and a queued continuation has nobody at the terminal.
  - **D14** *default*: diverged lane branches are merged (origin's into the box's) rather than one side winning; the
    merge commit is the lane's base, so both sides reach the PR.
- **The P1 defaults** (`lib/config.sh`, commented in `templates/user/config.sh`; Michael's to change):
  - `MAX_LANES=1`: one lane at a time, so a run behaves as before lanes from the outside except that its record
    travels on its own branch; Michael's config sets 2 once P1 merges (the brief), which runs 1 until P2 (D15).
    The coordinator opens a lane only while `lanes alive < MAX_LANES`; P2 adds admission by memory and the five-hour
    window.
  - `LANE_REBASE=suite`: when main moved under a verified lane, a lane whose files are disjoint from what main gained
    re-tags on a green suite (`verify` = a verify session every time). Set in P1, read in P2: until then D1 holds.
  - `RECORD_PR=end`: the record reaches main through one record PR at `finish` (`off` = none). Set in P1, built in
    P2: until then D2 holds and no PR carries the record.
- **The P1 review** (P1-06, `docs/plans/2026-10-26-P1-review.md`; each with a check, red then green):
  - A `--base` run is measured against its base with main merged (`git commit-tree` of their clean merge): its
    segments merge main in, so main's later files no longer read as the run's code and refuse its continue.
  - A record commit stages `.harness/runs/<run>/` only: a suite's or an init's leftovers in the record worktree
    (`finish` runs the suite there when no lane opened) never land on `harness/<run>`.
  - `F blocked` over the whole list (`laneBlocked`) names a given-up or parked feature in a milestone another lane
    waits on, so that run ends `blocked on <X>`, not `no feature left to try`.
  - A lane opened once the default lane's features pass starts on `harness-lane/<run>/default` (D7 above).
  - **D15** *default*: until P2, `MAX_LANES` above 1 is noted and runs 1: every lane got the run's one port, two
    merges of one milestone could race (a lane's verify and the coordinator's reap), and one lane's run end didn't
    stop the others. P2 lifts it with per-lane ports, a merge lock and admission. Updated in place 2026-10-27 (P2-02):
    lifted; the clamp and its note are gone.
  - **D16** *default* (P2-02): slot 0's lane uses the run's port, a lane in slot 1 and up the first free one from
    `BASE_PORT`, allocated under the record lock and the box-wide `state/port.lock`, which `cmd_start` takes too; a
    closed lane's port is free once its services are down (`port_taken`: a lane's port counts beside a pid, an
    `svc-up` or an `opening`). Admission never refuses the first lane, and the slot count gets no `waiting` note.
  - **D17** *default* (P2-02): a run's end (`LANE_END`) reaches the other lanes through `state/lanes-end` and exit 16
    (`the run is ending (<why>)`, a plain close), checked before the cap at the top of a lane's loop; `limit_wait` and
    `mem_gate` sleep in slices of at most 60 s that end early on it or a stop.
  - **D18** *default* (P2-02): merges run under `state/merge.lock` (lock order merge, then record); the session counter
    is printed from inside the record lock and the cap re-checked on it. Slots are opened `--no-track` and lane pushes
    carry no `-u`: git locks `.git/config` without waiting, so a coordinator opening slot 1 while lane M1 pushed with
    `-u` failed (`could not lock config file`) in the first two-lane check run.

- **Rejected:**
  - Lanes from the run branch (each lane branched off `harness/<run>`): every lane would carry the record and the
    commits of the milestones before it, which is the linear branch's taint again; lanes start from main plus their
    dependencies' verified tags.
  - A frozen legacy driver (keep the pre-lanes driver for runs started before P1): two drivers to maintain and test,
    and the old one's taint and held rules alive forever. A legacy run with unmerged code is refused with three ways
    forward instead (P1-05).
  - A worktree per milestone: every milestone would reinstall its ignored build and install directories; a slot
    (`slot-<k>`, `k < MAX_LANES`) keeps them from one milestone to the next, so `MAX_LANES=1` costs what one worktree
    did.
  - Feature-level lanes now (independent features of one milestone side by side): a milestone's features edit the same
    modules (plan, build, review), so they would conflict; it stays a `features.mjs` change for later.
  - `.git/info/exclude` for the copy: every worktree shares it, so the record worktree's own `git add -A` would stop
    seeing the record.
  - Copying the session's list back over the record's: another writer (a later lane, the phone) may have changed it
    meanwhile; only the one flip is applied.
  - Merging the lane with `merge_one` directly after verify: it would open PRs under `MERGE_POLICY=off` and skip
    `nomerge-<m>`; `merge_milestones <m>` keeps both gates.
  - Keeping the initializer's code edits on the record branch: the branch would stop being record-only, and `gc`
    and the invariant "no PR touches the record" would both break.
  - The plan's legacy test, `git diff merge-base(origin/main, HEAD)..HEAD` outside the record: a run branch that
    cherry-picked a commit main has would read as code of its own; the merge-tree diff asks what merging the
    branch would bring.
  - Refusing in the driver: its exit happens in tmux, so `harness continue` would print "started" and the refusal
    would be a silent exit.
