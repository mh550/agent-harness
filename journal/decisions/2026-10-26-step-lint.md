# Step lint: four pure rules over the feature list, reported and never applied

*(2026-10-26, run agent-harness-2026-10-26-2, feature F2-02; spec `docs/specs/2026-10-21-retro-fixes.md` R3, plan
`docs/plans/2026-10-26-F2-initializer-verify.md` § R3 and D1, D2, D4)*

- **Finding:** steps that no verifier can check, or that can't fail, cost whole features. The C7-05 park: its step
  grepped the run record for a line, the step was quoted into `progress.md`, so the grep matched the step itself and
  proved nothing. The measure run's E2-02 needed `~/projects/*/.harness/runs`, which its session may not read, so it
  could never pass and the run ended "blocked on E2-02". Four retros (rane-one-mixxx-2026-10-19,
  portfolio_site-2026-10-20, voice-concierge-2026-10-20, agent-harness-2026-10-21-measure) found steps like these, and
  steps with nothing concrete in them ("works correctly"). Nothing caught them before the first session.
- **Choice:** `lint(list)` in `lib/features.mjs` (pure; CLI `features.mjs lint <list>`, one
  `<id>\tstep <n>\t<rule>\t<text>` line per finding, exit 1 with findings and 0 clean; `--note` prints the one
  `lint: …` line for `harness-log.md` and exits 0). The rules, per step as written:
  - **`no-anchor`**: nothing concrete: no digit, backtick span, quoted string, path or file name. `the suite is
    green` is exempt (the initializer prompt asks for it as every feature's last step).
  - **`outside-repo`**: a `~` path, `$HOME`, `../`, or an absolute path under `/home /root /srv /etc /var /opt /usr
    /mnt /media`. **D1 *default***: other absolute paths pass: `/tmp` (the scratch directory), `/dev/null`, and web
    routes such as `GET /api/x`, which a "starts with /" rule would flag.
  - **`self-match`**: a `grep`/`egrep`/`fgrep`/`rg` in command position (the step's start, or after a backtick,
    `|`, `;`, `&`, `(` or `!`, so prose that says "grep" isn't one) whose target is a run-record file that quotes
    steps (a file named `progress.md`, `progress-archive.md`, `entries.jsonl`, `context.md` or `feature_list.json`,
    or anything under `.harness/runs/`) and whose pattern matches the step's own text: `-F` literal, `-E`/`-P`/`rg`
    a JS RegExp, else BRE converted (`\(`, `\{`, `\|` … are the operators); `\<`/`\>` as `\b`; `-i`, `-x`
    honoured; option values (`-m 1`, `-t md`, `--glob x`) and redirects skipped; a pattern JS can't compile is
    matched as a substring. **D2 *default***: `harness-log.md` is not a quoting file: only the driver writes it and
    it never quotes a step. Not seen: a quoting file piped in on stdin (`cat progress.md | grep …`).
  - **`undeclared`**: `undeclared()` as the driver's `dependencies:` note uses it, one finding (`step -`) on the first
    feature of each milestone after the first that has no `after`. **D4 *default***: the first milestone is exempt,
    as in that note.
  - The lint reports; **nothing edits the list** but the initializer that wrote it (the write rules of §6 stand).
- **Rejected:**
  - **The driver fixing or rejecting the list:** a rule is a heuristic (`step 3 is fine as written` has no anchor and
    may still be checkable); a wrong fix or a refused run costs more than a noted finding.
  - **An LLM judging the steps:** a session's cost on every run for what four regexes catch, and not reproducible.
  - **Linting descriptions:** the verifier checks steps, not descriptions; a description is prose by design.
  - **A "starts with /" outside-repo rule:** flags routes and `/tmp`, which are where sessions are meant to work.
