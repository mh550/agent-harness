# The trim: 22 checks removed, each with the check that makes its assertions now; five gaps closed; no covered line lost

*(2026-11-06, the slim suite's S2 built by hand (`docs/plans/2026-11-05-slim-suite-by-hand.md`, the trim session); spec
`docs/specs/2026-11-03-slim-suite.md` S2, items 1 and 3 (item 2, the shape, is the next session's); what it stands on:
`findings-and-research/2026-11-03-suite-coverage.md` (the coverage map and the mutation sample). Base tree `f455a1a`.)*

## Finding

The spec expected the trim to cut 15 % of the check names. Read check by check, the suite does not hold that much
repetition:

- **The map shows code run many times, not assertions made many times.** 3,072 of 6,779 lines are run by 20 or more
  check files, but that is the stub start's path: each of those files starts a run of its own with its own settings and
  asserts on what that run did. A rough scan of all 1,274 counted `check` calls found 33 whose every assertion also
  appears in another check's text and 95 more where half do; read in the files (four read-only readers, one per group
  of check files, then each row again by the session), most are the same words on a different run, which is a
  different behaviour. About 60 such leads were rejected with the reason for each.
- **What is really said twice is small**: a check whose one assertion is the first term of its neighbour's; a count
  asserted once alone and once with its source; a parse-only check (`bash -n`, `node --check`) of a file that other
  checks of the same file run or import; a pure function's branch asserted through its CLI where a unit test asserts
  the same input.
- **None of the three small scenario files lies inside its neighbour as written** (the map's Table 3). Their lines do;
  their assertions are made nowhere else. One could be folded by moving its assertions (rule b), one only by a
  push-down, one needs its two runs.
- **About 84 checks test a pure function through its CLI or a stub run with no unit test yet** (a push-down each: one
  check replaced by one unit test, so the count of names does not move).
- **Three checks asserted less than their names say**: a loop inside a check keeps only its last round's status, and
  one left by `break` is status 0. `92-resident-helper-run`'s `for … do … || false; done`, twice (the normal start's
  record for helper on and off, and `bash -n` on seven files: each asserted for the last item only), and
  `89-no-deadline`'s `… || { echo …; false; } || break; done` (the user config template's thirteen words: none
  asserted; the review found it).

## Choice

**What counts as covered.** A check is removed only when every assertion it makes is made by a check that stays: the
same assertion on the same state, a stricter one on it, or, for a pure function, a unit test on the same class of
input. A guard on a fixture (a `grep` that the fixture still holds the line that makes the case) moves verbatim into
the successor. A check with a behaviour assertion of its own stays, even when the rest of it is covered: two checks
with different assertions under one name is folding, which lowers the count and tells less when it is red. A check
S1's mutant table names as catching a mutant is not removed (59 names; none was).

**The rules, as the spec orders them, and what each gave:**

| rule | what it is | removed |
|---|---|---:|
| a | two checks on one state assert the same thing: the more specific stays | 13 |
| b | a check file whose lines and assertions are another's: merged into it | 0 names, 1 file (`17-run-8-thin-verify`, its check moved) |
| c | a check that only asserts that a command ran (its exit, a parse, one word of its output), where other checks assert on the same command's result on the same state | 4 |
| d | a pure function asserted through a CLI or a stub run: a unit test is its successor | 5, and 5 more moved one for one |

**The gaps (Decision 11 of the dispatch list, answer (a), Michael 2026-11-06).** Of the nine lines the mutation
sample found run and not asserted on, the five that need no new stub run get an assertion, and each one's mutant is
caught now (below). The other four stay known gaps.

**A served script's CLI answer is a unit test's to assert.** The unit tier's decision kept a CLI run a bash check
(`decisions/2026-11-03-unit-tier`, before `main(argv, io)` existed). Since the resident helper,
`tests/unit/cli-same.mjs`'s `sameAsCli` spawns the CLI and holds `main`'s bytes and exit code to it, so the five
checks moved here still run the real CLI, in the unit tier's one process file instead of a check file of their own.
`docs/architecture.md`'s unit-tier row says so now.

**The three loops** (`92-resident-helper-run`'s two, `89-no-deadline`'s one) keep every round's status in a flag.
All three checks are green with it.

Defaults against the spec and the procedure: the push-down is five checks, not every one found (below, *Found, not
done*); the file merge and the push-down are one commit (they share the fixtures and the tiers' table); a gap's mutant
was run against the one check file that holds its new assertion, not against every file that runs its line; the
mutants ran without S1's sandbox (five read changes: a notification body, a context section, an argument test, a card
line, a fallback function).
